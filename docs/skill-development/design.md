# Skills 设计文档

本文描述 `Sth32/skills` 的仓库级设计。README 只承担项目入口；这里保存跨 skill 的工作流模型、文档模型和统一约束。具体分支操作细节见 [`branch-workflow.md`](branch-workflow.md)。

## 1. 目标

这组 skills 的目标不是把开发强制变成瀑布流程，而是把口述需求逐步收敛为：

- 可追溯的产品规则；
- 可确认的技术决策；
- 可执行、可验证的配置与实现；
- 明确的服务端—客户端合同；
- 可独立 review、可长期维护的工程结果。

核心约束是：**事实只维护一份权威当前值，阶段只承担自己的职责，工作单元只被真实依赖阻塞。**

## 2. 工作流模型

### 2.1 简单需求

没有真实拆分价值时，保持单线：

```text
01 原始需求
  → 02 需求挖掘
  → 03 程序实现澄清
  → 04 配置规划
  → 05 框架实现
  → 06 完整实现
  → 客户端对接（按需）
  → 07 交叉评审
  → 长期功能文档
```

简单需求不创建 `00-工作流索引.md`，也不人为创建 `U01`。

### 2.2 可拆分需求

只要已经形成真实独立需求边界，就可以从 `01` 开始创建工作单元 `Uxx`，也允许在后续阶段继续拆分。

```text
共享需求基线（按需）
  ├─ U01：01 → 02 → 03 → 04 → 05 → 06 → 客户端对接 → 07-U01 Review
  ├─ U02：01 → 02 → 03 → 04 → 05 → 06 → 客户端对接 → 07-U02 Review
  └─ U03：可以依赖 U01/U02，也可以继续拆分

各目标叶单元独立 Review 完成
  ↓
按集成风险判断是否需要整体 07-交叉评审
  ↓
长期功能文档
```

工作单元用于形成：

- 独立需求边界；
- 独立推进边界；
- 独立阻塞边界；
- 独立客户端对接边界；
- 独立 review 边界。

因此：

- 无依赖兄弟工作单元不互相等待；
- 不要求所有分支推进到同一阶段；
- 不要求在 review 前重新合并成一个工作单元；
- 结构性变化只使真实受影响的下游和 Review 失效；
- 所有目标叶单元完成后，只有存在跨单元集成风险时才创建整体 `07-交叉评审.md`。

详细拆分、命名、依赖和整体 Review 规则见 [`branch-workflow.md`](branch-workflow.md)。

## 3. Skill 职责边界

| Skill | 阶段 | 主要职责 |
|---|---|---|
| `game-spec` | 01 | 无损整理需求；识别真实独立范围并按需创建工作单元 |
| `game-discovery` | 02 | 只保留需要需求负责人决定的高价值产品未决问题 |
| `game-tech-clarify` | 03 | 收敛高影响技术决策与真实技术未决问题 |
| `game-config` | 04 | 确认配置对象、配置真源、合法值域、关键值和修改范围，并完成验证 |
| `game-scaffold` | 05 | 确定数据权威、持久化、同步、客户端可见性和基础调用链 |
| `game-implement` | 06 | 补齐行为、边界、失败处理、兼容、测试和运维闭环 |
| `game-client-handoff` | 对接 | 从真实实现提炼服务端—客户端合同 |
| `game-review` | 07 | 独立检查工作单元；按需执行跨单元集成查漏 |
| `game-docs` | 长期文档 | 从当前实现和已确认 Review 提炼长期权威功能文档 |

下游阶段不得复制上游完整内容。需要依赖时引用上游事实，只在本阶段记录会改变本阶段决策或执行的内容。

## 4. 权威文档模型

### 4.1 基本原则

权威过程文档粒度是：**工作单元 × 阶段**。

同一工作单元在同一阶段最多维护一份权威过程文档。共享父文档只保存真实共享基线，不复制已经归属子单元的事实。

代码、配置源、Excel、生成物、测试结果、diff 和日志是实际产物或证据，不计作第二份过程文档。

阶段文档保存的是**当前真相**，不是过程日志：

- 新事实替代旧事实；
- 已解决问题从正文移除或改写为最终结论；
- 被新证据推翻的判断不得继续与新结论并列；
- 历史过程通过 Git、日志和 `record.jsonl` 追溯。

### 4.2 未分支目录

```text
docs/requirements/<feature>/
├── 01-原始需求.md
├── 02-需求挖掘.md
├── 03-程序实现澄清.md
├── 04-配置规划.md
├── 05-框架实现方案.md
├── 06-完整实现方案.md
├── <主题名>-客户端对接文档.md（按需）
├── 07-交叉评审.md
└── record.jsonl
```

### 4.3 分支目录

首次真实拆分后仍保持同一目录，不为 Uxx 增加子目录：

```text
docs/requirements/<feature>/
├── 00-工作流索引.md
├── 01-原始需求.md                         # 仅在存在共享基线时保留
├── 01-U01-战斗-原始需求.md
├── 01-U02-奖励-原始需求.md
├── 02-U01-战斗-需求挖掘.md
├── ...
├── 06-U02-奖励-完整实现方案.md
├── U01-战斗-客户端对接文档.md（按需）
├── U02-奖励-客户端对接文档.md（按需）
├── 07-U01-战斗-交叉评审.md
├── 07-U02-奖励-交叉评审.md
├── 07-交叉评审.md                         # 按集成风险可选
└── record.jsonl
```

`00-工作流索引.md` 只承担路由：工作单元 ID、范围、依赖、当前阶段、当前文档和整体 Review 状态。它不得复制需求规则、方案、配置值、验证结果、未决问题或阶段文档状态正文。

## 5. 阶段状态与切换门禁

阶段文档顶部 `状态` 是阶段状态的唯一权威来源。聊天中的“完成”“可以继续”不能替代文档状态。

开始一个按工作流顺序进入的下游阶段前，必须读取该 skill 声明的真实上游文档状态。未达到可移交终态时停止正常推进，回到上游闭环；只有 skill 明确允许并行或用户明确接受带阻塞并行时，才能做不依赖未决结论的安全工作。

当前主流程正常可移交终态：

| 阶段 | 正常可移交终态 |
|---|---|
| 01 原始需求 | 叶文档 `整理完成`；已拆分父文档可为 `已拆分` |
| 02 需求挖掘 | `已收敛` |
| 03 程序实现澄清 | `已收敛` |
| 04 配置规划 | `已完成` |
| 05 框架实现 | `骨架已完成` |
| 06 完整实现 | `已完成` |
| 07 交叉评审 | `通过`；`有条件通过` 仅按已明确接受的条件继续 |

结束阶段前必须先做一致性收敛：同一事项不得同时保留互斥状态、数值、操作要求或验证结论。证据不足时保持未完成或阻塞，不得以“已完成”结束阶段。

## 6. 文档更新与结构性变更传播

**结构性变更影响传播硬限制：当范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源发生变化时，必须在同一轮执行影响扫描，不得只修当前局部段落。当前阶段文档内至少核对顶部元信息、相关正文规则/矩阵、验证结论、阻塞与下一动作；同时定位已有且实际依赖该事实的上下游阶段文档、客户端合同与 `00-工作流索引.md` 中的旧引用。当前阶段和本 skill 允许直接维护的下游内容立即原位更新；若受影响的是需要用户确认才能改写的上游文档，必须明确列出受影响文件、旧事实与拟修改内容并等待确认，不得静默遗漏，也不得把未传播完成的结构性变化描述为已闭环。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

### 6.1 当前阶段立即落盘

任何新事实、确认、执行结果或验证结果，只要改变当前工作单元当前阶段内容，就在同一轮原位更新当前权威文档。

更新后明确告知用户变化路径，不把关键结论只留在聊天中。

### 6.2 上游修改先确认

如果新证据表明更早阶段存在根因性错误：

1. 当前阶段先记录最小必要阻塞或待回写状态；
2. 明确列出受影响上游文档、旧事实和拟修改内容；
3. 获得用户确认后再改写上游；
4. 上游修正后清理当前阶段临时阻塞。

不得为了维持错误上游而在下游打补丁。

### 6.3 结构性变化必须做影响扫描

以下变化属于结构性变化：

- 范围或工作单元拓扑；
- 阶段状态；
- 接口、RPC、事件合同；
- 数据权威；
- 工作单元依赖；
- 配置真源。

发生结构性变化时，同一轮至少检查：

- 当前阶段顶部元信息；
- 相关正文规则和矩阵；
- 验证结论；
- 阻塞与下一动作；
- 已存在且实际依赖该事实的上下游阶段文档；
- 客户端合同；
- `00-工作流索引.md` 中的旧引用。

只传播到真实受影响范围，不机械使所有兄弟分支失效。

## 7. `record.jsonl` 审计与反馈

**文档变更记录硬限制：每次逻辑上的文档变更完成后，在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；同一原因、同一轮、同一目录内的原子变更只记录一次，用 `documents` 列出全部实际变化文件，只有根因、结果或验证边界不同才拆记录。`record.jsonl` 自身追加不触发再次记录。新记录使用 schema v4：必须记录 skill usage/skill/version、运行环境、模型、思考等级、action、documents、trigger、reason、change summary、validation、outcome；正常进度使用 `feedback.signal=none`，不得为了填字段虚构问题、根因或预防建议。只有出现值得后续学习的偏差时才写 feedback：疑似可泛化但证据未足用 `candidate`；已经能定位根因且可形成防复发规则用 `actionable`，并填写稳定可复用的 snake_case `pattern`、severity、category、root_cause 与 prevention。用户改变需求使用 `trigger=user_change`；用户指出 Agent/文档错误使用 `trigger=user_correction`，两者不得混为同一质量信号。跨需求重复、skill 流程遗漏、模板诱导遗漏或 review 发现的通用缺陷不得默认归为 `project_context`；应归到最靠近根因的 `skill`/`template`/`eval`/`tooling`/`agent_execution`，只有确实依赖单一项目缺失事实时才用 `project_context`。只要当前 Agent 实际加载/执行了本 skill，就必须调用本 skill 自带的 `scripts/document_record.py append --skill <当前skill>`，skill version 由写入器从当前 `SKILL.md` 自动读取；实际没有使用任何 skill 才可 `--no-skill`。历史 v1/v2/v3 保持原字节；append 只因非 UTF-8、非法 JSON 或非 object 等存储层损坏而拒绝，历史 schema 语义问题只由 `check` 报告。禁止使用 shell/PowerShell 文本重定向或通用文本 API 绕过写入器。需要评审记录时使用受限 `query`、`stats` 或 `report`，不得把全文注入上下文；评价 skill 必须按 `skill_usage=used` 和明确 `skill_version` 分组，并结合 report 的 metadata coverage 判断模型/运行环境比较是否有足够样本。禁止写入完整提示词、正文、用户敏感信息或思维过程。**

每个过程文档目录维护 append-only `record.jsonl`。它是审计与 skill 改进元数据，不是第二份阶段文档。

基本规则：

- 每次逻辑上的文档变更完成后追加一条记录；
- 同一原因、同一轮、同一目录内的原子变更合并为一条，用 `documents` 列出实际变化文件；
- `record.jsonl` 自身追加不再次触发记录；
- 新记录使用 schema v4；历史 v1/v2/v3 保持原字节；
- 正常进度使用 `feedback.signal=none`，不得虚构问题或改进建议；
- 用户改变需求使用 `trigger=user_change`；用户指出 Agent/文档错误使用 `trigger=user_correction`；
- 只有可泛化偏差才进入 `candidate` / `actionable` feedback；
- 实际加载并执行 skill 时，通过该 skill 自带 `scripts/document_record.py append --skill <skill>` 写入，版本由写入器读取当前 `SKILL.md`；未使用 skill 时才使用 `--no-skill`；
- 查询历史时使用有限尾部查询或流式聚合，不把完整 `record.jsonl` 读入上下文。

`record.jsonl` 的目的不是保存操作流水，而是保留：为什么改、改了什么、如何验证、是否暴露可泛化流程缺陷。

## 8. 配置与客户端合同

`game-config` 的配置执行状态、人工填表步骤和验证结果仍维护在当前工作单元的 `04-配置规划.md` 中，不再生成另一份权威“配置执行清单”。

给策划的配表说明属于非权威交付物，可以包含：

- 简短配置提醒；
- 主体表和代码真实消费字段说明。

不影响实现的次要配置可以延后给策划填写，但必须在配置阶段收尾时明确暴露。

客户端对接文档同样按工作单元独立：未分支使用 `<主题>-客户端对接文档.md`；分支后使用 `Uxx-<主题>-客户端对接文档.md`。拆分前已经稳定的共享合同可作为共同基线，各 Uxx 只记录自己的新增或变化合同。

## 9. Review 模型

分支 Review 的对象是当前工作单元，而不是整个需求目录。当前 Uxx 达到自己的 pre-review 门禁后即可进入 `07-Uxx-<主题>-交叉评审.md`。

整体 Review 只承担跨工作单元集成查漏，典型触发条件包括：

- 共享代码或数据权威；
- 同一状态机；
- 共用配置表；
- RPC / 事件命名空间耦合；
- 客户端合同组合；
- 迁移或发布顺序；
- 其他组合运行风险。

整体 Review 优先复用分支 Review 已确认结论和当前组合代码/配置证据，不机械重做每个 Uxx 的内部 Review。

## 10. 长期功能文档

过程文档用于推进工作，长期功能文档用于维护当前实现。

长期文档优先服从目标项目已有约定；没有约定时使用：

```text
docs/features/<feature>.md
```

`game-docs` 应以当前实现、全部相关已完成分支 Review，以及存在时的整体 Review 为事实来源，不把过程文档历史直接复制成长期文档。

## 11. 设计原则

1. **简单路径零成本**：没有真实拆分就保持单线，不创建额外工作流结构。
2. **工作单元按真实边界拆分**：只有能独立推进、阻塞、对接或 review 的范围才创建 Uxx；同一闭环内的步骤使用 Step。
3. **一个工作单元一个阶段一份权威文档**：避免并行真相。
4. **分支不增加目录层级**：DAG 由 `00` 表达，文档保持同目录。
5. **ID 与拓扑解耦**：Uxx 只表达稳定身份，依赖关系单独维护。
6. **文档保存当前真相**：历史交给 Git、日志和 `record.jsonl`。
7. **一个事实只出现一次**：需要关联时引用，不复制正文。
8. **事实自己查，决策才问人**：代码、配置和历史实现能回答的事实不转嫁给用户。
9. **当前阶段立即落盘**：关键事实不只停留在聊天上下文。
10. **根因优先于补丁**：发现错误上游时回退并修正原决策。
11. **按真实依赖推进**：兄弟单元不是天然门禁。
12. **证据优于结论**：配置、实现、对接和 Review 都必须能落到真实消费链和验证证据。
13. **运行安全优先**：不完整功能可以受控关闭，但不得破坏服务器启动、资产、数据和其他系统。
14. **整体 Review 按风险触发**：独立分支不为形式强制汇合复审。

## 12. 验证

仓库通过以下层次验证 skill 规则：

```bash
python scripts/validate_skills.py
```

验证器会要求每个 `SKILL.md` 包含统一的文档更新、结构性变更影响传播、阶段完成一致性与记录硬限制；对技术澄清、框架、完整实现和客户端对接技能额外检查跨层合同/真实消费链规则；对 `02`–`06` 和客户端对接技能检查分支工作流协议，对 `game-review` 检查 07 汇合协议，并检查每个 skill 自带的 UTF-8 写入器与仓库规范版本完全一致。

## 13. 参考思想

本仓库吸收并重新组合了以下思路：

- `mattpocock/skills`：小型、可组合技能；事实从环境调查获得，决策才交给用户；
- `Fission-AI/OpenSpec`：用可更新工件承载迭代过程，而不是把真实开发伪装成单向瀑布；
- `obra/superpowers`：先理解与确认，再按依赖推进，并用行为场景验证 skill 本身。

这些项目提供方法启发，但本仓库的文档边界、工作单元模型、配置阶段和游戏研发协作约束以本设计文档及各专项规范为准。
