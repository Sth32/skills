# Skills 设计文档

本文描述 `Sth32/skills` 的仓库级设计。README 只承担项目入口；长期取舍准则统一维护在 [`principles.md`](principles.md)，这里保存跨 skill 的工作流模型、文档模型和具体约束。具体分支操作细节见 [`branch-workflow.md`](branch-workflow.md)。

## 1. 目标

这组 skills 的目标不是把开发强制变成瀑布流程，而是把口述需求逐步收敛为：

- 可追溯的产品规则；
- 可确认的技术决策；
- 可执行、可验证的配置与实现；
- 明确的服务端—客户端合同；
- 可独立 review、可长期维护的工程结果。

核心约束是：**事实只维护一份权威当前值，阶段只承担自己的职责，工作单元只被真实依赖阻塞。**

## 2. 工作流模型

### 2.1 简单需求

没有真实拆分价值时，保持单线：

```text
01 原始需求
  → 02 需求挖掘
  → 03 程序实现澄清
  → 04 配置规划
  → 05 框架实现
  → 06 完整实现
  → 客户端对接（按需）
  → 07 交叉评审
  → 长期功能文档
```

简单需求不创建 `00-工作流索引.md`，也不人为创建 `U01`。

### 2.2 可拆分需求

只要已经形成真实独立需求边界，就可以从 `01` 开始创建工作单元 `Uxx`，也允许在后续阶段继续拆分。

```text
共享需求基线（按需）
  ├─ U01：01 → 02 → 03 → 04 → 05 → 06 → 客户端对接 → 07-U01 Review
  ├─ U02：01 → 02 → 03 → 04 → 05 → 06 → 客户端对接 → 07-U02 Review
  └─ U03：可以依赖 U01/U02，也可以继续拆分

各目标叶单元独立 Review 完成
  ↓
按集成风险判断是否需要整体 07-交叉评审
  ↓
长期功能文档
```

工作单元用于形成：

- 独立需求边界；
- 独立推进边界；
- 独立阻塞边界；
- 独立客户端对接边界；
- 独立 review 边界。

因此：

- 无依赖兄弟工作单元不互相等待；
- 不要求所有分支推进到同一阶段；
- 不要求在 review 前重新合并成一个工作单元；
- 结构性变化只使真实受影响的下游和 Review 失效；
- 所有目标叶单元完成后，只有存在跨单元集成风险时才创建整体 `07-交叉评审.md`。

详细拆分、命名、依赖和整体 Review 规则见 [`branch-workflow.md`](branch-workflow.md)。

## 3. Skill 职责边界

| Skill | 阶段 | 主要职责 |
|---|---|---|
| `game-spec` | 01 | 无损整理需求；识别真实独立范围并按需创建工作单元 |
| `game-discovery` | 02 | 只保留需要需求负责人决定的高价值产品未决问题 |
| `game-tech-clarify` | 03 | 收敛高影响技术决策与真实技术未决问题 |
| `game-config` | 04 | 确认配置对象、配置真源、合法值域、关键值和修改范围，并完成验证 |
| `game-scaffold` | 05 | 确定数据权威、持久化、同步、客户端可见性和基础调用链 |
| `game-implement` | 06 | 补齐行为、边界、失败处理、兼容、测试和运维闭环 |
| `game-client-handoff` | 对接 | 从真实实现提炼服务端—客户端合同 |
| `game-review` | 07 | 独立检查工作单元；按需执行跨单元集成查漏 |
| `game-docs` | 长期文档 | 从当前实现和已确认 Review 提炼长期权威功能文档 |

下游阶段不得复制上游完整内容。需要依赖时引用上游事实，只在本阶段记录会改变本阶段决策或执行的内容。

## 4. 权威文档模型

### 4.1 基本原则

权威过程文档粒度是：**工作单元 × 阶段**。

同一工作单元在同一阶段最多维护一份权威过程文档。共享父文档只保存真实共享基线，不复制已经归属子单元的事实。

代码、配置源、Excel、生成物、测试结果、diff 和日志是实际产物或证据，不计作第二份过程文档。

阶段文档保存的是**当前真相**，不是过程日志：

- 新事实替代旧事实；
- 已解决问题从正文移除或改写为最终结论；
- 被新证据推翻的判断不得继续与新结论并列；
- 历史过程通过 Git 与外部审计记录追溯。

### 4.2 未分支目录

```text
docs/requirements/<feature>/
├── 01-原始需求.md
├── 02-需求挖掘.md
├── 03-程序实现澄清.md
├── 04-配置规划.md
├── 05-框架实现方案.md
├── 06-完整实现方案.md
├── <主题名>-客户端对接文档.md（按需）
├── 07-交叉评审.md
├── 收尾事项.md（按需，非阶段）
```

### 4.3 分支目录

首次真实拆分后仍保持同一目录，不为 Uxx 增加子目录：

```text
docs/requirements/<feature>/
├── 00-工作流索引.md
├── 01-原始需求.md                         # 仅在存在共享基线时保留
├── 01-U01-战斗-原始需求.md
├── 01-U02-奖励-原始需求.md
├── 02-U01-战斗-需求挖掘.md
├── ...
├── 06-U02-奖励-完整实现方案.md
├── U01-战斗-客户端对接文档.md（按需）
├── U02-奖励-客户端对接文档.md（按需）
├── 07-U01-战斗-交叉评审.md
├── 07-U02-奖励-交叉评审.md
├── 07-交叉评审.md                         # 按集成风险可选
├── 收尾事项.md（按需，feature 级、非阶段）
```

`00-工作流索引.md` 只承担路由：工作单元 ID、范围、依赖、当前阶段、当前文档和整体 Review 状态。它不得复制需求规则、方案、配置值、验证结果、未决问题或阶段文档状态正文。

## 5. 阶段状态与切换门禁

阶段文档顶部 `状态` 是阶段状态的唯一权威来源。聊天中的“完成”“可以继续”不能替代文档状态。

开始一个按工作流顺序进入的下游阶段前，必须读取该 skill 声明的真实上游文档状态。未达到可移交终态时停止正常推进，回到上游闭环；只有 skill 明确允许并行或用户明确接受带阻塞并行时，才能做不依赖未决结论的安全工作。

当前主流程正常可移交终态：

| 阶段 | 正常可移交终态 |
|---|---|
| 01 原始需求 | 叶文档 `整理完成`；已拆分父文档可为 `已拆分` |
| 02 需求挖掘 | `已收敛` |
| 03 程序实现澄清 | `已收敛` |
| 04 配置规划 | `已完成` |
| 05 框架实现 | `骨架已完成` |
| 06 完整实现 | `已完成` |
| 07 交叉评审 | `通过`；`有条件通过` 仅按已明确接受的条件继续 |

结束阶段前必须先做一致性收敛：同一事项不得同时保留互斥状态、数值、操作要求或验证结论。证据不足时保持未完成或阻塞，不得以“已完成”结束阶段。

## 6. 文档更新与结构性变更传播

**结构性变更影响传播硬限制：当范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源发生变化时，必须在同一轮执行影响扫描，不得只修当前局部段落。当前阶段文档内至少核对顶部元信息、相关正文规则/矩阵、验证结论、阻塞与下一动作；同时定位已有且实际依赖该事实的上下游阶段文档、客户端合同与 `00-工作流索引.md` 中的旧引用。当前阶段和本 skill 允许直接维护的下游内容立即原位更新；若受影响的是需要用户确认才能改写的上游文档，必须明确列出受影响文件、旧事实与拟修改内容并等待确认，不得静默遗漏，也不得把未传播完成的结构性变化描述为已闭环。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

### 6.1 当前阶段立即落盘

任何新事实、确认、执行结果或验证结果，只要改变当前工作单元当前阶段内容，就在同一轮原位更新当前权威文档。

更新后明确告知用户变化路径，不把关键结论只留在聊天中。

### 6.2 上游修改先确认

如果新证据表明更早阶段存在根因性错误：

1. 当前阶段先记录最小必要阻塞或待回写状态；
2. 明确列出受影响上游文档、旧事实和拟修改内容；
3. 获得用户确认后再改写上游；
4. 上游修正后清理当前阶段临时阻塞。

不得为了维持错误上游而在下游打补丁。

### 6.3 结构性变化必须做影响扫描

以下变化属于结构性变化：

- 范围或工作单元拓扑；
- 阶段状态；
- 接口、RPC、事件合同；
- 数据权威；
- 工作单元依赖；
- 配置真源。

发生结构性变化时，同一轮至少检查：

- 当前阶段顶部元信息；
- 相关正文规则和矩阵；
- 验证结论；
- 阻塞与下一动作；
- 已存在且实际依赖该事实的上下游阶段文档；
- 客户端合同；
- `00-工作流索引.md` 中的旧引用。

只传播到真实受影响范围，不机械使所有兄弟分支失效。

### 6.4 低价值旁路问题延期收尾

复杂玩法开发中，跨系统耦合和边角问题不应因为“已经发现”就自动获得当前开发优先级。只有同时满足以下条件，问题才允许延期：

- 不改变本玩法主流程、当前需求或验收结果；
- 不影响数据正确性、运行安全、兼容/迁移或其他系统的稳定性；
- 当前影响低；
- 处理成本明显高于当前收益；
- 延后不会显著放大风险、返工或形成不可逆状态。

满足条件时，在当前 feature 目录按需创建或更新 `收尾事项.md`，只做最小记录后继续当前阶段。该文件是 **feature 级非阶段旁路清单**：不创建新的 Uxx/Step，不改变当前阶段状态，不构成 `01`–`07` 的阶段门禁，也不因为存在未完成条目而自动阻塞 Review。

每条只记录足以重新识别问题的信息：来源工作单元/阶段或代码位置（有必要时）、问题或耦合点、当前影响判断、延期理由。不要在当前阶段先为它展开完整方案、跨系统调查或重构设计，否则会重新引入本机制要消除的负担。

当全部目标主流程开发和验收完成后，对 `收尾事项.md` 做一次集中收尾：能低风险处理的直接处理；仍值得做但需要独立投入的转成正式任务；已经无价值的明确删除或关闭。若新证据表明某条不再满足延期条件，应立即移出旁路清单，回到正常工作流作为当前阻塞、结构性变更或上游修正处理。

Review 发现的问题只有在确认不影响 Review 通过条件且满足上述延期条件时，才可以进入 `收尾事项.md`；不得用旁路清单降级真正的正确性、运行安全或验收缺陷。`收尾事项.md` 的变更同样通过外部 recorder 记录；同一原因、同一轮与阶段文档一起变化时合并为一次原子提交。

## 7. 外部审计记录

**外部记录硬限制：每次逻辑上的文档变更完成后，只通过 `sth32-skills-record append` 提交本次变更的最小结构化事实；记录存储属于仓库外部基础设施，Agent 不得查找、定位、读取、搜索、解析或直接修改任何历史记录、记录文件或 recorder 实现，也不得为了写记录而扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。命令不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过 recorder。**

记录系统是仓库外部 telemetry 基础设施，不属于需求目录、阶段文档或项目知识空间。正常开发 Agent 只拥有 append 接口，不以历史记录作为当前任务上下文。

Agent 侧只依赖稳定命令接口：

```bash
sth32-skills-record append ...
```

存储路径、文件名、编码、schema 持久化细节和历史查询能力均属于 recorder 实现细节，不在 skill、阶段文档或普通 Agent 规则中暴露。需要分析历史反馈时，应由独立的 skill-maintenance / record-analysis 流程执行，而不是由正常开发 Agent 读取记录。

记录只保留改进所需的最小事实，不写完整提示词、聊天原文、文档正文、用户敏感信息或内部思维过程。

## 8. 配置与客户端合同

`game-config` 的配置执行状态、人工填表步骤和验证结果仍维护在当前工作单元的 `04-配置规划.md` 中，不再生成另一份权威“配置执行清单”。

给策划的配表说明属于非权威交付物，可以包含：

- 简短配置提醒；
- 主体表和代码真实消费字段说明。

不影响实现的次要配置可以延后给策划填写，但必须在配置阶段收尾时明确暴露。

客户端对接文档同样按工作单元独立：未分支使用 `<主题>-客户端对接文档.md`；分支后使用 `Uxx-<主题>-客户端对接文档.md`。拆分前已经稳定的共享合同可作为共同基线，各 Uxx 只记录自己的新增或变化合同。

## 9. Review 模型

分支 Review 的对象是当前工作单元，而不是整个需求目录。当前 Uxx 达到自己的 pre-review 门禁后即可进入 `07-Uxx-<主题>-交叉评审.md`。

整体 Review 只承担跨工作单元集成查漏，典型触发条件包括：

- 共享代码或数据权威；
- 同一状态机；
- 共用配置表；
- RPC / 事件命名空间耦合；
- 客户端合同组合；
- 迁移或发布顺序；
- 其他组合运行风险。

整体 Review 优先复用分支 Review 已确认结论和当前组合代码/配置证据，不机械重做每个 Uxx 的内部 Review。

## 10. 长期功能文档

过程文档用于推进工作，长期功能文档用于维护当前实现。

长期文档优先服从目标项目已有约定；没有约定时使用：

```text
docs/features/<feature>.md
```

`game-docs` 应以当前实现、全部相关已完成分支 Review，以及存在时的整体 Review 为事实来源，不把过程文档历史直接复制成长期文档。

## 11. 设计原则

长期取舍准则统一维护在 [`principles.md`](principles.md)。本设计文档负责解释这些准则如何落到工作流、文档模型和具体机制；这里不维护第二份并行原则列表。

## 12. 验证

仓库通过以下层次验证 skill 规则：

```bash
python scripts/validate_skills.py
```

验证器会要求每个 `SKILL.md` 包含统一的文档更新、结构性变更影响传播、阶段完成一致性与记录硬限制；对技术澄清、框架、完整实现和客户端对接技能额外检查跨层合同/真实消费链规则；对 `02`–`06` 和客户端对接技能检查分支工作流协议，对 `game-review` 检查 07 汇合协议，并检查每个 skill 自带的 UTF-8 写入器与仓库规范版本完全一致。

## 13. 参考思想

本仓库吸收并重新组合了以下思路：

- `mattpocock/skills`：小型、可组合技能；事实从环境调查获得，决策才交给用户；
- `Fission-AI/OpenSpec`：用可更新工件承载迭代过程，而不是把真实开发伪装成单向瀑布；
- `obra/superpowers`：先理解与确认，再按依赖推进，并用行为场景验证 skill 本身。

这些项目提供方法启发，但本仓库的长期取舍以 [`principles.md`](principles.md) 为准；文档边界、工作单元模型、配置阶段和游戏研发协作机制以本设计文档及各专项规范为准。
