# 分支工作流规范

本文定义 `docs/requirements/<feature>/` 下过程文档的分支模型。目标是在**不增加子目录层级**的前提下，让大需求能够按独立工作单元串行或并行推进，同时保持每份文档的唯一职责和跨 session 可恢复性。

## 边界

- `01-原始需求.md` 永远只有一份，是整个需求的共同根，不分支、不带工作单元 ID。
- `01` 达到可移交终态后，到 `07` review 开始前，允许在 `02`、`03`、`04`、`05`、`06` 或客户端对接过程中创建、继续拆分或串并行调度工作单元。
- `07` 是强制汇合点：无论之前有多少工作单元，review 永远只维护一份 `07-交叉评审.md`，禁止 `07-Uxx-*`。
- 所有过程文档始终放在同一个 `docs/requirements/<feature>/` 目录；禁止因为分支再建立 `U01/`、`branch-a/` 等子目录。
- 简单需求不为可扩展性付固定成本：没有实际分支时继续使用旧文件名，不创建空的 `00-工作流索引.md`。

## 工作单元模型

分支的最小单位是**工作单元**，使用稳定 ID：`U01`、`U02`、`U03`……。

工作单元只表达身份，不表达拓扑。禁止使用 `A1`、`A1.2`、`U01.1` 等把父子、先后或层级编码进 ID。串行、并行、汇入关系统一由 `00-工作流索引.md` 中的依赖表达，因此拓扑调整不要求重命名已有文件。

适合拆成工作单元的情况：

- 可以独立推进和独立阻塞；
- 可以由不同 session 或 Agent 分别完成；
- 有独立的人类 review 边界；
- 依赖关系明确，拆开后能明显降低单次认知负担。

如果只是同一实现闭环里的连续步骤、不能独立交付或独立阻塞，优先使用阶段文档内部的 Step，不创建工作单元。

## 文件命名

未分支时保持兼容：

```text
02-需求挖掘.md
03-程序实现澄清.md
04-配置规划.md
05-框架实现方案.md
06-完整实现方案.md
<主题名>-客户端对接文档.md
```

工作单元进入某阶段后：

```text
<阶段号>-<Uxx>-<主题>-<阶段名>.md
```

例如：

```text
03-U01-战斗-程序实现澄清.md
04-U01-战斗-配置规划.md
04-U02-奖励-配置规划.md
05-U02-奖励-框架实现方案.md
06-U02-奖励-完整实现方案.md
U02-奖励-客户端对接文档.md
```

`<主题>` 是短且稳定的人类可读范围名；身份仍以 `Uxx` 为准。不得因为主题措辞调整重新分配工作单元 ID。

## `00-工作流索引.md`

第一次真正发生分支时创建，之后只维护拓扑和路由信息：

```markdown
# <功能名>：工作流索引

> 首次分支来源：<共享阶段文档或 ROOT>
> Review 汇合：未进入 / `07-交叉评审.md`
> 最后更新：<YYYY-MM-DD>

| 单元 | 范围 | 依赖 | 当前阶段 | 当前文档 |
|---|---|---|---|---|
| U01 | <范围> | ROOT | 03 | `03-U01-...md` |
| U02 | <范围> | ROOT | 03 | `03-U02-...md` |
| U03 | <范围> | U01,U02 | 04 | `04-U03-...md` |
```

规则：

- `ROOT` 表示第一次分支前的共同已确认基线；若从已有工作单元继续拆分，子单元依赖原工作单元。
- 索引只记录 ID、范围、依赖、当前阶段和当前文档，以及 review 汇合指针；不得复制需求规则、技术方案、配置值、验证结果、未决问题或阶段文档顶部状态。
- 阶段文档顶部状态仍是该文档状态的唯一权威来源；需要判断是否可推进时读取目标文档，不从索引猜状态。
- 只有拓扑、范围归属、当前阶段或当前文档变化时才更新索引，普通正文修改不重复写索引。
- 创建或修改索引也属于过程文档变更，必须按当前 skill 的 `record.jsonl` 规则记录。

## 创建或继续拆分

Agent 先根据依赖给出最短拆分，通常 2–5 个工作单元；用户已经明确要求拆分时可直接按最短依赖模型执行，否则先说明拆分理由、工作单元和依赖并取得用户确认。

发生拆分时：

1. 第一次分支先创建 `00-工作流索引.md`；已有索引则原位更新。
2. 为所有新后继分配新的 `Uxx`，不得复用或重解释旧 ID。
3. 若当前阶段文档已经包含拆分前的共享内容，将它压缩为仍然有效的共同基线，顶部状态改为 `已拆分`，并只保留到索引的最小指针；`已拆分` 是路由终态，不代表该父工作单元可以直接进入下一阶段。
4. 分支专属事实移动到对应子工作单元文档；共享上游事实通过引用继承，不复制到每个分支。
5. 同一轮更新索引和受影响阶段文档，并明确告知用户所有变更路径。

工作单元还可以继续拆分。父工作单元被拆分后不再创建新的后续阶段文档；只有它的叶子后继继续推进。

## 分支阶段门禁

存在 `00-工作流索引.md` 时，任何 `02`–`06` skill 在写入前必须先解析目标 `Uxx` 的实际依赖：

- 只检查该工作单元依赖的共享上游和直接前驱；
- 未被依赖的兄弟工作单元不构成阻塞，因此可以真正并行；
- 依赖多个前驱的工作单元必须等待这些前驱都达到对应可移交终态；
- 索引无法唯一确定目标工作单元、依赖或当前文档时，先修正索引，不得靠聊天记忆猜测；
- 每个“工作单元 × 阶段”最多一份权威文档。`00` 是路由元数据，不属于某个工作单元的阶段正文。

## Review 强制汇合

`game-review` 开始前：

1. 若不存在 `00`，按原单线门禁检查 `01`–`06`。
2. 若存在 `00`，读取完整 DAG，找出所有当前叶工作单元；被标记 `已拆分` 的父节点不算叶节点。
3. 每个叶工作单元的实际 pre-review 链路必须闭环，当前实现文档必须达到可 review 终态，通常为对应 `06=已完成`；存在的客户端对接文档也必须处于可移交状态。
4. 任一叶工作单元未闭环时不得创建或开始 `07`，应明确指出阻塞单元和文档。
5. 全部满足后把索引的 `Review 汇合` 指向 `07-交叉评审.md`，再创建或继续唯一的 `07-交叉评审.md`。review 包必须覆盖所有工作单元及共享基线。

review 中发现需要重新拆分工作时，不得创建 `07` 分支。应先把 `07` 保持为未通过/阻塞状态，暂停 review，回到 `02`–`06` 的适当阶段更新 DAG；所有新增工作单元再次闭环后，重新汇合到原来的 `07-交叉评审.md`。
