# 轻量维护工作流

本文定义 `Sth32/skills` 中不进入 `01–07` 正式功能开发链路的日常维护通道。它适用于 bug 修复、小需求、局部重构、轻量 Review 和线上 Hotfix。

## 1. 为什么需要独立维护通道

正式流程解决的是需求、技术、配置、框架、实现、对接和 Review 中存在较高不确定性或协作成本的功能开发问题。日常维护通常已经有明确目标和现有实现基础，如果仍强制创建阶段文档、状态门禁、Uxx 和多 Agent Review，会把流程成本放大到超过任务本身。

因此仓库同时支持两类路径：

```text
正式功能开发
01 → 02 → 03 → 04 → 05 → 06 → 对接 → 07 → 长期文档

轻量维护
调查事实 → 最小正确修改 → 按风险验证 → 收尾
```

轻量维护不是正式流程的“低质量版本”。它保留根因、证据、运行安全和真实依赖原则，只删除不产生实际价值的阶段状态管理。

## 2. Skill 路由

| Skill | 使用场景 | 核心约束 |
|---|---|---|
| `game-bugfix` | 已存在行为错误，需要定位根因并修复 | 根因优先；复现/证据；最小回归面 |
| `game-small-change` | 规则明确、范围局部的小需求或行为调整 | 沿现有机制扩展；不提前设计未来能力 |
| `game-refactor` | 不应改变外部行为的结构整理 | 先冻结行为；证明行为等价 |
| `game-light-review` | 对局部维护 diff 做快速可靠 Review | 只审实际风险面；证据优于偏好 |
| `game-hotfix` | 已上线或明确按生产约束处理的紧急修复 | 线上状态、存量数据、发布、回滚和止损优先 |

如果任务调查后越过当前 skill 边界，回到最早必要的正式 skill，而不是强行留在轻量路径。

## 3. 轻量维护共同原则

1. **事实自己查，决策才问人**：代码、配置、日志、测试和现有行为能回答的事实不得转嫁给用户。
2. **根因优先于补丁**：优先修正错误事实产生的位置；临时 workaround 必须显式标记退出条件。
3. **最小影响面**：只修改完成当前目标所需范围，不顺手扩展需求或进行无关重构。
4. **证据按风险扩展**：至少验证当前目标和直接回归面；只有实际经过异步、持久化、权限、跨实体/进程等边界时才继续深入。
5. **运行安全优先**：任何维护改动不得为了局部成功破坏启动、数据、资产或其他系统。
6. **低价值旁路问题不升级主任务**：记录或报告即可，除非它会影响当前正确性、验收或运行安全。
7. **越界就升级**：真正出现新产品规则、高影响技术决策、公共合同、数据模型或大范围结构变化时，进入正式流程。

## 4. 开发期与线上约束

这是轻量维护与 Hotfix 的关键分界。

### 4.1 普通维护默认按当前开发事实处理

`game-bugfix`、`game-small-change`、`game-refactor` 和普通 `game-light-review` **不得因为系统未来可能上线，就自动假设存在必须兼容的线上存量数据、在线玩家状态、灰度发布或无损迁移约束。**

如果项目当前仍处于开发期，允许根据项目现实采用清库、重建测试数据、重新生成开发资产等低成本路径；不能为了假设性的未来线上环境提前制造迁移和兼容复杂度。

如果是否已经上线会实质改变修改方案，而当前上下文无法可靠确认，Agent 只询问一次类似“这次需要按线上已有存量数据处理吗？”的高价值问题；确认仍在开发期后停止线上方向的深入探索。

### 4.2 Hotfix 默认按生产约束处理

只有以下情况进入 `game-hotfix`：

- 用户明确说明已上线/生产环境发生问题；
- 当前项目事实表明存在必须保护的真实玩家、在线状态或存量数据；
- 用户明确要求进行生产约束演练。

进入 Hotfix 后，线上状态、历史数据、版本并存、发布方式、灰度、监控、回滚、补偿和止损成为默认调查项。

“紧急”本身不是 Hotfix 的定义。开发期一个很急的 bug 仍然是 `game-bugfix`。

## 5. 维护文档模型

### 5.1 默认不创建过程文档

轻量维护默认只依赖用户目标、当前代码/diff、测试和实际运行证据，不创建：

- `01–07` 阶段文档；
- `00-工作流索引.md`；
- Uxx / DAG；
- 阶段状态或切换门禁；
- 为了形式而存在的计划、测试报告、完成总结。

### 5.2 只有用户明确要求才创建维护记录

新的维护记录只能由用户明确要求创建。跨 session、多人接力、事故处置、数据补偿或回滚等情况可以成为 Agent **建议用户留档**的理由，但不能成为 Agent 自行落盘的授权。

用户要求后，使用对应 skill 自带模板。维护记录只保存继续工作所需的当前事实：目标、已确认事实、实际修改、验证、剩余风险和接力点。它不是新的权威阶段体系，也不模仿 `01–07`。

### 5.3 长期权威文档仍只保存稳定事实

如果维护改动使已有长期模块文档中的系统契约失效，应指出并按项目已有文档规则处理；临时 bug、排查过程、事故流水、测试日志和任务状态不得写入长期文档。不存在长期权威文档时，不因为一次轻量维护自动创建新的功能文档。

## 6. 从轻量维护升级到正式流程

出现下列情况之一时，Agent 应明确说明越界原因，并进入最早真正需要的阶段：

- 正确产品行为仍需需求负责人决定 → `game-discovery`；
- 需要决定架构、数据权威、公共合同、一致性、兼容或发布模型 → `game-tech-clarify`；
- 配置对象/真源或字段语义需要重新设计 → `game-config`；
- 需要建立新的数据、同步、持久化或基础调用链框架 → `game-scaffold`；
- 已经有稳定框架但范围扩大为正式功能实现 → `game-implement`；
- 改动风险和组合面需要正式独立交叉评审 → `game-review`。

升级只从最早必要节点开始，不为了形式补齐与当前任务无关的阶段。
