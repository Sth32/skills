# Game Development Skills

一组面向游戏研发需求与实现协作的 Agent Skills。它把口述需求逐步收敛为可配置、可实现、可评审、可维护的工程结果，同时保持策划、服务端与客户端的职责边界。

## 工作流

```text
原始材料
  ↓
01 原始需求（唯一共同根，不分支）
  ↓
02–06 可按工作单元组成 DAG
  ├─ U01 ─→ 03/04/05/06 ... ─┐
  ├─ U02 ─→ 03/04/05/06 ... ─┼─→ 07 多 Agent 交叉评审（强制汇合，唯一文档）
  └─ U03 可依赖 U01/U02 ──────┘
       └─ 客户端对接文档按工作单元生成或更新
  ↓
项目长期功能文档
```

这些是可组合动作，不是不可逆的瀑布阶段。简单需求继续按单线推进；只有真实需要独立推进、独立阻塞或独立 review 时才创建工作单元。新事实改变当前阶段内容时，必须立即更新对应工作单元的当前阶段文档；新事实改变上游决策时，应先明确拟修改内容并获得用户确认，再更新对应上游文档，而不是在下游堆补丁、静默回写或保留多个版本。

## 技能

| 技能 | 主要产物 | 负责解决的问题 |
|---|---|---|
| `game-spec` | `01-原始需求.md` | 将口述、聊天、工单和各类文档无损压缩为简洁的当前需求；`01` 永不分支 |
| `game-discovery` | `02-需求挖掘.md` / `02-Uxx-<主题>-需求挖掘.md` | 基于需求与现有代码，只保留需要需求负责人决定的高价值未决问题 |
| `game-tech-clarify` | `03-程序实现澄清.md` / `03-Uxx-<主题>-程序实现澄清.md` | 收敛当前有效的高影响实现决策与真实未决技术问题 |
| `game-config` | `04-配置规划.md` / `04-Uxx-<主题>-配置规划.md` | 用差异优先的短文档确认配置对象、真实配置源、关键值和修改范围，再配表并验证 |
| `game-scaffold` | `05-框架实现方案.md` / `05-Uxx-<主题>-框架实现方案.md` + 可运行骨架 | 确定实体属性、数据权威与持久化、镜像同步、客户端可见性和空 RPC 路由，不实现产品规则 |
| `game-implement` | `06-完整实现方案.md` / `06-Uxx-<主题>-完整实现方案.md` + 完整代码 | 沿已确认框架补齐行为、边界、失败、兼容、测试和运维闭环 |
| `game-client-handoff` | `<主题>-客户端对接文档.md` / `Uxx-<主题>-客户端对接文档.md` | 从 Server 事实生成属性同步、实体生命周期、RPC/事件和数据充分性合同，不设计客户端内部实现 |
| `game-review` | `07-交叉评审.md` | 强制汇合全部 pre-review 工作单元，使用独立多 Agent 视角交叉证伪需求、配置、架构和实现问题 |
| `game-docs` | `docs/features/<feature>.md` | 在 review 汇合后从当前实现提炼模块权威文档，不记录配置快照与任务状态 |

## 过程文档结构

未发生分支时保持原结构，不创建额外索引：

```text
docs/requirements/<feature>/
├── 01-原始需求.md
├── 02-需求挖掘.md
├── 03-程序实现澄清.md
├── 04-配置规划.md
├── 05-框架实现方案.md
├── 06-完整实现方案.md
├── <主题名>-客户端对接文档.md（按需）
├── 07-交叉评审.md
└── record.jsonl（append-only 审计元数据）
```

第一次真正拆分后仍使用**同一目录**，禁止为分支增加一级子目录：

```text
docs/requirements/<feature>/
├── 00-工作流索引.md
├── 01-原始需求.md
├── 02-需求挖掘.md                         # 若分支发生在 02 之后，可作为共同上游
├── 03-U01-战斗-程序实现澄清.md
├── 03-U02-奖励-程序实现澄清.md
├── 04-U01-战斗-配置规划.md
├── 04-U02-奖励-配置规划.md
├── 05-U01-战斗-框架实现方案.md
├── 05-U02-奖励-框架实现方案.md
├── 06-U01-战斗-完整实现方案.md
├── 06-U02-奖励-完整实现方案.md
├── U01-战斗-客户端对接文档.md（按需）
├── U02-奖励-客户端对接文档.md（按需）
├── 07-交叉评审.md                         # 所有工作单元在这里汇合
└── record.jsonl
```

**权威文档粒度是“工作单元 × 阶段”。** 每个工作单元在一个阶段最多维护一份权威过程文档；不得为了人工执行、调查、验证、移交、总结或多 Agent 分工而给同一工作单元额外创建清单、报告、摘要或子文档。不同工作单元可以同时位于同一阶段，也可以处于不同阶段。代码、配置源、Excel、测试、生成物、diff 和日志属于实际产物或证据，不计作过程文档。

`00-工作流索引.md` 是分支工作流的路由元数据，不属于某个阶段的业务正文，因此不违反上述限制；它只能记录工作单元 ID、范围、依赖、当前阶段、当前文档和 review 汇合指针，不得复制需求规则、方案、配置值、验证结果、未决问题或阶段文档顶部状态。

`game-config` 的人工填表步骤、执行状态和验证结果仍全部写入当前工作单元的配置规划文档，不生成配置执行清单。

`game-client-handoff` 在未分支时继续使用 `<主题名>-客户端对接文档.md`；分支工作流中使用 `Uxx-<主题名>-客户端对接文档.md`，避免多个工作单元争用同一文件。拆分前已经存在的共享对接文档可作为共同基线保留，后续工作单元只记录自己的新增或变化合同，不复制共享合同。

长期实现文档优先服从项目已有约定；没有约定时写入：

```text
docs/features/<feature>.md
```

## 分支工作流

完整维护规范见 [`docs/skill-development/branch-workflow.md`](docs/skill-development/branch-workflow.md)。核心规则：

1. **01 不分支**：`01-原始需求.md` 永远是唯一共同根。工作单元只能在 `01` 达到可移交终态后创建。
2. **07 前可分支**：从 `02` 开始到 `game-review` 启动前，任何阶段都可以根据真实依赖拆成工作单元，或让工作单元继续拆分。
3. **简单路径零成本**：没有实际分支时不创建 `00`，继续使用原文件名。
4. **首次拆分才建 `00`**：ID 使用稳定的 `U01`、`U02`……；串行、并行和多前驱依赖统一写在索引中，不把拓扑编码进 ID。
5. **禁止分支子目录**：所有工作单元文档与 `01`、`07`、`record.jsonl` 保持同目录。
6. **兄弟分支互不阻塞**：阶段门禁只检查当前工作单元的共享上游和实际依赖；未被依赖的兄弟工作单元可以处于其他阶段。
7. **拆分父节点停止推进**：若一个正在进行的工作单元继续拆分，当前文档压缩为共同基线并标记 `已拆分`；后续只由索引中的叶子后继推进，父节点不得直接创建下一阶段文档。
8. **Step 与工作单元不同**：同一实现闭环内部的分批人工 review 用 `game-implement` 文档内的 Step；只有可以独立推进、独立阻塞或独立 review 的范围才拆 `Uxx`。
9. **07 强制汇合**：开始 `game-review` 前必须检查全部叶工作单元的 pre-review 链路都已闭环。`07` 永远只有 `07-交叉评审.md` 一份，禁止 `07-Uxx-*`。
10. **review 中不新开 07 分支**：若 review 发现必须新增独立工作单元，暂停 review、回退到 `02`–`06` 更新 DAG；新增工作闭环后重新汇合到原来的 `07-交叉评审.md`。

在所有 skill 中，统一的“本阶段唯一文档”硬限制在分支模式下解释为：**当前工作单元在当前阶段的唯一权威文档**。它不禁止同一阶段存在其他工作单元的权威文档；`00` 也不属于工作单元阶段正文。

## 文档变更记录

每个过程文档目录维护一个 append-only 的 `record.jsonl`，用于把实际失误、修正原因和验证结果反馈给 skill 开发者。它是审计元数据，不是第二份阶段文档。分支工作流中的 `00` 和各 `Uxx` 阶段文档同样遵守记录规则。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。每条新记录必须包含实际 `skill_version`；版本由写入器从当前 skill 根目录 `SKILL.md` 的 `metadata.version` 自动读取，禁止由 Agent 手填、猜测或沿用历史值。写入器无法读取版本、版本格式非法或 `--skill` 与当前 `SKILL.md` 名称不一致时，必须拒绝追加并明确报告；不得写 `unknown` 伪装新记录。历史 schema v1 记录缺少版本时保留原样，查询和统计统一视为 `skill_version=unknown`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill 及其实际版本、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须按 `skill_version` 过滤或分组，不能把版本未知的旧记录或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

每个 skill 目录都自带同一份 UTF-8 写入器。即使只复制单个 `skills/<skill-name>/` 目录，也必须使用该 skill 内的脚本，不得退回 Shell 追加。写入器会从该 skill 自己的 `SKILL.md` 自动读取 `metadata.version`，调用者不传版本：

```bash
python <skill-root>/scripts/document_record.py append --record docs/requirements/<feature>/record.jsonl \
  --skill game-spec --runtime codex-cli --model gpt-5.6 --reasoning-effort high \
  --action update --document docs/requirements/<feature>/01-原始需求.md \
  --trigger user_feedback --problem "预期同一规则只出现一次，实际在多个章节重复" \
  --root-cause "固定分类标题拆散同一问题" \
  --change "合并规则并删除重复内容" \
  --validation-status passed --validation "语义去重检查通过" \
  --outcome success --improvement-target eval \
  --prevention "增加重复事实回归场景"
```

查询时禁止全文读取。只允许有限尾部查询或流式聚合。滚动评估优先显式指定版本，避免把不同 skill 版本混在一起：

```bash
python <skill-root>/scripts/document_record.py check --record <path>/record.jsonl
python <skill-root>/scripts/document_record.py query --record <path>/record.jsonl --tail 20 --skill game-spec --skill-version 0.1.8
python <skill-root>/scripts/document_record.py stats --record <path>/record.jsonl --skill game-spec
```

`append` 会在进程内部流式校验已有文件，但不会把历史内容返回给 Agent。发现旧文件不是 UTF-8 JSONL 时必须停止追加并报告，不能继续制造混合编码；历史修复应作为一次显式迁移处理。schema v1 历史记录没有 `skill_version` 时保持原样，在查询和统计中归为 `unknown`，不得根据时间或提交猜测回填。

记录的目标不是保存操作流水，而是形成可执行反馈。当前暂不收紧记录触发范围；`problem` 应尽量写清预期与实际差异，`validation.evidence` 保存修复后的最小验证证据，`improvement.prevention` 写防复发机制而不是项目待办。

## 文档更新时序

所有技能必须遵守同一条硬规则：

1. 任何新事实、确认、执行结果或验证结果，只要改变当前工作单元当前阶段内容，就必须在同一轮立即原位更新对应权威文档。
2. 每次更新后必须明确告知用户已更新的文件路径，不能只在聊天中描述结论，也不能等到阶段结束、批次结束或用户再次提醒。
3. 若新结论会改变更早阶段文档，先在当前阶段文档记录最小必要的阻塞或待回写状态，并告知用户当前文档已更新。
4. 随后主动说明受影响的上游文档和拟修改内容，获得用户确认后才可更新上游文档；未确认前不得静默改写。
5. 上游更新完成后，必须明确告知用户对应路径，并立即清理当前阶段文档中已经解除的临时阻塞或待回写状态。
6. 若创建、拆分、结束工作单元导致拓扑、当前阶段或当前文档变化，同一轮更新 `00-工作流索引.md`；普通正文变化不重复写索引。

`game-discovery` 的特殊闭环仍是：回答先写入当前 `02`；需要形成正式产品规则时，先请求用户确认，再回写唯一的 `01`，最后从当前 `02` 删除临时待回写内容。

## 阶段完成一致性收敛

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

阶段文档承担的是“当前真相”，不是过程日志。历史尝试、旧状态和被新证据推翻的判断依赖 Git、diff、日志或 `record.jsonl` 追溯；正文只保留会影响后续决策和执行的唯一当前事实。`00` 只承担拓扑和路由，不成为第二份事实汇总。

## 阶段切换门禁

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

正常可移交终态以各阶段模板为准。当前主流程为：

| 阶段 | 权威文档 | 正常可移交终态 |
|---|---|---|
| 01 原始需求 | `01-原始需求.md` | `整理完成` |
| 02 需求挖掘 | `02-需求挖掘.md` | `已收敛` |
| 03 程序实现澄清 | `03-程序实现澄清.md` | `已收敛` |
| 04 配置规划 | `04-配置规划.md` | `已完成` |
| 05 框架实现 | `05-框架实现方案.md` | `骨架已完成` |
| 06 完整实现 | `06-完整实现方案.md` | `已完成` |
| 07 交叉评审 | `07-交叉评审.md` | `通过`；`有条件通过` 仅按已明确接受的条件继续 |

顶部状态只表达**当前阶段自身**是否闭环。下游依赖必须留在事项内，例如配置阶段已经完成但仍有代码接入工作时，`04` 顶部应为 `已完成`，代码依赖写在对应配置事项中，而不是把阶段状态写成“待代码接入”。

## 设计原则

1. **一个工作单元一个阶段一份权威文档**：同一 `Uxx` 在同一阶段不能有两个过程文档；不同工作单元允许并行存在。
2. **01 单根、07 单汇合**：原始需求永不分支；所有 pre-review 工作单元必须在唯一 `07-交叉评审.md` 汇合。
3. **分支不增加目录层级**：DAG 写在可选 `00-工作流索引.md`，所有文件保持同目录。
4. **ID 与拓扑解耦**：`Uxx` 只表达身份；串行、并行和多前驱关系由依赖表达，拓扑变化不重命名 ID。
5. **文档是当前真相**：问题、答案、状态、方案与证据写回对应文档；新结论替代旧内容，不追加平行版本。
6. **按问题聚合**：同一问题的条件、依据、结论和影响放在相邻位置，不按数值、状态、模块、数据或风险等分类拆散。
7. **一个事实只出现一次**：不建立重复的摘要、台账、当前批次或分类汇总；需要关联时使用引用，不复制正文。
8. **当前阶段立即落盘**：任何会改变当前工作单元内容的新信息必须在同一轮写回当前文档，并明确告知用户路径。
9. **上游修改先确认**：发现根因性错误时主动提出上游修订，但必须先说明受影响文档和拟修改内容，获得用户确认后再更新。
10. **沟通后立即闭环**：每轮沟通结束后更新权威文档，移除已解决、被覆盖、失效或不再有价值的内容。
11. **事实自己查，决策才问人**：代码、配置和历史实现能回答的事实，不转嫁给策划或程序。
12. **按影响收敛**：只讨论会改变行为、范围、架构、数据安全或交付风险的事项。
13. **逐层保持职责**：原始需求保存产品规则；需求挖掘只保留未决产品问题；程序澄清保存高影响技术决策；后续阶段不得复制上游内容。
14. **运行安全优先**：不完整功能可以受控关闭，但不得破坏服务器启动、资产、数据和其他系统。
15. **证据优于结论**：配置需导表和加载验证，实现需测试和运行证据，对接文档需与实际属性、协议和同步代码一致，review 需触发路径和代码依据。
16. **允许回退上游**：发现根因性错误时修订原决策，不以下游补丁维持错误框架；上游修订必须经过用户确认。

## 安装

```bash
npx skills@latest add Sth32/skills
```

也可以只复制需要的 `skills/<skill-name>/` 目录到 Agent 的 skills 目录。

## 验证

运行静态验证：

```bash
python scripts/validate_skills.py
```

验证器会要求每个 `SKILL.md` 包含统一的文档更新、阶段完成一致性与记录硬限制；对 `02`–`06` 和客户端对接技能额外检查分支工作流协议，对 `game-review` 检查 07 汇合协议，并检查每个 skill 自带的 UTF-8 写入器与仓库规范版本完全一致。

`evals/` 中包含每个技能的行为测试场景；`evals/branch-workflow.md` 专门覆盖简单需求零额外成本、中途拆分、兄弟并行、多前驱依赖、Step 与工作单元区分、客户端对接命名、07 强制汇合以及 review 中回退重拆等失效模式。

## 参考思想

本仓库吸收以下项目的方法，并按游戏研发中“策划—程序—配置—实现—维护”的协作边界重新设计：

- `mattpocock/skills`：小型、可组合技能；事实通过环境调查获得；决策逐个确认。
- `Fission-AI/OpenSpec`：以可更新工件承载迭代过程，不把真实开发伪装成单向阶段。
- `obra/superpowers`：先理解与确认，再进入实现；按依赖推进；使用行为场景验证技能本身。
