# Game Development Skills

一组面向游戏研发需求与实现协作的 Agent Skills。它把口述需求逐步收敛为可配置、可实现、可评审、可维护的工程结果，同时保持策划、服务端与客户端的职责边界。

## 工作流

```text
原始材料
  ↓
01 原始需求
  ↓
02 需求挖掘（面向策划）
  ↓
03 程序实现澄清（面向负责程序）
  ↓
04 配置规划与配表
  ↓
05 数据与消息拓扑骨架
  ↓
06 完整实现
  ├─ 客户端对接文档（属性 / RPC 合同，按需生成或更新）
  ↓
07 多 Agent 交叉评审
  ↓
项目长期功能文档
```

这些是可组合动作，不是不可逆的瀑布阶段。新事实改变当前阶段内容时，必须立即更新当前阶段文档；新事实改变上游决策时，应先明确拟修改内容并获得用户确认，再更新对应上游文档，而不是在下游堆补丁、静默回写或保留多个版本。

## 技能

| 技能 | 主要产物 | 负责解决的问题 |
|---|---|---|
| `game-spec` | `01-原始需求.md` | 将口述、聊天、工单和各类文档无损压缩为简洁的当前需求 |
| `game-discovery` | `02-需求挖掘.md` | 基于需求与现有代码，只保留需要需求负责人决定的高价值未决问题 |
| `game-tech-clarify` | `03-程序实现澄清.md` | 收敛当前有效的高影响实现决策与真实未决技术问题 |
| `game-config` | `04-配置规划.md` | 用差异优先的短文档确认配置对象、真实配置源、关键值和修改范围，再配表并验证 |
| `game-scaffold` | `05-框架实现方案.md` + 可运行骨架 | 确定实体属性、数据权威与持久化、镜像同步、客户端可见性和空 RPC 路由，不实现产品规则 |
| `game-implement` | `06-完整实现方案.md` + 完整代码 | 沿已确认框架补齐行为、边界、失败、兼容、测试和运维闭环 |
| `game-client-handoff` | `客户端对接文档.md` | 从 Server 事实生成属性同步、实体生命周期、RPC/事件和数据充分性合同，不设计客户端内部实现 |
| `game-review` | `07-交叉评审.md` | 使用独立多 Agent 视角交叉证伪需求、配置、架构和实现问题 |
| `game-docs` | `docs/features/<feature>.md` | 将当前实现提炼为简洁的模块权威文档，明确职责、核心规则、数据权威、持久化、同步和跨模块契约，不记录配置快照与任务状态 |

默认过程文档目录：

```text
docs/requirements/<feature>/
├── 01-原始需求.md
├── 02-需求挖掘.md
├── 03-程序实现澄清.md
├── 04-配置规划.md
├── 05-框架实现方案.md
├── 06-完整实现方案.md
├── 客户端对接文档.md（独立对接阶段，按需）
└── 07-交叉评审.md
```

**每个阶段最多维护一份权威过程文档。** 不得为了人工执行、调查、验证、移交、总结或多 Agent 分工而额外创建清单、报告、摘要或子文档；这些内容应压缩到本阶段唯一文档的对应事项附近。代码、配置源、Excel、测试、生成物、diff 和日志属于实际产物或证据，不计作过程文档。

`game-config` 的人工填表步骤、执行状态和验证结果全部写入 `04-配置规划.md`，不再生成 `04-配置执行清单.md`。

`game-client-handoff` 是独立的对接阶段，因此拥有自己的唯一文档。它可在属性和 RPC 骨架稳定后先生成，并在完整实现后原位更新；不得再拆分属性清单、RPC 清单或客户端缺口报告。

长期实现文档优先服从项目已有约定；没有约定时写入：

```text
docs/features/<feature>.md
```

## 文档更新时序

所有技能必须遵守同一条硬规则：

1. 任何新事实、确认、执行结果或验证结果，只要改变当前阶段内容，就必须在同一轮立即原位更新当前阶段唯一文档。
2. 每次更新后必须明确告知用户已更新的文件路径，不能只在聊天中描述结论，也不能等到阶段结束、批次结束或用户再次提醒。
3. 若新结论会改变更早阶段文档，先在当前阶段文档记录最小必要的阻塞或待回写状态，并告知用户当前文档已更新。
4. 随后主动说明受影响的上游文档和拟修改内容，获得用户确认后才可更新上游文档；未确认前不得静默改写。
5. 上游更新完成后，必须明确告知用户对应路径，并立即清理当前阶段文档中已经解除的临时阻塞或待回写状态。

`game-discovery` 的特殊闭环是：回答先写入 `02`；需要形成正式产品规则时，先请求用户确认，再回写 `01`，最后从 `02` 删除临时待回写内容。

## 设计原则

1. **一个阶段一份权威文档**：每个 skill 只能维护其声明的主文档，不创建执行清单、验证报告、reviewer 子报告或其他旁支过程文档。
2. **文档是当前真相**：问题、答案、状态、方案与证据写回对应文档；新结论替代旧内容，不追加平行版本。
3. **按问题聚合**：同一问题的条件、依据、结论和影响放在相邻位置，不按数值、状态、模块、数据或风险等分类拆散。
4. **一个事实只出现一次**：不建立重复的摘要、台账、当前批次或分类汇总；需要关联时使用引用，不复制正文。
5. **当前阶段立即落盘**：任何会改变当前阶段内容的新信息必须在同一轮写回当前文档，并明确告知用户路径。
6. **上游修改先确认**：发现根因性错误时主动提出上游修订，但必须先说明受影响文档和拟修改内容，获得用户确认后再更新。
7. **沟通后立即闭环**：每轮沟通结束后更新权威文档，移除已解决、被覆盖、失效或不再有价值的内容。
8. **事实自己查，决策才问人**：代码、配置和历史实现能回答的事实，不转嫁给策划或程序。
9. **按影响收敛**：只讨论会改变行为、范围、架构、数据安全或交付风险的事项。
10. **逐层保持职责**：原始需求保存产品规则；需求挖掘只保留未决产品问题；程序澄清保存高影响技术决策；后续阶段不得复制上游内容。
11. **运行安全优先**：不完整功能可以受控关闭，但不得破坏服务器启动、资产、数据和其他系统。
12. **证据优于结论**：配置需导表和加载验证，实现需测试和运行证据，对接文档需与实际属性、协议和同步代码一致，review 需触发路径和代码依据。
13. **允许回退上游**：发现根因性错误时修订原决策，不以下游补丁维持错误框架；上游修订必须经过用户确认。

## 安装

```bash
npx skills@latest add Sth32/skills
```

也可以只复制需要的 `skills/<skill-name>/` 目录到 Agent 的 skills 目录。

## 验证

运行静态验证：

```bash
python scripts/validate_skills.py
```

验证器会要求每个 `SKILL.md` 包含统一的“文档更新时序硬限制”，防止后续维护时某个阶段退回到延迟更新或静默修改上游文档。

`evals/` 中包含每个技能的行为测试场景，用于检查需求丢失、越界提问、危险占位、无证据完成、对接合同缺失、review 锚定和文档过度细化等失效模式。

## 参考思想

本仓库吸收以下项目的方法，并按游戏研发中“策划—程序—配置—实现—维护”的协作边界重新设计：

- `mattpocock/skills`：小型、可组合技能；事实通过环境调查获得；决策逐个确认。
- `Fission-AI/OpenSpec`：以可更新工件承载迭代过程，不把真实开发伪装成单向阶段。
- `obra/superpowers`：先理解与确认，再进入实现；按依赖推进；使用行为场景验证技能本身。
