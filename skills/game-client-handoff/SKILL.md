# 生成服务端到客户端对接文档

## 目标

从服务端事实出发，生成或更新简洁的 `<本次主题名>-客户端对接文档.md`，让客户端明确：

- 同步哪些属性、由谁同步、何时变化；
- 实体创建、更新、销毁、离开视野和重连时会收到什么；
- RPC/事件何时发送、参数与结果是什么；
- 现有数据是否足以支撑客户端完成表现。

**核心边界：描述 Server 提供的合同，不设计客户端内部架构。**

**目录与命名硬限制：对接文档必须放在本次主题已有 `01` 至 `06` 阶段文档所在目录，禁止另建平行目录；文件名必须为 `<本次主题名>-客户端对接文档.md`，不得使用不含主题名的 `客户端对接文档.md`。主题名沿用本次需求或功能在已有阶段文档中的名称，不得临时换同义名。若无法唯一确定已有阶段目录或主题名，必须先向用户确认，不得自行新建目录或使用泛化名称。**

**单文档硬限制：本阶段只能维护 `<本次主题名>-客户端对接文档.md` 一份过程文档。** 不得另建属性清单、RPC 清单、生命周期说明、服务端缺口报告、客户端待办或变更摘要。同一合同的字段、同步时机、生命周期和失败语义必须放在相邻位置。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 输入与产物

优先核对：

1. 当前服务端属性 Schema、协议/RPC/事件定义和实际代码；
2. 生成后的类型或协议定义；
3. `05-框架实现方案.md`、`06-完整实现方案.md` 与当前 diff；
4. 原始需求和配置文档。

代码与本阶段对接文档冲突时，以当前服务端实现为准，并在同一轮原位修正文档、明确告知用户路径。若冲突同时证明 `01` 至 `06` 的上游文档需要修订，不得直接改写；必须先说明受影响文档和拟修改内容，获得用户确认后再更新。

唯一过程文档：

```text
<本次主题已有阶段文档所在目录>/<本次主题名>-客户端对接文档.md
```

开始生成前必须先定位本次主题已有的 `01-原始需求.md` 至 `06-完整实现方案.md` 中至少一份权威阶段文档，并继承其所在目录。若多份阶段文档分散在不同目录，以当前仍在维护、阶段最靠后的权威文档目录为准，同时指出目录异常；不得为了套用默认路径而复制或迁移上游文档。

主题名优先沿用用户明确给出的本次主题名；用户未明确时，从同目录阶段文档的标题或当前功能名称中提取。文件名中的主题名只做文件系统必需的非法字符替换，不得擅自缩写、泛化或改写。

使用 [客户端对接文档模板](references/客户端对接文档模板.md)。已有旧版 `客户端对接文档.md` 且确认属于本次主题时，应将其迁移为规范文件名并继续原位维护，迁移后删除旧文件，禁止保留两个并行版本。

## 文档范围

### 必须包含

- 新增或变化的客户端可见实体、属性和属性组；
- 服务端权威来源与实际同步实体/组件；
- 全量、增量、按需返回或广播方式；
- 属性的类型、单位、枚举、缺省/空值语义；
- 实体生命周期中的同步变化；
- 客户端发起 RPC 的时机、参数、回包和后续推送；
- 服务端主动事件/推送的触发条件与参数；
- 客户端完成表现仍缺少的服务端数据或未确认合同。

### 不要展开

- 客户端 MVC、UI 层级、状态管理、缓存和代码目录；
- 动画、资源加载、交互组件的具体实现；
- 与客户端合同无关的服务端线程、持久化和算法细节；
- 完整服务端调用栈、所有内部属性或整份协议 Schema；
- 没有证据的客户端轮询、补算或容错方案。

服务端内部权威、镜像或跨线程链路，只在它影响同步时机、可见范围、一致性或失败表现时说明。

## 工作流程

### 1. 确定目录、主题名与合同范围

先定位本次主题已有阶段文档目录，并确定与已有文档一致的主题名和规范目标路径。不得先生成到工作区根目录、默认目录或临时目录，再声称后续移动。

随后搜索本功能涉及的：

- 实体属性定义、客户端视图、全量/增量同步入口；
- 创建、加载、进入视野、状态变化、销毁和重连恢复路径；
- C2S RPC、S2C 回包、异步推送和广播事件；
- 配置 ID、资源 ID、时间戳、枚举和错误码。

只记录本功能新增、修改或客户端必须依赖的合同，不另建调查清单。目录、主题名或合同范围一旦确认或变化，立即更新规范路径下的对接文档并告知用户。

### 2. 按合同聚合属性同步

对每个属性或紧密相关的属性组，在同一连续分块写清：

- 客户端识别的实体与唯一标识；
- 字段名、类型、含义、单位、枚举和空值；
- 服务端权威者，以及真正执行同步的实体/组件；
- 首次获得方式：登录全量、进入视野、创建推送或 RPC 返回；
- 哪些服务端变化会触发增量同步；
- 实体销毁、离开视野、失去权限或重连时如何清除、替换或重新全量同步；
- 哪些用户或阵营可见。

不要把同一属性拆到“字段表”“生命周期表”和“同步说明”中重复出现。每完成或修正一个属性合同，立即更新主文档并告知用户。

### 3. 按接口聚合 RPC 与事件

每个 RPC/事件在同一分块说明：

- 方向、名称、发送者和接收者；
- 客户端应在什么时机发送，服务端在什么条件下推送；
- 请求/事件参数的名称、类型、必填、含义、单位和枚举；
- 同步回包内容与错误码；
- 若最终结果通过异步推送返回，明确区分“请求受理”与“业务完成”；
- 重复发送、超时、顺序或 requestId 仅在客户端必须处理时说明。

嵌套结构复杂时给一个最小示例，不复制完整生成代码，也不另建协议附录。每完成或修正一个接口合同，立即更新主文档并告知用户。

### 4. 检查实体生命周期

检查实际相关的登录、创建、进入视野、属性变化、销毁、离开视野、权限变化、重连和跨场景场景。

生命周期结果直接写回对应属性组或接口附近；没有对应场景时跳过，不为完整性虚构流程。发现变化后在同一轮更新文档并告知用户。

### 5. 做客户端数据充分性检查

确认客户端仅依据合同即可：

- 唯一识别实体并建立、更新、移除表现；
- 展示关键状态、进度、数量、倒计时和结果；
- 正确发起操作并关联回包或异步结果；
- 区分未开放、失败、空数据、不可见和同步未完成；
- 通过配置 ID 或资源 ID 找到所需展示资源。

若数据不足，在最相关合同分块内标记“服务端缺口”，写明缺少的数据、影响和应回退的服务端阶段；不得另建缺口报告，也不得用客户端猜测掩盖缺口。缺口一经发现，立即更新当前文档并告知用户；随后说明拟修改的上游文档和内容，获得用户确认后再回退补齐。

### 6. 原位压缩并核对

不设行数目标。属性按业务合同聚合，RPC 按接口聚合；不重复需求背景和服务端实现过程。

交付前核对实际字段名、类型、触发时机、可见范围、错误语义、目录和文件名。沟通或实现变化后立即原位替换旧内容，删除已解决缺口、旧字段和失效说明，并明确告知用户已更新的完整路径。完整 Schema、diff 和生成记录留在代码仓库中。

上游文档经用户确认并完成修订后，立即清理本阶段文档中已经解决的服务端缺口或临时阻塞，并再次告知用户。

## 完成条件

- 对接文档与本次主题已有阶段文档位于同一目录；
- 文件名为 `<本次主题名>-客户端对接文档.md`，主题名与本次需求或功能一致；
- 客户端可见属性及生命周期变化明确；
- 每项属性都有同步来源、首次同步和增量触发；
- RPC/事件的发送时机、参数、回包和异步结果明确；
- 服务端权威与同步载体没有混淆；
- 文档提供足够数据支撑表现，但没有越界设计客户端实现；
- 服务端缺口和待确认项在对应合同附近显式可追踪；
- 无尚待用户确认修订的上游文档阻塞；
- 文档与当前服务端代码、协议和生成定义一致；
- 本阶段只有规范命名的一份对接过程文档，不存在旧名或并行版本。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 在默认目录或工作区根目录新建对接文档 | 先定位本次主题已有阶段文档，并写入同一目录 |
| 固定命名为 `客户端对接文档.md` | 使用 `<本次主题名>-客户端对接文档.md` |
| 新文件与旧名文档并存 | 确认属于同一主题后迁移并删除旧文件，只保留规范文件 |
| 为属性、RPC、生命周期分别建文档 | 按属性组或接口把相关合同放在相邻位置 |
| 数据不足时另写服务端缺口报告 | 在最相关合同分块内记录并回退对应阶段 |
| 只抄属性 Schema | 补首次同步、变化触发、清除和可见范围 |
| 只写 RPC 名称和参数 | 补发送时机、回包、异步结果和错误语义 |
| 把权威实体写成同步实体 | 分别说明谁拥有事实、谁把数据发给客户端 |
| 深入设计客户端 UI 和代码 | 只证明 Server 数据足以支撑表现 |
| 数据不足时建议客户端自己算 | 记录服务端缺口并移交补齐 |
| 把请求受理当作业务成功 | 明确最终结果来自回包还是后续推送 |
| 合同变化后只在聊天里说明 | 同一轮更新规范路径下的对接文档并告知完整路径 |
| 发现服务端上游文档过时后直接改写 | 先说明拟修改内容并获得用户确认 |
