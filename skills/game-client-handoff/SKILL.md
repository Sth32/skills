# 生成服务端到客户端对接文档

## 目标

从服务端事实出发，生成或更新简洁的 `客户端对接文档.md`，让客户端明确：

- 同步哪些属性、由谁同步、何时变化；
- 实体创建、更新、销毁、离开视野和重连时会收到什么；
- RPC/事件何时发送、参数与结果是什么；
- 现有数据是否足以支撑客户端完成表现。

**核心边界：描述 Server 提供的合同，不设计客户端内部架构。**

## 输入与产物

优先核对：

1. 当前服务端属性 Schema、协议/RPC/事件定义和实际代码；
2. 生成后的类型或协议定义；
3. `05-框架实现方案.md`、`06-完整实现方案.md` 与当前 diff；
4. 原始需求和配置文档。

代码与文档冲突时，以当前服务端实现为准，并标记差异。无法从现有材料确认的内容不得猜测。

默认产物：

```text
docs/requirements/<feature>/客户端对接文档.md
```

使用 [客户端对接文档模板](references/客户端对接文档模板.md)。已有文档时原位更新。

## 文档范围

### 必须包含

- 新增或变化的客户端可见实体、属性和属性组；
- 服务端权威来源与实际同步实体/组件；
- 全量、增量、按需返回或广播方式；
- 属性的类型、单位、枚举、缺省/空值语义；
- 实体生命周期中的同步变化；
- 客户端发起 RPC 的时机、参数、回包和后续推送；
- 服务端主动事件/推送的触发条件与参数；
- 客户端完成表现仍缺少的服务端数据或未确认合同。

### 不要展开

- 客户端 MVC、UI 层级、状态管理、缓存和代码目录；
- 动画、资源加载、交互组件的具体实现；
- 与客户端合同无关的服务端线程、持久化和算法细节；
- 完整服务端调用栈、所有内部属性或整份协议 Schema；
- 没有证据的客户端轮询、补算或容错方案。

服务端内部权威、镜像或跨线程链路，只在它影响同步时机、可见范围、一致性或失败表现时说明。

## 工作流程

### 1. 建立合同清单

搜索本功能涉及的：

- 实体属性定义、客户端视图、全量/增量同步入口；
- 创建、加载、进入视野、状态变化、销毁和重连恢复路径；
- C2S RPC、S2C 回包、异步推送和广播事件；
- 配置 ID、资源 ID、时间戳、枚举和错误码。

只记录本功能新增、修改或客户端必须依赖的合同。

### 2. 记录属性同步

对每个属性或紧密相关的属性组写清：

- 客户端识别的实体与唯一标识；
- 字段名、类型、含义、单位、枚举和空值；
- 服务端权威者，以及真正执行同步的实体/组件；
- 首次获得方式：登录全量、进入视野、创建推送或 RPC 返回；
- 哪些服务端变化会触发增量同步；
- 实体销毁、离开视野、失去权限或重连时如何清除、替换或重新全量同步；
- 哪些用户或阵营可见。

不要只列字段名。客户端必须能判断“何时创建、何时更新、何时移除”。

### 3. 记录 RPC 与事件

每个 RPC/事件至少说明：

- 方向、名称、发送者和接收者；
- 客户端应在什么时机发送，服务端在什么条件下推送；
- 请求/事件参数的名称、类型、必填、含义、单位和枚举；
- 同步回包内容与错误码；
- 若最终结果通过异步推送返回，明确区分“请求受理”与“业务完成”；
- 重复发送、超时、顺序或 requestId 仅在客户端必须处理时说明。

嵌套结构复杂时给一个最小示例，不复制完整生成代码。

### 4. 检查实体生命周期

至少检查相关场景：

- 首次登录或重新登录；
- 实体创建/进入可见范围；
- 属性变化；
- 实体销毁/离开可见范围；
- 权限或阵营关系变化导致可见性变化；
- 断线重连、跨场景或跨服切换。

没有对应场景时跳过，不为完整性虚构流程。

### 5. 做客户端数据充分性检查

确认客户端仅依据合同即可：

- 唯一识别实体并建立、更新、移除表现；
- 展示关键状态、进度、数量、倒计时和结果；
- 正确发起操作并关联回包或异步结果；
- 区分未开放、失败、空数据、不可见和同步未完成；
- 通过配置 ID 或资源 ID 找到所需展示资源。

若数据不足，新增“服务端缺口”，写明缺少的数据、影响、建议由哪个服务端阶段补齐。不得用客户端猜测或本地推导掩盖缺口。

### 6. 压缩并核对

文档目标为 **50–120 个非空行**。属性按业务组聚合，RPC 按接口单独描述；不重复需求背景和服务端实现过程。

交付前核对实际字段名、类型、触发时机、可见范围和错误语义。未验证的内容标记“待确认”，不得写成既定合同。

## 完成条件

- 客户端可见属性及生命周期变化明确；
- 每项属性都有同步来源、首次同步和增量触发；
- RPC/事件的发送时机、参数、回包和异步结果明确；
- 服务端权威与同步载体没有混淆；
- 文档提供足够数据支撑表现，但没有越界设计客户端实现；
- 服务端缺口和待确认项显式可追踪；
- 文档与当前服务端代码、协议和生成定义一致。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 只抄属性 Schema | 补首次同步、变化触发、清除和可见范围 |
| 只写 RPC 名称和参数 | 补发送时机、回包、异步结果和错误语义 |
| 把权威实体写成同步实体 | 分别说明谁拥有事实、谁把数据发给客户端 |
| 深入设计客户端 UI 和代码 | 只证明 Server 数据足以支撑表现 |
| 数据不足时建议客户端自己算 | 记录服务端缺口并移交补齐 |
| 把请求受理当作业务成功 | 明确最终结果来自回包还是后续推送 |
