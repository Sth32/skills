# 修复游戏代码缺陷

## 目标

处理疑似或已知 bug 时，不默认“发现问题就必须彻底修复”。先确认问题是否真实存在，再判断是否值得修、能否安全跳过/降级/补偿，以及修复复杂度是否值得引入；需要修时才选择最小正确方案并完成必要验证。

默认不进入 `01–07` 正式功能开发流程，也不为修复过程强制创建阶段文档。

**核心原则：先判断问题是否真实、是否值得处理，再决定修法；游戏业务代码优先保持简单，不用高复杂度机制消灭收益很低的理论边界。**

## 默认边界

- 事实自己查，只有会改变产品规则、高影响技术边界或处理取舍的决策才询问用户。
- 不把日志猜测、静态可能性或理论竞态直接当成已存在 bug；先找能够证明实际可达或现实风险的证据。
- 修复收益必须与复杂度匹配。不要为了极低概率、低影响、可恢复的边界，在业务逻辑中引入明显更复杂的状态机、异步协调、锁、重试或补偿机制。
- 低概率不等于可以忽略。资产重复/丢失、数据破坏、安全漏洞、可利用作弊、持续崩溃或不可恢复错误，即使发生概率低，也应按后果和可利用性提高优先级。
- 如果异常可以安全跳过、降级、重试或事后补偿，并且代价明显低于永久增加代码复杂度，可以选择不做完整技术修复，但必须确认不会把错误扩散到数据、资产或其他系统。
- 如果复杂防护属于一类调用都需要的通用可靠性能力，优先考虑下沉到公共框架/底层封装，而不是在每个玩法实现里重复一套复杂逻辑；本次 bugfix 不因此自动扩展成底层重构，必要时先提出方案。
- 优先修根因，不在下游堆保护性补丁掩盖上游错误；但当永久根因修复成本显著高于问题风险时，允许明确选择跳过、降级或补偿，而不是为了“理论完整”过度设计。
- 修改范围保持最小，不顺手扩展需求或进行无关重构。
- 开发期默认不假设存在必须兼容的线上存量数据、在线玩家状态或灰度发布约束。是否已上线只能由用户确认；不得根据部署脚本、生产配置、分支名或其他仓库迹象自行推断。
- 如果线上状态会实质改变修复方案，而用户尚未说明，只询问一次是否需要按已上线环境处理；确认仍在开发期后停止该方向的深入探索。

## Bug 处理决策

在真正修改代码前依次回答四个问题。

### 1. Bug 是否真实存在

优先用复现、日志、真实调用链、测试、状态可达性或代码证据确认：

- 用户描述的现象是否确实能发生；
- 发生条件是否真实可达，而不是纯理论组合；
- 当前代码是否已经有其他保护或上层约束使该路径不可达；
- 观察到的现象是否其实是设计行为、环境问题、配置问题或误判。

证据不足时明确写“尚未确认”，不要为了进入修复流程而假装 bug 已成立。

### 2. 是否有必要修复

不要只问“代码是否不完美”，而要比较现实风险和永久复杂度。至少考虑：

- 发生概率与现实触发条件；
- 对玩家体验、资产、数据一致性、服务器稳定性的影响；
- 是否可被主动利用或放大；
- 是否容易观测、恢复或补偿；
- 修复需要增加多少代码、状态、并发/异步复杂度和长期维护成本。

可以不修或降低优先级的典型情况：极难触发、影响轻、不会扩散、可自动恢复或低成本补偿，而彻底消灭它需要明显复杂化主流程。

不能仅因低概率忽略的典型情况：资产/数据不可恢复损失、可利用作弊、安全问题、持续性状态污染、严重崩溃或一旦发生就难以止损。

### 3. 能否安全跳过、降级或补偿

当永久修复性价比不高时，检查是否有更简单的闭环：

- 当前操作失败后安全返回/跳过；
- 使用已有重试或下一轮自然恢复；
- 通过幂等的事后补偿修正少量异常；
- 在可观测前提下记录并人工处理极少量案例；
- 开发期直接清理/重建受影响测试数据。

选择这类方案时必须确认异常不会继续传播、重复扣发资产、制造脏数据或阻塞后续主流程。

### 4. 修复复杂度是否需要先讨论

**简单、局部、低风险且方向明确的修复：直接修改、验证并向用户汇报。** 不为形式先写方案或等待确认。

出现以下情况时，先向用户说明根因、可选方案、复杂度/风险差异和建议，再动大改动：

- 需要改动较多文件、多个模块或核心公共路径；
- 需要新增复杂异步状态机、锁、重试、幂等/补偿协议；
- 修复方案会明显增加长期维护复杂度；
- 存在“业务层复杂修复”与“底层统一封装”两种方向；
- 不同方案在代码复杂度、风险、性能或未来维护上存在明显取舍；
- 修复已经接近架构/公共合同/数据模型调整。

讨论目标是选择处理方式，不是把简单 bugfix 重新变成正式阶段流程。

## 什么时候应升级到正式流程

调查中出现以下任一情况时，停止把任务当作普通 bugfix，并明确说明需要升级的原因和最早必要阶段：

- bug 的正确行为本身没有明确产品规则；
- 需要新增或改变公共 RPC、Event、协议语义或客户端合同；
- 需要改变数据权威、持久化 schema、迁移策略或跨版本兼容模型；
- 需要重新设计跨实体/线程/进程的一致性、幂等、失败补偿或生命周期，而不是复用/修正已有机制；
- 修复已经演变成跨多个模块的大范围结构性改造；
- 无法用局部证据可靠证明修改安全。

不要因为“可能以后会上线”而自动升级。开发期可清库、可重建测试数据等事实，以用户确认的项目阶段为准。

## 执行流程

### 1. 确认问题与根因

先完成上面的 Bug 处理决策。需要修复时，再沿实际数据/状态来源向上追踪，区分：

- 症状位置；
- 第一个错误事实产生的位置；
- 为什么现有保护、测试或约束没有阻止它。

存在多个合理解释时保留竞争假设直到证据能够区分；简单明确的问题不人为制造假设。

### 2. 选择比例合适的处理方式

按优先级选择：

1. 不需要处理；
2. 安全跳过/降级/已有机制恢复；
3. 低成本补偿；
4. 简单局部根因修复；
5. 复杂修复或底层统一能力。

不是层级越高越“正确”。目标是在风险可接受的前提下，用最低长期复杂度闭环问题。

### 3. 实施或讨论

简单方案直接实施。复杂方案先讨论确认方向，再编码。

实现时优先修改产生错误事实的最早合理位置；如果选择保护/补偿而非根因修复，明确说明为什么这是有意的成本取舍，而不是把 workaround 冒充完整修复。

### 4. 验证

修复类方案至少验证：

1. 原问题路径不再产生目标错误；
2. 直接相邻正常路径仍成立；
3. 新增分支、终态或保护不会留下隐式未完成状态。

跳过/降级/补偿类方案至少验证：异常不会扩散，主流程能继续或安全失败，补偿不会重复执行或制造更大问题。

按实际风险追加单元、集成、启动、重启恢复、异步乱序、并发/幂等或故障验证；不要因为代码里存在异步就机械穷举理论时序。不能执行的验证明确说明剩余风险。

### 5. 汇报

最终简明说明：

- Bug 是否确认存在及关键证据；
- 处理决策：修复 / 跳过 / 降级 / 补偿 / 暂不处理；
- 为什么这个处理成本与风险匹配；
- 实际改动与验证；
- 若保留残余边界，说明触发条件和为什么可以接受。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，优先放到项目既有维护/任务目录；没有约定时先询问或仅给出建议路径，不擅自建立新的权威文档体系。
- 跨 session、多人接力或问题较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若修改会使已有长期权威文档失真，指出具体文档与需要更新的事实；不存在长期文档时，不因为本次 bugfix 自动创建一份新的功能文档。

维护记录只保存继续工作需要的当前事实，不复制 `01–07` 正式流程结构。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
