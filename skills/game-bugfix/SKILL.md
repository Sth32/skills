# 修复游戏代码缺陷

## 目标

针对已存在行为中的 bug，先确认真实现象、触发条件和根因，再以最小正确改动完成修复与回归验证；默认不进入 `01–07` 正式功能开发流程，也不为修复过程强制创建阶段文档。

**核心原则：先证明问题为什么发生，再修正确的事实源；不把“报错消失”当成根因修复。**

## 默认边界

- 事实自己查，只有会改变产品规则或高影响技术边界的决策才询问用户。
- 优先修根因，不在下游堆保护性补丁掩盖上游错误。
- 修改范围保持最小，不顺手扩展需求或进行无关重构。
- 验证强度按风险决定：至少覆盖原触发路径和直接邻近回归；涉及异步、状态机、持久化、权限、跨实体/进程或共享数据时，继续追踪实际消费链。
- 开发期默认不假设存在必须兼容的线上存量数据、在线玩家状态或灰度发布约束。只有用户明确说明已上线、需要兼容存量数据，或当前任务属于 `game-hotfix` 时，才把这些问题作为默认约束深入处理。
- 如果当前是否已上线无法从上下文/项目事实确认，且这个差异会实质改变修复方案，只询问一次是否需要按线上存量数据处理；确认仍在开发期后停止该方向的深入探索。
- 若代码、配置或现有测试可以回答，不得仅因担心潜在边界就把问题转交给用户。

## 什么时候应升级到正式流程

调查中出现以下任一情况时，停止把任务当作普通 bugfix，并明确说明需要升级的原因和最早必要阶段：

- bug 的正确行为本身没有明确产品规则；
- 需要新增或改变公共 RPC、Event、协议语义或客户端合同；
- 需要改变数据权威、持久化 schema、迁移策略或跨版本兼容模型；
- 需要重新决定跨实体/线程/进程的一致性、幂等、失败补偿或生命周期；
- 修复已经演变成跨多个模块的大范围结构性改造；
- 无法用局部证据可靠证明修改安全。

不要因为“可能以后会上线”而自动升级。开发期可清库、可重建测试数据等事实，应以当前项目实际状态为准。

## 工作流程

### 1. 重建现象

从用户描述、日志、报错、调用链、测试、当前 diff 和相关代码重建：

- 实际错误行为；
- 期望行为；
- 最小触发条件；
- 影响范围。

能复现时优先形成稳定复现；不能直接运行时，用代码路径和现有证据建立最小可验证解释，不虚构“已复现”。

### 2. 找到根因

沿实际数据/状态来源向上追踪，区分：

- 症状位置；
- 第一个错误事实产生的位置；
- 为什么现有保护、测试或约束没有阻止它。

至少保留一个竞争解释直到关键证据能够区分；简单明确的问题不人为制造假设。

### 3. 选择最小正确修复

优先修改产生错误事实的最早合理位置。修复不得无意改变无关外部行为；若必须扩大修改面，说明原因。

### 4. 验证

至少验证：

1. 原问题路径不再失败或产生错误结果；
2. 直接相邻的正常路径仍成立；
3. 新增分支、终态或保护不会留下隐式未完成状态。

按风险追加单元、集成、启动、重启恢复、异步乱序、并发/幂等或故障验证。不能执行的验证明确说明剩余风险。

### 5. 收尾

检查最终 diff 是否仍只覆盖修复目标，删除调试代码、危险占位和失效 workaround。若发现低价值旁路问题，简短报告，不自动扩展当前任务。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，优先放到项目既有维护/任务目录；没有约定时先询问或仅给出建议路径，不擅自建立新的权威文档体系。
- 跨 session、多人接力或问题较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若修改会使已有长期权威文档失真，指出具体文档与需要更新的事实；不存在长期文档时，不因为本次 bugfix 自动创建一份新的功能文档。

维护记录只保存继续工作需要的当前事实，不复制 `01–07` 正式流程结构。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
