# 整理游戏原始需求

## 目标

把分散、口语化、重复或结构混乱的需求材料，整理为简洁的 `01-原始需求.md`。

**核心原则：只改变表达和结构，不改变需求语义。**

**硬限制：同一个需求事实在最终文档中只能描述一次。** 不得为了填充不同章节，将同一规则、数值、状态、边界或约束再次以原句、摘要、表格、括号补充或同义改写的方式重复描述。

- 每个原子事实必须归入唯一的主位置；
- 后续章节不得再次汇总、概括或换一种说法复述；
- 表格与列表、正文与括号、规则与“数值/边界/约束”之间的重复同样算违规；
- 冲突与待确认项需要关联既有规则时，优先引用规则编号或短名称，不完整复制规则正文；只有展示来源差异所必需的原文片段可以重复。

## 产物

默认写入：

```text
docs/requirements/<feature>/01-原始需求.md
```

使用 [原始需求模板](references/原始需求模板.md)。已有文档时原位更新，不另建平行版本。

## 输入范围

可处理：

- 口述、会议记录、聊天记录；
- 策划案、工单、邮件、表格、截图和其他需求文档；
- 多份互相补充或修正的材料；
- 明确给出的产品规则、数值、限制和技术约束。

## 无损整理契约

最终文档必须保留每一项有意义的信息：

- 谁执行、作用于什么对象；
- 触发条件、前置条件和时序；
- 系统行为、结果和反馈；
- 数值、范围、概率、次数和优先级；
- 例外、排除项、失败分支和“不处理”；
- 明确给出的兼容、运营或技术限制。

允许：

- 删除口头语、重复表达和无信息量的铺垫；
- 合并语义完全相同的内容；
- 将长句拆成原子规则；
- 为便于阅读增加标题、分组和编号；
- 用更短的句子表达同一含义。

禁止：

- 补充来源中没有的目标、规则、边界或验收标准；
- 用“通常做法”替换原始说法；
- 擅自修正看似不合理的数值或逻辑；
- 静默解决冲突、歧义或前后不一致；
- 将可能、建议、暂定改写为确定要求；
- 扩展实现方案、测试计划或需求挖掘问题；
- 在不同章节重复描述同一个需求事实，即使措辞、粒度或呈现形式不同。

## 工作流程

### 1. 建立来源顺序

列出本次使用的来源。只有在材料明确表示“修正、替换、以此为准”时，后文才覆盖前文；否则并列保留并标记冲突。

### 2. 提取原子事实

逐条提取“主体—条件—行为—结果—例外”。不要因为某条看似显然、重复或不重要而跳过。

为每个原子事实建立临时唯一标识。来源中的多处表述若指向同一事实，只合并到同一个标识，不生成多个正文条目。

### 3. 去重但不压扁条件

两句话只有在主体、条件、行为、结果和例外都一致时才可合并。任一限定不同，就保留为独立规则或子规则。

判断是否重复看语义，不看字面：只要两段内容对实现或验收表达的是同一个要求，就只能保留一处。

### 4. 为每个事实确定唯一归属

每个原子事实只放进最能表达其语义的一个章节：

- 流程中的数值、状态、限制和例外，直接写进对应流程规则；
- 只有无法自然归入流程或主题规则的独立数值、状态、边界或约束，才进入专门章节；
- 专门章节不是摘要区，不得收集正文已经出现过的内容；
- 某个章节没有独立信息时必须省略，不能为了模板完整而复述其他章节。

### 5. 组织为短文档

按玩家流程、系统模块或规则主题分组。每条只表达一个主要规则。优先使用短列表，不写长篇背景解释。

省略没有内容的章节。除非来源本身很复杂，正文应以“一次正常阅读即可掌握”为尺度，而不是追求形式完整。

### 6. 处理不确定内容

- 看不清或听不清：放入“原文待确认”，保留原始片段和来源；
- 两种解释都成立：并列写出，不替用户选择；
- 来源互相冲突：放入“冲突项”，说明各自来源；
- 明确但不合理：照实记录，可标记“原文如此”，不可修正。

冲突与待确认项只描述差异或缺口。能通过规则编号定位的内容不得再次完整复述。

### 7. 做覆盖与重复检查

完成前逐个回看所有来源，确认每条有效信息已进入以下三处之一：

1. 正式需求；
2. 明确的范围外内容；
3. 冲突或原文待确认。

任何内容都不能无声消失。

随后按原子事实标识检查最终文档：

- 每个事实必须出现且只能出现一次；
- 同一事实出现在两个标题、列表、表格或括号说明中，必须删除次要位置；
- 删除重复后若需要建立联系，只保留编号引用，不再解释内容；
- 发现无法判断是否为重复时，宁可合并到更完整的一处，不保留两个近义版本。

## 输出要求

- 标题与规则可重写，专有名词、数值和限定词不得随意替换；
- 同一需求事实的正文描述次数必须为 `1`；
- 不设置重复性的“汇总”“数值摘要”“边界摘要”或“已给定约束摘要”；
- 不写“可能还需要考虑……”之类扩展内容；
- 文末只列来源中已有的冲突与歧义，不主动展开采访；
- 完成后说明文件路径，以及冲突/待确认项数量。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为了完整补出常见边界 | 只保留来源已有内容，边界交给需求挖掘 |
| 把口语压缩成过度抽象的一句话 | 保留行为、条件、结果和例外 |
| 默认最后一份材料覆盖前文 | 仅在明确修正时覆盖 |
| 将技术描述全部删除 | 明确给出的技术约束原样归档，但不扩展 |
| 生成很长的 PRD | 原始需求追求无损且易读，不追求模板齐全 |
| 在“需求规则”后再次用“数值与状态”“异常与边界”“已给定约束”汇总同一内容 | 每个事实选择唯一章节；没有新增独立信息的章节直接省略 |
| 用不同措辞或表格再次表达同一规则 | 语义相同即视为重复，只保留信息最完整的一处 |
