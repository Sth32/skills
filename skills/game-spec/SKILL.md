# 整理游戏原始需求

## 目标

把分散、口语化、重复或结构混乱的需求材料，整理为简洁的 `01-原始需求.md`。

**核心原则：只改变表达和结构，不改变需求语义。**

**信息密度硬限制：同一个需求事实在最终文档中只能描述一次。** 不得为了填充不同章节，将同一规则、数值、状态、边界或约束再次以原句、摘要、表格、括号补充或同义改写的方式重复描述。

**邻接硬限制：同一个问题的主体、条件、行为、结果、数值、例外和限制必须放在相邻位置。** 不得按“流程、数值、状态、边界、约束”等维度把一个完整规则拆散到不同分块。

**结构硬限制：正文默认只保留一个固定二级标题——“需求规则”。** 不得预设“目标与背景”“数值与状态”“异常与边界”“已给定约束”等分类标题。标题必须由实际内容产生，不能为了套模板而创建。

**当前真相硬限制：沟通产生新结论后必须原位更新文档。** 新结论替代旧描述时，删除已失效、已解决、被覆盖或不再有用的内容，不保留历史堆叠。

**根文档硬限制：`01-原始需求.md` 永远是本次需求唯一共同根，不允许按模块、子功能、Agent 或实现批次拆成多份，不允许使用 `01-Uxx-*`，也不在本阶段创建 `00-工作流索引.md`。工作单元只能在 `01` 达到可移交终态后，由后续 `02`–`06` 或客户端对接阶段按真实依赖创建。**

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。新记录使用 schema v3，并区分“实际使用 skill”和“未使用 skill”：只要当前 Agent 实际加载/执行了本 skill（即使用户没有显式写出 skill 名称），就必须调用本 skill 自带的 `scripts/document_record.py append --skill <当前skill>`，写入 `skill_usage=used`，`skill_version` 由写入器从当前 `SKILL.md` 的 `metadata.version` 自动读取，禁止 Agent 手填、猜测或沿用历史值；若一次变更实际没有使用任何 skill，才可使用 `--no-skill`，写入 `skill_usage=not_used`、`skill=null`、`skill_version=null`，不得挑选一个“最接近”的 skill 冒充来源。用户是否显式声明 skill 不是归因依据，实际是否加载/执行才是。写入器 append 前只校验已有文件仍可逐行解析为 UTF-8 JSON object；历史行的 schema 字段缺失或语义错误（例如旧 schema v2 缺少 `skill_version`）必须由 `check` 报告，但不得阻塞后续独立追加，也不得静默修改旧行；只有非 UTF-8、非法 JSON、非 object 等存储层损坏才拒绝 append。历史 schema v1 或非法 v2 无版本记录在查询和统计时统一视为 `skill_version=unknown`；no-skill v3 视为 `skill=none`、`skill_version=not_applicable`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过。记录至少包含时间、skill usage、skill/版本归因、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须只使用 `skill_usage=used` 且按 `skill_version` 过滤或分组，不能把 no-skill、版本未知或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 产物

默认写入：

```text
docs/requirements/<feature>/01-原始需求.md
```

使用 [原始需求模板](references/原始需求模板.md)。已有文档时原位更新，不另建平行版本。即使需求很大，本阶段也先保持一份完整的共同产品根；后续是否拆工作单元由 `01` 完成后的实际独立性决定。

## 输入范围

可处理：

- 口述、会议记录、聊天记录；
- 策划案、工单、邮件、表格、截图和其他需求文档；
- 多份互相补充或修正的材料；
- 明确给出的产品规则、数值、限制和技术约束。

## 无损整理契约

最终文档必须保留每一项有意义的信息：

- 谁执行、作用于什么对象；
- 触发条件、前置条件和时序；
- 系统行为、结果和反馈；
- 数值、范围、概率、次数和优先级；
- 例外、排除项、失败分支和“不处理”；
- 明确给出的兼容、运营或技术限制。

允许：

- 删除口头语、重复表达和无信息量的铺垫；
- 合并语义完全相同的内容；
- 将长句拆成相邻的原子规则；
- 仅在确有多组独立规则时，按实际流程或主题增加三级标题；
- 用更短的句子表达同一含义；
- 新结论确认后直接替换旧表述。

禁止：

- 补充来源中没有的目标、规则、边界或验收标准；
- 用“通常做法”替换原始说法；
- 擅自修正看似不合理的数值或逻辑；
- 静默解决冲突、歧义或前后不一致；
- 将可能、建议、暂定改写为确定要求；
- 扩展实现方案、测试计划或需求挖掘问题；
- 在不同位置重复描述同一个需求事实，即使措辞、粒度或呈现形式不同；
- 为了结构完整创建没有独立信息的标题；
- 把同一规则中的数值、状态、边界或约束拆到其他章节；
- 保留已经被后续确认覆盖的旧版本、旧问题或旧解释；
- 因为预期后续会并行开发就在 `01` 阶段提前拆文件。

## 工作流程

### 1. 建立来源顺序

列出本次使用的来源。只有在材料明确表示“修正、替换、以此为准”时，后文才覆盖前文；否则并列保留并标记冲突。

### 2. 提取原子事实

逐条提取“主体—条件—行为—结果—例外”。不要因为某条看似显然、重复或不重要而跳过。

为每个原子事实建立临时唯一标识。来源中的多处表述若指向同一事实，只合并到同一个标识，不生成多个正文条目。

### 3. 按问题聚合

先识别一个完整问题或规则主题，再把属于它的条件、流程、数值、状态、限制、优先级、失败结果和例外放在一起。

分类只能帮助排序，不能把同一问题拆散。读者不应为了理解一条规则在多个标题之间跳转。

### 4. 去重但不压扁条件

两句话只有在主体、条件、行为、结果和例外都一致时才可合并。任一限定不同，就保留为相邻的独立规则或子规则。

判断是否重复看语义，不看字面：只要两段内容对实现或验收表达的是同一个要求，就只能保留一处。

### 5. 围绕实际规则组织内容

所有正式需求默认写入“需求规则”。按玩家流程、系统流程或规则主题分组；只有确实存在两组以上独立内容时才增加三级标题。

功能范围优先写成文档头部的一句“范围”元信息，不单独创建“需求范围”章节。

### 6. 仅按需创建特殊章节

只有来源确实包含对应内容时，才可增加：

- `明确排除`：来源明确要求不处理或不在本次范围的事项；
- `冲突与原文待确认`：来源冲突、无法唯一理解或无法识别的内容。

没有对应内容时直接省略，不写“无”。除这两类外，不增加固定分类章节。

### 7. 沟通后更新当前真相

收到补充、修正或确认后：

1. 将结论写回它所属的原规则位置；
2. 用新结论替换旧描述，不在旁边追加第二个版本；
3. 删除已解决的待确认项、失效假设、旧选项和重复说明；
4. 仍未解决的部分只保留剩余缺口，不保留已经回答的上下文；
5. 检查新结论是否使其他段落失效，并同步删除或改写；
6. 在同一轮完成文档写入，并在回复中明确告知已更新的路径。

文档是当前有效需求，不是沟通历史。

### 8. 做覆盖、重复与结构检查

完成前逐个回看所有来源，确认每条有效信息已进入以下三处之一：

1. 正式需求；
2. 明确排除；
3. 冲突或原文待确认。

随后检查：

- 每个原子事实必须出现且只能出现一次；
- 同一问题的相关信息是否相邻；
- 同一事实出现在列表、表格、括号或不同标题中，删除次要位置；
- 删除重复后需要建立联系时，只保留编号引用；
- 正文是否存在除“需求规则”外、不具备必要性的二级标题；
- 任一标题删除后不损失信息，就应删除该标题并合并内容；
- 是否残留已被新结论覆盖的旧内容；
- 发现无法判断是否重复时，合并到信息更完整的一处，不保留两个近义版本。

## 输出要求

- 标题与规则可重写，专有名词、数值和限定词不得随意替换；
- 同一需求事实的正文描述次数必须为 `1`；
- 同一问题的完整信息应连续阅读，不跨分类章节；
- 正文默认只有“需求规则”一个固定二级标题；
- 三级标题必须根据实际流程或主题命名，不能照抄分类模板；
- 不设置重复性的汇总、数值、状态、边界或约束章节；
- 沟通完成后必须更新文档并删除不再有用的旧内容；
- 不写“可能还需要考虑……”之类扩展内容；
- 每次发生内容更新后立即说明已更新的文件路径；
- 完成后说明文件路径，以及冲突/待确认项数量；
- 不在 `01` 阶段创建工作单元或工作流索引。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为了完整补出常见边界 | 只保留来源已有内容，边界交给需求挖掘 |
| 把口语压缩成过度抽象的一句话 | 保留行为、条件、结果和例外 |
| 默认最后一份材料覆盖前文 | 仅在明确修正时覆盖 |
| 将技术描述全部删除 | 明确给出的技术约束原样归档，但不扩展 |
| 生成很长的 PRD | 原始需求追求无损且易读，不追求模板齐全 |
| 按“数值、状态、边界、约束”分别建章 | 将同一问题的全部信息放在对应规则附近 |
| 模板列了标题就全部生成 | 只生成实际内容需要的标题；默认只有“需求规则” |
| 用不同措辞或表格再次表达同一规则 | 语义相同即视为重复，只保留信息最完整的一处 |
| 新答案写在旧答案下面 | 原位替换并删除已失效内容，保留当前真相 |
| 内容已变化但只在聊天中说明 | 同一轮更新 `01-原始需求.md`，并明确告知用户路径 |
| 大需求在 01 就拆成多个文件 | 01 保持唯一共同根；完成后再由后续阶段决定是否创建 Uxx |
