# 搭建游戏功能实现框架

## 目标

先让整体实现框架定型：明确模块边界、核心数据结构、主流程、配置接线和安全的未完成边界；经用户确认后实现可运行骨架，并维护 `05-框架实现方案.md`。

**核心原则：这一阶段交付的是“可继续完成且不伤害现有系统的骨架”，不是伪装成完整功能的半成品。配置阶段移交的代码依赖必须在这里被接管、验证和归档。**

## 前置条件与产物

必须读取：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- `04-配置规划.md`，特别是“后续实现依赖”和“待代码接入”状态；
- 相关代码、配置、测试、架构约定和启动方式。

若仍有会改变架构方向的未解决 P0/P1 问题，先返回对应技能处理。

默认写入：

```text
docs/requirements/<feature>/05-框架实现方案.md
```

使用 [框架实现方案模板](references/框架实现方案模板.md)。

## 配置阶段交接契约

`game-config` 可以发现代码依赖，但不能实现运行时代码。本阶段必须逐条处理这些依赖，不得假设“配置已经写好，所以功能自然生效”。

对 `04-配置规划.md` 中每条后续实现依赖：

1. 重新检查代码事实，确认依赖仍成立；
2. 说明它连接哪个配置源、影响哪个运行时行为；
3. 分类为：
   - **框架接线**：注册、映射、加载入口、类型接入、基础协议或组件边界，本阶段处理；
   - **完整业务细节**：复杂规则、边界、结算、补偿等，延期到 `game-implement`；
   - **已失效/重复**：代码调查证明无需改，记录依据并关闭；
4. 将分类、落点和验证方式写入 `05-框架实现方案.md`；
5. 用户确认框架前不修改这些代码。

例如 `AllyOrgViewHostComp.VIEW_MAP` 缺少新属性登记：它属于配置到运行时的注册接线，通常应纳入框架方案，确认后在本阶段实现，而不是在 `game-config` 中修改。

## 本阶段应该定型的内容

- 功能归属和模块责任；
- 核心实体、持久化数据、状态与关键不变量；
- 主流程、入口、出口和跨模块契约；
- 配置读取、注册、映射和校验边界；
- `game-config` 移交依赖的处理结论；
- 失败隔离、开关、降级和未完成功能的安全表现；
- 后续细节应落在哪些扩展点；
- 证明服务器和其他系统不受影响的最小验证方式。

本阶段不追求：

- 穷举所有边界分支；
- 完成所有业务算法、奖励细节和运营工具；
- 大量局部重构、命名优化和非必要抽象；
- 为未来假设提前建设通用框架。

## 工作流程

### 1. 建立当前基线

先确认：

- 相关模块当前职责和可复用路径；
- 服务器启动、构建、导表和测试基线；
- 本次允许修改的代码与配置范围；
- 公共接口、持久化格式和跨进程契约；
- 现有功能中不能被改变的行为；
- 配置源已经完成、待人工或待代码接入的真实状态。

基线已失败时，记录并区分既有问题，不把它误认为本次实现结果。

### 2. 建立配置依赖接管表

从 `04-配置规划.md` 提取所有“后续实现依赖”和“待代码接入”项，形成表格：

- 配置对象；
- 代码路径或符号；
- 缺少的行为；
- 是否属于框架接线；
- 本阶段动作；
- 验证方式；
- 状态。

不能只复制原文。必须检查代码，淘汰错误、重复或已完成的依赖。

### 3. 产出简洁框架方案

方案必须展示：

1. **模块图**：新增/修改模块及责任，不列无关文件；
2. **核心数据结构**：关键字段、所有权、生命周期和不变量；
3. **主流程**：正常路径及少量关键失败出口；
4. **接口契约**：谁调用、输入、输出、幂等或状态要求；
5. **配置连接**：配置源如何经过加载、注册或映射进入运行时；
6. **依赖接管**：每条 config 代码依赖在本阶段处理还是延期；
7. **安全边界**：哪些细节暂缓、暂缓时系统如何稳定运行；
8. **骨架验证**：启动、注册、加载和隔离测试。

优先使用短表格、伪代码或 Mermaid。不要把方案写成逐函数施工清单。

### 4. 区分框架决策和延期细节

只有影响后续大部分代码的内容才在本阶段定型，例如：

- 数据归属、状态模型、模块边界和公共接口；
- 同步/异步主路径；
- 事务、一致性和失败隔离的基本策略；
- 配置模型、注册映射和兼容策略。

可以延期：

- 低影响边界行为；
- 不阻塞主流程的运营辅助能力；
- 局部算法优化和低风险性能优化；
- 已有明确扩展点承载的次要分支。

延期项必须写明后续落点，不能只写“以后处理”。

### 5. 确认后再实现

向用户展示框架方案、核心数据结构、主流程、配置依赖接管和延期项，明确请求确认。

用户未确认前：

- 可以调查、写方案、画流程和准备验证命令；
- 不创建正式业务代码；
- 不修改公共接口、数据格式、注册链路或 `VIEW_MAP`。

确认后，只按已确认框架实施。发现方向性矛盾时暂停并修订方案，不用局部补丁掩盖。

### 6. 实现可运行骨架

骨架通常包括：

- 模块、服务或组件的基本边界；
- 核心类型、数据模型和序列化结构；
- 配置加载和启动期校验；
- 配置阶段移交的必要注册、映射和类型接线；
- 入口、路由、事件或协议注册；
- 主流程编排和明确的扩展点；
- 必要的日志、错误类型和最小可观测性；
- 能证明接线正确的 smoke test 或最小集成测试。

只实现建立框架所需的业务逻辑。不要在骨架阶段顺手完成大量细节。

### 7. 安全处理未完成内容

允许内部功能暂时不完整，但必须满足：

- 服务器可构建、导入、启动和正常关闭；
- 未完成功能不会在启动时抛出致命异常；
- 不产生半写入、错误扣除、重复发奖或不可恢复状态；
- 对外入口默认关闭、受功能开关保护，或返回明确且可控的未开放结果；
- 不改变其他功能的成功路径和数据；
- `TODO`、占位实现和临时分支均有明确归属，并记录在文档中；
- 不以空 catch、静默吞错或伪造成功来维持“能跑”。

涉及持久化或资产时，宁可在写入前拒绝，也不要执行不完整流程。

### 8. 验证并回写实际状态

至少验证：

- 标准构建、静态检查和服务器启动；
- 配置可加载，缺失或错误配置能受控失败；
- 配置到注册、映射和消费端的接线正确；
- 新入口关闭或未完成时行为安全；
- 现有关键功能的 smoke test 不受影响；
- 数据结构可序列化/反序列化，旧数据兼容策略成立；
- 实际代码边界与方案一致。

将已实现框架、配置依赖处理结果、验证证据、延期项和偏差回写 `05-框架实现方案.md`，并同步更新 `04-配置规划.md` 中对应依赖的状态或引用。

## 完成条件

- 用户已确认框架方案；
- 模块、核心数据、主流程和接口边界已经定型；
- `04-配置规划.md` 中所有 P0/P1 代码依赖已完成、关闭或明确延期；
- 配置加载、注册和运行时接线有可验证结果；
- 服务器可以正常运行，其他系统不受影响；
- 未完成内容全部可见、受控且没有危险副作用；
- 后续可在不推翻框架的情况下完成细节；
- 文档明确说明“已完成骨架”和“待完整实现”的边界。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 忽略 game-config 移交的代码依赖 | 逐条检查、分类、纳入方案并验证 |
| config 阶段已误改一半，scaffold 直接沿用 | 先核对基线和 diff，修复或回退半实现后再按确认方案接管 |
| 方案还未确认就修改注册链路 | 先展示配置接线和影响并获得确认 |
| 为了“能跑”吞掉所有异常 | 对未完成入口受控拒绝，保留真实错误 |
| 骨架阶段实现所有细节 | 只完成决定整体形状和接线的部分 |
| 留空逻辑仍然写入资产或状态 | 在任何副作用前阻断 |
| 新模块启动即强依赖不完整数据 | 使用校验、开关或安全默认关闭 |
| 实际代码偏离方案但不更新文档 | 暂停、修订并重新确认方向性变化 |
