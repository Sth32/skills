# 搭建游戏功能框架

## 目标

为当前工作单元建立可运行的**数据与消息拓扑骨架**，并维护未分支的 `05-框架实现方案.md`，或 `05-Uxx-<主题>-框架实现方案.md`。

**框架不是功能的简化实现。框架阶段只确定数据放在哪里、谁是权威、如何持久化和同步、消息经过哪些实体；不实现产品规则。**

**框架真实链路硬限制：框架完成不能只证明类型、字段、RPC 或空方法“已经定义”。对本阶段实际新增的跨层路径，必须沿定义/Schema → 生成物或注册 → 暴露/路由 → 权威实体到达 → 技术失败返回形成最小可达证据；配置或属性若声明会被后续运行时使用，必须至少定位真实消费入口，不能把“字段存在/导表成功”当成“运行链路已接入”。Server 内部可调用方法不等于 Client RPC 可达。**

**单文档硬限制：当前工作单元在本阶段只能维护一份框架实现方案过程文档。** 不得为同一工作单元另建数据设计、RPC 清单、持久化方案、验证报告、移交清单或实现总结。不同工作单元可以分别拥有自己的 `05`；代码、Schema、测试和运行日志属于实际产物或证据，不算过程文档。

**分支工作流硬限制：工作单元最早可在 `01` 需求整理阶段创建，并可独立推进到客户端对接和 `07-Uxx` Review；不存在“所有分支先汇合才能 review”的门禁。当前阶段若发现真实独立范围，仍可继续拆分稳定工作单元 `U01`、`U02`……；所有文件保持在同一个 `docs/requirements/<feature>/` 目录，不增加分支子目录。没有真实分支时继续使用原文件名。第一次拆分创建 `00-工作流索引.md`，只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针；拓扑只由依赖表达。分支文档命名为 `05-<Uxx>-<主题>-框架实现方案.md`。当前 Uxx 只检查自己的共享需求基线、自身/祖先需求文档和真实依赖；无依赖兄弟工作单元不构成阻塞。**

在分支工作流中，下述“本阶段唯一文档”指当前工作单元的唯一 `05` 权威文档；`00` 只做路由，不复制架构结论、验证结果或阶段状态。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**结构性变更影响传播硬限制：当范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源发生变化时，必须在同一轮执行影响扫描，不得只修当前局部段落。当前阶段文档内至少核对顶部元信息、相关正文规则/矩阵、验证结论、阻塞与下一动作；同时定位已有且实际依赖该事实的上下游阶段文档、客户端合同与 `00-工作流索引.md` 中的旧引用。当前阶段和本 skill 允许直接维护的下游内容立即原位更新；若受影响的是需要用户确认才能改写的上游文档，必须明确列出受影响文件、旧事实与拟修改内容并等待确认，不得静默遗漏，也不得把未传播完成的结构性变化描述为已闭环。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

存在 `00` 时，开始或恢复本阶段前必须解析当前 `Uxx` 的共享上游和直接前驱，只检查真实依赖；未被依赖的兄弟工作单元不构成阻塞。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**

创建或修改 `00-工作流索引.md` 同样必须追加记录；普通框架正文变化若不改变拓扑、当前阶段或当前文档，不重复改写索引。

## 输入与产物

未分支时读取：

- `01-原始需求.md`、`02-需求挖掘.md`、`03-程序实现澄清.md`；
- `04-配置规划.md`，特别是待代码接入项；
- 相关实体、组件、属性定义、持久化、启动恢复、RPC/事件、客户端视图和线程路由代码。

存在 `00` 时，先定位当前 `Uxx`，再读取当前工作单元适用的需求基线 与索引声明的当前工作单元实际 `02`–`04` 依赖和直接前驱；不得因为无依赖兄弟工作单元仍停在 `03/04` 就阻塞当前 `05`。

未分支过程文档：

```text
docs/requirements/<feature>/05-框架实现方案.md
```

分支后当前工作单元过程文档：

```text
docs/requirements/<feature>/05-<Uxx>-<主题>-框架实现方案.md
```

使用 [框架实现方案模板](references/框架实现方案模板.md)。沟通、实现或验证后原位更新，不生成旁支文档。

若框架调查证明当前单元包含多个可独立拥有数据/消息边界、独立实现和独立验证的范围，可继续拆分：更新 `00`、分配新 `Uxx`、把父 `05` 压缩为共同拓扑基线并标记 `已拆分`，然后由子 `05` 继续。父单元不再直接进入 `06`。

## 阶段边界

### 本阶段允许

- 新增实体、组件、属性和序列化结构；
- 声明权威数据的持久化字段与恢复入口；
- 定义镜像数据、全量/增量同步消息和 `ready` 状态；
- 建立客户端可见属性、视图映射和同步通道；
- 注册 RPC、事件、类型和实体路由；
- 实现空 RPC：只做解析、寻址、跨线程转发和技术错误返回；
- 实现目标实体不存在、超时、序列化失败等技术性受控失败。

### 本阶段禁止

- 权限、资格、科技、等级、次数等产品判断；
- 扣除、奖励、占领、结算和业务状态转换；
- 基于产品规则选择路径、目标或执行结果；
- 为了“功能可用”提前实现 `game-implement` 的行为。

代码一旦根据产品规则决定“能不能做、做了发生什么”，默认属于 `game-implement`。最终权威端的空实现应在任何副作用前返回明确的未实现结果。

## 数据权威与持久化

每项关键数据必须明确：权威者、持久化、镜像、起服恢复、运行时同步、未就绪行为、客户端可见性。默认纪律：跨重启数据由权威所有者持久化；镜像可重建且不能成为第二写源；起服先恢复权威再同步镜像；权威写成功后再发布增量；未 ready 时不得拿默认值参与业务判断。

只有项目已有明确双写、灾备或快照机制时才偏离，并写明一致性责任。

## 消息与线程拓扑

对当前工作单元每个触发点记录：当前实体/线程、已有数据、缺失数据及权威者、镜像/RPC/回源方式、下一参与实体、请求回包数据、目标不存在/未 ready/超时行为。框架阶段验证消息能到正确权威实体，不验证产品条件。

## 工作流程

### 1. 定位工作单元并建立基线

存在 `00` 时先确认当前 `Uxx`、范围、依赖和当前 `05`；没有则按单线。确认相关实体分布、线程边界、持久化习惯、启动顺序、镜像同步、客户端视图和 RPC 路由约定。

若基线调查证明当前工作单元适用的需求基线 或当前工作单元实际依赖的 `02`–`04` 需要修订，先在当前 `05` 相关事项写最小阻塞并告知用户；随后说明拟修改内容并获得确认。

### 2. 设计数据拓扑

在当前 `05` 完成数据权威与持久化内容，区分权威持久化、权威非持久化、镜像、可重建缓存、运行时派生值。结论形成或变化即更新文档并告知用户。

### 3. 设计消息拓扑

完成当前工作单元触发点与消息流转，重点确认每一步能拿到什么数据、缺少的数据去哪里取、最终由谁执行写入。若两组拓扑没有共享所有权/消息边界且能独立推进，可考虑拆工作单元；仅模块多不构成拆分理由。

### 4. 划定实现范围

明确本阶段建立的属性、持久化、镜像、客户端视图、注册和空 RPC；移交给当前工作单元 `game-implement` 的产品规则；当前配置依赖哪些属于结构接线、哪些属于业务实现。用户确认前不修改正式结构。

### 5. 实现骨架

确认后只完成当前工作单元已批准的结构与技术接线。每完成一个可独立确认的骨架事项立即回写当前 `05` 并告知路径。

### 6. 验证并原位收敛

按实际改动验证 Schema/序列化、权威恢复、镜像全量/增量/ready、客户端视图、RPC/事件跨线程路由、技术失败、空实现无业务副作用、服务器启动和既有链路。未执行运行验证时只能写“骨架代码已落地，待运行验证”。

上游经确认修订后，立即清理当前 `05` 已解除阻塞。

### 7. 更新索引

只有工作单元创建/拆分/终止、依赖变化、当前阶段或当前文档变化时更新 `00`。架构方案、字段、消息或验证内容不得复制进索引。

## 完成条件

对当前叶工作单元：

- 关键数据都有唯一权威者和明确写入责任；
- 持久化所有者和恢复路径明确；
- 跨线程读取有镜像、RPC 或回源方案；
- 镜像全量、增量、ready 与重建方式明确；
- 客户端可见范围和同步来源明确；
- 每个触发点的数据与消息路由明确；
- 空 RPC/事件可运行且无业务副作用；
- 产品规则完整移交给当前工作单元 `game-implement`；
- 必要启动、恢复、同步和路由验证已有结果；
- 无尚待确认的上游文档阻塞；
- 当前工作单元本阶段只有一份 `05` 权威文档。

当前 `Uxx` 骨架完成后可以进入它自己的 `06`，不要求未依赖兄弟工作单元同步完成，也不代表功能已具备进入 `game-review` 的条件。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为数据、RPC、持久化分别建文档 | 全部维护在当前工作单元 `05` 的对应事项中 |
| 为验证或移交另建报告 | 回写当前主文档，证据留在代码、测试和日志 |
| 把主业务流程实现成“骨架” | 只建立数据、持久化、可见性和消息拓扑 |
| 多个实体分别持久化同一事实 | 权威者存盘，其他实体使用可重建镜像 |
| 镜像未同步就用默认值判断 | 设置 ready 门槛，拒绝、等待或回源 |
| 空 RPC 中顺手做资格和扣除 | 只转发，最终端副作用前返回未实现 |
| 只做静态检查就标记完成 | 未运行必要验证时保持待验证状态 |
| 设计、实现或验证变化后只在聊天里说明 | 同一轮更新当前 `05` 并告知路径 |
| 为工作单元增加子目录 | 所有过程文档保持同目录 |
| 父 `05` 拆分后继续创建父 `06` | 父标记已拆分，仅叶子后继推进 |
| 兄弟分支仍在 04 就阻止当前 Uxx 做 05 | 只按 DAG 的真实依赖门禁 |
