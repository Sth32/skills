# 搭建游戏功能框架

## 目标

建立可运行的**数据与消息拓扑骨架**，并维护 `05-框架实现方案.md`。

**框架不是功能的简化实现。框架阶段只确定数据放在哪里、谁是权威、如何持久化和同步、消息经过哪些实体；不实现产品规则。**

**单文档硬限制：本阶段只能维护 `05-框架实现方案.md` 一份过程文档。** 不得另建数据设计、RPC 清单、持久化方案、验证报告、移交清单或实现总结。代码、Schema、测试和运行日志属于实际产物或证据，不算过程文档；相关结论必须回写主文档的对应事项。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入只能使用单次 append，禁止为了记录而读取、重写或总结历史全文。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 阶段边界

### 本阶段允许

- 新增实体、组件、属性和序列化结构；
- 声明权威数据的持久化字段与恢复入口；
- 定义镜像数据、全量/增量同步消息和 `ready` 状态；
- 建立客户端可见属性、视图映射和同步通道；
- 注册 RPC、事件、类型和实体路由；
- 实现空 RPC：只做解析、寻址、跨线程转发和技术错误返回；
- 实现目标实体不存在、超时、序列化失败等技术性受控失败。

### 本阶段禁止

- 权限、资格、科技、等级、次数等产品判断；
- 扣除、奖励、占领、结算和业务状态转换；
- 基于产品规则选择路径、目标或执行结果；
- 为了“功能可用”提前实现 `game-implement` 的行为。

代码一旦根据产品规则决定“能不能做、做了发生什么”，默认属于 `game-implement`。最终权威端的空实现应在任何副作用前返回明确的未实现结果。

## 数据权威与持久化

每项关键数据必须明确：

| 维度 | 要回答的问题 |
|---|---|
| 权威者 | 哪个实体、组件和线程拥有最终解释权与写权限？ |
| 持久化 | 是否跨重启保留，由谁存盘，存在哪里？ |
| 镜像 | 哪些实体为跨线程读取保存副本？ |
| 起服恢复 | 权威何时加载，镜像何时全量同步并标记 ready？ |
| 运行时同步 | 全量、增量、事件还是按需回源？ |
| 未就绪行为 | 拒绝、等待或回源；不得把默认值当真实值。 |
| 客户端可见 | 谁可见，通过什么视图，全量还是增量？ |

默认纪律：

1. 需要跨重启保留的数据，通常由权威所有者持久化；
2. 其他实体保存可重建镜像，通常不独立持久化；
3. 起服时先恢复权威数据，再向镜像持有者发送全量快照；
4. 权威写入成功后再发布增量更新；
5. 镜像不能成为第二写入源；
6. 镜像未 ready 时，不得用空值或默认值参与业务判断；
7. 缓存和派生值必须可从权威数据重建。

只有项目已有明确的双写、灾备或快照恢复机制时，才偏离上述默认规则，并写明一致性责任。

## 消息与线程拓扑

对每个触发点记录：

- 当前实体和线程；
- 当前能直接获得的实体与数据；
- 缺少的数据及其权威者；
- 是否读取本地镜像、跨线程 RPC 或按需查询；
- 下一步参与实体；
- 请求与回包携带的数据；
- 目标不存在、未 ready、超时和重试行为。

框架阶段验证消息能够到达正确权威实体，不验证产品条件是否成立。

## 工作流程

### 1. 建立基线

确认现有实体分布、线程边界、持久化习惯、启动顺序、镜像同步方式、客户端视图和 RPC 路由约定。区分既有错误与本次改动。

若基线调查证明 `01` 至 `04` 的内容需要修订，先在 `05-框架实现方案.md` 的相关事项内写入最小阻塞说明并立即告知用户文档已更新；随后主动说明受影响的上游文档和拟修改内容，获得用户确认后再更新上游文档。未确认前不得静默回写。

### 2. 设计数据拓扑

在 `05-框架实现方案.md` 中完成数据权威与持久化内容。属性必须区分：权威持久化、权威非持久化、镜像、可重建缓存、运行时派生值。

设计结论一旦形成或发生变化，立即原位更新 `05` 并告知用户，不等待整份框架方案完成。

### 3. 设计消息拓扑

在同一文档中完成触发点与消息流转内容。重点确认每一步实际能拿到什么数据，缺少的数据去哪里取，最终由谁执行写入。

消息拓扑结论一旦形成或发生变化，立即原位更新 `05` 并告知用户。

### 4. 划定实现范围

在同一文档内明确：

- 本阶段建立的属性、持久化、镜像、客户端视图、注册和空 RPC；
- 移交给 `game-implement` 的全部产品规则和副作用；
- `game-config` 移交项中哪些属于结构接线，哪些属于业务实现。

用户确认前不修改正式结构、持久化格式、视图映射或 RPC 链路。用户确认范围后，立即更新 `05` 的批准状态并告知用户，再开始实现。

### 5. 实现骨架

确认后只完成已批准的结构与技术接线。空 RPC 可以连续转发到最终权威实体，但不得执行产品判断或业务写入。

每完成一个可独立确认的骨架事项，立即将实际状态和偏差回写 `05-框架实现方案.md` 并告知用户，不另建实施记录，也不等到整批代码完成。

### 6. 验证并原位收敛

至少根据实际改动验证：

- 属性、Schema 和序列化可生成或加载；
- 权威数据可恢复，镜像全量同步与 ready 时序成立；
- 增量同步能够更新镜像和客户端视图；
- RPC/事件可跨线程到达预期实体并返回；
- 目标缺失、未 ready 或超时时受控失败；
- 空实现没有扣除、写状态或其他业务副作用；
- 服务器启动及既有关键链路不受影响。

每获得一项验证结果，立即回写对应设计事项并告知用户 `05` 已更新；不得积攒到阶段结束。删除已解决问题、旧状态和失效方案。完整日志留在工具输出或仓库中。未执行运行验证时，状态只能写“骨架代码已落地，待运行验证”，不能写“骨架已完成”。

上游文档经用户确认并完成修订后，立即清理 `05` 中已解除的临时阻塞并再次告知用户。

## 完成条件

- 所有关键数据都有唯一权威者和明确写入责任；
- 跨重启数据的持久化所有者和恢复路径明确；
- 所有跨线程读取都有镜像、RPC 或回源方案；
- 镜像的起服全量、运行时增量、ready 与重建方式明确；
- 客户端可见范围和同步来源明确；
- 每个触发点的参与实体、可用数据、权威者和消息路由明确；
- 空 RPC/事件链路可运行且无产品判断和业务副作用；
- 产品规则完整移交给 `game-implement`；
- 必要的启动、恢复、同步和路由验证已有结果；
- 无尚待用户确认修订的上游文档阻塞；
- 本阶段只有 `05-框架实现方案.md` 一份过程文档。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为数据、RPC、持久化分别建文档 | 全部维护在 `05-框架实现方案.md` 的对应事项中 |
| 为验证或移交另建报告 | 将当前结果回写主文档，证据留在代码、测试和日志中 |
| 把主业务流程实现成“骨架” | 只建立数据、持久化、可见性和消息拓扑 |
| 多个实体分别持久化同一事实 | 权威者存盘，其他实体使用可重建镜像 |
| 镜像未同步就用默认值判断 | 设置 ready 门槛，拒绝、等待或回源 |
| 空 RPC 中顺手做资格和扣除 | 只转发；最终端在副作用前返回未实现 |
| 只画模块图，不说明每步可用数据 | 建立触发点与消息流转表 |
| 只做静态检查就标记完成 | 未运行启动/同步/RPC 验证时标记待验证 |
| 设计、实现或验证变化后只在聊天里说明 | 同一轮更新 `05-框架实现方案.md` 并告知路径 |
| 发现上游决策错误后直接改文档 | 先说明拟修改内容并获得用户确认 |
