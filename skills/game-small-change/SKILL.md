# 实现日常小需求

## 目标

对规则明确、范围局部、可以沿现有机制完成的小需求直接调查、实现和验证；默认不创建 `01–07` 阶段文档，也不因为“正式流程更完整”而人为扩大任务成本。

**核心原则：先确认现有机制能否承载，再做最小完整改动；事实自己查，真正的产品或高影响技术决策才问用户。**

## 默认边界

- 优先沿现有入口、数据模型、配置和公共能力扩展，不为小需求创建第二套机制。
- 不把变量名、文件位置、普通实现偏好或代码可查事实变成用户问题。
- 开发期默认不假设需要兼容线上存量数据、在线玩家状态、灰度或无损迁移；只有用户明确要求或任务实际处于线上环境时才深入处理。
- 如果当前是否已上线无法从上下文/项目事实确认，且这个差异会实质改变实现方案，只询问一次是否需要按线上存量数据处理；确认仍在开发期后停止该方向的深入探索。
- 只实现用户当前要求，不顺手补“可能以后需要”的能力。
- 若修改涉及配置、接口、异步、权限或持久化，只验证当前变化真实经过的链路，不机械执行完整功能流程的所有检查项。

## 升级条件

出现以下情况时，明确告知用户当前任务已经超出 small-change，并转到最早必要的正式 skill：

- 新增规则仍需要产品决定；
- 需要改变公共协议、客户端合同、数据权威或配置真源；
- 需要新增持久化 schema、迁移、历史数据兼容；
- 需要重新设计一致性、幂等、跨进程时序或失败补偿；
- 修改范围扩展为多个可独立推进/review 的功能单元；
- 局部修改已经无法可靠验证。

## 工作流程

### 1. 确认期望行为与现有入口

从用户要求和当前代码确认：现有行为、目标行为、受影响范围、可复用机制。若代码已有类似实现，优先复用而不是另起路径。

### 2. 检查隐藏影响

只检查会改变实现选择的边界，例如：调用方、状态生命周期、权限对象、配置消费、持久化、异步回包和客户端可见合同。没有经过这些边界时不展开无关分析。

### 3. 实现最小完整闭环

实现目标行为及必要的失败/终态处理，不提前加入未要求的扩展点。若实际实现与用户要求存在方向性差异，先说明再继续。

### 4. 验证

至少验证新增/修改行为和直接相邻旧行为。按风险追加集成、启动、异步、重启恢复或兼容验证。缺少运行条件时说明替代证据和剩余风险。

### 5. 收尾

检查 diff 是否包含无关改动、危险占位或临时调试逻辑；发现旁路问题只报告，不自动扩大范围。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，不得模仿 `01–07` 正式流程建立阶段状态、门禁或工作单元结构。
- 跨 session、多人接力或修改较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若修改会使已有长期权威文档失真，指出具体文档与需要更新的稳定事实；不存在长期文档时，不因为本次小需求自动创建新的功能文档。
