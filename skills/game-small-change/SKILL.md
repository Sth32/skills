# 实现日常小需求

## 目标

处理规则明确、范围局部的小需求时，先确认当前系统已经怎么实现、现有机制能否直接承载，再选择最简单且贴合现有框架的方案完成实现。

设计保持简单，但实现必须完整：不能为了“小需求”省掉真实会经过的失败路径、状态收尾、数据写入、权限、配置消费或其他必要闭环；也不能为了理论上的未来扩展提前建立新抽象、新框架或第二套机制。

默认不创建 `01–07` 阶段文档。

**核心原则：先理解现有实现，能简单沿用就简单实现；方案尽量小，实现必须完整；如果小需求开始明显冲击已有框架，先和用户确认实现方案再修改。**

## 默认边界

- 开始设计前先调查现有入口、调用链、数据模型、配置、公共能力和相似实现，不在不了解当前机制时凭空设计新路径。
- 优先沿已有机制增加最少的新行为；现有框架已经能表达需求时，不创建新的抽象层、状态体系、配置体系或旁路实现。
- 简单设计不等于只改“能跑通 happy path”的几行代码。真实经过的输入校验、失败返回、状态终态、权限、数据更新、配置消费、异步结果或客户端可见行为必须按实际链路闭环。
- 完整实现只覆盖当前需求真实需要的边界，不为了“以后可能扩展”提前增加未使用接口、通用化参数、预留状态或复杂兼容层。
- 不把变量名、文件位置、普通实现偏好或代码可查事实变成用户问题。
- 是否已上线只能由用户确认；不得根据部署脚本、生产配置、分支名或其他仓库迹象自行推断。若生产状态会实质改变实现方案而用户尚未说明，只询问一次；确认仍在开发期后停止生产兼容方向的深入探索。
- 开发期默认不假设需要兼容线上存量数据、在线玩家状态、灰度或无损迁移。
- 若修改涉及配置、接口、异步、权限或持久化，只检查并验证本次变化实际经过的链路，不机械展开完整功能流程的所有检查项。

## 小需求处理决策

### 1. 先确认当前实现

在提出方案前，先回答：

- 当前行为由哪个入口和调用链负责；
- 已有数据/状态放在哪里，谁拥有修改权；
- 是否已有相同或相似能力可以复用；
- 当前约束是代码设计本身，还是只是某个局部实现没有覆盖；
- 用户要求是否能在现有框架中自然表达。

代码、配置和现有实现能回答的问题自己调查，不要求用户重复说明。

### 2. 判断能否简单实现

优先选择与当前架构方向一致、改动面最小、最容易理解和验证的方案。

典型优先级：

1. 复用现有字段/状态/公共函数直接增加一个分支；
2. 在现有模块内增加局部数据或逻辑；
3. 对已有公共能力做小幅、向后兼容的扩展；
4. 只有现有框架确实无法自然承载时，才考虑新增抽象或改变框架。

不要把“可以抽象”当成“应该抽象”。小需求默认不为未来未知场景建设通用系统。

### 3. 检查是否会明显冲击已有框架

出现以下情况时，不直接大改；先向用户说明当前实现、为什么简单路径不足、候选方案、影响面和建议，获得方向确认后再继续：

- 需要改变核心公共调用链或多个既有模块的职责；
- 需要新增一套新的状态管理、事件/RPC 路径、配置体系、缓存/持久化机制；
- 需要修改很多调用方才能容纳这一个小需求；
- 需要让已有抽象承担明显不同的语义，或者破坏原有边界；
- 存在“局部实现即可”与“重构/扩展底层框架”两种成本明显不同的方向；
- 方案虽然能实现，但会给已有框架带来明显长期复杂度或行为风险。

这里的目标是**先确认实现方案**，不是自动升级正式流程。用户确认后，如果改动仍然边界清楚、无需重新定义产品/合同/数据模型，可以继续作为 small-change 完成。

### 4. 设计简单，实现完整

方案确定后，只设计完成当前需求所需的最小结构，但实现时沿实际消费链补齐必要闭环。

至少检查与本次需求实际相关的：

- 输入条件和资格判断；
- 成功路径与失败返回；
- 状态更新及终态；
- 数据读写和必要持久化；
- 权限对象与实际执行对象；
- 配置值的真实消费；
- 异步回包、超时或取消（只有实际经过异步边界时）；
- 客户端/RPC/Event 可见结果（只有实际修改公共合同或可见行为时）。

不要为了“实现完整”机械加入与本次调用链无关的边界，也不要用大量防御代码掩盖框架本应提供的能力。

## 什么时候升级到正式流程

只有调查/讨论后真正出现下列新设计问题，才停止作为普通 small-change，并进入最早必要的正式 skill：

- 正确产品规则本身仍需要决定；
- 需要重新定义公共 RPC、Event、协议语义或客户端合同，而不是沿现有合同增加已明确行为；
- 需要重新决定数据权威、配置真源或模块职责；
- 需要新增/重构持久化 schema、迁移或跨版本兼容模型；
- 需要重新设计一致性、幂等、跨进程时序、失败补偿或生命周期模型；
- 改动已经演变为多个可独立推进/review 的功能单元或大范围架构调整；
- 无法用局部证据可靠证明修改安全。

不要因为改了多个文件、需要补几项验证，或“未来可能继续扩展”就自动升级。

## 执行流程

### 1. 调查现有实现

定位入口、真实调用链、现有数据/状态、相似能力和直接调用方，确认需求能否自然落在当前机制中。

### 2. 选择最简单方案

若现有框架可直接承载，直接确定最小改动；不为了形式输出长方案。若会明显冲击框架，则先和用户讨论方案再实施。

### 3. 完整实现

完成当前需求所有实际必要行为和收尾，不提前增加未来能力，不留下“主路径能跑、异常/状态/数据没闭环”的半成品。

### 4. 验证

至少验证：

1. 新需求的主路径成立；
2. 当前实现中与它直接相邻的旧行为未被破坏；
3. 本次实际经过的失败/终态/数据或接口边界已经闭环。

按真实风险追加集成、启动、异步、重启恢复或兼容验证；没有经过的边界不机械测试。缺少运行条件时说明替代证据和剩余风险。

### 5. 汇报

简明说明：

- 当前原实现是什么；
- 采用了什么最小方案以及为什么不需要更复杂设计；
- 实际完成了哪些行为闭环；
- 验证结果；
- 如果为了保持框架简单有意没有做某些未来扩展，必要时说明即可。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，不得模仿 `01–07` 正式流程建立阶段状态、门禁或工作单元结构。
- 跨 session、多人接力或修改较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若修改会使已有长期权威文档失真，指出具体文档与需要更新的稳定事实；不存在长期文档时，不因为本次小需求自动创建新的功能文档。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
