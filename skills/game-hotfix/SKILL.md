# 处理线上 Hotfix

## 目标

在**用户明确确认需要按已上线/生产环境处理**后，为紧急修复增加生产风险视角：按当前问题真实涉及的范围关注在线状态、存量数据、兼容、止损、观测、回滚与补偿，并完成最小、可验证的修复。

本 skill **不是 Hotfix 发布框架、事故响应流程或项目基础设施规范**。它只提醒 Agent 在生产场景下不要遗漏高代价边界；具体发布、灰度、开关、回滚、数据修复和事故处置方式服从项目已有机制与用户指令，不假设这些能力一定存在，也不为使用本 skill 主动创建一套新的机制。

**核心原则：生产状态由用户确认；相关生产风险按实际改动检查；不把通用 Hotfix 方法论强行映射成项目实现。**

## 使用前提

只有以下任一条件成立才使用 `game-hotfix`：

- 用户明确说明本次问题发生在已上线/生产环境；
- 用户明确要求本次按线上已有数据、真实玩家或生产约束处理；
- 用户明确要求即使尚未上线，也按生产约束演练。

**Agent 不得自行判断“项目已经上线”。** 部署脚本、生产配置、历史 schema、灰度代码、运维目录、版本号、分支名、日志格式或其他上线能力，只能说明项目可能具备生产环境相关机制，不能替代用户对当前任务环境的确认。

如果用户没有说明是否按线上处理，而这个差异会实质改变方案，只问一次简短问题，例如：**“这次需要按已经上线、有存量数据的环境处理吗？”** 在获得确认前，不主动沿生产迁移、在线状态、灰度或补偿方向做深入设计。

若用户确认仍处于开发期，则使用 `game-bugfix` / `game-small-change` 等普通维护 skill；开发期可以按项目现实采用清库、重建测试数据等低成本路径。

“紧急”“今天必须修”本身不构成 Hotfix。

## 关注点

进入 Hotfix 后，只检查当前问题实际相关的生产风险。常见关注点包括：

- **影响面**：哪些玩家、实例、版本、数据或流程可能受影响，问题是否仍在扩大；
- **在线状态**：正在进行的会话、异步任务、定时器、跨服/跨进程流程是否会与修复冲突；
- **存量数据**：错误数据是否已经产生，修复后旧数据是否仍会继续影响系统；
- **兼容**：实际存在新旧版本并存时，协议、配置、schema、时序是否兼容；
- **止损与恢复**：如果项目已有关闭入口、降级、回滚、隔离、补偿等能力，是否需要使用；没有时不虚构机制；
- **不可逆动作**：资产、批量数据修改、删除、迁移等操作是否有范围限制、幂等/重复执行保护和恢复依据；
- **可观测性**：项目现有日志、指标、告警或查询入口是否足以证明修复生效并发现新异常。

没有经过的边界不机械展开。不能因为“这是 Hotfix”就要求项目补齐一整套灰度、开关、事故系统或发布平台。

## 工作流程

### 1. 确认生产处理前提

先确认用户已经明确要求按线上/生产约束处理。未确认时只做不依赖生产假设的普通代码调查；若生产状态会改变方案，询问用户，不从仓库迹象自行推断。

### 2. 重建问题与真实影响

从现象、日志、代码、配置、数据样本和当前版本事实确认：

- 错误行为与触发条件；
- 根因或当前竞争解释；
- 当前已知影响范围；
- 哪些生产关注点与本问题真正相关。

系统可以直接查到的事实自己查；是否把当前任务视为已上线环境这一事实由用户提供。

### 3. 判断是否需要先止损

若问题仍可能扩大，检查项目**已有**的低风险止损能力是否适用，并向用户说明选择与影响。没有现成机制时只指出风险和可选方向，不为了 Hotfix 身份擅自设计或实现通用止损基础设施。

涉及资产、删除数据、批量修复、不可逆迁移或大范围回滚时，不凭推断直接执行；先确认影响范围和恢复/补偿路径。

### 4. 选择最小正确修复

优先修根因并控制修改面。Hotfix 不用于顺手重构或扩展功能。

如果永久正确修复必须改变公共合同、数据模型或大范围架构，可以把当前 Hotfix 限定为必要止血/局部修复，并把后续结构性修改升级到正式流程。

### 5. 按实际风险验证

至少验证原故障路径和直接回归面；再根据实际相关性检查：

- 存量数据或在线状态在修复后的行为；
- 实际存在版本并存时的兼容；
- 实际涉及回滚/补偿时路径是否可执行；
- 项目已有观测入口能否判断修复是否生效。

不要求不存在的灰度、监控、回滚系统；无法取得关键生产证据时保持“未确认”，不要把本地测试或 CI 绿色描述成线上已经恢复。

### 6. 按项目方式执行与收尾

发布、切流、灰度、配置调整、数据处置等动作只按项目已有机制和用户授权执行。本 skill 不规定命令、平台、发布顺序或事故管理工具。

收尾时只确认与当前问题相关的事项：问题是否停止扩大、受影响数据/玩家是否有明确处置、临时 workaround 是否有退出条件、是否存在需要转正式流程的永久修复。

## 文档

Hotfix 比普通维护更值得保留最小事故记录，但**仍然只有用户明确要求时才创建新的 Hotfix 记录**。

- 用户要求记录时：使用 `references/Hotfix记录模板.md`，只保存当前事故事实、止损、修复、发布、数据处置与接力点。
- 跨 session/多人接力、存在数据修复/补偿/回滚步骤，或事故尚未完全闭环时，Agent 应建议用户保存记录，但用户未明确要求前不得自行创建。
- 不得套用 `01–07` 正式功能开发文档。
- 若最终稳定系统契约变化导致已有长期权威文档失真，指出需要更新的具体事实；事故流水本身不进入长期功能文档，也不因为本次 hotfix 自动创建新的功能文档。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
