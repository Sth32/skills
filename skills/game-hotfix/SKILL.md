# 处理线上 Hotfix

## 目标

在已经上线、存在真实玩家/存量数据，或用户明确要求按线上约束处理的前提下，快速定位故障并完成可回滚、低影响、可验证的修复；优先恢复正确服务，不把 hotfix 变成顺手重构或新功能开发。

**核心原则：线上真实状态优先于代码洁癖；先控制影响面，再修根因；任何不可逆的数据或发布动作都必须有证据、保护与回滚/补偿路径。**

## 使用前提

只有以下任一条件成立才默认进入 hotfix：

- 用户明确说明问题已发生在线上/生产环境；
- 当前版本已经面向真实玩家运行，存在必须保护的在线状态或存量数据；
- 用户明确要求即使尚未正式上线，也按生产约束演练处理。

**不要因为“以后可能上线”“这个字段将来可能有历史数据”“看起来像线上 bug”就自动进入 hotfix。**

如果当前环境是否已上线会实质改变方案，而上下文无法确认，先询问用户是否需要按线上约束处理。若用户说明仍在开发期，则退回 `game-bugfix` / `game-small-change`，默认允许清库、重建测试数据或采用开发期简化路径。

## 默认线上约束

进入 hotfix 后，默认必须调查当前任务实际涉及的：

- 受影响版本、实例、玩家范围和触发条件；
- 在线状态、正在进行的异步/定时/跨服流程；
- 存量数据、历史 schema、旧值与兼容边界；
- 发布方式、灰度/分批能力、配置开关和回滚路径；
- 修复前后可观测指标、日志、告警和验证入口；
- 修复失败或只修一半时的最坏后果与止损动作。

没有经过的边界不机械扩展成全系统审计，但不能用“测试通过”代替真实线上链路判断。

## 决策优先级

1. 阻止继续扩大损失；
2. 保持服务器可运行、数据可恢复、资产不被重复发放/扣除；
3. 恢复正确主路径；
4. 补齐兼容、补偿和可观测性；
5. 最后才考虑结构整理。

紧急情况下允许临时止血方案，但必须明确它是 workaround、适用范围、退出条件和后续根因修复；不得把止血补丁伪装成永久闭环。

## 工作流程

### 1. 固定事故范围

确认：

- 线上现象与首次/最近发生时间；
- 受影响版本、服务器、玩家/数据范围；
- 是否仍在持续扩大；
- 当前是否已有人工止损、配置关闭、回滚或补偿动作。

事实不清时优先从日志、指标、配置、代码版本和数据样本确认，不让用户回答系统可以直接查到的事实。

### 2. 先判断是否需要止血

如果问题仍在扩大，先评估最低风险止损：关闭入口、配置降级、暂停任务、回滚版本、隔离异常数据或其他已有机制。

涉及资产、删除数据、批量修复、不可逆迁移或大范围回滚时，不得凭推断直接执行；必须先确认影响范围和恢复路径。

### 3. 定位根因与数据影响

区分代码根因、配置根因、数据污染、版本不一致、异步/并发时序和外部依赖故障。除代码错误本身，还要确认：

- 已经产生的错误数据是否会在修复后继续影响系统；
- 旧实例/旧协议/旧配置是否会与新修复并存；
- 重启、切流或回滚是否会再次触发问题；
- 补偿脚本是否具备幂等、范围限制和审计证据。

### 4. 选择最小可发布修复

优先选择：改动小、依赖少、可灰度、可回滚、容易监控的修复。除非根因本身无法局部修正，不在 hotfix 中进行大重构。

若真正需要修改公共合同、数据模型或大范围架构，明确指出 hotfix 只能先止血，并将永久修复升级到正式流程。

### 5. 发布前验证

至少确认：

- 原故障路径已被覆盖；
- 存量数据/在线状态在修复后有明确行为；
- 新旧版本并存时不会产生协议、数据或时序冲突（若发布方式可能并存）；
- 回滚不会因为 schema/数据变化变得不可执行；
- 关键日志/指标可以判断修复是否生效和是否产生新异常。

### 6. 发布与观察

优先使用项目已有灰度、开关、分批或回滚机制。发布后检查真实线上证据，不以 CI 绿或本地测试通过作为最终闭环。

如果无法获得关键线上验证证据，明确保持“未确认”，不要宣布事故已解决。

### 7. 收尾

确认：

- 故障不再持续扩大；
- 已受影响数据/玩家有明确处置；
- 临时 workaround 有退出计划；
- 永久修复若需要正式流程，已经明确下一步而不是塞进 hotfix 继续扩展。

## 文档

Hotfix 比普通维护更值得保留最小事故记录，但**仍然只有用户明确要求时才创建新的 Hotfix 记录**。

- 用户要求记录时：使用 `references/Hotfix记录模板.md`，只保存当前事故事实、止损、修复、发布、数据处置与接力点。
- 跨 session/多人接力、存在数据修复/补偿/回滚步骤，或事故尚未完全闭环时，Agent 应建议用户保存记录，但用户未明确要求前不得自行创建。
- 不得套用 `01–07` 正式功能开发文档。
- 若最终稳定系统契约变化导致已有长期权威文档失真，指出需要更新的具体事实；事故流水本身不进入长期功能文档，也不因为本次 hotfix 自动创建新的功能文档。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
