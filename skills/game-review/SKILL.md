# 多 Agent 交叉 Review 游戏功能

## 目标

针对需求链路、配置、方案、代码和测试进行独立、交叉验证的 review，并维护唯一的 `07-交叉评审.md`。

**核心原则：让不同 reviewer 从不同失效模型出发独立找问题，再互相证伪；不以意见数量代替代码证据。**

**单文档硬限制：本阶段只能维护 `07-交叉评审.md` 一份过程文档。** 不得为不同 reviewer、不同视角、不同轮次、修复验证或发布结论分别创建子报告。各 reviewer 的原始输出只作为临时输入，协调者去重、证伪后写入同一文档；被证伪、重复或失效的内容应删除。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。每条新记录必须包含实际 `skill_version`；版本由写入器从当前 skill 根目录 `SKILL.md` 的 `metadata.version` 自动读取，禁止由 Agent 手填、猜测或沿用历史值。写入器无法读取版本、版本格式非法或 `--skill` 与当前 `SKILL.md` 名称不一致时，必须拒绝追加并明确报告；不得写 `unknown` 伪装新记录。历史 schema v1 记录缺少版本时保留原样，查询和统计统一视为 `skill_version=unknown`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill 及其实际版本、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须按 `skill_version` 过滤或分组，不能把版本未知的旧记录或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 前置条件与产物

优先读取：

- `01-原始需求.md` 至 `06-完整实现方案.md`；
- 配置源及导表 diff；
- 固定基线到当前实现的代码 diff；
- 测试、启动、迁移和运行证据；
- 项目编码规范、架构约定和同类实现。

唯一过程文档：

```text
docs/requirements/<feature>/07-交叉评审.md
```

使用 [交叉评审模板](references/交叉评审模板.md)。所有 reviewer 发现、证伪结果、修复状态和最终结论都原位维护在这一份文档中。

## Review 范围固定

开始前在主文档中记录：

- 仓库、分支、基线提交和目标提交；
- 需求与方案文档版本；
- 配置文件、生成物和迁移；
- 明确不在本次 review 的内容；
- 已知无法运行的验证。

review 期间发现范围变化时，立即更新同一文档并告知用户，再重新固定范围；不混合两个不同版本的结论，也不另建新一轮报告。

## 多 Agent 结构

优先使用真正独立的子 Agent。至少安排三种视角：

1. **需求一致性 reviewer**
   - 检查实现是否遗漏、篡改或超出已确认需求；
   - 对照范围外、延期项和验收结果；
   - 关注玩家可见行为、资产、公平和运营规则。

2. **架构与正确性 reviewer**
   - 检查模块边界、数据所有权、状态机和不变量；
   - 关注并发、幂等、事务、跨进程时序、失败与补偿；
   - 检查实现是否破坏既定框架或形成隐蔽耦合。

3. **集成与运行 reviewer**
   - 检查配置、导表、协议、兼容、迁移、灰度和回滚；
   - 检查启动安全、日志、指标、运维和故障表现；
   - 检查测试是否真正证明关键行为。

高风险功能可增加安全/反作弊、性能容量或客户端协议 reviewer。不要为凑数量安排重复角色。

如果环境不支持子 Agent，使用隔离的多轮 review：每轮重新读取固定 review 包，不查看其他轮发现。隔离过程不生成额外文档，只在最终主文档中标记限制。

## 工作流程

### 1. 协调者准备 review 包

协调者只做范围、材料和问题分类，不预先给 reviewer 结论，避免锚定。

每个 reviewer 独立输出临时候选，候选必须包含：

- 严重级别；
- 代码/配置位置；
- 触发场景；
- 违反的需求、决策、不变量或项目约定；
- 具体影响；
- 可验证的修复方向；
- 置信度和仍需确认的事实。

临时候选不得直接作为永久子报告提交。

### 2. 使用风险驱动方法

根据改动选择方法，而不是机械遍历清单：

- **需求追踪**：需求规则 → 配置/代码 → 测试；
- **差异 review**：从基线 diff 识别新增状态和副作用；
- **不变量 review**：资产守恒、次数单调、唯一归属、状态合法性；
- **状态机 review**：非法转换、重复事件、乱序和恢复；
- **失败路径 review**：部分成功、超时、重试、补偿和回滚；
- **兼容 review**：旧数据、旧配置、旧协议和灰度混部；
- **配置 review**：主键、引用、默认值、范围、热更和跨端一致；
- **测试 review**：测试是否覆盖行为而非只覆盖实现细节；
- **可观测性 review**：线上问题是否能被发现、定位和处置。

只使用与本功能风险相关的方法。

### 3. 交叉证伪

第一轮独立完成后，将每条候选交给另一 reviewer 尝试证伪：

- 查找代码、测试或文档中已处理该问题的证据；
- 构造最小触发路径；
- 判断它是实际缺陷、文档缺陷、测试缺口还是偏好；
- 检查严重级别是否夸大；
- 合并同一根因的重复发现。

reviewer 不得仅回复“同意”。必须给证据或说明无法验证。

### 4. 协调者写入唯一文档

不按投票决定。只把满足以下条件的发现写入 `07-交叉评审.md`：

1. 有明确位置或可复现路径；
2. 影响具体且与本次范围相关；
3. 不是纯命名、风格或个人偏好；
4. 没有被现有代码、测试或已确认范围反证；
5. 修复价值高于引入的复杂度。

同一根因只保留一个发现，其证据、影响、修复和验证放在相邻位置。每条发现一经证实，立即写入 `07` 并告知用户；不得等待所有 reviewer 完成后再统一落盘。严重级别：

- **S0 阻断**：数据/资产损失、严重安全或一致性错误、服务器不可用、不可回滚破坏；
- **S1 必须修复**：主流程错误、常见失败导致错误结果、重大兼容或发布风险；
- **S2 建议修复**：非主流程缺陷、明确维护风险、重要测试或观测缺口；
- **S3 记录**：低影响改进或后续优化，不阻塞交付。

### 5. 修复与原位复审

- S0/S1 必须有处理结论：修复、回退方案、明确拒绝及依据；
- 修复后由非原作者 reviewer 验证触发路径和回归测试；
- 新发现若只是原问题的下游症状，合并到根因；
- 修复完成后立即原位更新发现状态，删除失效证据、旧方案和重复描述，并告知用户；
- 不另建复审报告或修复确认单。

发现来自需求、配置或方案矛盾时：

1. 先在 `07-交叉评审.md` 中记录已证实的根因、影响和当前阻塞，并立即告知用户 `07` 已更新；
2. 主动指出需要修订的 `01` 至 `06` 文档及拟修改内容；
3. 获得用户确认后，才更新对应上游文档，并明确告知每个已更新路径；
4. 上游修订和代码修复完成后，立即回到 `07` 更新发现状态并再次告知用户。

不得因为“review 发现了错误”就绕过确认，静默改写此前阶段的权威文档。

## 输出结论

最终状态只能是：

- **通过**：无未解决 S0/S1，关键证据充分；
- **有条件通过**：无 S0，少量 S1 有明确且获接受的处置条件；
- **不通过**：存在未解决 S0/S1 或无法证明关键正确性。

最终状态直接写在 `07-交叉评审.md` 顶部，并立即告知用户文档已更新。文档只保留当前有效发现、必要证据、处理状态和真实剩余风险，不保存 reviewer 流水。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 每个 reviewer 各写一份报告 | 原始输出仅作临时输入，统一汇总到 `07-交叉评审.md` |
| 修复后再建复审报告 | 原位更新同一发现的状态和证据 |
| 多个 Agent 都做同一种通用 review | 按独立失效模型分配视角 |
| reviewer 看到前人的结论后再检查 | 第一轮隔离，避免锚定 |
| 以两个 Agent 都同意作为证据 | 回到代码、配置、测试和触发路径 |
| 罗列大量命名和风格建议 | 只保留影响正确性、风险或长期边界的问题 |
| 只 review diff，不看需求和方案 | 同时做需求追踪与实现正确性检查 |
| 修复后由原 reviewer 自证通过 | 交给另一 reviewer 复核 |
| 发现或修复完成后只在聊天里汇报 | 同一轮更新 `07-交叉评审.md` 并告知路径 |
| 发现上游文档错误后直接改写 | 先列明拟修改内容并获得用户确认 |
