# 多 Agent 交叉 Review 游戏功能

## 目标

针对整个需求的需求链路、配置、方案、代码和测试进行独立、交叉验证的 review，并维护唯一的 `07-交叉评审.md`。如果 `02`–`06` 曾经拆成多个工作单元，本阶段负责把所有叶工作单元强制汇合到一个完整 review 范围。

**核心原则：让不同 reviewer 从不同失效模型出发独立找问题，再互相证伪；不以意见数量代替代码证据。**

**单文档硬限制：本阶段只能维护 `07-交叉评审.md` 一份过程文档。** 不得为不同工作单元、reviewer、视角、轮次、修复验证或发布结论分别创建子报告。禁止创建 `07-Uxx-*`、`Uxx-07-*` 或第二份交叉评审文档。各 reviewer 原始输出只作为临时输入，协调者去重、证伪后写入同一文档。

**Review 汇合硬限制：`07` 是整个分支工作流唯一且强制的汇合点。若不存在 `00-工作流索引.md`，按原单线门禁检查 `01`–`06`；若存在 `00`，必须读取完整 DAG，识别全部当前叶工作单元，并逐个核对其实际 pre-review 链路是否达到可移交终态。被标记 `已拆分` 的父工作单元不是叶节点，不可代替子工作单元检查。任一叶工作单元尚未闭环时不得创建或开始 `07-交叉评审.md`，必须指出具体 `Uxx`、当前文档和阻塞状态。全部叶工作单元满足条件后，先把 `00` 的 Review 汇合指向 `07-交叉评审.md`，再开始唯一的完整 review。**

`07` 中可以为发现标注所属 `Uxx`，但这只是问题路由信息，不表示 review 再次分支。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

本阶段的“实际前置”由 Review 汇合硬限制定义：存在 `00` 时不是某一条单线 `01`–`06`，而是共享根 + 所有叶工作单元各自真实 pre-review 链路。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。新记录使用 schema v3，并区分“实际使用 skill”和“未使用 skill”：只要当前 Agent 实际加载/执行了本 skill（即使用户没有显式写出 skill 名称），就必须调用本 skill 自带的 `scripts/document_record.py append --skill <当前skill>`，写入 `skill_usage=used`，`skill_version` 由写入器从当前 `SKILL.md` 的 `metadata.version` 自动读取，禁止 Agent 手填、猜测或沿用历史值；若一次变更实际没有使用任何 skill，才可使用 `--no-skill`，写入 `skill_usage=not_used`、`skill=null`、`skill_version=null`，不得挑选一个“最接近”的 skill 冒充来源。用户是否显式声明 skill 不是归因依据，实际是否加载/执行才是。写入器 append 前只校验已有文件仍可逐行解析为 UTF-8 JSON object；历史行的 schema 字段缺失或语义错误（例如旧 schema v2 缺少 `skill_version`）必须由 `check` 报告，但不得阻塞后续独立追加，也不得静默修改旧行；只有非 UTF-8、非法 JSON、非 object 等存储层损坏才拒绝 append。历史 schema v1 或非法 v2 无版本记录在查询和统计时统一视为 `skill_version=unknown`；no-skill v3 视为 `skill=none`、`skill_version=not_applicable`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过。记录至少包含时间、skill usage、skill/版本归因、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须只使用 `skill_usage=used` 且按 `skill_version` 过滤或分组，不能把 no-skill、版本未知或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

`00-工作流索引.md` 的 Review 汇合指针由本 skill 更新时，也必须按同一记录规则追加 `record.jsonl`。

## 前置条件与产物

### 未分支

优先读取：

- `01-原始需求.md` 至 `06-完整实现方案.md`；
- 已存在的客户端对接文档；
- 配置源及导表 diff；
- 固定基线到当前实现的代码 diff；
- 测试、启动、迁移和运行证据；
- 项目编码规范、架构约定和同类实现。

正常进入要求 `01=整理完成`、`02=已收敛`、`03=已收敛`、`04=已完成`、`05=骨架已完成`、`06=已完成`，以及实际存在且属于本次范围的客户端对接文档达到可移交状态。

### 已分支

必须先读取 `00-工作流索引.md`：

1. 重建完整 DAG；
2. 找出所有当前叶工作单元；
3. 排除顶部状态为 `已拆分` 的父工作单元；
4. 对每个叶工作单元按索引追溯其共享上游和直接前驱；
5. 核对该叶单元实际要求的最后阶段文档已达到可 review 终态，通常为对应 `06=已完成`；
6. 若该工作单元存在客户端对接文档，核对其达到可移交状态；
7. 检查所有叶工作单元共同代码、配置和生成物已经处在同一个可 review 基线。

任一叶单元缺少必要阶段、处于进行中/待人工/待步骤 review/阻塞，或索引无法唯一解析 DAG，都停止 review，不创建 `07`。

全部通过后，更新 `00`：`Review 汇合 = 07-交叉评审.md`，再创建或继续：

```text
docs/requirements/<feature>/07-交叉评审.md
```

使用 [交叉评审模板](references/交叉评审模板.md)。所有工作单元、reviewer 发现、证伪结果、修复状态和最终结论都维护在这一份文档中。

## Review 范围固定

开始前在主文档记录：仓库/分支/基线/目标提交；共享 `01`、`00`（若有）以及所有叶工作单元的需求与方案文档；配置/生成物/迁移；所有客户端对接文档；明确排除和无法运行验证。

分支工作流中，review 包必须覆盖**全部叶工作单元 + 它们的共享基线 + 跨工作单元集成面**。不能只分别 review 每个 Uxx 而遗漏组合后的冲突、顺序、共享数据或协议问题。

review 期间范围变化时立即更新同一 `07` 并告知用户，不混合不同版本结论。

## 多 Agent 结构

至少安排三类独立视角：

1. **需求一致性 reviewer**：检查所有工作单元合起来是否完整满足唯一 `01`，是否遗漏、篡改、重复实现或跨单元冲突。
2. **架构与正确性 reviewer**：检查各工作单元内部及跨工作单元的数据所有权、状态机、不变量、并发、幂等、事务、失败与补偿。
3. **集成与运行 reviewer**：检查配置、导表、协议、客户端合同、兼容、迁移、灰度、回滚、启动安全、日志和测试。

高风险功能可增加安全/反作弊、性能容量或客户端协议 reviewer。第一轮 reviewer 应独立读取固定 review 包，不先看其他 reviewer 结论。

## 工作流程

### 1. 协调者准备完整 review 包

协调者只固定范围、材料和工作单元映射，不预先给结论。每个 reviewer 候选必须包含严重级别、所属 `Uxx`（共享问题写 `shared`）、代码/配置位置、触发场景、违反规则/决策/不变量、影响、可验证修复方向、置信度和待确认事实。

### 2. 使用风险驱动方法

按实际改动选择需求追踪、差异 review、不变量、状态机、失败路径、兼容、配置、测试、可观测性等方法。分支工作流额外检查：

- 两个工作单元是否同时写同一事实；
- DAG 中的先后依赖是否在代码时序里真实成立；
- 共享上游变化是否被所有叶单元正确吸收；
- 独立通过的工作单元合并后是否出现集成冲突；
- 客户端合同是否存在字段/RPC 重复、语义冲突或缺口。

### 3. 交叉证伪

第一轮后，把每条候选交给另一 reviewer 尝试证伪：查代码/测试/文档证据、构造最小路径、判断实际缺陷/文档缺陷/测试缺口/偏好、校正严重级别、合并同根因发现。不得靠“多人同意”作为证据。

### 4. 协调者写入唯一 `07`

只把有明确位置或路径、具体影响、不是纯偏好、未被现有证据反证、修复价值足够的发现写入 `07`。每条发现标记所属 `Uxx` 或 `shared`，同一根因只保留一条。

严重级别：S0 阻断；S1 必须修复；S2 建议修复；S3 记录。每条发现一经证实立即写入并告知用户，不等待全部 reviewer 完成。

### 5. 修复与原位复审

S0/S1 必须有处理结论。修复后由非原作者 reviewer 验证触发路径和回归测试。发现来自某个工作单元的上游文档时：

1. 先在 `07` 记录根因、所属 `Uxx`、影响和阻塞；
2. 明确指出需要修订的具体 `02-Uxx`/`03-Uxx`/`04-Uxx`/`05-Uxx`/`06-Uxx`，或共享 `01`/共享上游，并说明拟修改内容；
3. 获得用户确认后才更新对应上游；
4. 修复完成后回到原 `07` 更新发现状态。

### 6. review 中需要新增工作单元

如果已开始的 review 证明修复本身需要一个新的独立生命周期：

1. **不得**创建 `07-Uxx-*` 或第二份 `07`；
2. 当前 `07` 保持 `评审中`/`不通过`，记录阻塞根因；
3. 暂停完整 review；
4. 回到最早受影响的 `02`–`06` 阶段，更新 `00` 并创建新的稳定 `Uxx`；
5. 新增工作单元和其他受影响叶单元重新达到 pre-review 可移交终态；
6. 再次执行完整汇合门禁，继续**原来的** `07-交叉评审.md`，重新固定新的 review 基线。

这保证所有分支最终只在一个 review 结论上收敛。

## 输出结论

最终状态只能是：

- **通过**：无未解决 S0/S1，关键证据充分；
- **有条件通过**：无 S0，少量 S1 有明确且获接受的处置条件；
- **不通过**：存在未解决 S0/S1 或无法证明关键正确性。

最终状态写入唯一 `07` 顶部并立即告知用户。若存在 `00`，其 Review 汇合继续指向同一 `07`，不创建“review 完成后的新分支状态”。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 每个 Uxx 各做一份完整 review | 所有叶工作单元先闭环，再统一进入一份 `07` |
| 创建 `07-U01-交叉评审.md` | 禁止；07 是强制汇合点 |
| U01 完成、U02 实现中时先 review U01 | 可做实现阶段内部 review，但不能启动完整 game-review |
| 把 `已拆分` 父节点当作完成叶子 | 从 00 找真正叶工作单元逐个检查 |
| 只 review 各 Uxx，不检查集成面 | review 包必须覆盖组合后的共享数据、时序、协议和配置 |
| 每个 reviewer 各写一份报告 | 原始输出仅临时，统一汇总到 `07` |
| 修复后另建复审报告 | 原位更新同一发现 |
| review 发现需新分支就在 07 下拆 | 暂停 07，回退 02–06 扩 DAG，闭环后回原 07 |
| 以多个 Agent 同意作为证据 | 回到代码、配置、测试和触发路径 |
| 发现上游错误后直接改写 | 先列明具体 Uxx 文档和拟修改内容并获得确认 |
