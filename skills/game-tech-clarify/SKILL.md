# 澄清游戏程序实现

## 目标

基于 `01-原始需求.md`、`02-需求挖掘.md`、代码架构和现有实现，向负责程序确认会显著影响架构、数据、接口、风险或验证方式的实现决策，并维护高密度的 `03-程序实现澄清.md`。

**核心原则：先查明事实，只讨论高影响决策；问题越往后越少。**

**文档职责：`03` 只保存当前有效的高影响实现决策、尚未解决的高影响技术问题，以及已经发现但尚待用户确认修订上游文档的最小阻塞说明。产品规则留在 `01`，未解决产品问题留在 `02`，不得跨文档长期重复。**

**邻接硬限制：一个实现事项的决策、必要依据、选项、结论和关键影响必须放在同一个连续分块。** 不得按“模块、数据、接口、失败、发布、验证”等维度把同一决策拆到多个摘要章节。

**结构硬限制：正文默认只有“实现事项”一个固定二级标题。** 禁止再建立“实现决策摘要、当前批次、问题台账、局部默认、阻塞与延期、收敛检查”等重复分块。

**闭环硬限制：每轮沟通结束后立即原位重写当前阶段事项。** 决策确认后，用精简结论替换问题、选项、推荐和回答记录；删除已失效、被覆盖或不再有用的内容。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。每条新记录必须包含实际 `skill_version`；版本由写入器从当前 skill 根目录 `SKILL.md` 的 `metadata.version` 自动读取，禁止由 Agent 手填、猜测或沿用历史值。写入器无法读取版本、版本格式非法或 `--skill` 与当前 `SKILL.md` 名称不一致时，必须拒绝追加并明确报告；不得写 `unknown` 伪装新记录。历史 schema v1 记录缺少版本时保留原样，查询和统计统一视为 `skill_version=unknown`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill 及其实际版本、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须按 `skill_version` 过滤或分组，不能把版本未知的旧记录或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 产物

必须读取 `01` 与 `02`。若仍有会改变实现方向的 P0/P1 产品问题，立即在 `03` 记录最小阻塞状态并告知用户，然后按上游文档确认流程回到 `game-discovery`；不得静默修改 `01` 或 `02`。

默认维护：

```text
docs/requirements/<feature>/03-程序实现澄清.md
```

使用 [程序实现澄清模板](references/程序实现澄清模板.md)。文档表示当前实现决策，不保存采访流水。

## 什么应该问程序

只询问会改变以下内容的高影响决定：

- 模块归属和跨系统责任；
- 持久化、迁移、历史数据兼容；
- 并发、一致性、幂等和跨进程时序；
- 协议、公共接口和上下游契约；
- 失败、补偿、回滚和灾难恢复；
- 发布、灰度、开关、降级和关键验证；
- 存在真实风险时的容量和性能约束。

不要询问变量、函数、类、文件命名，普通局部代码写法，可由代码直接确认的事实，或不影响公共契约、数据安全和维护成本的微小偏好。

## 工作流程

### 1. 建立产品边界

读取已确认规则、明确排除、延期项和重大风险。程序澄清不得重新定义产品目标；发现产品矛盾时，不得直接修改上游文档。

先立即更新 `03-程序实现澄清.md`，在最相关事项内写明阻塞事实及受影响的上游文档，并告知用户 `03` 已更新。随后主动说明拟对 `01` 或 `02` 做出的具体修改，获得用户确认后再调用 `game-spec` 或 `game-discovery` 更新；上游更新完成后，立即清理 `03` 中已解除的临时阻塞并再次告知用户。

### 2. 调查代码与架构

检查相关模块、数据模型、状态流转、配置、协议、同类实现、失败处理、测试、发布方式和兼容约束。

能从环境确认的事实直接用于分析，不把代码阅读问题转问负责人，也不写成长篇现状报告。

### 3. 筛选高影响决策

事项只有同时满足以下条件才进入文档：

1. 现有代码和约定无法给出可靠答案；
2. 答案会改变架构、公共契约、持久化数据、故障安全、发布方案或显著工作量；
3. 现在决定比编码中临时决定更便宜；
4. 负责程序拥有决定权；
5. 不是未解决产品问题的伪装。

P0 表示不可逆数据/协议、架构阻塞、一致性正确性或重大线上风险；P1 表示重要边界、失败恢复、迁移发布或验证路径；P2 仅在维护影响确实值得记录时保留。

### 4. 按事项聚合

每个待确认事项最多包含：

- ID、优先级、状态；
- 一个可直接决定的问题；
- 理解决策所必需的代码与架构依据；
- 最多三个真正不同的方案及关键权衡；
- 一条推荐方案。

模块、数据、接口、风险和验证影响若属于同一决策，必须写在同一分块附近，不能分别建章。

### 5. 分批沟通

每批处理 1–3 个强相关事项，按依赖顺序推进。后一批应更少、更聚焦；不因检查表还有项目就继续追问。

### 6. 回答后原位压缩

收到回答后，在同一轮完成：

1. 将原事项改写为“已确认”状态；
2. 用一句明确结论替换原问题、选项、推荐和回答记录；
3. 只保留会指导后续实现的关键影响；
4. 删除讨论过程、被否决方案、失效依据和重复描述；
5. 部分解决时只保留剩余决策分支；
6. 已取消、已默认或不再高影响的事项直接移除；
7. 同步更新或移除因该答案失效的其他事项；
8. 在回复中明确告知 `03-程序实现澄清.md` 已更新。

若该答案同时证明 `01` 或 `02` 已过时，先完成上述 `03` 更新，再说明受影响上游文档与拟修改内容并请求用户确认。确认后更新上游文档，告知其路径，再清理 `03` 中临时的上游阻塞状态。

版本历史承担过程追溯，当前文档只保留当前有效决策和真实未决项。

### 7. 保持问题局部完整

已确认事项应当可以在一个分块内直接读懂：

- 做什么决定；
- 为什么它影响实现；
- 对哪些关键边界产生结果。

只写实际相关的影响，不机械列出模块、数据、接口、风险、验证五个空分类。

## 收敛条件

- 无未解决 P0/P1 实现问题；
- 无尚待用户确认修订的上游文档阻塞；
- 核心边界、数据、契约、失败路径和兼容策略明确；
- 发布与回滚不存在未归属重大风险；
- 关键验证方式足以证明实现正确；
- `03` 中没有重复摘要、旧问答或失效方案。

结束时只更新顶部状态并说明能否进入实现计划，不再生成额外决策摘要。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一决策分别写进模块、数据、接口和风险章节 | 把相关内容放进同一个事项分块 |
| 同时保留决策摘要、当前批次和问题台账 | 每个事项只出现一次 |
| 回答后保留原问题、三个方案和完整回复 | 原位压缩为结论与关键影响 |
| 把代码阅读问题转问负责人 | 先调查，只有高影响决策才问 |
| 产品问题未解决却用技术默认值顶上 | 立即更新 `03` 标记阻塞，再确认后修订上游文档 |
| 发现上游错误后直接改 `01` 或 `02` | 先告知拟修改内容并获得用户确认 |
| 只在聊天中说明新决策 | 同一轮更新 `03` 并明确告知路径 |
| 越问越细、永不结束 | 以后续决策价值和收敛条件停止 |
