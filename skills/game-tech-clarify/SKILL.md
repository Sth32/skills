# 澄清游戏程序实现

## 目标

基于 `01-原始需求.md`、`02-需求挖掘.md`、代码架构和现有实现，向负责程序确认会显著影响架构、数据、接口、风险或验证方式的实现决策，并维护高密度的 `03-程序实现澄清.md`。

**核心原则：先查明事实，只讨论高影响决策；问题越往后越少。**

**文档职责：`03` 只保存当前有效的高影响实现决策，以及尚未解决的高影响技术问题。产品规则留在 `01`，未解决产品问题留在 `02`，不得跨文档重复。**

**邻接硬限制：一个实现事项的决策、必要依据、选项、结论和关键影响必须放在同一个连续分块。** 不得按“模块、数据、接口、失败、发布、验证”等维度把同一决策拆到多个摘要章节。

**结构硬限制：正文默认只有“实现事项”一个固定二级标题。** 禁止再建立“实现决策摘要、当前批次、问题台账、局部默认、阻塞与延期、收敛检查”等重复分块。

**闭环硬限制：每轮沟通结束后立即原位重写事项。** 决策确认后，用精简结论替换问题、选项、推荐和回答记录；删除已失效、被覆盖或不再有用的内容。

## 产物

必须读取 `01` 与 `02`。若仍有会改变实现方向的 P0/P1 产品问题，先回到 `game-discovery`。

默认维护：

```text
docs/requirements/<feature>/03-程序实现澄清.md
```

使用 [程序实现澄清模板](references/程序实现澄清模板.md)。文档表示当前实现决策，不保存采访流水。

## 什么应该问程序

只询问会改变以下内容的高影响决定：

- 模块归属和跨系统责任；
- 持久化、迁移、历史数据兼容；
- 并发、一致性、幂等和跨进程时序；
- 协议、公共接口和上下游契约；
- 失败、补偿、回滚和灾难恢复；
- 发布、灰度、开关、降级和关键验证；
- 存在真实风险时的容量和性能约束。

不要询问变量、函数、类、文件命名，普通局部代码写法，可由代码直接确认的事实，或不影响公共契约、数据安全和维护成本的微小偏好。

## 工作流程

### 1. 建立产品边界

读取已确认规则、明确排除、延期项和重大风险。程序澄清不得重新定义产品目标；发现产品矛盾时退回 `game-discovery`。

### 2. 调查代码与架构

检查相关模块、数据模型、状态流转、配置、协议、同类实现、失败处理、测试、发布方式和兼容约束。

能从环境确认的事实直接用于分析，不把代码阅读问题转问负责人，也不写成长篇现状报告。

### 3. 筛选高影响决策

事项只有同时满足以下条件才进入文档：

1. 现有代码和约定无法给出可靠答案；
2. 答案会改变架构、公共契约、持久化数据、故障安全、发布方案或显著工作量；
3. 现在决定比编码中临时决定更便宜；
4. 负责程序拥有决定权；
5. 不是未解决产品问题的伪装。

P0 表示不可逆数据/协议、架构阻塞、一致性正确性或重大线上风险；P1 表示重要边界、失败恢复、迁移发布或验证路径；P2 仅在维护影响确实值得记录时保留。

### 4. 按事项聚合

每个待确认事项最多包含：

- ID、优先级、状态；
- 一个可直接决定的问题；
- 理解决策所必需的代码与架构依据；
- 最多三个真正不同的方案及关键权衡；
- 一条推荐方案。

模块、数据、接口、风险和验证影响若属于同一决策，必须写在同一分块附近，不能分别建章。

### 5. 分批沟通

每批处理 1–3 个强相关事项，按依赖顺序推进。后一批应更少、更聚焦；不因检查表还有项目就继续追问。

### 6. 回答后原位压缩

收到回答后，在同一轮完成：

1. 将原事项改写为“已确认”状态；
2. 用一句明确结论替换原问题、选项、推荐和回答记录；
3. 只保留会指导后续实现的关键影响；
4. 删除讨论过程、被否决方案、失效依据和重复描述；
5. 部分解决时只保留剩余决策分支；
6. 已取消、已默认或不再高影响的事项直接移除；
7. 同步更新或移除因该答案失效的其他事项。

版本历史承担过程追溯，当前文档只保留当前有效决策和真实未决项。

### 7. 保持问题局部完整

已确认事项应当可以在一个分块内直接读懂：

- 做什么决定；
- 为什么它影响实现；
- 对哪些关键边界产生结果。

只写实际相关的影响，不机械列出模块、数据、接口、风险、验证五个空分类。

## 收敛条件

- 无未解决 P0/P1 实现问题；
- 核心边界、数据、契约、失败路径和兼容策略明确；
- 发布与回滚不存在未归属重大风险；
- 关键验证方式足以证明实现正确；
- `03` 中没有重复摘要、旧问答或失效方案。

结束时只更新顶部状态并说明能否进入实现计划，不再生成额外决策摘要。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一决策分别写进模块、数据、接口和风险章节 | 把相关内容放进同一个事项分块 |
| 同时保留决策摘要、当前批次和问题台账 | 每个事项只出现一次 |
| 回答后保留原问题、三个方案和完整回复 | 原位压缩为结论与关键影响 |
| 把代码阅读问题转问负责人 | 先调查，只有高影响决策才问 |
| 产品问题未解决却用技术默认值顶上 | 回退需求挖掘 |
| 越问越细、永不结束 | 以后续决策价值和收敛条件停止 |
