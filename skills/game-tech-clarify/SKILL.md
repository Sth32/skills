# 澄清游戏程序实现

## 目标

基于 `01-原始需求.md`、`02-需求挖掘.md`、代码架构和现有实现，向负责程序确认会显著影响架构、数据、接口、风险或验证方式的实现决策，并持续维护 `03-程序实现澄清.md`。

**核心原则：先查明事实，只讨论高影响决策；问题越往后越少，而不是越挖越细。**

## 前置条件与产物

- 必须读取原始需求与需求挖掘文档；
- 若仍存在会改变实现方向的 P0/P1 产品问题，先回到 `game-discovery`，不要用技术假设替代产品决定；
- 默认写入：

```text
docs/requirements/<feature>/03-程序实现澄清.md
```

使用 [程序实现澄清模板](references/程序实现澄清模板.md)。全部问题、选项、答案和结论都围绕这一文档维护。

## 什么应该问程序

只询问需要负责人判断的高影响事项，例如：

- 功能归属、模块边界和跨系统责任；
- 持久化数据、状态机、迁移和历史数据兼容；
- 并发、一致性、幂等、重复请求和跨进程时序；
- 协议、公共接口、配置格式和上下游兼容；
- 失败、重试、补偿、回滚和灾难恢复；
- 发布、灰度、开关、降级和运维处置；
- 性能容量存在真实风险时的约束；
- 关键验证边界、测试入口和可观测性。

不要询问：

- 变量、函数、类或文件如何命名；
- 普通局部代码怎么写；
- 从现有代码可直接确认的事实；
- 不影响接口、数据、安全或维护成本的微小偏好；
- 为覆盖检查表而穷举所有实现细节。

## 工作流程

### 1. 读取已确认需求

建立不可越过的产品边界：

- 哪些规则已经确认；
- 哪些内容明确不做；
- 哪些风险由程序评估；
- 哪些 P2 产品项采用默认值或延期。

程序实现澄清不得重新定义产品目标。发现产品矛盾时，记录阻塞并退回需求挖掘。

### 2. 调查代码与架构

先检查相关：

- 模块和进程边界；
- 数据模型、状态流转、配置和协议；
- 同类功能与可复用路径；
- 失败处理、日志、监控和运维工具；
- 测试入口、发布方式和兼容约束；
- 最近相关改动及已知技术债。

能通过环境确认的事实直接写入“现状依据”。不要问负责人“现在代码是怎么写的”。

### 3. 生成候选决策

只从实际变更路径寻找可能造成以下后果的决策：

- 架构方向或模块职责不同；
- 持久化格式、迁移方式或线上数据安全不同；
- 公共接口、协议或上下游改动不同；
- 一致性、并发和故障恢复结果不同；
- 工期、回滚能力、发布风险或验证成本显著不同。

### 4. 通过价值门槛

只有同时满足以下条件才问：

1. 无法仅靠代码与现有约定得出可靠答案；
2. 答案会改变架构、公共契约、持久化数据、故障安全、发布方案或显著工作量；
3. 现在决定比编码中临时决定更便宜；
4. 负责程序拥有决定权或必须确认；
5. 问题不是未解决产品问题的伪装。

局部且可逆的选择由执行者按现有模式决定，并在必要时记录假设，不进入采访。

### 5. 排优先级

- **P0**：架构阻塞；不可逆数据或协议决定；线上数据安全；一致性正确性；跨服务硬契约；无法回滚的发布风险。
- **P1**：重要模块边界；主要失败与补偿路径；迁移、兼容、灰度、容量或关键测试边界。
- **P2**：具有中等维护影响的局部权衡，可默认或延期。

按依赖顺序处理 P0 → P1 → P2。下游问题依赖上游答案时，不提前发问。

### 6. 形成可决策问题

每个问题先写入文档，并包含：

- 决策 ID、状态和优先级；
- 需要负责人确认的单一决策；
- 为什么必须现在决定；
- 代码与架构依据；
- 最多三个可行选项及关键权衡；
- 推荐方案与理由；
- 负责人回答；
- 对模块、数据、接口、风险和验证的影响；
- 是否产生新的高价值问题。

问题应让负责人能够直接选择、修正或补充，而不是从零替 Agent 做分析。

### 7. 多批次采访并收敛

每批 2–4 个强相关问题：

- 同一批围绕一个架构主题或依赖层；
- 先给当前现状和推荐方案，再问决策；
- 收到回答后立即回写文档，关闭、合并或淘汰问题；
- 仅当答案产生新的高影响分支时新增问题；
- 后一批应比前一批更聚焦，问题数量总体下降；
- 不因“还可以继续问”而继续，只有决策价值足够才进入下一批。

回答含糊时，只追问造成不同实现结果的部分，不重新讨论整题。

### 8. 形成实现决策摘要

问题解决后，把结论从问答记录提升为稳定决策，至少说明：

- 模块与责任边界；
- 核心数据和状态流转；
- 跨模块/跨进程契约；
- 失败、补偿与回滚；
- 兼容、迁移与发布；
- 验证入口和可观测性；
- 明确延期项和执行者可自行决定的局部事项。

## 收敛条件

满足以下条件后结束：

- 没有未解决 P0/P1 实现问题；
- 核心边界、数据、契约、失败路径和兼容策略明确；
- 发布与回滚不存在未归属的重大风险；
- 关键验证方式足以证明需求被正确实现；
- 剩余 P2 已采用默认方案、延期或指定负责人；
- 新一轮已无法产生足够高价值的问题。

结束时标记“程序实现澄清已收敛”，说明是否可进入实现计划；不要直接开始编码，除非用户另行要求。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把代码阅读问题转问负责人 | 先调查，只有决策才问 |
| 一次问完整技术检查表 | 只问会改变关键实现路径的问题 |
| 不给选项和建议，让负责人从零设计 | 提供现状、选项、权衡和推荐 |
| 产品问题未解决却用技术默认值顶上 | 回退到需求挖掘 |
| 越问越细、永不结束 | 以后续决策价值和收敛条件为停止标准 |
| 只记录答案，不记录影响 | 将答案转为可执行的实现决策摘要 |
