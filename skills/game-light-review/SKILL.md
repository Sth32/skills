# 轻量 Review 日常改动

## 目标

对 bugfix、小需求、局部重构等维护型改动做快速但可靠的独立 Review，优先发现会改变正确性、数据安全、接口契约和运行稳定性的真实问题；默认不创建 `07` 正式交叉评审文档，也不机械要求多 Agent 交叉证伪。

**核心原则：Review 改动本身和它实际触及的边界；不因范围小而只看代码表面，也不因追求完整而把局部 diff 扩展成全系统审计。**

## 输入

优先读取：

- 用户目标或 bug 现象；
- 当前 diff / commit；
- 受影响代码、调用方、测试和配置；
- 若存在用户要求的维护记录，再把它作为导航而非权威证据。

## Review 重点

按改动实际经过的边界选择检查项：

- 目标是否真正被满足，是否存在漏改或误改；
- 根因修复是否只是症状补丁；
- 状态机、终态、失败路径、异常恢复；
- 数据所有权、持久化、异步乱序、并发/幂等；
- 权限检查对象与最终执行对象是否一致；
- RPC/Event/协议、配置和客户端合同是否意外漂移；
- 测试是否覆盖原问题/新增行为及直接回归面；
- diff 是否混入无关功能或危险调试逻辑。

没有经过的高风险边界不机械展开。

## 环境与线上数据边界

开发期默认不假设存在必须保护的线上存量数据、在线玩家状态、灰度发布或无损迁移要求。只有用户明确说明已上线、要求兼容存量数据，或当前 review 对象是 `game-hotfix`，才把这些作为默认审查重点。

如果是否处于线上环境会实质改变 review 结论，而现有上下文无法确认，明确询问一次；否则按当前可证实的开发环境判断，不进行大段假设性线上分析。

## 升级到完整 `game-review`

出现以下情况时，说明 light-review 已不足够：

- 改动跨多个独立工作单元或共享系统，组合风险明显；
- 涉及新的公共协议、数据权威、持久化 schema、迁移或复杂跨进程一致性；
- 单一 reviewer 无法用局部证据可靠覆盖关键风险；
- 用户明确要求正式交叉 Review。

## 工作流程

### 1. 固定范围

确认目标 diff、基线和本次 review 目的。若 review 期间 diff 变化，重新检查受影响结论。

### 2. 重建意图与风险面

从用户目标和代码事实确认应该改变什么、必须保持什么，再定位真正被改动触及的系统边界。

### 3. 找问题并尝试证伪

每个候选问题都必须给出代码/配置/测试证据、触发场景和实际影响。优先主动寻找能够推翻自己判断的反例；没有证据的问题降为待确认，不把偏好写成缺陷。

### 4. 输出结论

按严重度优先输出可行动问题。没有发现阻塞问题时，明确说明已检查的主要风险面和仍无法验证的部分，不用“看起来没问题”替代证据。

## 文档

默认只在对话中输出 Review 结果，不创建维护文档。

只有用户明确要求保存 review、需要跨 session 接力或团队流程要求落盘时，才使用 `references/轻量评审模板.md`。不得创建 `07-交叉评审.md` 或模仿正式 Review 的多 Agent 状态结构，除非用户明确切换到 `game-review`。
