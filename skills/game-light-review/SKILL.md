# 轻量 Review 日常改动

## 目标

对 bugfix、小需求、局部重构等维护型改动做快速、独立、证据驱动的 Review，优先发现会造成真实功能错误、资产/数据问题、运行风险、接口漂移或明显长期维护负担的问题。

轻量 Review 不追求“能挑出多少问题”，而是筛出**值得当前修改的问题**。默认不进入 `01–07` 正式功能流程，不创建 `07` 正式交叉评审文档，也不机械要求多 Agent 交叉证伪。

**核心原则：Finding 必须落到现实可达路径、实际影响和处理价值；Review 只阻止值得阻止的问题，不把风格偏好、理论完备或“还能更优雅”包装成缺陷。**

## 输入与范围

优先读取：

- 用户目标、bug 现象或小需求；
- 当前 diff / commit 与基线；
- 为理解改动所需的直接调用方、被调用方、配置、数据结构和测试；
- 若存在用户要求的维护记录，把它作为导航而非权威证据。

Review 范围是“当前改动 + 判断其真实风险所必需的最小上下文”，不是整个系统。没有证据表明相关的模块，不为了完整感机械展开审计。

## Finding 判定

### 1. 先确认问题真实成立

候选问题进入 Finding 前，优先确认：

- 路径是否真实可达，而不是静态上理论可能；
- 上层约束、状态机、框架或已有保护是否已经使它不成立；
- 当前 diff 是否真的引入/保留了问题；
- 描述、注释、测试与实现不一致时，是否存在历史需求或特殊约束。

能够从代码、配置、测试、调用链或历史实现查清的事实自己查。证据不足时标成“待确认/风险提示”，不要直接定性为 bug。

### 2. 判断是否值得现在改

Finding 的严重度由现实风险决定，至少综合：

- 发生概率与触发难度；
- 玩家体验、资产、数据、服务器稳定性和接口影响；
- 是否可被主动利用或放大；
- 是否能自然恢复、跳过、降级或低成本补偿；
- 修复本身会引入多少复杂度和回归风险。

低概率、低影响、可恢复的问题，不因为“理论上不完美”就要求复杂修复。资产重复/丢失、数据污染、安全/作弊、严重崩溃、不可恢复状态等高后果问题，即使概率低也提高优先级。

如果正确处理应由公共底层能力统一承担，不要求某个玩法业务为了通过 Review 临时堆一套复杂机制；可以指出局部风险并建议后续下沉，必要时与用户讨论方案。

### 3. 区分 Finding 与偏好

以下内容默认**不作为 Finding**：

- 纯格式、命名、注释风格、个人代码习惯；
- 只因为存在重复就要求抽象；
- 为未知未来需求要求预留接口或通用框架；
- 与当前 diff 无关的历史代码问题；
- 无现实影响证据的理论竞态、理论空指针或极端组合；
- “我会这样写”“这样更优雅”但当前实现同样正确、清晰且可维护的替代方案。

只有当这些问题已经造成误用风险、显著理解成本、重复缺陷、扩展成本或违反项目明确规范时，才升级为可行动问题。

## Review 重点

按改动真实经过的边界选择检查项：

- **目标闭环**：用户目标是否真正实现，有无漏改、误改或只完成 happy path；
- **Bugfix**：原 bug 是否真实存在，修复是否针对根因，是否值得当前复杂度；
- **Small change**：是否贴合已有实现，设计是否过度，必要行为链是否完整；
- **Refactor**：行为是否等价，是否误删历史特例、错误统一高变化策划规则或混入功能修改；
- **状态与失败**：终态、失败返回、取消/超时、恢复是否与实际调用链一致；
- **数据与资产**：所有权、写入、持久化、重复扣发、幂等和恢复；
- **权限与对象**：校验对象与最终执行对象是否一致；
- **合同**：RPC/Event/协议、配置语义、客户端可见行为是否意外漂移；
- **异步/并发**：只有实际触及这些边界时，检查现实可达的乱序、重入和生命周期风险；
- **实现卫生**：是否混入危险调试逻辑、临时绕过或无关大改。

## 严重度与输出

按“是否需要阻止当前合入/交付”排序，而不是按代码洁癖排序：

- **阻塞**：会造成高影响正确性、资产/数据、安全、崩溃或公共合同问题，当前不应继续交付；
- **应修**：现实可达且影响明确，修复成本合理，建议当前一起修；
- **建议**：不阻塞当前目标，但有明确维护收益或风险，用户可决定是否处理；
- **待确认**：有合理迹象但关键事实缺失，不能在证据不足时冒充 Finding。

每条 Finding 至少包含：位置/范围、触发场景、证据、现实影响、为什么值得修、建议处理方向。不要为了显得全面输出大量无行动价值的 nit。

## 环境与线上数据边界

开发期默认不假设存在必须保护的线上存量数据、在线玩家状态、灰度发布或无损迁移要求。是否已经上线只能由用户确认；不得根据 production 配置、部署脚本、分支名、schema 历史等仓库迹象自行判断。

只有用户明确说明已上线/按生产约束处理，或 review 对象明确属于 `game-hotfix`，才把存量数据、在线状态、回滚/补偿和发布风险作为默认重点。如果是否按线上处理会实质改变结论且用户尚未说明，只询问一次。

## QA 与验证边界

Review 应检查已有自动化验证是否与改动风险匹配，但**不得把 CI、单测、服务端脚本或静态检查通过冒充完整游戏功能验收**。

当改动涉及 Agent 无法可靠覆盖的客户端表现、多玩家交互、复杂游戏场景、真实操作节奏或历史特殊规则时，在结论中给 QA/测试人员提供精简的回归样例，按需包含：

- 前置账号/场景/配置状态；
- 操作步骤；
- 期望结果；
- 重点观察的客户端表现、服务器状态或日志；
- 与本次 diff 直接相关的旧行为回归点。

简单改动只给少量高价值用例；高风险改动再扩大。不为了 Review 形式自动创建测试文档。

## 升级到完整 `game-review`

出现以下情况时，说明 light-review 已不足够：

- 改动跨多个独立工作单元或共享核心系统，组合风险明显；
- 涉及新的公共协议、数据权威、持久化 schema、迁移或复杂跨进程一致性设计；
- 单一 reviewer 无法用局部证据覆盖关键风险，需要独立视角交叉证伪；
- 用户明确要求正式交叉 Review。

不要因为 diff 文件多、代码量大一点或存在普通异步调用就自动升级；看实际独立风险面和设计边界。

## 工作流程

### 1. 固定目标和 diff

确认用户目标、基线、目标 diff 和本次 Review 目的。Review 期间 diff 变化时，只重新检查受变化影响的结论和风险面。

### 2. 重建当前实现与修改意图

先理解原实现为什么这样、这次应该改变什么、什么必须保持不变。对异常特判、描述与实现不一致、故意未统一的路径额外谨慎，不能把“看起来不合理”直接当成错误。

### 3. 按实际风险寻找问题

沿真实调用链和数据流检查当前改动，不机械套 checklist。发现候选问题后先尝试证伪，再判断影响、概率、恢复能力和修复成本。

### 4. 输出最少但有价值的结论

先输出阻塞/应修问题，再给必要建议和待确认项。没有发现值得修改的问题时，可以明确给出“未发现阻塞/应修 Finding”，并说明已检查的主要风险面和无法由 Agent 覆盖的 QA 边界。

**“未发现问题”不是证明代码绝对正确；结论强度必须匹配已检查证据。**

## 文档

默认只在对话中输出 Review 结果，不创建维护文档。**只有用户明确要求保存本次 Review 时，才创建新的轻量评审记录。**

- 用户要求保存时：使用 `references/轻量评审模板.md`。
- QA 回归样例默认直接随 Review 结论输出；只有用户要求留档时才写入评审记录。
- 跨 session、多人接力或团队可能需要留档时，Agent 可以建议保存，但用户未明确要求前不得自行创建。
- 不得创建 `07-交叉评审.md` 或模仿正式 Review 的多 Agent 状态结构，除非用户明确切换到 `game-review`。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
