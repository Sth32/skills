# 配置源识别指南

仅在文件职责或写入边界不清时读取。

## 判断顺序

1. 谁把它当作事实来源：策划配置系统、生成工具，还是运行时代码？
2. 它是否主要声明数据，还是包含函数、条件、循环、调用和副作用？
3. 它是否会被导表或生成工具覆盖？
4. 修改条目是在改变数据，还是在增加程序行为？
5. 同类文件通常如何维护和发布？

## 可直接修改的真实配置源

在范围确认后可修改：

- Excel、CSV；
- XML、YAML、JSON、INI、TOML；
- 文本 DSL；
- 项目明确用作纯数据表的 Lua、Python、JavaScript 文件。

前提是它们是事实源、以数据声明为主，并由通用加载器或配置系统消费。

## 不直接修改的生成物

- Excel 导出的 Lua、JSON、XML；
- Schema 生成的数据类、常量和访问代码；
- 客户端或服务端的可再生配置包。

应修改真实源并重新执行标准生成流程。

## 禁止在 game-config 修改的代码

- Component、Service、Manager、Handler、Controller；
- 协议处理、状态机、业务校验、同步、结算；
- 运行时代码中的注册表、映射表、白名单、`VIEW_MAP`；
- 导表器、生成器、加载器的程序逻辑；
- 为支持新配置而新增的方法、分支、解析或消费代码。

## Schema 与元数据

字段、类型、索引、引用、输出范围和声明式校验规则可以属于配置 Schema。它们会扩大影响面，必须单独确认。

生成器模板或解析器代码不属于声明式 Schema，应移交实现阶段。

## 模糊案例

扩展名不能决定类别：

- `BuildingTypes.xml` 只声明数据且由通用加载器读取：配置源；
- Excel 导出的 `BuildingTypes.xml`：生成物；
- XML 中嵌入可执行规则并由业务引擎解释：先调查，必要时按代码依赖处理；
- `ActorTypes.lua` 只有静态数据表：可能是配置源；
- `AllyOrgViewHostComp.lua` 中的 `VIEW_MAP`：运行时代码。

仍不确定时默认不写，记录“类别待确认”。
