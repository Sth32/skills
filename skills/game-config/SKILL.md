# 规划并修改游戏配置

## 目标

把当前工作单元的已确认需求转成可执行的配置变更，并持续维护未分支的 `04-配置规划.md`，或当前工作单元的 `04-Uxx-<主题>-配置规划.md`。配置阶段收尾时，如当前功能存在策划需要理解、补齐或长期维护的配表，再额外生成一份简短的策划配表说明交付物。

**核心边界：本阶段修改配置事实，不实现运行时代码。先判断职责，再决定能否写入；不要按扩展名判断。**

**配置契约优先硬限制：对“具体配什么 / 配多少”这类内容值，先收敛配置契约，不追最终业务值。必须明确真实配置源、字段与引用方式、ID 的业务域或合法范围、类型/范围校验以及消费方式；只要具体 ID、数量、概率、阈值等最终取值不改变 Schema、主键/查找方式、引用关系、加载成功、控制流、协议语义或测试成立条件，就可由策划后续配表，不得把最终业务值作为 `04` 阻塞。例如需求只要求“发放货币”，本阶段应确认奖励 ID 仅允许货币类 ID、数量字段可配置及其校验/消费链路，不要求决定某个具体货币 ID 和数量。若运行时必须存在配置行或值才能加载、生成或验证，则使用安全默认/占位或最小测试值，但必须明确它不是最终业务配置。**

**过程文档唯一性硬限制：当前工作单元在本阶段只能维护一份配置规划过程文档。** 不得额外创建配置执行清单、人工填表清单、验证报告、调查记录、差异摘要或其他过程旁支文档。配置阶段收尾时允许额外生成 **一份策划配表说明交付物**；它不是阶段状态或配置事实的权威来源，只服务于策划后续配表和理解功能配置。不同工作单元可拥有各自的 `04` 过程文档和各自的一份策划配表说明；代码、Excel、XML、生成物和日志属于实际产物或证据，不算过程文档。

**策划交付物边界硬限制：策划配表说明必须保持两块内容分离。** “策划配表提醒”只放不阻塞当前实现、可留给策划后续补齐的零碎配置动作，使用简短小条；“功能配表说明”只介绍代码已消费或已明确将在实现阶段直接消费的主要配置对象与主体字段，以表格和短说明为主。不得把提醒塞进字段说明表，也不得把所有字段、完整 Schema、执行历史、验证日志、阶段状态或未决技术问题搬进交付物。

**可延后配置硬限制：只有最终取值不影响当前实现正确性的配置才能转为策划收尾提醒。** 若缺失或变化会影响 Schema、主键/查找方式、引用关系、加载成功、控制流、协议语义、测试成立条件或当前实现分支，就仍是本阶段阻塞配置，必须先收敛；不能为了推进阶段把实现依赖伪装成“策划后配”。展示文案、表现资源、可安全替换的平衡数值等仅在项目已有可用默认值/占位值且不改变上述实现契约时才可延后。

**邻接硬限制：同一逻辑配置对象的真实源、关键变化、执行方式、状态、验证结果和后续代码依赖必须放在同一个连续事项内。** 不得按“规划、执行、验证、移交”等维度重复记录同一对象。

**当前真相硬限制：配置执行或沟通完成后必须原位更新事项。** 删除已解决问题、失效步骤、旧状态和不再有用的人工操作说明，不保留执行流水。策划配表说明只在收尾时从已收敛的当前事实生成或刷新，不作为并行维护的第二套事实源。

**分支工作流硬限制：工作单元最早可在 `01` 需求整理阶段创建，并可独立推进到客户端对接和 `07-Uxx` Review；不存在“所有分支先汇合才能 review”的门禁。当前阶段若发现真实独立范围，仍可继续拆分稳定工作单元 `U01`、`U02`……；所有文件保持在同一个 `docs/requirements/<feature>/` 目录，不增加分支子目录。没有真实分支时继续使用原文件名。第一次拆分创建 `00-工作流索引.md`，只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针；拓扑只由依赖表达。分支文档命名为 `04-<Uxx>-<主题>-配置规划.md`。当前 Uxx 只检查自己的共享需求基线、自身/祖先需求文档和真实依赖；无依赖兄弟工作单元不构成阻塞。**

在分支工作流中，下述“本阶段唯一文档”指当前工作单元的唯一 `04` 权威过程文档；`00-工作流索引.md` 只是路由元数据，不复制配置事实、执行状态或验证结果。策划配表说明同样不是权威过程文档，不得被 `00` 当作“当前文档”。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。** 收尾阶段若这些事实改变策划配表说明，也必须在宣布阶段完成前同步刷新交付物。

**结构性变更影响传播硬限制：当范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源发生变化时，必须在同一轮执行影响扫描，不得只修当前局部段落。当前阶段文档内至少核对顶部元信息、相关正文规则/矩阵、验证结论、阻塞与下一动作；同时定位已有且实际依赖该事实的上下游阶段文档、客户端合同与 `00-工作流索引.md` 中的旧引用。当前阶段和本 skill 允许直接维护的下游内容立即原位更新；若受影响的是需要用户确认才能改写的上游文档，必须明确列出受影响文件、旧事实与拟修改内容并等待确认，不得静默遗漏，也不得把未传播完成的结构性变化描述为已闭环。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

存在 `00` 时，开始或恢复本阶段前必须先解析当前 `Uxx` 的共享上游和直接前驱，只检查实际依赖；未被依赖的兄弟工作单元可以处于其他阶段，不构成阻塞。索引无法唯一确定当前工作单元、依赖或文档时，先修正索引。

**外部记录硬限制：每次逻辑上的文档变更完成后，只通过 `sth32-skills-record append` 提交本次变更的最小结构化事实；记录存储属于仓库外部基础设施，Agent 不得查找、定位、读取、搜索、解析或直接修改任何历史记录、记录文件或 recorder 实现，也不得为了写记录而扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。命令不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过 recorder。**

创建或修改 `00-工作流索引.md` 同样必须追加记录；普通配置事项变化若不改变拓扑、当前阶段或当前文档，不重复修改索引。策划配表说明属于同目录文档变更，应与同轮收尾文档变更合并记录在同一条 `documents` 中。

配置阶段收尾时，如果存在策划后续需要补齐的非阻塞配置，或当前功能包含策划需要理解和维护的主体配置，则生成一份策划配表说明：

```text
# 未分支
docs/requirements/<feature>/04-策划配表说明.md
```

若配置调查证明当前工作单元实际上包含多个可以独立配置、独立阻塞并独立交给后续代码阶段的范围，可在本阶段继续拆分：更新 `00`、给后继分配新 `Uxx`、把父 `04` 压缩为共同配置基线并标记 `已拆分`，再创建子 `04`。父工作单元不再直接进入 `05`。

## 复杂度门槛

先选择最小充分路径，不要默认审计整个配置系统。

- **简单数据变更**：单一真实源、无 Schema 变化、无多端差异。直接完成分类、确认、修改和必要校验。
- **复杂配置变更**：跨多个物理源、新增字段或类型、多目标输出、生成代码、覆盖层或复杂引用。读取 [复杂配置管线指南](references/复杂配置管线指南.md)。
- **配置与代码边界不清**：读取 [配置源识别指南](references/配置源识别指南.md)。
- **需要设计验证范围**：读取 [配置校验清单](references/配置校验清单.md)。
- **本轮已经误改代码**：立即停止并读取 [误改代码处置](references/误改代码处置.md)。

不要为了展示完整性而读取所有参考文件。

## 最小工作流

### 1. 定位当前工作单元并识别应配置的内容

存在 `00` 时先确认当前 `Uxx`、范围、依赖和当前 `04`；没有则按单线工作。优先配置当前工作单元中策划或运营需要调整的数值、文本、奖励、概率、时间、阈值、开关、映射和分组。遇到“发一些货币”“给若干奖励”这类模糊内容值时，先识别业务类别、配置字段和合法 ID 域，不追问最终 ID 或数量。

通常保留在代码中：算法、状态机、协议语义、运行时控制流、局部技术参数和不可变业务约束。

### 2. 按逻辑配置对象聚合

一个功能对象可能分布在 Excel、XML、YAML、Schema 和生成物中。先把属于同一业务对象的内容聚合，再列物理源，避免只改其中一处。每个逻辑对象在当前工作单元文档中只出现一次。

如果两个配置对象没有共同决策/执行依赖、可以分别被不同 session 推进，且后续代码也独立，才考虑拆工作单元；仅仅存在两个表或两个文件不构成拆分理由。

### 3. 写入前分类

| 类别 | 本阶段动作 |
|---|---|
| 真实声明式配置源 | 确认后修改并验证 |
| Excel 源 | 询问手动或自动；该选择只影响 Excel |
| 声明式 Schema/字段/校验元数据 | 单独确认后可修改 |
| 可再生生成物 | 不直接修改；修改真实源后重新生成 |
| 运行时代码或生成/加载程序逻辑 | 禁止修改；记录后续实现依赖 |
| 策划收尾配置 | 最终内容值不影响实现契约时可延后；先收敛字段、引用、合法 ID 域/范围与安全默认/占位，不作为实现阻塞，收尾时写入策划配表提醒 |

XML、YAML、JSON、INI、CSV、纯数据 Lua 等都可能是配置；Component、Manager、Handler、`VIEW_MAP` 等即使是文本文件仍属于代码。

### 4. 维护当前工作单元的高密度文档

每个配置事项只写：逻辑对象及真实源/Schema、字段与引用方式、ID 业务域/合法范围等关键约束、关键变化、执行方式与当前结果、最小充分验证、后续代码依赖。使用“参照对象 + 变化字段”，不复制完整行、表结构、日志或调查过程。

对于可延后的策划收尾配置，在事项中只保留“为什么不阻塞实现 + 已收敛的合法域/字段约束 + 当前安全默认/占位 + 交给策划补什么”的最小事实；不要把策划交接文档提前当作过程文档维护。

### 5. 执行允许的配置修改

- 修改真实配置源，不手改生成物；
- Excel 手动时将对应事项标记为待人工，并继续当前工作单元其他已确认配置源；
- Excel 自动时保留格式、公式、数据验证和合并单元格；
- 不为“让配置生效”而顺手修改运行时代码；
- 发现缺少注册、映射、加载分支或业务消费时，写入同一事项的后续代码依赖；
- 对确认为策划收尾配置的项，不为了“阶段全绿”编造最终业务 ID 或数值，只验证合法域、字段能力和默认/占位不会阻塞当前实现。

每完成一项实际修改，立即回写当前 `04` 并告知完整路径。

### 6. 做必要而非穷尽的验证

根据实际变化选择语法/解析、类型与唯一性、引用/枚举/范围、ID 业务域、导表/生成、目标端输出或加载等最小充分检查。验证结果直接回写对应事项，不另建报告。

策划收尾配置至少验证“合法 ID 域/字段约束成立，且当前默认/占位不会破坏加载、引用和实现测试”；不能验证这一点时，不得把它降级为非阻塞提醒。

### 7. 沟通与执行后原位收敛

每轮完成后更新对应事项状态和结果，删除已解决问题、旧步骤和失效说明。若调查、执行或验证证明当前工作单元适用的需求基线 或当前工作单元实际依赖的 `02`/`03` 需要修订，先更新当前 `04` 的最小阻塞并告知用户，再说明拟修改上游内容并获得确认。

### 8. 生成策划配表说明

只在当前工作单元准备收尾时生成或刷新，不与过程文档并行滚动维护。

- **策划配表提醒**：只收录可延后的非阻塞配置；每条尽量一句，直接写“在哪 / 配什么 / 合法 ID 域或必要范围约束”，不写技术过程和长解释。
- **功能配表说明**：先用 1～3 句说明这些配置共同控制什么，再用表格列重要配置对象和代码主体字段。只收录现有代码已消费或后续实现明确会直接读取的主要字段；优先写配置源/对象、主键或定位方式、主体字段、字段含义/代码用途、合法 ID 域/关键约束。
- 提醒可以包含零碎值、表现资源、文案或内容补齐；主体字段表不能为了“完整”把这些琐碎提醒全部列进去。
- 不复制完整字段百科，不列纯导出/生成技术字段、显然沿用默认值的字段、仅策划编辑器内部使用且代码不消费的辅助字段。
- 若实现阶段后来改变了主体字段或配置关系，应由产生变更的后续阶段按影响传播规则同步更新这份交付物。

### 9. 更新索引

仅在工作单元创建/拆分/终止、依赖变化、当前阶段或当前过程文档变化时更新 `00`。当前配置值、人工步骤、验证结果和策划配表说明路径不得复制到索引。

## 完成条件

对当前叶工作单元：

- 需要配置和保留代码的边界清楚；
- 所有候选目标已分类；
- 配置契约已经收敛：真实源、字段/引用方式、ID 业务域或合法范围、类型/范围校验与消费方式明确；
- 用户已确认可写范围、Excel 方式及必要 Schema 变化；
- 已确认由 Agent 处理的真实配置源均已修改；
- 必要解析、引用、生成或加载验证已有结果；
- 没有直接修改生成物或运行时代码；
- 实现所依赖的配置事实已经收敛；任何仍延后的最终业务 ID/数值均满足“最终取值不影响当前实现契约”，且当前默认/占位已验证安全；
- 待人工操作和后续代码依赖在对应事项内清晰可追踪；
- 如存在策划收尾配置或值得策划理解的主体配表，策划配表说明已按模板生成/刷新，提醒与主体字段说明保持分离；
- 无尚待用户确认修订的上游文档阻塞；
- 当前工作单元本阶段只有一份 `04` 权威过程文档；
- 主文档能让后续人员一分钟内看懂“改什么、当前状态、还缺什么”。

某个 `Uxx` 的配置阶段完成后可进入它自己的 `05`；不要求无依赖的兄弟工作单元同步完成，也不代表整个功能可以进入 `game-review`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为人工填表另建执行清单 | 人工执行事实仍写入对应配置事项；只有收尾时可生成一份非权威的策划配表说明 |
| 为“发货币”反复追问具体货币 ID 和数量 | 收敛“仅允许货币类 ID + 数量可配 + 校验/消费链路”；最终 ID 和数量留给策划配表 |
| 把所有待配置项都推给策划后续处理 | 只有不影响 Schema、查找/引用、加载、控制流和测试成立条件的最终取值才允许延后；配置契约本身必须先收敛 |
| 把提醒和字段说明揉成一个大表 | 同一交付文档中分成“策划配表提醒”和“功能配表说明”两个独立内容块 |
| 功能配表说明列出整个 Schema | 只列代码实际消费或已确定将直接消费的主体字段及其含义 |
| 同一对象分别写进规划、验证和移交章节 | 在一个连续事项中维护完整当前状态 |
| 简单改值也分析完整配置架构 | 走最小充分路径，只检查受影响链路 |
| 把 `.xml`、`.lua` 一律当配置 | 按职责、加载方式和生成关系分类 |
| Excel 选手动后停止整个任务 | 只暂停 Excel，继续其他已确认配置源 |
| 搜到运行时映射就直接修改 | 记录后续依赖，交给实现阶段 |
| 导表成功就视为全部验证 | 根据变化补引用、输出或加载检查 |
| 修改或验证完成后只在聊天里汇报 | 同一轮更新当前 `04` 并告知路径 |
| 发现上游规则过时后直接改写 | 先说明拟修改内容并获得用户确认 |
| 为 U01/U02 创建子目录 | 所有分支文件留在同一 feature 目录 |
| 兄弟工作单元未完成就阻塞当前配置 | 只检查当前 Uxx 的实际依赖 |
| 父 `04` 拆分后继续建父 `05` | 父标记已拆分，仅叶子后继推进 |
