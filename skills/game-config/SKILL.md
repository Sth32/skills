# 规划并修改游戏配置

## 目标

把当前工作单元的已确认需求转成可执行的配置变更，并持续维护未分支的 `04-配置规划.md`，或当前工作单元的 `04-Uxx-<主题>-配置规划.md`。

**核心边界：本阶段修改配置事实，不实现运行时代码。先判断职责，再决定能否写入；不要按扩展名判断。**

**单文档硬限制：当前工作单元在本阶段只能维护一份配置规划过程文档。** 不得为同一工作单元额外创建配置执行清单、人工填表清单、验证报告、调查记录、差异摘要或其他旁支文档。不同工作单元可拥有各自的 `04` 文档；代码、Excel、XML、生成物和日志属于实际产物或证据，不算过程文档。

**邻接硬限制：同一逻辑配置对象的真实源、关键变化、执行方式、状态、验证结果和后续代码依赖必须放在同一个连续事项内。** 不得按“规划、执行、验证、移交”等维度重复记录同一对象。

**当前真相硬限制：配置执行或沟通完成后必须原位更新事项。** 删除已解决问题、失效步骤、旧状态和不再有用的人工操作说明，不保留执行流水。

**分支工作流硬限制：`01-原始需求.md` 永远只有一份。`01` 完成后到 `game-review` 启动前，若当前配置范围能够独立推进、独立阻塞或独立 review，可拆成稳定工作单元 `U01`、`U02`……；所有文件仍位于同一个 `docs/requirements/<feature>/` 目录，禁止增加分支子目录。没有真实分支时继续使用 `04-配置规划.md`。第一次拆分时创建 `00-工作流索引.md`，只记录工作单元 ID、范围、依赖、当前阶段和当前文档；串行、并行与多前驱只由依赖表达，不把拓扑编码进 ID。分支文档命名为 `04-<Uxx>-<主题>-配置规划.md`。**

在分支工作流中，下述“本阶段唯一文档”指当前工作单元的唯一 `04` 权威文档；`00-工作流索引.md` 只是路由元数据，不复制配置事实、执行状态或验证结果。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

存在 `00` 时，开始或恢复本阶段前必须先解析当前 `Uxx` 的共享上游和直接前驱，只检查实际依赖；未被依赖的兄弟工作单元可以处于其他阶段，不构成阻塞。索引无法唯一确定当前工作单元、依赖或文档时，先修正索引。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。每条新记录必须包含实际 `skill_version`；版本由写入器从当前 skill 根目录 `SKILL.md` 的 `metadata.version` 自动读取，禁止由 Agent 手填、猜测或沿用历史值。写入器无法读取版本、版本格式非法或 `--skill` 与当前 `SKILL.md` 名称不一致时，必须拒绝追加并明确报告；不得写 `unknown` 伪装新记录。历史 schema v1 记录缺少版本时保留原样，查询和统计统一视为 `skill_version=unknown`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill 及其实际版本、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须按 `skill_version` 过滤或分组，不能把版本未知的旧记录或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

创建或修改 `00-工作流索引.md` 同样必须追加记录；普通配置事项变化若不改变拓扑、当前阶段或当前文档，不重复修改索引。

## 输入与产物

未分支时必须读取：

- `01-原始需求.md`、`02-需求挖掘.md`、`03-程序实现澄清.md`；
- 相关配置源、同类配置、导表或生成命令、生成物和消费代码。

存在 `00` 时，先定位当前 `Uxx`，再读取唯一 `01` 与索引声明的当前工作单元实际 `02`/`03` 上游和直接依赖，以及相关配置事实。不得机械要求所有兄弟工作单元的 `02`/`03` 都完成。

未分支唯一过程文档：

```text
docs/requirements/<feature>/04-配置规划.md
```

分支后当前工作单元过程文档：

```text
docs/requirements/<feature>/04-<Uxx>-<主题>-配置规划.md
```

使用 [配置规划模板](references/配置规划模板.md)。用户需要人工填表交接时，把必要操作直接写入当前工作单元对应配置事项，不生成第二份文档。

若配置调查证明当前工作单元实际上包含多个可以独立配置、独立阻塞并独立交给后续代码阶段的范围，可在本阶段继续拆分：更新 `00`、给后继分配新 `Uxx`、把父 `04` 压缩为共同配置基线并标记 `已拆分`，再创建子 `04`。父工作单元不再直接进入 `05`。

## 复杂度门槛

先选择最小充分路径，不要默认审计整个配置系统。

- **简单数据变更**：单一真实源、无 Schema 变化、无多端差异。直接完成分类、确认、修改和必要校验。
- **复杂配置变更**：跨多个物理源、新增字段或类型、多目标输出、生成代码、覆盖层或复杂引用。读取 [复杂配置管线指南](references/复杂配置管线指南.md)。
- **配置与代码边界不清**：读取 [配置源识别指南](references/配置源识别指南.md)。
- **需要设计验证范围**：读取 [配置校验清单](references/配置校验清单.md)。
- **本轮已经误改代码**：立即停止并读取 [误改代码处置](references/误改代码处置.md)。

不要为了展示完整性而读取所有参考文件。

## 最小工作流

### 1. 定位当前工作单元并识别应配置的内容

存在 `00` 时先确认当前 `Uxx`、范围、依赖和当前 `04`；没有则按单线工作。优先配置当前工作单元中策划或运营需要调整的数值、文本、奖励、概率、时间、阈值、开关、映射和分组。

通常保留在代码中：算法、状态机、协议语义、运行时控制流、局部技术参数和不可变业务约束。

### 2. 按逻辑配置对象聚合

一个功能对象可能分布在 Excel、XML、YAML、Schema 和生成物中。先把属于同一业务对象的内容聚合，再列物理源，避免只改其中一处。每个逻辑对象在当前工作单元文档中只出现一次。

如果两个配置对象没有共同决策/执行依赖、可以分别被不同 session 推进，且后续代码也独立，才考虑拆工作单元；仅仅存在两个表或两个文件不构成拆分理由。

### 3. 写入前分类

| 类别 | 本阶段动作 |
|---|---|
| 真实声明式配置源 | 确认后修改并验证 |
| Excel 源 | 询问手动或自动；该选择只影响 Excel |
| 声明式 Schema/字段/校验元数据 | 单独确认后可修改 |
| 可再生生成物 | 不直接修改；修改真实源后重新生成 |
| 运行时代码或生成/加载程序逻辑 | 禁止修改；记录后续实现依赖 |

XML、YAML、JSON、INI、CSV、纯数据 Lua 等都可能是配置；Component、Manager、Handler、`VIEW_MAP` 等即使是文本文件仍属于代码。

### 4. 维护当前工作单元的高密度文档

每个配置事项只写：逻辑对象及真实源/Schema、关键变化、执行方式与当前结果、最小充分验证、后续代码依赖。使用“参照对象 + 变化字段”，不复制完整行、表结构、日志或调查过程。

### 5. 执行允许的配置修改

- 修改真实配置源，不手改生成物；
- Excel 手动时将对应事项标记为待人工，并继续当前工作单元其他已确认配置源；
- Excel 自动时保留格式、公式、数据验证和合并单元格；
- 不为“让配置生效”而顺手修改运行时代码；
- 发现缺少注册、映射、加载分支或业务消费时，写入同一事项的后续代码依赖。

每完成一项实际修改，立即回写当前 `04` 并告知完整路径。

### 6. 做必要而非穷尽的验证

根据实际变化选择语法/解析、类型与唯一性、引用/枚举/范围、导表/生成、目标端输出或加载等最小充分检查。验证结果直接回写对应事项，不另建报告。

### 7. 沟通与执行后原位收敛

每轮完成后更新对应事项状态和结果，删除已解决问题、旧步骤和失效说明。若调查、执行或验证证明唯一 `01` 或当前工作单元实际依赖的 `02`/`03` 需要修订，先更新当前 `04` 的最小阻塞并告知用户，再说明拟修改上游内容并获得确认。

### 8. 更新索引

仅在工作单元创建/拆分/终止、依赖变化、当前阶段或当前文档变化时更新 `00`。当前配置值、人工步骤和验证结果不得复制到索引。

## 完成条件

对当前叶工作单元：

- 需要配置和保留代码的边界清楚；
- 所有候选目标已分类；
- 用户已确认可写范围、Excel 方式及必要 Schema 变化；
- 已确认由 Agent 处理的真实配置源均已修改；
- 必要解析、引用、生成或加载验证已有结果；
- 没有直接修改生成物或运行时代码；
- 待人工操作和后续代码依赖在对应事项内清晰可追踪；
- 无尚待用户确认修订的上游文档阻塞；
- 当前工作单元本阶段只有一份 `04` 权威文档；
- 主文档能让后续人员一分钟内看懂“改什么、当前状态、还缺什么”。

某个 `Uxx` 的配置阶段完成后可进入它自己的 `05`；不要求无依赖的兄弟工作单元同步完成，也不代表整个功能可以进入 `game-review`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为人工填表另建执行清单 | 将必要操作写入当前工作单元对应配置事项 |
| 同一对象分别写进规划、验证和移交章节 | 在一个连续事项中维护完整当前状态 |
| 简单改值也分析完整配置架构 | 走最小充分路径，只检查受影响链路 |
| 把 `.xml`、`.lua` 一律当配置 | 按职责、加载方式和生成关系分类 |
| Excel 选手动后停止整个任务 | 只暂停 Excel，继续其他已确认配置源 |
| 搜到运行时映射就直接修改 | 记录后续依赖，交给实现阶段 |
| 导表成功就视为全部验证 | 根据变化补引用、输出或加载检查 |
| 修改或验证完成后只在聊天里汇报 | 同一轮更新当前 `04` 并告知路径 |
| 发现上游规则过时后直接改写 | 先说明拟修改内容并获得用户确认 |
| 为 U01/U02 创建子目录 | 所有分支文件留在同一 feature 目录 |
| 兄弟工作单元未完成就阻塞当前配置 | 只检查当前 Uxx 的实际依赖 |
| 父 `04` 拆分后继续建父 `05` | 父标记已拆分，仅叶子后继推进 |
