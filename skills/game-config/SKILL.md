# 规划并修改游戏配置

## 目标

识别需求中真正应该配置化的内容，选择现有表或配置文件，完成已确认的配置源修改，并维护简洁的 `04-配置规划.md`。

**核心原则：可以修改配置数据，不能在本阶段实现业务代码。文件是否可改取决于它的职责，不取决于扩展名。**

## 前置条件与产物

必须读取：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- 项目的配置源、导表工具、生成物、加载代码和同类配置。

默认主产物：

```text
docs/requirements/<feature>/04-配置规划.md
```

使用 [配置规划模板](references/配置规划模板.md)。已有文档时原位更新。

只有用户明确要求提供手动填表交接材料时，才额外生成：

```text
docs/requirements/<feature>/04-配置执行清单.md
```

使用 [配置执行清单模板](references/配置执行清单模板.md)。它是执行辅助，不是长期方案文档。

## 主文档长度契约

`04-配置规划.md` 的目标是 **40–80 个非空行**，只保留：

1. 配置结论；
2. 配置对象、目标源和执行方式；
3. 高影响待确认项；
4. 后续代码依赖；
5. 实际修改与验证结果。

超过 80 个非空行时，必须删除重复、合并同类对象，或把执行细节移入可选清单。表格单元格使用短语或 1–2 个短句。

## 什么应该配置化

优先考虑：

- 策划或运营需要调整的数值、文本、奖励、概率、时间、阈值和开关；
- 与已有配置实体自然对应的映射、分组、阶段或规则参数；
- 不同环境、活动、赛季或版本可能变化的值；
- 需要被导表校验、客户端或多个服务共同消费的数据。

通常保留在代码中：

- 算法结构、状态机拓扑、协议语义和不可变业务约束；
- Component、Service、Manager、Handler 等运行时行为；
- 业务注册、同步、结算、校验和调用链；
- 局部实现常量、缓存键和技术参数。

判断依据是变化责任和生命周期，不是“它是不是数字”或“它是不是文本文件”。

## 写入前分类门槛

在修改任何文件之前，必须把每个候选目标分类。未完成分类时不得写入。

### A. 声明式配置源：本阶段可修改

同时满足以下特征时，才视为配置源：

- 项目把它作为配置事实来源，而不是业务实现；
- 内容以数据声明为主，没有业务控制流；
- 由通用加载器、导表器或配置系统消费；
- 修改条目只是改变数据，不是在新增程序行为；
- 它不是其他源文件生成的可再生产物。

常见形式包括：

- Excel、CSV；
- XML、YAML、JSON、INI、TOML；
- 文本 DSL；
- 项目明确作为纯数据表使用的 Lua、Python 或 JavaScript 文件。

例如 XML 中声明建筑类型、资源映射、开关或白名单，且由通用配置加载器读取，可以作为配置源修改。

### B. 生成物：本阶段不得直接修改

例如：

- Excel 导出的 Lua、JSON、XML；
- Schema 生成的代码常量；
- 客户端或服务端的可再生数据文件。

应修改真实源并重新生成。生成物即使是 XML、JSON 或 Lua，也不是可直接修改的配置源。

### C. 运行时代码：本阶段禁止修改

包括但不限于：

- Component、Service、Manager、Handler、Controller；
- 协议处理、状态机、业务校验、同步和结算逻辑；
- 运行时代码中的注册表、映射表、白名单或 `VIEW_MAP`；
- 为使新配置生效而增加的分支、方法、枚举处理或调用链；
- 测试代码、迁移程序和运维脚本中的业务实现。

即使文件扩展名是 `.lua`、`.py`、`.js`、`.xml`，只要修改会直接改变程序执行逻辑，就属于代码，不能在 `game-config` 中修改。

### D. 配置 Schema 和导表元数据：必须单独确认

纯声明式字段定义、类型元数据或校验规则，在用户单独确认后可以修改。

以下内容属于后续代码实现：

- 导表器、生成器或加载器的程序逻辑；
- 新增解析分支；
- 新增运行时类型处理；
- 修改业务消费代码。

### 无法确定时

无法可靠判断某个 Lua/XML/Python 文件是配置还是代码时：

1. 先查看其加载方式和同类文件；
2. 检查是否存在函数、条件、循环、调用或副作用；
3. 检查它是否由生成工具覆盖；
4. 仍不确定时默认不写，标为“类别待确认”。

不得为了快速完成而把模糊目标当作配置修改。

## 代码修改禁令

`game-config` 可以搜索和阅读代码，以确认：

- 配置消费端；
- 现有注册和映射约定；
- 配置生效还缺少什么实现；
- 后续验证入口。

但不得为了“让配置立即生效”而修改运行时代码。

发现配置依赖代码改动时：

1. 停止对该代码路径的写入；
2. 在 `04-配置规划.md` 的“后续实现依赖”中记录；
3. 写清代码路径或符号、缺少的行为、关联配置和风险；
4. 标明交给 `game-scaffold` 还是 `game-implement`；
5. 将配置状态标记为“配置已准备，待代码接入”或“待后续实现验证”；
6. 不得宣称功能已经生效或配置闭环完成。

示例：Excel 权限表新增了 `huiMengTan` 与建筑类型，但服务端 `AllyOrgViewHostComp.VIEW_MAP` 缺少对应登记。正确处理是记录该代码依赖并交给 `game-scaffold`，不是在本阶段修改 Component。

## 误改代码的处置

如果本轮已经误改运行时代码：

1. 立即停止继续实现；
2. 检查 diff，区分本轮 Agent 改动和用户原有改动；
3. 只有在改动完全由本轮产生、范围明确且可安全隔离时，才能回退；
4. 不得回退用户已有改动、其他任务改动或归属不明的混合 diff；
5. 无法安全回退时，列出文件、符号和 diff，明确请求用户处理；
6. 不得把半实现代码作为 `game-config` 的交付结果；
7. 将真正需要的代码工作记录为后续实现依赖。

## 混合配置执行契约

一个需求可能同时涉及 Excel 与 XML、YAML、JSON、Lua 数据表等配置源。执行方式必须按配置源分别确认和跟踪，不能设置覆盖全部文件的全局“手动/自动”状态。

必须遵守：

1. 用户选择“Excel 手动配置”，只表示 Agent 不直接修改 Excel；
2. 该选择不撤销其他已确认配置源的修改范围；
3. 非 Excel 配置源尚未确认时，单独请求确认；
4. 已确认的 XML/YAML/JSON 等配置源必须继续修改并验证；
5. 运行时代码无论是否为文本格式，都只记录依赖，不在本阶段修改；
6. 仍有已确认配置源处于“待配置”时，不得宣布完成；
7. 只有用户明确排除、撤销或只要求方案时，才可以不修改已确认配置源，并记录原因。

## 工作流程

### 1. 调查配置链路

确认真实配置源、生成物、加载方式、同类对象、主键、引用、导表和消费端。调查用于做决定，不把系统全貌倾倒进主文档。

### 2. 提取并筛选候选

分为：

- **必须配置**：维护责任、变化频率或跨端消费要求配置化；
- **建议配置**：有现实调整价值，但首版可固定；
- **保留代码**：配置收益低于复杂度和误配风险。

“保留代码”只列影响后续实现边界的少数事项，默认不超过 3 条。

### 3. 建立目标分类与执行矩阵

至少检查：

- Excel/CSV；
- XML、YAML、JSON、INI、TOML、文本 DSL；
- 纯数据 Lua/Python/JavaScript；
- 生成物；
- Schema 与导表元数据；
- 运行时代码依赖；
- 客户端与服务端是否存在不同源。

每个目标记录：

- 路径、Sheet 或表；
- 类别；
- 格式；
- 修改对象；
- 执行方式；
- 当前状态；
- 验证结果。

状态可用：`待确认`、`直接修改`、`Excel 手动`、`Excel 自动`、`生成物不直改`、`后续代码`、`明确不改`、`已完成`。

### 4. 选择目标表或文件

优先复用同领域、同行粒度、同生命周期和同维护者的现有配置源。

只有以下情况才考虑新表或 Schema：

- 行粒度或主键明显不同；
- 需要独立发布、复用、校验、版本或迁移；
- 放入现有表会造成大量空字段、重复行或跨域依赖；
- 现有表会因此承担第二种职责。

新表、Schema 或导表结构变化必须单独确认。

### 5. 按差异写规划

配置清单默认一行对应一个目标文件、Sheet、表或配置实体，而不是一个字段。

每行只写：

- 新增或修改什么；
- 关键字段和值；
- 参照对象或关键引用；
- 类别、执行方式和状态；
- 阻塞执行的事项。

使用“参照对象 + 变化字段”，不复制完整行定义。

### 6. 分别确认修改范围

一次性展示所有候选目标及其分类：

- **声明式配置源**：确认范围后直接修改并验证；
- **Excel**：询问手动或自动；
- **Schema/导表元数据**：单独确认；
- **运行时代码**：不请求本阶段修改，只记录后续依赖；
- **生成物**：不直接修改。

用户未确认某个配置源时，只暂停该源，其他已确认源继续执行。

### 7. 修改并验证

按执行矩阵逐项处理：

1. 修改所有已确认的真实配置源；
2. 自动 Excel 才修改 Excel，手动 Excel 标记待人工；
3. 不修改运行时代码和生成物；
4. 运行导表、格式检查、Schema 校验或配置加载；
5. 检查类型、主键、引用、枚举、范围和生成物 diff；
6. 记录配置是否仍需代码接入；
7. 将结果压缩回写主文档。

验证部分默认不超过 5 条，只写执行项、结果、失败原因和剩余风险。完整日志保留原位置并提供路径。

## 完成前检查

交付前逐项检查：

- 是否对每个候选文件完成了职责分类；
- 是否错误地按扩展名判断配置与代码；
- 是否把 XML/YAML/JSON 等真实配置源遗漏了；
- 是否修改了 Component、Manager、`VIEW_MAP` 等运行时代码；
- 是否仍有本轮产生的半实现代码未处理；
- Excel 手动是否错误地导致其他配置源被跳过；
- 是否仍有已确认配置源停留在“待配置”；
- 是否把代码依赖记录并移交给后续阶段；
- 是否能在一分钟内看出要改哪些配置、还缺哪些实现。

任一答案不理想，先修正再交付。

## 完成条件

- 配置候选都有配置化、保留代码或后续实现的明确结论；
- 每个目标都已分类为配置源、生成物、Schema 元数据或运行时代码；
- 目标表、文件和关键差异清楚；
- 用户已确认配置源修改范围和 Excel 手动/自动方式；
- 所有已确认由 Agent 修改的配置源均已完成并通过必要验证；
- 运行时代码未在本阶段修改；
- 代码依赖已记录并分派给 `game-scaffold` 或 `game-implement`；
- 手动 Excel 和待代码接入状态没有被伪装为全部完成；
- 主文档足以作为 `game-scaffold` 的配置契约。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把所有 `.lua`、`.xml` 当作配置 | 按职责、加载方式和是否包含运行逻辑分类 |
| 为使配置生效直接修改 `VIEW_MAP` | 记录后续实现依赖，交给 `game-scaffold` |
| 把导出的 JSON/XML 当作源文件修改 | 修改真实源并重新生成 |
| 用户选 Excel 手动后停止整个任务 | 只暂停 Excel，继续完成其他已确认配置源 |
| 已确认 XML 配置但只写方案不落地 | 修改真实 XML 源并执行解析或加载校验 |
| 误改代码后继续补齐功能 | 停止、隔离并安全回退本轮代码改动，记录后续任务 |
| 把配置规划写成完整填表教程 | 主文档只写关键差异，执行清单按需独立生成 |
| 未确认就自动修改 Excel | 必须让用户选择手动或自动 |
