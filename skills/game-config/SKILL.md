# 规划并修改游戏配置

## 目标

识别需求中真正应该配置化的内容，选择现有表或新表，并维护简洁的 `04-配置规划.md`。

**核心原则：主文档是配置决策摘要，不是逐字段填表说明书。只记录变化和关键决策，不复制已有表结构。**

## 前置条件与产物

必须读取：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- 项目的配置源、导表工具、生成物、加载代码和同类配置。

默认主产物：

```text
docs/requirements/<feature>/04-配置规划.md
```

使用 [配置规划模板](references/配置规划模板.md)。已有文档时原位更新。

只有用户明确要求提供手动填表交接材料时，才额外生成：

```text
docs/requirements/<feature>/04-配置执行清单.md
```

使用 [配置执行清单模板](references/配置执行清单模板.md)。它是执行辅助，不是长期方案文档。

## 主文档长度契约

`04-配置规划.md` 的目标是 **40–80 个非空行**，并且只保留四类信息：

1. 配置结论；
2. 配置对象与目标表；
3. 需要用户或负责人确认的高影响事项；
4. 实际修改与验证结果。

超过 80 个非空行时，必须删除重复、合并同类对象，或把执行细节移入可选清单。只有新增复杂表结构时才允许例外，并需说明超长原因。复杂不等于可以写成字段百科。

表格单元格使用短语或 1–2 个短句，不在一个单元格中堆放完整行定义。

## 什么应该配置化

优先考虑：

- 策划或运营需要调整的数值、文本、奖励、概率、时间、阈值和开关；
- 与已有配置实体自然对应的映射、分组、阶段或规则参数；
- 不同环境、活动、赛季或版本可能变化的值；
- 需要被导表校验、客户端或多个服务共同消费的数据。

通常保留在代码中：

- 算法结构、状态机拓扑、协议语义和不可变业务约束；
- 局部实现常量、运行时值、缓存键和技术参数；
- 没有明确维护者、无法安全调整或配置后更难理解的内容。

判断依据是变化责任和生命周期，不是“它是不是数字”。

## 信息优先级

### 必须写入主文档

- 哪些内容需要配置，哪些关键内容保留代码；
- 目标文件、Sheet 或表，以及复用还是新建；
- 新增或修改的配置对象；
- 来自需求的关键数值、标识和跨表引用；
- 会改变表结构、消费端或发布范围的决定；
- 当前真正阻塞配表的未决项；
- 修改方式、实际结果和验证结论。

### 仅在影响决策时写入

- 主键和行粒度；
- 单位、空值和默认值语义；
- 导表、热更、客户端同步和迁移影响；
- 复用现有表的理由；
- 保留代码的高影响边界。

### 禁止写入主文档

- 从参照行复制而来、此次不需要改动的全部字段；
- 每个单元格的填写步骤；
- 项目已有且本次没有变化的完整导表链路；
- 所有默认值、展示字段、图标字段和普通布尔字段的穷举；
- 同一事实同时出现在摘要、明细、范围和结果四处；
- 与配置无关的完整代码任务清单；
- 长篇调查过程、命令输出和验证日志。

需要这些信息时，引用参照行、代码路径、diff 或日志位置，不把内容复制进主文档。

## 工作流程

### 1. 调查但不倾倒调查结果

确认配置源格式、真实源文件、同类表、主键、引用、导表方式、生成物和消费端。

调查用于做决定。除非它改变配置方案，否则不要把配置系统全貌写进 `04-配置规划.md`。不要直接修改可再生生成物。

### 2. 提取并筛选配置候选

将候选分为：

- **必须配置**：维护责任、变化频率或跨端消费要求配置化；
- **建议配置**：有现实调整价值，但首版可固定；
- **保留代码**：配置收益低于复杂度和误配风险。

“保留代码”只列会影响后续实现边界的少数事项，默认不超过 3 条。不要把所有非配置规则重新抄一遍。

### 3. 选择目标表

优先复用同领域、同行粒度、同生命周期和同维护者的现有表。

只有出现以下情况才考虑新表或 Schema：

- 行粒度或主键明显不同；
- 需要独立发布、复用、校验、版本或迁移；
- 放入现有表会造成大量空字段、重复行或跨域依赖；
- 现有表会因此承担第二种职责。

新表或导表结构变化必须单独确认。

### 4. 按“差异”写配置规划

配置清单默认 **一行对应一个目标表、Sheet 或配置实体**，而不是一行对应一个字段。

每行只写：

- 要新增或修改什么；
- 关键字段和值；
- 关键引用或参照对象；
- 尚未确定且会阻塞执行的事项。

可使用这样的表达：

> 复制望楼 1046 的两行结构，新建会盟坛 1050；仅调整 ID、元素引用、名称、消耗、耗时和耐久，其余字段沿用参照行。

不要把参照行的全部字段再次列出。需求已明确的数值直接写，项目默认值只在它影响产品或安全时写。

### 5. 确认直接修改范围

一次性展示计划修改的源文件、Sheet/表、配置对象和是否涉及新表或导表规则。

按源格式处理：

- **文本配置**：范围确认后可直接修改，精确 diff 是执行细节的主要载体，主文档只记录摘要；
- **Excel 配置**：必须询问用户选择“手动配置”还是“自动配置”；
  - 手动：主文档仍保持简洁。只有用户明确要求交接清单时，才生成 `04-配置执行清单.md`，且只列需要改动的字段；
  - 自动：先备份并保留格式、公式、验证和合并单元格，完成后给出紧凑变更摘要，不把单元格流水账写回主文档；
- **新增表或修改导表结构**：必须单独确认。

用户未确认时，不修改配置源。

### 6. 修改并验证

在已确认范围内：

1. 修改真实配置源；
2. 运行项目标准导表；
3. 检查类型、主键、引用、枚举、范围和生成物 diff；
4. 验证服务器或消费端能够加载；
5. 将结果压缩回写主文档。

验证部分默认不超过 5 条，只写“执行了什么、是否通过、失败原因、剩余风险”。完整日志保留在原位置并提供路径。

## 完成前压缩检查

交付前逐项检查：

- 能否在一分钟内看出要改哪些表、关键值是什么、还缺什么决定；
- 是否一行字段可以改写为“参照对象 + 变化字段”；
- 是否重复解释了导表链路、手动方式或已确认状态；
- 是否列出了不变字段或完整行定义；
- 是否把真正的 P0/P1 未决项埋在文末；
- 是否可以删除一半文字而不损失配置决策。

任一答案不理想，先压缩再交付。

## 完成条件

- 关键需求配置项都有配置化或保留代码的结论；
- 目标表与关键差异清楚，不依赖字段百科才能理解；
- 未决项按影响排序且不会被细节淹没；
- 用户已确认修改范围及 Excel 手动/自动方式；
- 已执行修改通过必要的导表和加载验证；
- 主文档足以作为 `game-scaffold` 的配置契约。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把配置规划写成完整填表教程 | 主文档只写关键差异；手工教程按需放独立清单 |
| 抄出参照行所有字段 | 引用参照行，只列需要改变的字段 |
| 每个字段占一行 | 默认按目标表、Sheet 或配置实体聚合 |
| 重复记录导表链路和确认状态 | 每项事实只保留一个权威位置 |
| 未决项放在几十页细节后 | P0/P1 直接进入摘要或确认区 |
| 未确认就自动修改 Excel | 必须让用户选择手动或自动 |
| 手改导出生成物 | 修改真实配置源并重新导表 |
