# 规划并修改游戏配置

## 目标

把已确认需求转为可执行的配置变更：先识别**逻辑配置对象**，再追踪它从真实数据源到 Schema、校验、生成物、输出目标和运行时消费端的受影响链路，完成本阶段允许的配置修改，并维护简洁的 `04-配置规划.md`。

**核心原则：配置阶段处理配置事实，不实现运行时代码；按逻辑配置对象组织工作，不按文件扩展名或单个物理文件组织。**

## 前置条件与产物

必须读取：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- 项目的配置源、Schema 或定义、校验器、导表/生成命令、生成物、加载代码和同类配置。

默认主产物：

```text
docs/requirements/<feature>/04-配置规划.md
```

使用 [配置规划模板](references/配置规划模板.md)。已有文档时原位更新。

只有用户明确要求提供手动填表交接材料时，才额外生成：

```text
docs/requirements/<feature>/04-配置执行清单.md
```

使用 [配置执行清单模板](references/配置执行清单模板.md)。它是执行辅助，不是长期方案文档。

## 主文档长度契约

`04-配置规划.md` 的目标是 **40–80 个非空行**，只保留：

1. 配置结论；
2. 逻辑配置对象及其关键管线；
3. 高影响待确认项；
4. 后续代码依赖；
5. 实际修改与验证结论。

超过 80 个非空行时，必须删除重复、合并同类对象或把执行细节移入可选清单。表格单元格使用短语或 1–2 个短句。

## 核心工作模型

### 逻辑配置对象

逻辑配置对象是一个具有稳定业务职责、维护者和生命周期的配置实体，例如“同盟设施权限”“建筑定义”“技能效果”“活动奖励组”。

必须遵守：

- 一个逻辑对象可以来自多个 Excel Sheet、XML、JSON 或其他源；
- 一个物理文件可以承载多个逻辑对象；
- 不把“一个文件”默认等同于“一个配置对象”；
- 主文档默认一行对应一个逻辑配置对象，而不是一个字段或一个物理文件；
- 只有执行方式、负责人或发布路径不同时，才把同一逻辑对象拆成多行。

### 通用配置管线

对每个受影响对象，只追踪本次实际涉及的阶段：

```text
Schema / 定义（可选）
  → 真实数据源
  → 校验
  → 数据生成（可选）
  → 类型或访问代码生成（可选）
  → 输出目标
  → 运行时消费端
```

项目不一定拥有全部阶段。不得为了套模型而虚构不存在的 Schema、代码生成或多目标输出。

配置规划应回答：

- 配置事实的真实来源在哪里；
- 本次改变哪一层；
- 哪些生成物会变化；
- 哪些客户端、服务端或工具目标会收到结果；
- 哪些运行时消费端仍需要代码接线；
- 用什么证据证明配置链路成立。

## 什么应该配置化

优先考虑：

- 策划或运营需要调整的数值、文本、奖励、概率、时间、阈值和开关；
- 与已有配置实体自然对应的映射、分组、阶段或规则参数；
- 不同环境、活动、赛季或版本可能变化的值；
- 需要被统一校验、客户端或多个服务共同消费的数据。

通常保留在代码中：

- 算法结构、状态机拓扑、协议语义和不可变业务约束；
- Component、Service、Manager、Handler 等运行时行为；
- 业务注册、同步、结算、校验和调用链；
- 局部实现常量、缓存键和技术参数。

判断依据是变化责任、生命周期和表达形态，不是“它是不是数字”或“它是不是文本文件”。

## 写入前双重分类门槛

修改任何文件前，必须同时确定它的**职责类别**和本次的**变更层级**。任一项不明确时不得写入。

### 职责类别

#### A. 声明式配置源：本阶段可修改

同时满足以下特征时，才视为配置源：

- 项目把它作为配置事实来源，而不是业务实现；
- 内容以数据声明为主，没有业务控制流；
- 由通用加载器、导表器或配置系统消费；
- 修改条目只是改变数据，不是在新增程序行为；
- 它不是其他源文件生成的可再生产物。

常见形式包括 Excel、CSV、XML、YAML、JSON、INI、TOML、文本 DSL，以及项目明确作为纯数据表使用的 Lua、Python 或 JavaScript 文件。

#### B. 生成物：本阶段不得直接修改

包括 Excel 导出的 Lua/JSON/XML、Schema 生成的类型代码、客户端或服务端的可再生数据文件。应修改真实源并重新生成。

#### C. 配置 Schema 或声明式元数据：单独确认

包括字段、类型、索引、引用、范围、输出范围和校验声明。用户单独确认后可以修改；导表器、生成器或加载器的程序逻辑仍属于后续代码。

#### D. 运行时代码：本阶段禁止修改

包括 Component、Service、Manager、Handler、Controller、协议处理、状态机、业务校验、同步、结算、运行时注册表、`VIEW_MAP`、测试业务逻辑和迁移程序。

即使扩展名是 `.lua`、`.py`、`.js` 或 `.xml`，只要修改会直接改变程序执行逻辑，就属于代码。

### 变更层级

对每个逻辑对象标记：

- **数据变更**：新增或修改记录、值、映射、文本、资源引用；本阶段可执行；
- **Schema 变更**：新增字段、类型、索引、约束或输出范围；单独确认后执行声明部分；
- **生成管线变更**：修改解析器、生成器、模板或加载逻辑；只记录并移交后续实现；
- **运行时代码变更**：修改注册、同步、结算、业务规则或调用链；只记录并移交后续实现。

同一个 XML 文件可能承载数据，也可能承载 Schema；同一个 Lua 文件可能是纯数据，也可能是运行时代码。必须根据职责和改动效果判断。

### 无法确定时

1. 查看加载方式和同类文件；
2. 检查是否存在函数、条件、循环、调用或副作用；
3. 检查是否会被生成工具覆盖；
4. 仍不确定时默认不写，标为“类别待确认”。

## 配置表达形态

选择现有表、新表或其他配置源时，先判断数据形态和维护方式：

- 大量同构记录、需要批量编辑：优先现有表格体系；
- 单例或少量全局参数：优先现有单例配置或结构化数据源；
- 深层嵌套、异构节点、多态效果：优先项目已有的结构化文件、DSL 或专用编辑器；
- 简单开关、白名单、环境差异：优先项目已有轻量配置源；
- 已有成熟同类对象：优先复用其配置模型和管线。

不要因为项目大量使用 Excel 就把所有复杂结构强行平铺到 Excel，也不要为简单数值无理由引入新格式。

## 输出目标与消费范围

若项目存在客户端、服务端、编辑器、运营工具或不同平台输出，必须确认：

- 哪些目标需要该逻辑配置对象；
- 是否存在表级或字段级输出过滤；
- 服务端专属、内部结算或敏感数据是否会误导出到客户端；
- 各目标的数据格式、版本和加载入口是否一致；
- 某个目标不需要变化时，生成物 diff 是否保持稳定。

项目只有单一输出时，只记录该目标，不人为增加分组设计。

## 校验覆盖契约

对每个逻辑配置对象选择相关校验，不要求机械执行全部类别：

1. 语法、解析和编码；
2. 类型、必填、默认值与空值语义；
3. 主键、联合键、索引和唯一性；
4. 跨表、跨文件或资源引用；
5. 范围、枚举、集合和概率约束；
6. 资源路径或外部对象存在性；
7. 列表对齐、基数、跨记录不变量；
8. 目标生成、加载和消费端可读性。

优先运行项目已有校验器。需要新增声明式校验规则时单独确认；只能通过业务代码验证的规则记录给 `game-scaffold` 或 `game-implement`，不要在本阶段临时编写业务代码。

## 生成契约

先区分：

- **数据生成**：从源数据产生运行时数据文件；
- **类型或访问代码生成**：从 Schema 产生类型、常量或访问代码。

必须遵守：

- 仅改数据时，不默认重新生成类型代码，按项目标准流程执行；
- 改 Schema 时，检查是否同时需要数据生成和代码生成；
- 不直接修改任何可再生生成物；
- 生成后检查 diff，只允许预期对象和目标发生变化；
- 多输出目标时分别检查客户端、服务端或工具产物；
- 生成器确定性强且执行成本可接受时，可在无输入变化下再次生成，确认第二次不产生新 diff；不满足条件时记录未执行原因。

## 代码修改禁令与交接

`game-config` 可以搜索和阅读代码，以确认消费端、注册约定、输出范围和验证入口，但不得为了“让配置立即生效”而修改运行时代码。

发现代码依赖时：

1. 停止对代码路径写入；
2. 在 `04-配置规划.md` 的“后续实现依赖”中记录；
3. 写清逻辑配置对象、代码路径或符号、缺少行为和风险；
4. 标明交给 `game-scaffold` 还是 `game-implement`；
5. 将对象状态标记为“配置已准备，待代码接入”或“待后续实现验证”；
6. 不宣称功能已经生效或配置闭环完成。

例如权限数据已增加新设施，但服务端 `VIEW_MAP` 缺少运行时登记：应记录为框架接线并交给 `game-scaffold`，不是在本阶段修改 Component。

## 误改代码的处置

如果本轮已经误改运行时代码：

1. 立即停止继续实现；
2. 区分本轮 Agent 改动和用户原有改动；
3. 只有本轮改动范围明确且可安全隔离时才回退；
4. 不得回退用户已有改动或归属不明的混合 diff；
5. 无法安全回退时列出精确 diff 请求用户处理；
6. 不得把半实现代码作为配置阶段交付；
7. 将真正需要的代码工作记录为后续实现依赖。

## 混合配置执行契约

执行方式按真实配置源分别确认和跟踪，不能设置覆盖全部文件的全局“手动/自动”状态。

- 用户选择“Excel 手动”，只表示 Agent 不直接修改 Excel；
- 该选择不撤销其他已确认配置源的范围；
- 已确认的 XML/YAML/JSON 等配置源必须继续修改并验证；
- Schema 变更必须单独确认；
- 运行时代码始终只记录依赖；
- 仍有已确认配置源处于“待配置”时，不得宣布完成；
- 只有用户明确排除、撤销或只要求方案时，才可以不修改已确认配置源。

## 工作流程

### 1. 建立逻辑对象与受影响管线

从需求规则出发识别逻辑配置对象，调查其真实源、Schema、校验、生成物、输出目标和运行时消费端。只追踪本次受影响的链路。

### 2. 筛选配置候选

将候选分为必须配置、建议配置、保留代码。保留代码只列影响后续实现边界的少数事项，默认不超过 3 条。

### 3. 建立对象执行矩阵

每个对象记录：

- 业务职责；
- 变更层级；
- 真实源与 Schema；
- 关键差异；
- 输出目标与消费端；
- 校验覆盖；
- 执行方式与状态；
- 后续代码依赖。

### 4. 选择现有对象或新结构

优先复用同领域、同行粒度、同生命周期、同维护者和同输出目标的现有配置模型。

只有行粒度、结构形态、发布周期、复用方式、校验或输出目标显著不同，且放入现有模型会造成大量空字段、重复行或跨域依赖时，才考虑新表、Schema 或配置源。

新表、Schema 或输出范围变化必须单独确认。

### 5. 按逻辑对象写简洁规划

主表默认一行对应一个逻辑配置对象，只写：

- 变更层级；
- 真实源或 Schema；
- 关键差异；
- 输出目标或关键消费端；
- 执行方式和状态。

使用“参照对象 + 变化字段”，不复制完整行定义、完整管线调查或所有生成物路径。

### 6. 分别确认修改范围

一次性展示各逻辑对象、真实源、变更层级和建议执行方式：

- 声明式配置数据：确认范围后修改并验证；
- Excel：询问手动或自动；
- Schema/输出范围：单独确认；
- 生成管线与运行时代码：只记录后续依赖；
- 生成物：不直接修改。

用户未确认某个源时，只暂停该源，其他已确认源继续执行。

### 7. 修改、生成并验证

1. 修改所有已确认的真实配置源；
2. 自动 Excel 才修改 Excel，手动 Excel 标记待人工；
3. 按需修改已单独确认的声明式 Schema；
4. 不修改生成管线程序、运行时代码和生成物；
5. 运行语法、Schema、引用、范围、资源和业务不变量中的相关校验；
6. 分别执行需要的数据生成与代码生成；
7. 检查各输出目标 diff 和加载结果；
8. 条件允许时执行可重复生成检查；
9. 记录仍需代码接入的对象；
10. 将结果压缩回写主文档。

## 完成前检查

交付前逐项检查：

- 是否以逻辑对象而不是文件列表组织结果；
- 是否识别一个对象的全部相关真实源；
- 是否区分数据、Schema、生成管线和运行时代码变更；
- 是否确认真实源，避免直接修改生成物；
- 是否检查输出目标和敏感数据暴露；
- 是否覆盖相关的键、引用、范围、资源和跨记录校验；
- 是否区分数据生成和代码生成；
- 是否错误修改 Component、`VIEW_MAP` 或生成器逻辑；
- Excel 手动是否错误导致其他配置源被跳过；
- 是否仍有已确认配置源处于待配置；
- 是否将代码依赖完整移交后续阶段；
- 是否能在一分钟内看出要改什么、输出到哪里、如何验证、还缺什么。

任一答案不理想，先修正再交付。

## 完成条件

- 需求配置候选都有配置化、保留代码或后续实现结论；
- 每个逻辑对象的受影响管线和真实源清楚；
- 每个变更已分类为数据、Schema、生成管线或运行时代码；
- 用户已确认配置源、Schema 和 Excel 执行方式；
- 已确认配置源完成修改并通过相关校验；
- 数据生成、代码生成和输出目标按实际需要执行；
- 生成物未被直接修改，生成 diff 仅包含预期变化；
- 运行时代码未在本阶段修改；
- 代码依赖已分派给 `game-scaffold` 或 `game-implement`；
- 手动 Excel 和待代码接入没有被伪装为全部完成；
- 主文档足以作为后续实现的配置契约。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把一个文件当作一个完整配置对象 | 从业务职责识别逻辑对象，再映射到多个物理源 |
| 只修改主要 Excel，遗漏 XML 或覆盖数据 | 沿逻辑对象追踪全部真实源和覆盖层 |
| 把所有 `.lua`、`.xml` 当作配置 | 按职责、加载方式和改动效果分类 |
| 把导出的 JSON/XML 当作源文件修改 | 找到真实源并重新生成 |
| 只改数据却无必要地重生成所有类型代码 | 区分数据生成和代码生成 |
| Schema 已变化却只生成数据 | 同时检查类型代码、校验和各输出目标 |
| 服务端专属字段被导出到客户端 | 检查输出目标和字段可见范围 |
| 只做语法校验 | 按对象选择键、引用、范围、资源和跨记录校验 |
| 复杂异构结构仍强行平铺到 Excel | 评估数据形态和项目已有结构化工具 |
| 为使配置生效直接修改 `VIEW_MAP` | 记录后续实现依赖并交给 `game-scaffold` |
| 用户选 Excel 手动后停止整个任务 | 只暂停 Excel，继续其他已确认配置源 |
| 把配置规划写成完整填表教程 | 主文档只写对象、关键差异、输出和验证 |
