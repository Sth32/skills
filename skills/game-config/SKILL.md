# 规划并修改游戏配置

## 目标

把已确认需求转成可执行的配置变更，并持续维护唯一的阶段文档 `04-配置规划.md`。

**核心边界：本阶段修改配置事实，不实现运行时代码。先判断职责，再决定能否写入；不要按扩展名判断。**

**单文档硬限制：本阶段只能维护 `04-配置规划.md` 一份过程文档。** 不得额外创建配置执行清单、人工填表清单、验证报告、调查记录、差异摘要或其他旁支文档。代码、Excel、XML、生成物和日志属于实际产物或证据，不算过程文档。

**邻接硬限制：同一逻辑配置对象的真实源、关键变化、执行方式、状态、验证结果和后续代码依赖必须放在同一个连续事项内。** 不得按“规划、执行、验证、移交”等维度重复记录同一对象。

**当前真相硬限制：配置执行或沟通完成后必须原位更新事项。** 删除已解决问题、失效步骤、旧状态和不再有用的人工操作说明，不保留执行流水。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入只能使用单次 append，禁止为了记录而读取、重写或总结历史全文。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 输入与产物

必须读取：

- `01-原始需求.md`、`02-需求挖掘.md`、`03-程序实现澄清.md`；
- 相关配置源、同类配置、导表或生成命令、生成物和消费代码。

唯一过程文档：

```text
docs/requirements/<feature>/04-配置规划.md
```

使用 [配置规划模板](references/配置规划模板.md)。用户需要人工填表交接时，把必要操作直接写入对应配置事项，不生成第二份文档。

## 复杂度门槛

先选择最小充分路径，不要默认审计整个配置系统。

- **简单数据变更**：单一真实源、无 Schema 变化、无多端差异。直接完成分类、确认、修改和必要校验。
- **复杂配置变更**：跨多个物理源、新增字段或类型、多目标输出、生成代码、覆盖层或复杂引用。读取 [复杂配置管线指南](references/复杂配置管线指南.md)。
- **配置与代码边界不清**：读取 [配置源识别指南](references/配置源识别指南.md)。
- **需要设计验证范围**：读取 [配置校验清单](references/配置校验清单.md)。
- **本轮已经误改代码**：立即停止并读取 [误改代码处置](references/误改代码处置.md)。

不要为了展示完整性而读取所有参考文件。

## 最小工作流

### 1. 识别应配置的内容

优先配置策划或运营需要调整的数值、文本、奖励、概率、时间、阈值、开关、映射和分组。

通常保留在代码中：算法、状态机、协议语义、运行时控制流、局部技术参数和不可变业务约束。

### 2. 按逻辑配置对象聚合

一个功能对象可能分布在 Excel、XML、YAML、Schema 和生成物中。先把属于同一业务对象的内容聚合，再列物理源，避免只改其中一处。

每个逻辑对象在文档中只出现一次。它的来源、变化、执行、验证和依赖都写在该事项附近。

### 3. 写入前分类

每个候选目标必须分类：

| 类别 | 本阶段动作 |
|---|---|
| 真实声明式配置源 | 确认后修改并验证 |
| Excel 源 | 询问手动或自动；该选择只影响 Excel |
| 声明式 Schema/字段/校验元数据 | 单独确认后可修改 |
| 可再生生成物 | 不直接修改；修改真实源后重新生成 |
| 运行时代码或生成/加载程序逻辑 | 禁止修改；记录后续实现依赖 |

XML、YAML、JSON、INI、CSV、纯数据 Lua 等都可能是配置；Component、Manager、Handler、`VIEW_MAP` 等即使是文本文件仍属于代码。

无法判断时，先检查加载方式、是否含控制流、是否由工具生成；仍不确定则不写并标记待确认。

### 4. 维护单一高密度文档

`04-配置规划.md` 不设行数目标，不为显得完整而增加章节。每个配置事项只写：

- 逻辑对象及真实源或 Schema；
- 相对现有配置的关键变化；
- 自动、人工或待确认的执行方式与当前状态；
- 已执行的最小充分验证及结果；
- 尚需后续代码接入的行为或入口。

使用“参照对象 + 变化字段”，不复制完整行、完整表结构、生成日志或调查过程。

人工填表时，在对应事项内写清 Sheet、定位方式、需改字段和校验方式；不得复制到独立执行清单。

### 5. 执行允许的配置修改

- 修改真实配置源，不手改生成物；
- Excel 手动时将对应事项标记为待人工，并继续完成其他已确认配置源；
- Excel 自动时保留格式、公式、数据验证和合并单元格；
- 不为“让配置生效”而顺手修改运行时代码；
- 发现缺少注册、映射、加载分支或业务消费时，写入同一事项的后续代码依赖。

每完成一项实际修改，立即回写该事项并在回复中明确告知 `04-配置规划.md` 已更新，不等待整个配置批次结束。

### 6. 做必要而非穷尽的验证

根据实际变化选择最小充分检查：

- 语法或解析；
- 类型、必填、主键和唯一性；
- 引用、范围、枚举、概率或资源路径；
- 导表/生成及生成物 diff；
- 目标端输出和配置加载。

验证结果直接回写对应配置事项，不另建验证章节或报告。完整日志和 diff 留在仓库或工具输出中。

每获得一项验证结果，立即更新对应事项并告知用户文档路径；不得积攒到最终总结时才写入。

### 7. 沟通与执行后原位收敛

每轮完成后：

1. 更新对应事项的状态和结果；
2. 删除已解决的待确认内容和失效操作步骤；
3. 人工步骤执行完后压缩为实际修改与验证结果；
4. 失败时只保留当前阻塞原因和下一步，不堆叠尝试历史；
5. 因新事实失效的其他事项同步修改或删除；
6. 明确告知用户本轮已更新 `04-配置规划.md`。

若配置调查、执行或验证证明 `01`、`02` 或 `03` 的内容需要修订，先在 `04` 的相关事项内记录最小阻塞事实并告知用户当前文档已更新；随后主动说明受影响的上游文档和拟修改内容，获得用户确认后再更新上游文档。上游更新完成后，立即清理 `04` 中已解除的临时阻塞并再次告知。

文档只表示当前配置状态，不保存操作流水；追溯依赖 Git 历史、配置 diff 和工具日志。

## 完成条件

- 需要配置和保留代码的边界清楚；
- 所有候选目标已分类，未按扩展名误判；
- 用户已确认可写范围、Excel 方式及必要的 Schema 变化；
- 已确认由 Agent 处理的真实配置源均已修改；
- 必要的解析、引用、生成或加载验证已有结果；
- 没有直接修改生成物或运行时代码；
- 待人工操作和后续代码依赖都在对应配置事项内清晰可追踪；
- 无尚待用户确认修订的上游文档阻塞；
- 本阶段只有 `04-配置规划.md` 一份过程文档；
- 主文档能让后续人员一分钟内看懂“改什么、当前状态、还缺什么”。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为人工填表另建执行清单 | 将必要操作写入对应配置事项 |
| 同一对象分别写进规划、验证和移交章节 | 在一个连续事项中维护完整当前状态 |
| 简单改值也分析完整配置架构 | 走最小充分路径，只检查受影响链路 |
| 把 `.xml`、`.lua` 一律当配置 | 按职责、加载方式和生成关系分类 |
| Excel 选手动后停止整个任务 | 只暂停 Excel，继续其他已确认配置源 |
| 搜到运行时映射就直接修改 | 记录后续依赖，交给实现阶段 |
| 抄出参照行全部字段 | 只写参照对象和变化字段 |
| 导表成功就视为全部验证 | 根据变化补引用、输出或加载检查 |
| 执行后保留旧步骤和旧状态 | 原位更新，只保留当前真相 |
| 修改或验证完成后只在聊天里汇报 | 同一轮更新 `04-配置规划.md` 并告知路径 |
| 发现上游规则过时后直接改写 | 先说明拟修改内容并获得用户确认 |
