# 完成游戏功能实现

## 目标

基于当前工作单元已确认并可运行的框架，补齐需求细节、失败路径、兼容与验证；根据实现规模选择一次完成或分步骤实现，控制单次人工 review 负担；持续维护未分支的 `06-完整实现方案.md`，或当前工作单元的 `06-Uxx-<主题>-完整实现方案.md`，使新的 session 能从当前文档、实际依赖与代码安全接力。

**核心原则：沿既定框架完成行为闭环；复杂实现按可 review 的纵向闭环分步推进；真正可以独立推进的范围拆工作单元；发现框架根因问题时修订框架，不在细节层堆补丁。**

**单文档硬限制：当前工作单元在本阶段只能维护一份完整实现方案过程文档。** 不得为同一工作单元的不同实现步骤另建实施计划、步骤文档、需求矩阵、测试报告、验证清单、上线说明、风险清单或完成总结。不同工作单元可分别拥有自己的 `06`；代码、测试、迁移、diff 和运行日志属于实际产物或证据，不算过程文档。

**分支工作流硬限制：`01-原始需求.md` 永远只有一份。`01` 完成后到 `game-review` 启动前，若当前实现范围能够独立推进、独立阻塞或独立 review，可拆成稳定工作单元 `U01`、`U02`……；所有文件仍位于同一个 `docs/requirements/<feature>/` 目录，禁止增加分支子目录。没有真实分支时继续使用 `06-完整实现方案.md`。第一次拆分时创建 `00-工作流索引.md`，只记录工作单元 ID、范围、依赖、当前阶段和当前文档；串行、并行与多前驱只由依赖表达，不把拓扑编码进 ID。分支文档命名为 `06-<Uxx>-<主题>-完整实现方案.md`。**

在分支工作流中，下述“本阶段唯一文档”指当前工作单元的唯一 `06` 权威文档。`00-工作流索引.md` 只做路由；一个工作单元完成不代表所有工作单元完成，也不代表可以开始完整 `game-review`。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

存在 `00` 时，开始或恢复本阶段前必须解析当前 `Uxx` 的共享上游和直接前驱，只检查实际依赖；未被依赖的兄弟工作单元不构成阻塞。

**跨 session 可恢复性硬限制：当前工作单元的完整实现方案文档不得依赖当前聊天上下文才能继续实现。** 在开始编码、每个分步 review 边界、暂停或结束当前 session 前，文档必须能明确回答：当前工作单元、实现模式、步骤划分、已确认范围、当前步骤及状态、实际代码基线与关键入口、已完成行为和验证证据、尚未解决的阻塞或决策、下一动作及进入下一步的条件。不得复制共享 `01` 或其他工作单元全文来制造“自包含”；只保留继续实现必需的引用、差异和当前状态。新的 session 必须先用当前文档核对实际代码/diff，发现不一致时以代码事实为依据立即修正文档后再继续。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。每条新记录必须包含实际 `skill_version`；版本由写入器从当前 skill 根目录 `SKILL.md` 的 `metadata.version` 自动读取，禁止由 Agent 手填、猜测或沿用历史值。写入器无法读取版本、版本格式非法或 `--skill` 与当前 `SKILL.md` 名称不一致时，必须拒绝追加并明确报告；不得写 `unknown` 伪装新记录。历史 schema v1 记录缺少版本时保留原样，查询和统计统一视为 `skill_version=unknown`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill 及其实际版本、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须按 `skill_version` 过滤或分组，不能把版本未知的旧记录或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

创建或修改 `00-工作流索引.md` 同样必须追加记录；普通实现正文变化若不改变拓扑、当前阶段或当前文档，不重复改写索引。

## 前置条件与产物

未分支时读取并核对：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- `04-配置规划.md`；
- `05-框架实现方案.md`；
- 已存在的 `06-完整实现方案.md`（若有）；
- 已实现骨架、当前 diff、测试和启动结果。

存在 `00` 时，先定位当前 `Uxx`，再读取唯一 `01` 与索引声明的当前工作单元实际 `02`–`05` 依赖和直接前驱、当前 `06`、代码与测试。不得机械读取并等待所有兄弟工作单元。

未分支过程文档：

```text
docs/requirements/<feature>/06-完整实现方案.md
```

分支后当前工作单元过程文档：

```text
docs/requirements/<feature>/06-<Uxx>-<主题>-完整实现方案.md
```

使用 [完整实现方案模板](references/完整实现方案模板.md)。方案、实现模式、步骤状态、接力点、验证结果和剩余风险都原位更新在当前工作单元这一份文档中。

若当前骨架不能安全运行，先立即在当前 `06` 记录阻塞并告知用户；随后说明拟对当前工作单元对应 `05` 做出的修改，获得用户确认后再回到 `game-scaffold` 修复。

## 工作单元与实现 Step

两者解决不同层级的问题：

- **拆工作单元 `Uxx`**：范围可以独立推进、独立阻塞、由不同 session/Agent 承担，或需要独立的人类 review 生命周期；依赖写入 `00`。
- **文档内 Step**：仍属于同一工作单元，后一步建立在前一步稳定基线上，不能作为独立交付分支；只用于降低一次人工 review 负担。

不得因为实现要分三次 review 就机械创建三个 `Uxx`；也不得把真正可以并行的两个独立功能硬塞成一个 `06` 的 Step。

若到了实现阶段才发现需要真正拆工作单元：

1. 更新或创建 `00`，为直接后继分配新 `Uxx`；
2. 当前父 `06` 只保留共同实现基线并标记 `已拆分`；
3. 若子范围仍继承同一套已确认 `01`–`05`，可直接创建子 `06`；若拆分同时暴露产品、技术、配置或框架决策差异，则子工作单元回到最早受影响的 `02`–`05` 阶段，不得强行从 `06` 开始；
4. 父工作单元停止后续推进，仅索引中的叶子后继继续。

## 工作流程

### 1. 验证当前工作单元框架与基线

开始或恢复实现前检查实际模块、数据结构、主流程、配置、旧数据和上下游是否与当前 `05` 及索引依赖一致；检查当前 `06` 的步骤、代码入口与实际 diff 是否一致。

局部差异可在当前实现方案说明。需要推翻核心边界时，先更新当前 `06` 阻塞，再说明受影响的实际上游文档并取得用户确认。

### 2. 建立当前工作单元需求完成状态

逐条对照当前范围，把每项标为：已由骨架完成、本阶段实现、延期/范围外、外部承载、存在矛盾或缺决策。这些状态只属于当前 `06`，不另建需求矩阵。

### 3. 判断单次实现、分 Step，还是拆工作单元

先判断独立生命周期：若范围可以独立推进/阻塞/review，优先拆 `Uxx`。剩余仍属于同一工作单元时，再判断人工 review 负担：多个可顺序验收的行为闭环、跨多个高影响边界、单次 diff 过大或验证天然分段时，主动推荐 2–5 个 Step。

每个 Step 必须是可单独理解、实现、验证和 review 的纵向行为闭环，不按文件/层级横向切割。Agent 先给建议拆法，再让用户采用或调整。

实现模式和步骤边界确定后立即写入当前 `06` 并告知用户。

### 4. 产出可执行实现方案

按依赖顺序覆盖实际相关的核心规则与状态、配置与数据、权限/资格/资产、副作用、持久化/并发/幂等、失败/补偿/恢复、兼容/发布/回滚、可观测性与测试。描述决策与行为，不粘贴大段最终代码。

分 Step 时在同一当前 `06` 维护步骤表；跨工作单元依赖只在 `00` 维护，不复制兄弟状态。

### 5. 确认后开始实现

向用户展示当前工作单元剩余范围、重要边界、方向变化、实现模式、步骤划分、验证方式和延期项。获得确认前不开始大规模细节编码。用户部分确认或调整边界时立即原位更新当前 `06`。

### 6. 按当前 Step 形成纵向闭环

单次模式连续完成；分 Step 模式一次只实现当前已确认 Step。每步完成规则、配置/数据接入、失败与副作用边界、危险占位清理、测试和验证，并立即回写当前 `06` 的实际实现、证据、偏差和接力点。

分 Step 模式完成当前步后停在人工 review 边界；用户确认前不得开始下一 Step。Step 级 review 只是 `game-implement` 内部门禁，不是 `game-review`。

### 7. 在 review 或换 session 前写好接力点

任何暂停位置都要让当前 `06` 明确当前工作单元、实现模式、步骤状态、代码基线、关键入口、已完成行为与证据、有效偏差、未决阻塞、下一动作和进入下一步条件。不得依赖聊天记录。

### 8. 完整验证并收敛当前工作单元

根据风险选择单元、集成、回归、启动/升级、并发/幂等、故障、性能等验证。每获得结果立即写回当前 `06`。不能运行的验证说明原因、替代证据和剩余风险。

全部 Step 完成后，用实际实现替换计划描述，删除过时方案和失效风险，保留必要验证摘要、真实延期/范围外和已知风险，把接力点收敛为“当前工作单元实现完成，等待工作流汇合/完整交叉 review”。

### 9. 更新工作流索引与 review 门禁

当前 `Uxx` 完成后，把 `00` 中它的当前阶段/文档更新到真实状态。若还有其他叶工作单元未达到 pre-review 可移交终态，明确告诉用户当前分支已完成但**完整 `game-review` 尚不可开始**；不得创建 `07-Uxx-*`，也不得用局部 review 代替完整 review。

只有全部叶工作单元闭环后，才由 `game-review` 统一执行汇合门禁。

## 完成条件

对当前叶工作单元：

- 已确认范围内需求行为全部有实现或外部承载；
- 分 Step 时所有 Step 均完成且没有越过人工 review 门禁；
- 骨架危险占位和隐式未完成逻辑已清除；
- 配置、数据、接口、失败、兼容和回滚形成闭环；
- 关键测试和运行验证通过；
- 不存在未标记 P0/P1 实现风险；
- 无尚待确认修订的上游文档阻塞；
- 当前 `06` 与实际代码一致并能供新 session 复核；
- 当前工作单元本阶段没有其他旁支过程文档。

满足这些条件只表示当前工作单元可进入汇合等待；**是否可以启动完整 `game-review` 由全部叶工作单元共同决定。**

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 大需求仍一次给出全部方案并连续实现 | 先判断应拆工作单元还是同一单元分 Step |
| 直接问用户“你想怎么拆” | Agent 先分析依赖并给建议 |
| 按文件/层级切 Step | 按纵向行为闭环切分 |
| 当前 Step 完成后顺手继续下一步 | 更新当前 `06`，等待用户 review |
| 每个 Step 新建一个实现文档 | 同一工作单元的 Step 全在一份 `06` |
| 真正独立的两块工作只做 Step | 拆成不同 Uxx，并在 00 显式依赖 |
| 依赖上一 session 聊天恢复 | 当前 `06` 保存接力点，先核对代码/diff |
| 实施结束后另写完成报告 | 原位更新当前主文档 |
| 无法执行测试却宣称完成 | 记录限制、替代证据和剩余风险 |
| 实现变化后只在聊天汇报 | 同一轮更新当前 `06` 并告知路径 |
| 一个 Uxx 完成就开始 07 | 等全部叶工作单元闭环后统一汇合 |
| 创建 `07-U01-*` 做局部完整 review | 禁止；07 永远只有一份整体交叉评审 |
| 为 Uxx 增加子目录 | 所有过程文档保持同目录 |
