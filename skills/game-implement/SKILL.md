# 完成游戏功能实现

## 目标

基于已确认并可运行的框架，补齐需求细节、失败路径、兼容与验证；根据实现规模选择一次完成或分步骤实现，控制单次人工 review 负担；持续维护 `06-完整实现方案.md`，使任意新的 session 都能仅依赖当前文档、上游文档与实际代码安全接力。

**核心原则：沿既定框架完成行为闭环；复杂实现按可 review 的纵向闭环分步推进；发现框架根因问题时修订框架，不在细节层堆补丁。**

**单文档硬限制：本阶段只能维护 `06-完整实现方案.md` 一份过程文档。** 不得为不同实现步骤另建实施计划、步骤文档、需求矩阵、测试报告、验证清单、上线说明、风险清单或完成总结。代码、测试、迁移、diff 和运行日志属于实际产物或证据，不算过程文档；当前结论、步骤状态与接力信息必须回写主文档。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**跨 session 可恢复性硬限制：`06-完整实现方案.md` 不得依赖当前聊天上下文才能继续实现。** 在开始编码、每个分步 review 边界、暂停或结束当前 session 前，文档必须能明确回答：当前实现模式、步骤划分、已确认范围、当前步骤及状态、实际代码基线与关键入口、已完成行为和验证证据、尚未解决的阻塞或决策、下一动作及进入下一步的条件。不得复制 `01` 至 `05` 的全文来制造“自包含”；只保留继续实现必需的引用、差异和当前状态。新的 session 必须先用文档核对实际代码/diff，发现不一致时以代码事实为依据立即修正文档后再继续，不能假设上一 session 的聊天内容仍然可用。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 前置条件与产物

必须读取并核对：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- `04-配置规划.md`；
- `05-框架实现方案.md`；
- 已存在的 `06-完整实现方案.md`（若有）；
- 已实现骨架、当前 diff、测试和启动结果。

若是新的 session，不得从聊天记忆推断进度；先从 `06` 的当前接力点恢复，再核对实际代码状态。

若骨架不能安全运行，先立即在 `06-完整实现方案.md` 记录阻塞并告知用户；随后说明拟对 `05-框架实现方案.md` 做出的修改，获得用户确认后再回到 `game-scaffold` 修复，不在不稳定基线上继续扩展。

唯一过程文档：

```text
docs/requirements/<feature>/06-完整实现方案.md
```

使用 [完整实现方案模板](references/完整实现方案模板.md)。方案、实现模式、步骤状态、接力点、验证结果和剩余风险都原位更新在这一份文档中。

## 工作流程

### 1. 验证框架与当前基线

开始或恢复实现前检查：

- 实际模块、数据结构和主流程是否与 `05` 一致；
- 延期点是否仍可在既定扩展点内完成；
- 是否出现会推翻数据归属、公共接口或状态模型的新事实；
- 配置、旧数据和上下游是否仍满足原决策；
- 服务器基线和骨架验证是否通过；
- `06` 记录的当前步骤、代码入口和验证状态是否与实际代码/diff 一致。

局部差异可在完整方案中说明。若需要推翻核心边界，先立即更新 `06` 中最相关事项并告知用户当前文档已更新；随后主动说明受影响的 `01` 至 `05` 文档和拟修改内容，获得用户确认后再修订对应上游文档。未确认前不得把重新设计伪装成细节实现，也不得静默改写上游文档。

### 2. 建立需求完成状态

逐条对照已确认需求，把每项标为：

- 已由骨架完成；
- 本阶段需要实现；
- 明确延期或不在范围；
- 被配置、外部系统或既有代码满足；
- 当前存在矛盾或缺少决策。

这些状态属于 `06-完整实现方案.md` 的内容，不得另建需求矩阵文档。只有真实需求和高价值安全项进入实现，不为“看起来完整”增加无来源能力。

状态建立或变化后立即更新 `06` 并告知用户，不等待方案全部完成。

### 3. 判断一次实现还是分步骤实现

先判断**人工 review 负担**，而不是只看代码量。以下任一情况明显存在时，应主动推荐分步骤实现：

- 剩余范围包含多个可以独立验收的行为闭环；
- 同时跨越多个高影响边界，如状态模型、资产、持久化、协议、跨进程、兼容或迁移；
- 一次实现会让用户需要同时 review 多组互不相关的决策和代码；
- 验证天然可以分段，且前一步能形成安全、可运行的稳定基线；
- 预计单次 diff 或方案大到不利于用户聚焦判断正确性。

只有一个紧凑行为闭环、review 范围很小的任务，不要为了流程而强行拆步或额外询问用户。

需要分步时：

1. Agent 先基于依赖关系给出建议拆法，通常控制在 2–5 个步骤；
2. 每一步必须是可单独理解、实现、验证和 review 的纵向行为闭环，不按“先改模型、再改 handler、最后补测试”这类文件/层级横向切割；
3. 优先让前一步形成后一步可依赖的稳定基线，避免同时保留多个半成品；
4. 向用户说明为什么建议拆步、建议如何拆，并询问是否采用或调整；不要把没有分析过的“你想怎么拆”开放题直接丢给用户；
5. 用户选择一次完成时，记录为单次模式并继续；用户未指定具体拆法但接受分步时，采用 Agent 给出的最短依赖拆分。

实现模式和步骤边界一旦确定，立即写入 `06` 并告知用户。

### 4. 产出可执行实现方案

方案按依赖顺序描述剩余工作，至少覆盖实际相关的：

- 核心规则和状态转换；
- 配置字段如何影响流程；
- 权限、资格、次数、消耗、奖励和重复操作；
- 持久化、并发、幂等、事务和跨进程时序；
- 失败、重试、补偿、取消和恢复；
- 旧数据、旧协议、灰度、开关和回滚；
- 日志、指标、告警和运维入口；
- 测试层级、关键场景和完成证据。

同一实现事项的规则、代码入口、失败边界和验证方式应放在相邻位置，不按类别拆成重复汇总。描述决策和行为，不粘贴大段最终代码。

分步模式下，还必须在同一文档中维护步骤表：每步的行为闭环、依赖、状态、完成证据和 review 门禁。步骤表只表达当前有效计划，不保存实施流水。

每形成或修改一个可执行事项，立即原位更新主文档并告知用户。

### 5. 确认后开始实现

向用户展示主文档中的剩余范围、重要边界、方向变化、实现模式、步骤划分、验证方式和延期项。获得确认前不开始大规模细节编码。

用户只确认部分范围或调整步骤边界时，立即原位更新对应事项状态并告知用户，不另建批准清单。

### 6. 按当前步骤形成纵向闭环

单次模式按依赖顺序连续完成；分步模式一次只实现当前已确认步骤。每个步骤均执行：

1. 完成该步骤相互依赖的规则；
2. 补齐数据与配置使用；
3. 完成失败和副作用边界；
4. 清除该步骤范围内的 `TODO`、临时返回、硬编码测试值或危险占位；
5. 添加或更新测试；
6. 运行相关验证；
7. 立即回写主文档中的实际实现、验证证据、偏差和当前接力点，并告知用户。

分步模式在完成当前步骤后必须停在 review 边界：向用户给出本步的实际行为、关键改动、验证结果、需要重点 review 的内容和下一步范围；**在用户确认当前步骤或明确要求继续前，不得开始下一步骤。** 步骤级 review 属于 `game-implement` 内部推进门禁；只有全部实现步骤完成并收敛后，才进入 `game-review` 的完整交叉评审。

### 7. 在 review 或换 session 前写好接力点

任何可能暂停较长时间的位置，尤其是分步 review 后，必须把 `06` 收敛为可直接恢复的当前状态，至少包含：

- 当前实现模式与步骤总览；
- 当前步骤是待实现、实现中、待 review、已确认还是阻塞；
- 实际代码基线，以及继续实现最关键的文件、类、函数或数据入口；
- 已完成行为及最小验证证据；
- 与原方案的有效偏差；
- 仍未解决且会阻塞下一动作的问题；
- 下一动作和进入下一步骤前必须满足的条件。

不要保存冗长实施日志，也不要复制已经稳定的上游需求。已完成步骤应压缩为“当前事实 + 证据”；过时计划、已解除风险和无效接力说明立即删除。

新的 session 恢复时，先读该接力点并核对实际代码/diff；若代码比文档更新或更旧，立即以实际仓库状态修正文档并告知用户，再决定继续当前步骤还是重新进入 review。

### 8. 完整验证并收敛实际状态

所有步骤完成后，根据风险选择验证层级：

- 单元测试：纯规则、状态转换和不变量；
- 集成测试：配置、存储、消息、协议和跨模块流程；
- 回归测试：受影响的既有系统；
- 启动与升级测试：旧数据、缺省配置、迁移和回滚；
- 并发/幂等测试：资产、次数、重复请求和跨进程操作；
- 故障测试：超时、部分失败、重试和补偿；
- 性能验证：仅在真实容量风险存在时执行。

每获得一项验证结果，立即写回对应实现事项并告知用户 `06-完整实现方案.md` 已更新。完整测试输出保留在测试系统或日志中，不另建测试报告。不能运行的验证要说明原因、替代证据和剩余风险，不能写成“应该没问题”。

最终更新 `06-完整实现方案.md`：

- 用实际实现替换计划性描述；
- 删除已完成步骤中的过程性计划、旧方案和失效风险；
- 只保留与当前代码不同步时仍需处理的偏差；
- 记录必要的测试与运行证据摘要；
- 保留真实延期、范围外和已知风险；
- 把当前接力点收敛为“实现完成，待完整交叉 review”。

若实现或验证证明上游文档需要修订，先更新 `06` 中的阻塞状态，再说明受影响文档与拟修改内容并请求用户确认；确认后更新上游文档，告知路径，并立即清理 `06` 中已解除的临时阻塞。

文档表示当前实现状态，不保存实施流水；过程追溯依赖版本历史、代码 diff、测试记录和 `record.jsonl`。

## 完成条件

- 已确认范围内的需求行为全部有实现或明确的外部承载；
- 分步模式下所有步骤均完成，并且不存在未经用户 review 确认却越过的步骤门禁；
- 骨架中的危险占位和隐式未完成逻辑已清除；
- 配置、数据、接口、失败、兼容和回滚形成闭环；
- 关键测试和服务器运行验证通过；
- 不再存在未标记的 P0/P1 实现风险；
- 无尚待用户确认修订的上游文档阻塞；
- `06-完整实现方案.md` 与实际代码一致，并包含可供新 session 直接复核的最终接力状态；
- 可进入 `game-review` 完整交叉 review；
- 本阶段没有其他旁支过程文档。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 大需求仍一次给出全部方案并连续实现 | 先按人工 review 负担判断，必要时主动推荐 2–5 个纵向步骤 |
| 直接问用户“你想怎么拆” | Agent 先分析依赖并给建议拆法，再让用户采用或调整 |
| 按文件、层级或技术工种切步骤 | 按可独立理解、验证和 review 的行为闭环切分 |
| 当前步骤完成后顺手继续下一步 | 更新 `06`、给出 review 重点并等待用户确认 |
| 每个步骤新建一个实现文档 | 全部步骤、状态和接力点都维护在唯一的 `06-完整实现方案.md` |
| 依赖上一 session 的聊天记录恢复进度 | `06` 保存当前接力点；新 session 先核对实际代码/diff 再继续 |
| 为需求矩阵、测试和上线分别建文档 | 全部收拢到 `06-完整实现方案.md` 的对应事项 |
| 实施结束后另写完成报告 | 原位更新主文档，删除过时计划 |
| 在既定框架上不断打局部补丁 | 发现根因性边界错误时先确认再修订上游框架 |
| 把未完成 TODO 留在“完成”代码中 | 实现、明确延期或受控移出范围 |
| 只测试成功主流程 | 覆盖资产、状态、失败、重试和兼容 |
| 方案写得很细但没有需求追踪 | 在同一文档中维护需求与实现状态 |
| 无法执行测试却宣称完成 | 记录限制、替代证据和剩余风险 |
| 实现或验证变化后只在聊天里汇报 | 同一轮更新 `06-完整实现方案.md` 并告知路径 |
| 发现上游错误后直接改 `01` 至 `05` | 先说明拟修改内容并获得用户确认 |
