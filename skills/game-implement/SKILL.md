# 完成游戏功能实现

## 目标

基于已确认并可运行的框架，补齐需求细节、失败路径、兼容与验证；持续维护 `06-完整实现方案.md`，并据此完成代码。

**核心原则：沿既定框架完成行为闭环；发现框架根因问题时修订框架，不在细节层堆补丁。**

**单文档硬限制：本阶段只能维护 `06-完整实现方案.md` 一份过程文档。** 不得另建需求矩阵、实施计划、测试报告、验证清单、上线说明、风险清单或完成总结。代码、测试、迁移、diff 和运行日志属于实际产物或证据，不算过程文档；当前结论必须回写主文档。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 前置条件与产物

必须读取并核对：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- `04-配置规划.md`；
- `05-框架实现方案.md`；
- 已实现骨架、当前 diff、测试和启动结果。

若骨架不能安全运行，先立即在 `06-完整实现方案.md` 记录阻塞并告知用户；随后说明拟对 `05-框架实现方案.md` 做出的修改，获得用户确认后再回到 `game-scaffold` 修复，不在不稳定基线上继续扩展。

唯一过程文档：

```text
docs/requirements/<feature>/06-完整实现方案.md
```

使用 [完整实现方案模板](references/完整实现方案模板.md)。方案、实施状态、验证结果和剩余风险都原位更新在这一份文档中。

## 工作流程

### 1. 验证框架仍然成立

开始前检查：

- 实际模块、数据结构和主流程是否与 `05` 一致；
- 延期点是否仍可在既定扩展点内完成；
- 是否出现会推翻数据归属、公共接口或状态模型的新事实；
- 配置、旧数据和上下游是否仍满足原决策；
- 服务器基线和骨架验证是否通过。

局部差异可在完整方案中说明。若需要推翻核心边界，先立即更新 `06` 中最相关事项并告知用户当前文档已更新；随后主动说明受影响的 `01` 至 `05` 文档和拟修改内容，获得用户确认后再修订对应上游文档。未确认前不得把重新设计伪装成细节实现，也不得静默改写上游文档。

### 2. 在主文档中建立需求完成状态

逐条对照已确认需求，把每项标为：

- 已由骨架完成；
- 本阶段需要实现；
- 明确延期或不在范围；
- 被配置、外部系统或既有代码满足；
- 当前存在矛盾或缺少决策。

这些状态属于 `06-完整实现方案.md` 的内容，不得另建需求矩阵文档。只有真实需求和高价值安全项进入实现，不为“看起来完整”增加无来源能力。

状态建立或变化后立即更新 `06` 并告知用户，不等待方案全部完成。

### 3. 产出完整实现方案

方案按依赖顺序描述剩余工作，至少覆盖实际相关的：

- 核心规则和状态转换；
- 配置字段如何影响流程；
- 权限、资格、次数、消耗、奖励和重复操作；
- 持久化、并发、幂等、事务和跨进程时序；
- 失败、重试、补偿、取消和恢复；
- 旧数据、旧协议、灰度、开关和回滚；
- 日志、指标、告警和运维入口；
- 测试层级、关键场景和完成证据。

同一实现事项的规则、代码入口、失败边界和验证方式应放在相邻位置，不按类别拆成重复汇总。描述决策和行为，不粘贴大段最终代码。

每形成或修改一个可执行事项，立即原位更新主文档并告知用户。

### 4. 确认后开始完整实现

向用户展示主文档中的剩余范围、重要边界、方向变化、实现批次、验证方式和延期项。获得确认前不开始大规模细节编码。

用户只确认部分范围时，立即原位更新对应事项状态并告知用户，不另建批准清单。

### 5. 按纵向闭环实现

每个批次应形成可验证的行为闭环，而不是按文件类型横向铺开：

1. 完成一组相互依赖的规则；
2. 补齐数据与配置使用；
3. 完成失败和副作用边界；
4. 添加或更新测试；
5. 运行相关验证；
6. 立即回写主文档并告知用户，再进入下一组。

优先完成主流程，再处理高影响边界。不要同时留下多个无法运行的半成品分支。

### 6. 清除骨架阶段的临时边界

逐一处理：

- `TODO`、`NotImplemented`、临时返回和默认关闭入口；
- 占位数据、硬编码测试值和临时配置；
- 仅为骨架存在的兼容分支；
- 缺失的错误处理、日志和指标；
- 未验证的迁移、序列化和回滚路径。

确实延期的内容必须转为显式范围外、任务或受控开关，不能以隐蔽占位留在完成状态中。每处理一项后立即更新对应文档事项并告知用户。

### 7. 完整验证

根据风险选择验证层级：

- 单元测试：纯规则、状态转换和不变量；
- 集成测试：配置、存储、消息、协议和跨模块流程；
- 回归测试：受影响的既有系统；
- 启动与升级测试：旧数据、缺省配置、迁移和回滚；
- 并发/幂等测试：资产、次数、重复请求和跨进程操作；
- 故障测试：超时、部分失败、重试和补偿；
- 性能验证：仅在真实容量风险存在时执行。

每获得一项验证结果，立即写回对应实现事项并告知用户 `06-完整实现方案.md` 已更新。完整测试输出保留在测试系统或日志中，不另建测试报告。不能运行的验证要说明原因、替代证据和剩余风险，不能写成“应该没问题”。

### 8. 原位收敛实际完成状态

更新 `06-完整实现方案.md`：

- 用实际实现替换计划性描述；
- 删除已完成步骤、旧方案和失效风险；
- 只保留与当前代码不同步时仍需处理的偏差；
- 记录必要的测试与运行证据摘要；
- 保留真实延期、范围外和已知风险。

每次状态变化都在同一轮更新并告知用户。若实现或验证证明上游文档需要修订，先更新 `06` 中的阻塞状态，再说明受影响文档与拟修改内容并请求用户确认；确认后更新上游文档，告知路径，并立即清理 `06` 中已解除的临时阻塞。

文档表示当前实现状态，不保存实施流水；过程追溯依赖版本历史、代码 diff 和测试记录。

## 完成条件

- 已确认范围内的需求行为全部有实现或明确的外部承载；
- 骨架中的危险占位和隐式未完成逻辑已清除；
- 配置、数据、接口、失败、兼容和回滚形成闭环；
- 关键测试和服务器运行验证通过；
- 不再存在未标记的 P0/P1 实现风险；
- 无尚待用户确认修订的上游文档阻塞；
- `06-完整实现方案.md` 与实际代码一致，可进入交叉 review；
- 本阶段没有其他旁支过程文档。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为需求矩阵、测试和上线分别建文档 | 全部收拢到 `06-完整实现方案.md` 的对应事项 |
| 实施结束后另写完成报告 | 原位更新主文档，删除过时计划 |
| 在既定框架上不断打局部补丁 | 发现根因性边界错误时先确认再修订上游框架 |
| 按文件批量写完后再集成 | 按行为闭环分批实现和验证 |
| 把未完成 TODO 留在“完成”代码中 | 实现、明确延期或受控移出范围 |
| 只测试成功主流程 | 覆盖资产、状态、失败、重试和兼容 |
| 方案写得很细但没有需求追踪 | 在同一文档中维护需求与实现状态 |
| 无法执行测试却宣称完成 | 记录限制、替代证据和剩余风险 |
| 实现或验证变化后只在聊天里汇报 | 同一轮更新 `06-完整实现方案.md` 并告知路径 |
| 发现上游错误后直接改 `01` 至 `05` | 先说明拟修改内容并获得用户确认 |
