# 重构游戏代码

## 目标

在冻结外部可观察行为和关键系统契约的前提下，改善职责、复杂度归属、重复、可读性、可测试性或局部性能，同时避免把“代码更整齐”误当成重构成功。

游戏需求长期变化，现有代码中也可能存在为历史策划规则、兼容特例或难以复现的问题保留的异常结构。因此，重构不仅要证明当前行为没有被无意改变，还要避免过早消除未来仍有价值的变化点和暂时无法解释的特殊处理。

**核心原则：先冻结行为和变化边界，再调整结构；复杂度放到正确层级，而不是为了形式消灭所有重复；无法解释的异常先当作约束调查，不能直接“清理”。**

## 默认边界

- 默认不进入 `01–07` 正式功能开发流程。
- 事实自己查，不让用户确认可以由代码、测试、配置、调用链和历史实现回答的事实。
- 是否已上线只能由用户确认；不得根据部署脚本、生产配置、分支名或其他仓库迹象自行推断。开发期默认不引入线上迁移、存量数据兼容、灰度或在线状态保护要求。
- 不顺便改变玩家规则、接口语义、配置意义、数据权威、持久化格式或失败语义。
- 不因为代码“丑”、文件较长、分支较多或存在重复就自动重构；必须先说明实际维护问题。
- 不为未知未来需求预建抽象，但对已经频繁变化、明显受策划驱动的规则保留合理变化点；允许有意的局部冗余，避免把语义相近但可能独立变化的需求强行统一。
- 重构发现的 bug、产品行为变化或需求缺口默认单独报告，不混入等价重构；需要处理时切换到 `game-bugfix` / `game-small-change` 或正式流程。

## 重构前决策

### 1. 冻结什么不能变

先确认本次重构必须保持的真实外部行为，包括实际相关的：

- RPC / Event / 协议及客户端可见结果；
- 配置语义和值的消费方式；
- 数据格式、持久化结果和恢复行为；
- 状态生命周期、终态和关键副作用；
- 权限、奖励、扣除、错误码和其他业务结果；
- 关键性能特征或时序约束（如果它们是当前设计的一部分）。

不要只根据函数签名判断行为等价；真正的契约可能存在于消费链和副作用中。

### 2. 理解为什么当前结构会这样

在把现有结构判断为“坏设计”前，检查：

- 这是偶然复杂度，还是业务规则本身复杂；
- 重复代码是否真的承担相同语义，还是只是当前恰好长得一样；
- 奇怪的分支、绕路、字段或调用顺序是否承担生命周期、性能、兼容、历史需求或事故规避作用；
- 注释/需求描述与实现不一致时，哪一边更接近当前真实行为，差异是否有历史原因；
- Git 历史、相关 issue/任务、测试、调用方或配置是否能解释这个异常。

**异常结构保护规则：描述与实现不一致、看似多余的特判、难以理解的绕路、两个相似流程故意未合并，都视为需要调查的信号。没有证据证明可以删除时，不因为“不优雅”就消掉它。若该差异会被本次重构抹平且无法解释，先向用户说明并确认。**

### 3. 明确具体重构目标

目标必须能够判断完成，例如：

- 三处真正同义的状态判断收敛为一个权威入口；
- 奖励发放职责从多个玩法模块收敛到已有奖励层；
- 消除循环依赖或错误的跨层调用；
- 把多个业务都重复实现的异步生命周期保护下沉到底层；
- 降低新增一种同类玩法/Actor 时必须修改的模块数量；
- 让当前关键逻辑可以被独立测试。

“代码更漂亮”“更现代”“抽象更统一”不是足够的目标。

### 4. 判断该统一，还是保留灵活性

策划规则变化频繁时，重构目标不是最大程度去重，而是降低未来真实变化的修改成本。

优先统一：

- 已经长期稳定、语义一致、由同一个业务规则驱动的重复；
- 多处重复实现且任何一处遗漏都会造成一致性风险的公共能力；
- 本来就应由底层负责，却散落在多个业务模块中的技术复杂度。

倾向保留独立变化点或局部冗余：

- 两段逻辑当前相同，但分别属于不同策划规则，未来很可能独立调整；
- 为了统一需要引入大量 mode/type/flag 参数和条件分发；
- 抽象后理解一个玩法反而需要跨更多层和文件；
- 合并后任何一个小规则变化都会影响其他玩法或公共框架。

**不要把 DRY 机械化。错误抽象通常比少量重复更难维护；适度冗余可以是对高变化需求的主动隔离。**

### 5. 判断是 Refactor 还是 Redesign

若方案需要改变以下边界，停止称为纯重构并先讨论/切换 skill：

- 外部行为或产品规则；
- RPC/Event/协议或客户端合同语义；
- 数据 schema、持久化、迁移或历史兼容；
- 配置真源或字段语义；
- 数据权威、模块职责或生命周期模型；
- 一致性、幂等、时序、失败补偿模型；
- 为性能引入新的缓存、异步化、分片或架构边界。

重构过程中如果发现“只有重新定义这些边界才能真正变好”，先向用户说明现有问题、重构方案和 redesign 方案的差异，不借重构名义直接推进设计变更。

## 实施方法

### 1. 优先小步、可验证、可回退

典型顺序：

```text
确认行为基线 → 建立必要保护/观测 → 小步移动或抽取 → 验证 → 再继续
```

除非用户明确要求且风险可控，不采用“理解大概后一次性重写”的方式替换有状态、异步、持久化或跨进程核心逻辑。

### 2. 复杂度放到负责它的层级

复杂度未必能消失，但应归属正确：

- 多个玩法都处理旧异步回包 → 优先考虑 RPC/Task/生命周期层；
- 多个业务都重复保证幂等 → 优先检查事务/命令/资产层是否应统一承担；
- 多个模块都自己管理通用生命周期 → 优先检查 Actor/Entity/框架层。

但“应该下沉”不等于本次自动大改底层。若下沉会扩大影响面或改变框架职责，先与用户讨论方案。

### 3. 不把重构、修 Bug、加需求混成一个改动

发现旁路 bug 或产品差异时：

- 先记录证据并报告；
- 用户要处理时，尽量独立修改/commit 或先切换对应 skill；
- 若该 bug 不修就无法证明重构行为等价，停止继续并先处理依赖关系。

这样出现回归时，才能区分是结构调整还是行为修改导致。

### 4. 达到目标就停止

重构开始前明确范围和完成标准。目标完成后不要因为“附近还能整理”继续扩大 diff。

## 验证与 QA

### Agent 侧验证：证明能证明的部分

Agent 至少验证：

1. 可执行的既有自动化测试、静态检查或构建仍通过；
2. 受影响主路径的输入、输出、状态和关键副作用与基线一致；
3. 公共接口、配置、持久化和调用方向没有意外变化；
4. 若声称性能改善，提供重构前后的可比较证据。

按真实风险追加启动、重启恢复、并发、异步乱序或故障验证；没有经过这些边界时不机械扩展。

### 不把 Agent 验证冒充完整游戏验收

在当前这类游戏项目中，Agent 通常无法完整覆盖客户端表现、多玩家交互、复杂场景组合、真实操作节奏和完整游戏体验。**不能因为代码检查、单测、服务端脚本或 CI 通过，就宣称重构已经完成全部功能测试。**

如果本次改动存在 Agent 无法可靠覆盖的游戏行为，收尾时给 QA/测试人员提供精简、可执行的测试样例。测试样例按需包含：

- 前置条件/账号或场景状态；
- 操作步骤；
- 期望结果；
- 需要重点观察的状态、日志或客户端表现；
- 与本次重构直接相关的回归路径；
- 特殊历史分支/异常结构对应的验证点（如果本次触及）。

测试样例服务于实际回归，不为形式穷举整个系统。简单局部重构给少量高价值用例即可；高风险改动再扩大覆盖面。

如果 QA 结果尚未获得，最终状态要区分“Agent 可验证部分已通过”与“完整游戏回归待 QA”，不得虚构闭环。

## 收尾汇报

简明说明：

- 本次重构解决的具体维护问题；
- 哪些行为/特殊分支被明确保持；
- 哪些重复被消除，哪些冗余被有意保留及原因；
- Agent 已完成的验证证据；
- QA 建议测试样例（存在 Agent 无法覆盖的行为时）；
- 仍无法解释但本次选择保留的异常结构（如有）；
- 是否发现需要独立处理的 bug / redesign 问题。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，不得套用 `01–07` 正式流程结构。
- QA 测试样例默认可以直接在收尾汇报中给出，不因为需要 QA 回归就自动创建测试文档；用户要求留档时再写入维护记录。
- 跨 session、多人接力或重构较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若重构会使已有长期权威文档中的模块职责或稳定契约失真，指出具体文档与需要更新的事实；不存在长期文档时，不因为本次重构自动创建新的功能文档。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**
