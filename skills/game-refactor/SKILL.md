# 重构游戏代码

## 目标

在冻结外部可观察行为和关键系统契约的前提下，完成局部结构整理、去重、职责收敛、可读性改进或低风险性能整理，并用证据证明没有把“重构”做成隐式功能修改。

**核心原则：先冻结行为，再改变结构；无法证明行为保持不变时，不把它称为纯重构。**

## 默认边界

- 默认不进入 `01–07` 正式功能开发流程。
- 事实自己查，不让用户确认可以由代码、测试、配置和当前行为回答的实现事实。
- 优先缩小复杂度和重复，不为“更优雅”而跨越不必要模块边界。
- 开发期默认不引入线上迁移、存量数据兼容、灰度或在线状态保护要求；只有用户明确要求或任务处于线上环境时才处理。
- 如果当前是否已上线无法从上下文/项目事实确认，且这个差异会实质改变重构方案，只询问一次是否需要按线上存量数据处理；确认仍在开发期后停止该方向的深入探索。
- 不顺便改变玩家规则、接口语义、配置意义、数据权威、持久化格式或失败语义。

## 何时不再属于 refactor

若修改需要以下任一变化，停止按纯重构处理，并明确转为 `game-small-change`、`game-bugfix` 或正式流程：

- 外部行为或产品规则改变；
- RPC/Event/协议或客户端合同语义改变；
- 数据 schema、持久化、迁移或历史兼容改变；
- 配置真源或配置字段语义改变；
- 一致性、幂等、时序、失败补偿模型改变；
- 性能目标需要新的缓存、异步化、分片或架构边界。

## 工作流程

### 1. 冻结基线

确认本次重构必须保持不变的行为、公共接口、数据格式、配置语义和关键副作用。优先读取现有测试和调用方形成可验证基线。

### 2. 确认重构目标

明确真正要改善的问题，例如重复逻辑、职责混乱、过深调用、不可测试结构、无效分支或局部性能浪费。不要把泛化的“代码更漂亮”当成目标。

### 3. 选择最小结构调整

尽量在单一职责边界内完成；若必须跨模块移动代码，检查调用方向、初始化顺序、生命周期和依赖反转是否变化。

### 4. 验证行为等价

至少验证：

1. 关键既有测试仍通过；
2. 受影响主路径的输入、输出和副作用保持一致；
3. 公共接口、配置和持久化格式没有意外变化。

按风险追加启动、性能对比、并发、异步或重启恢复验证。性能重构必须给出可比较证据，而不是只凭代码形态判断更快。

### 5. 收尾

检查 diff 是否混入功能修改、顺手修 bug 或无关格式化。若发现真实 bug 或需求变化，单独报告并切换到合适 skill，不隐藏在重构提交中。

## 文档

默认不创建维护文档。**只有用户明确要求记录本次维护时，才创建新的维护记录。**

- 用户要求记录时：使用 `references/维护记录模板.md`，不得套用 `01–07` 正式流程结构。
- 跨 session、多人接力或重构较复杂时，Agent 可以建议用户保存维护记录，但用户未明确要求前不得自行创建。
- 若重构会使已有长期权威文档中的模块职责或稳定契约失真，指出具体文档与需要更新的事实；不存在长期文档时，不因为本次重构自动创建新的功能文档。
