# 挖掘游戏需求

## 目标

基于唯一的 `01-原始需求.md`、代码和现有实现，找出真正会改变产品规则的遗漏点，通过多轮沟通维护未分支的 `02-需求挖掘.md`，或当前工作单元的 `02-Uxx-<主题>-需求挖掘.md`。

**核心原则：事实自己查，只把产品决策交给需求负责人。**

**文档职责：`01` 保存整个需求的当前有效产品规则；当前 `02` 只保存当前工作单元尚未解决的高价值产品问题、必要风险、明确延期，以及已经回答但尚待用户确认回写 `01` 的最小临时结论。上游回写确认完成后，该临时内容必须从当前 `02` 删除。**

**结构硬限制：一个问题只允许一个连续分块，问题、必要依据和建议放在一起。禁止再建立“已确认结论、当前批次、问题台账、暂不追问、收敛检查”等重复分块。**

**闭环硬限制：每轮沟通结束后立即更新当前阶段文档。已解决、已取消、被覆盖或不再有价值的内容必须移除；部分解决时只保留剩余问题。需要回写 `01` 时，只在原问题分块内保留最小的待回写状态，不另建结论区。**

**分支工作流硬限制：`01-原始需求.md` 永远只有一份，不参与分支。`01` 完成后到 `game-review` 开始前，若范围能够独立推进、独立阻塞或独立 review，可拆成稳定工作单元 `U01`、`U02`……；所有文件仍放在同一个 `docs/requirements/<feature>/` 目录，禁止为分支增加子目录。没有真实分支时继续使用 `02-需求挖掘.md`，不得为形式统一创建 `00` 或 `U01`。第一次拆分时创建 `00-工作流索引.md`，只记录工作单元 ID、范围、依赖、当前阶段和当前文档；串行/并行只由依赖表达，不把拓扑编码进 ID。分支文档命名为 `02-<Uxx>-<主题>-需求挖掘.md`。**

在分支工作流中，下述“本阶段唯一文档”指**当前工作单元在本阶段的唯一权威文档**；同一阶段可以存在其他工作单元的 `02` 文档。`00-工作流索引.md` 是路由元数据，不属于某个工作单元的阶段正文。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

存在 `00` 时，上述门禁必须先从索引解析目标 `Uxx` 和实际依赖；未被当前工作单元依赖的兄弟分支不构成阻塞。索引无法唯一确定目标工作单元、依赖或当前文档时，先修正索引，不得靠聊天记忆猜测。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。新记录使用 schema v3，并区分“实际使用 skill”和“未使用 skill”：只要当前 Agent 实际加载/执行了本 skill（即使用户没有显式写出 skill 名称），就必须调用本 skill 自带的 `scripts/document_record.py append --skill <当前skill>`，写入 `skill_usage=used`，`skill_version` 由写入器从当前 `SKILL.md` 的 `metadata.version` 自动读取，禁止 Agent 手填、猜测或沿用历史值；若一次变更实际没有使用任何 skill，才可使用 `--no-skill`，写入 `skill_usage=not_used`、`skill=null`、`skill_version=null`，不得挑选一个“最接近”的 skill 冒充来源。用户是否显式声明 skill 不是归因依据，实际是否加载/执行才是。写入器 append 前只校验已有文件仍可逐行解析为 UTF-8 JSON object；历史行的 schema 字段缺失或语义错误（例如旧 schema v2 缺少 `skill_version`）必须由 `check` 报告，但不得阻塞后续独立追加，也不得静默修改旧行；只有非 UTF-8、非法 JSON、非 object 等存储层损坏才拒绝 append。历史 schema v1 或非法 v2 无版本记录在查询和统计时统一视为 `skill_version=unknown`；no-skill v3 视为 `skill=none`、`skill_version=not_applicable`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过。记录至少包含时间、skill usage、skill/版本归因、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须只使用 `skill_usage=used` 且按 `skill_version` 过滤或分组，不能把 no-skill、版本未知或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

创建或修改 `00-工作流索引.md` 也必须使用本 skill 的同一记录规则追加 `record.jsonl`；普通 `02` 正文变化若不改变拓扑、当前阶段或当前文档，不重复改写 `00`。

## 产物与工作单元

必须先有且只允许有一份 `01-原始需求.md`。

未分支时维护：

```text
docs/requirements/<feature>/02-需求挖掘.md
```

分支后当前工作单元维护：

```text
docs/requirements/<feature>/02-<Uxx>-<主题>-需求挖掘.md
```

使用 [需求挖掘模板](references/需求挖掘模板.md)。文档表示当前状态，不保存问答流水。

需要拆分时，Agent 先判断是否真的存在多个可独立推进/阻塞/review 的产品问题域。若用户已明确要求拆分，按最短依赖模型执行；否则先给出建议工作单元及依赖并获得用户确认。通常控制在 2–5 个直接后继，不为每个小问题创建工作单元。

若在已有当前 `02` 上继续拆分：

1. 第一次拆分先创建 `00-工作流索引.md`，已有则原位更新；
2. 为所有后继分配新的稳定 `Uxx`；
3. 当前父文档只保留仍有效的共同基线，顶部状态改为 `已拆分`；
4. 分支专属未决问题移动到对应子 `02`，共享事实通过 `01` 或父文档引用，不复制正文；
5. 父工作单元不再直接创建 `03`，只由索引中的叶子后继继续。

## 职责边界

可以询问会改变玩家行为、规则、范围、资产、资格、时序、失败结果、跨系统关系或运营兼容的产品决定。

不要询问类、模块、表、协议、缓存、存储、并发实现、接口命名和其他不改变产品结果的技术选择。代码能回答的事实不得转问负责人。

## 工作流程

### 1. 定位工作单元并调查事实

若存在 `00`，先读取索引定位当前 `Uxx`、范围、实际依赖和当前文档；否则按未分支路径处理。随后读取 `01`、当前工作单元相关代码、配置、协议、测试、历史行为和现有待确认事项。代码细节只用于判断影响，不写成长篇背景。

如果调查证明当前范围应拆成独立工作单元，按“产物与工作单元”的规则先完成拆分和索引更新，再继续提问；不得在一份 `02` 中长期混合多个可以独立推进的分支。

### 2. 筛选问题

问题只有同时满足以下条件才进入当前工作单元文档：

1. 答案可能改变产品行为、范围、资产、安全或验收；
2. 需求负责人拥有决定权；
3. 现有资料无法可靠回答；
4. 影响值得沟通；
5. 不是重复问题或实现细节；
6. 属于当前工作单元范围，而不是兄弟工作单元。

优先级：P0 为核心矛盾或重大资产/公平风险；P1 为主要流程和重要边界；P2 仅在确有价值时保留。

### 3. 按问题聚合

每个问题分块最多包含：

- ID、优先级、状态；
- 一个可直接回答的问题；
- 理解该问题所必需的需求或代码依据；
- 明显低风险时的一条建议。

同一问题的信息必须相邻，不按依据、状态、结论等维度拆到其他章节。

### 4. 分轮沟通

每轮提出 1–3 个强相关问题，按依赖顺序推进。分支较大时一次只问一个，不批量堆积低价值边界。

### 5. 回答后立即更新当前阶段

收到回答后，在同一轮完成：

1. 立即原位更新当前 `02` 文档；
2. 部分解决时重写原分块，只保留剩余缺口；
3. 已取消、已默认、价值下降或失效的问题直接移除；
4. 清理因答案变化而失效的其他内容；
5. 仅在产生新的高价值缺口时新增问题；
6. 在回复中明确告知当前 `02` 的完整路径已更新。

若答案形成需要写入唯一 `01-原始需求.md` 的产品规则：

1. 不得直接或静默修改 `01`；
2. 在原问题分块内将状态压缩为“已回答，待确认回写 `01`”，只保留拟回写的最小结论；
3. 主动向用户说明拟修改 `01` 的具体位置和内容，并请求确认；
4. 用户确认后，立即更新 `01`，明确告知用户 `01` 已更新；
5. 随后立即从当前 `02` 删除该临时待回写内容，并再次告知当前 `02` 已更新。

过程追溯由版本历史承担，当前文档不保留旧问题、旧选项和旧答案。

### 6. 更新路由元数据

只有发生以下变化时才同步更新 `00`：

- 新建、拆分或终止工作单元；
- 当前工作单元进入新的阶段；
- 当前权威文档路径变化；
- 工作单元依赖关系变化。

不得把当前问题、P0/P1 数量、答案或状态摘要复制进 `00`。

## 可选保留内容

只有三类内容可在普通待确认问题之外保留：

- 需求负责人明确延期、未来仍需产品决策的事项；
- 足以影响范围、工期或可行性，需要程序评估的重大风险；
- 已回答但尚待用户确认回写 `01` 的最小临时结论。

没有内容时不创建章节，也不写“无”。待回写内容必须留在原问题位置，不能集中成独立章节。

## 收敛条件

对当前叶工作单元：

- 无未解决 P0/P1 产品问题；
- 无尚未确认回写 `01` 的临时结论；
- 当前范围的核心规则可唯一理解；
- 重大技术风险已移交；
- `01` 已在用户确认后吸收全部有效产品结论；
- 当前 `02` 不再重复已确认规则。

结束时只更新当前文档顶部状态并说明该工作单元能否进入程序实现澄清，不生成结论摘要。某个工作单元收敛不代表兄弟工作单元已完成，也不代表整个功能可以进入 `game-review`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一问题出现在当前批次、结论表和台账 | 只保留一个连续问题分块 |
| 回答后在旧问题下面继续追加 | 立即压缩当前分块；需要回写 `01` 时先请求确认 |
| 回答后直接改写 `01` | 先更新当前 `02` 并告知用户，再说明拟回写内容并获得确认 |
| 部分解决仍保留完整旧问题 | 只留下尚未明确的部分 |
| 建立“暂不追问”垃圾桶 | 无决策价值的内容直接移除 |
| 把代码阅读问题转问策划 | 先调查，只有产品决策才问 |
| 只在聊天里说结论，未更新当前 `02` | 同一轮更新当前工作单元文档并明确告知路径 |
| 无实际独立工作却预建 U01/00 | 保持未分支旧文件名，只有真正拆分时才创建索引 |
| 为 U01/U02 创建子目录 | 所有工作单元文件保持在同一 feature 目录 |
| 用 U01.1/U01.2 表达父子关系 | 分配新的稳定 Uxx，父子与串并行统一写在 00 的依赖中 |
| 兄弟分支未完成就阻塞当前分支 | 只检查当前 Uxx 的实际依赖 |
