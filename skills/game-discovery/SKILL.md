# 挖掘游戏需求

## 目标

基于 `01-原始需求.md`、代码和现有实现，找出真正会改变产品规则的遗漏点，通过多轮沟通维护 `02-需求挖掘.md`。

**核心原则：事实自己查，只把产品决策交给需求负责人。**

**文档职责：`01` 保存当前有效产品规则；`02` 只保存尚未解决的高价值产品问题、必要风险、明确延期，以及已经回答但尚待用户确认回写 `01` 的最小临时结论。上游回写确认完成后，该临时内容必须从 `02` 删除。**

**结构硬限制：一个问题只允许一个连续分块，问题、必要依据和建议放在一起。禁止再建立“已确认结论、当前批次、问题台账、暂不追问、收敛检查”等重复分块。**

**闭环硬限制：每轮沟通结束后立即更新当前阶段文档。已解决、已取消、被覆盖或不再有价值的内容必须移除；部分解决时只保留剩余问题。需要回写 `01` 时，只在原问题分块内保留最小的待回写状态，不另建结论区。**

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

## 产物

必须先有 `01-原始需求.md`。默认维护：

```text
docs/requirements/<feature>/02-需求挖掘.md
```

使用 [需求挖掘模板](references/需求挖掘模板.md)。文档表示当前状态，不保存问答流水。

## 职责边界

可以询问会改变玩家行为、规则、范围、资产、资格、时序、失败结果、跨系统关系或运营兼容的产品决定。

不要询问类、模块、表、协议、缓存、存储、并发实现、接口命名和其他不改变产品结果的技术选择。代码能回答的事实不得转问负责人。

## 工作流程

### 1. 调查事实

读取原始需求、相关代码、配置、协议、测试、历史行为和现有待确认事项。代码细节只用于判断影响，不写成长篇背景。

### 2. 筛选问题

问题只有同时满足以下条件才进入文档：

1. 答案可能改变产品行为、范围、资产、安全或验收；
2. 需求负责人拥有决定权；
3. 现有资料无法可靠回答；
4. 影响值得沟通；
5. 不是重复问题或实现细节。

优先级：P0 为核心矛盾或重大资产/公平风险；P1 为主要流程和重要边界；P2 仅在确有价值时保留。

### 3. 按问题聚合

每个问题分块最多包含：

- ID、优先级、状态；
- 一个可直接回答的问题；
- 理解该问题所必需的需求或代码依据；
- 明显低风险时的一条建议。

同一问题的信息必须相邻，不按依据、状态、结论等维度拆到其他章节。

### 4. 分轮沟通

每轮提出 1–3 个强相关问题，按依赖顺序推进。分支较大时一次只问一个，不批量堆积低价值边界。

### 5. 回答后立即更新当前阶段

收到回答后，在同一轮完成：

1. 立即原位更新 `02-需求挖掘.md`；
2. 部分解决时重写原分块，只保留剩余缺口；
3. 已取消、已默认、价值下降或失效的问题直接移除；
4. 清理因答案变化而失效的其他内容；
5. 仅在产生新的高价值缺口时新增问题；
6. 在回复中明确告知用户 `02-需求挖掘.md` 已更新。

若答案形成需要写入 `01-原始需求.md` 的产品规则：

1. 不得直接或静默修改 `01`；
2. 在原问题分块内将状态压缩为“已回答，待确认回写 `01`”，只保留拟回写的最小结论；
3. 主动向用户说明拟修改 `01` 的具体位置和内容，并请求确认；
4. 用户确认后，立即更新 `01`，明确告知用户 `01` 已更新；
5. 随后立即从 `02` 删除该临时待回写内容，并再次告知 `02` 已更新。

过程追溯由版本历史承担，当前文档不保留旧问题、旧选项和旧答案。

## 可选保留内容

只有三类内容可在普通待确认问题之外保留：

- 需求负责人明确延期、未来仍需产品决策的事项；
- 足以影响范围、工期或可行性，需要程序评估的重大风险；
- 已回答但尚待用户确认回写 `01` 的最小临时结论。

没有内容时不创建章节，也不写“无”。待回写内容必须留在原问题位置，不能集中成独立章节。

## 收敛条件

- 无未解决 P0/P1 产品问题；
- 无尚未确认回写 `01` 的临时结论；
- 核心规则与范围可唯一理解；
- 重大技术风险已移交；
- `01` 已在用户确认后吸收全部有效结论；
- `02` 不再重复已确认规则。

结束时只更新顶部状态并说明能否进入程序实现澄清，不再生成结论摘要。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一问题出现在当前批次、结论表和台账 | 只保留一个连续问题分块 |
| 回答后在旧问题下面继续追加 | 立即压缩当前分块；需要回写 `01` 时先请求确认 |
| 回答后直接改写 `01` | 先更新 `02` 并告知用户，再说明拟回写内容并获得确认 |
| 部分解决仍保留完整旧问题 | 只留下尚未明确的部分 |
| 建立“暂不追问”垃圾桶 | 无决策价值的内容直接移除 |
| 把代码阅读问题转问策划 | 先调查，只有产品决策才问 |
| 只在聊天里说结论，未更新 `02` | 同一轮更新当前阶段文档并明确告知路径 |
