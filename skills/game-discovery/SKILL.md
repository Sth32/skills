# 挖掘游戏需求

## 目标

基于 `01-原始需求.md`、代码架构和现有实现，找出会实质改变游戏规则、玩家结果或需求范围的遗漏点，并通过多轮采访维护 `02-需求挖掘.md`。

**核心原则：代码用于发现事实与影响，问题只交给真正拥有产品决策权的人。**

## 前置条件与产物

- 必须先有 `01-原始需求.md`；没有时先使用 `game-spec`。
- 默认写入：

```text
docs/requirements/<feature>/02-需求挖掘.md
```

使用 [需求挖掘模板](references/需求挖掘模板.md)。整个采访过程围绕这一份文档更新，不在聊天中维护独立问题清单。

## 职责边界

可以问需求负责人：

- 玩家或系统在某种条件下应该发生什么；
- 规则适用于谁、何时生效、何时结束；
- 奖励、消耗、资格、次数、状态和优先级；
- 失败、取消、重复操作和跨系统交互的产品结果；
- 旧数据、旧玩法、活动配置或运营流程是否需要兼容；
- 哪些内容明确不在本次范围。

不要问需求负责人：

- 使用哪个类、模块、表、协议、缓存或存储；
- 如何拆服务、发消息、加锁或处理并发；
- 具体代码路径、接口命名、测试框架；
- 纯粹由程序选择且不改变产品结果的实现方式。

如发现重大实现风险，只写为“风险提醒”，说明它可能影响范围、工期或可行性，并要求程序专项评估；不要让策划设计技术方案。

## 工作流程

### 1. 读取事实，而不是先提问

先检查：

- 原始需求及其冲突项；
- 相关代码、配置、协议、数据结构、测试和历史行为；
- 同类玩法或既有规则；
- 已记录的答案和已关闭问题。

代码能直接回答的“当前系统如何工作”，写入依据，不再询问负责人。

### 2. 生成候选缺口

从实际需求与代码影响出发检查：

- 核心规则是否存在两种合理解释；
- 主体、资格、触发、时序、状态变化或结束条件是否缺失；
- 奖励、消耗、次数、冲突优先级是否会影响公平或资产；
- 常见失败、取消、重复、并发操作的玩家结果是否未定义；
- 与现有系统、历史数据、活动配置或旧版本是否产生产品冲突；
- 范围边界是否会让不同角色得出不同结论。

这些只是搜索方向，不是必须逐项发问的检查表。

### 3. 通过价值门槛

候选问题只有同时满足以下条件才可提出：

1. 答案可能改变玩家可见行为、规则、范围、资产、安全或验收结果；
2. 需求负责人有权做这个决定；
3. 现有需求、代码或资料无法可靠回答；
4. 发生概率与影响相乘后值得讨论；
5. 问题不是另一个未解决问题的重复或下游细节。

任一条件不满足，删除候选问题或记录为程序实现事项。

### 4. 排优先级

- **P0**：核心规则矛盾；阻塞需求定义；可能导致玩家资产、经济、公平、数据损失或线上严重冲突。
- **P1**：影响常见流程、生命周期、跨系统行为、重要例外或主要验收结果。
- **P2**：有一定价值但不影响主流程，可采用明确默认值或延期。

先解决 P0，再解决 P1。P0/P1 未收敛时，不因“看起来完整”而批量追问 P2。

### 5. 先写文档，再发问题

每个问题必须先进入 `02-需求挖掘.md`，至少包含：

- 问题 ID、状态和优先级；
- 面向负责人的问题；
- 为什么值得问；
- 来自原始需求或代码的依据；
- 可选的建议默认值；
- 负责人原意的简洁记录；
- 处理结论与衍生问题。

问题本身使用产品语言。代码细节只出现在“依据”中，且翻译为负责人能理解的影响。

### 6. 分轮采访

每轮提出 1–3 个强相关问题：

- 决策分支较大时，一次只问一个；
- 可共同回答且互不依赖时，最多三个；
- 按依赖顺序提问，不让负责人回答尚未成立的下游问题；
- 每个问题保持短而具体，必要时给 2–3 个可选答案；
- 只有存在明显低风险默认方案时才给建议，并说明理由。

### 7. 回答后立即回写并重新评估

收到回答后：

1. 将答案压缩为不改变原意的决策记录；
2. 标记为“已解决、部分解决、已延期或取消”；
3. 说明它改变了哪些需求规则；
4. 更新 `01-原始需求.md` 时，只追加已确认内容并保留来源；
5. 检查是否产生新的高价值问题；
6. 删除已被答案覆盖、价值下降或不再成立的问题；
7. 再生成下一轮，而不是沿用旧问题列表机械追问。

“问题已回答”不等于“问题已解决”。只有答案足够明确、能落入确定规则时才算解决。

## 收敛条件

满足以下条件后结束需求挖掘：

- 没有未解决的 P0/P1 产品问题；
- 核心规则、生命周期、主要结果和范围边界可被唯一理解；
- 重大风险已明确交给程序评估；
- 剩余 P2 已有默认值、负责人或延期理由；
- 文档中的结论与原始需求没有未标记矛盾。

结束时在文档顶部标记“需求挖掘已收敛”，并输出已确认结论、剩余延期项和是否可进入程序实现澄清。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为显示专业而罗列几十个边界问题 | 只保留会改变决策的少数问题 |
| 把代码看不懂变成策划问题 | 先调查代码，事实自己解决 |
| 问策划“用数据库还是缓存” | 改问对玩家结果有影响的产品规则，技术选择留给程序 |
| 每轮只新增问题，不关闭问题 | 回答后更新状态、影响和衍生关系 |
| 把极低概率且低影响情况当阻塞项 | 采用默认值或延期，不钻牛角尖 |
| 发现技术风险后直接否定需求 | 提醒风险和影响，由程序评估可行性 |
