# 挖掘游戏需求

## 目标

基于 `01-原始需求.md`、代码和现有实现，找出真正会改变产品规则的遗漏点，通过多轮沟通维护 `02-需求挖掘.md`。

**核心原则：事实自己查，只把产品决策交给需求负责人。**

**文档职责：`01` 保存当前有效产品规则；`02` 只保存尚未解决的高价值产品问题、必要风险和明确延期。已确认结论必须回写 `01`，不得同时留在 `02`。**

**结构硬限制：一个问题只允许一个连续分块，问题、必要依据和建议放在一起。禁止再建立“已确认结论、当前批次、问题台账、暂不追问、收敛检查”等重复分块。**

**闭环硬限制：每轮沟通结束后立即更新文档。已解决、已取消、被覆盖或不再有价值的内容必须移除；部分解决时只保留剩余问题。**

## 产物

必须先有 `01-原始需求.md`。默认维护：

```text
docs/requirements/<feature>/02-需求挖掘.md
```

使用 [需求挖掘模板](references/需求挖掘模板.md)。文档表示当前状态，不保存问答流水。

## 职责边界

可以询问会改变玩家行为、规则、范围、资产、资格、时序、失败结果、跨系统关系或运营兼容的产品决定。

不要询问类、模块、表、协议、缓存、存储、并发实现、接口命名和其他不改变产品结果的技术选择。代码能回答的事实不得转问负责人。

## 工作流程

### 1. 调查事实

读取原始需求、相关代码、配置、协议、测试、历史行为和现有待确认事项。代码细节只用于判断影响，不写成长篇背景。

### 2. 筛选问题

问题只有同时满足以下条件才进入文档：

1. 答案可能改变产品行为、范围、资产、安全或验收；
2. 需求负责人拥有决定权；
3. 现有资料无法可靠回答；
4. 影响值得沟通；
5. 不是重复问题或实现细节。

优先级：P0 为核心矛盾或重大资产/公平风险；P1 为主要流程和重要边界；P2 仅在确有价值时保留。

### 3. 按问题聚合

每个问题分块最多包含：

- ID、优先级、状态；
- 一个可直接回答的问题；
- 理解该问题所必需的需求或代码依据；
- 明显低风险时的一条建议。

同一问题的信息必须相邻，不按依据、状态、结论等维度拆到其他章节。

### 4. 分轮沟通

每轮提出 1–3 个强相关问题，按依赖顺序推进。分支较大时一次只问一个，不批量堆积低价值边界。

### 5. 回答后立即更新

收到回答后，在同一轮完成：

1. 把明确结论写回 `01` 的对应规则；
2. 用新结论替换旧描述；
3. 从 `02` 移除已解决问题；
4. 部分解决时重写原分块，只保留剩余缺口；
5. 移除已取消、已默认、价值下降或失效的问题；
6. 清理因答案变化而失效的其他内容；
7. 仅在产生新的高价值缺口时新增问题。

过程追溯由版本历史承担，当前文档不保留旧问题、旧选项和旧答案。

## 可选保留内容

只有两类内容可在待确认问题之外保留：

- 需求负责人明确延期、未来仍需产品决策的事项；
- 足以影响范围、工期或可行性，需要程序评估的重大风险。

没有内容时不创建章节，也不写“无”。

## 收敛条件

- 无未解决 P0/P1 产品问题；
- 核心规则与范围可唯一理解；
- 重大技术风险已移交；
- `01` 已吸收全部有效结论；
- `02` 不再重复已确认规则。

结束时只更新顶部状态并说明能否进入程序实现澄清，不再生成结论摘要。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一问题出现在当前批次、结论表和台账 | 只保留一个连续问题分块 |
| 回答后在旧问题下面继续追加 | 回写 `01`，移除已解决内容 |
| 部分解决仍保留完整旧问题 | 只留下尚未明确的部分 |
| 建立“暂不追问”垃圾桶 | 无决策价值的内容直接移除 |
| 把代码阅读问题转问策划 | 先调查，只有产品决策才问 |
