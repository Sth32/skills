# 游戏模块权威文档

## 目标

从当前已实现代码中提炼一份简洁、稳定、可长期信任的模块文档，使维护者能够快速回答：

- 模块负责什么，不负责什么；
- 核心业务规则和唯一事实来源在哪里；
- 数据由谁持有，哪些持久化，哪些只是镜像或运行时派生；
- 模块通过哪些属性、RPC、事件或公共判定与其他实体协作；
- 修改时有哪些不可破坏的系统约束。

**核心原则：分析可以深入，落盘只保留长期稳定的系统契约。**

**单文档硬限制：同一功能或模块只能存在一份权威实现文档。** 不得另建架构摘要、数据说明、接口手册、实现复盘、维护清单、FAQ、`v2` 或 `final` 平行版本。已有内容必须原位重写；代码注释、测试、协议定义和配置源属于事实来源，不算旁支权威文档。

文档描述当前生效的系统事实，不是代码导读、实现复盘、评审报告、排查记录或任务清单。

## 输入与默认产物

读取：

- `01-原始需求.md` 至 `07-交叉评审.md` 中实际存在且仍有解释价值的结论；
- 当前代码、属性定义、RPC、持久化、配置消费点和测试；
- 项目既有文档结构、命名和索引约定；
- 当前提交或可确认的版本标识。

优先遵循项目已有文档目录。没有约定时默认写入：

```text
docs/features/<feature>.md
```

使用 [功能实现文档模板](references/功能实现文档模板.md)。已有同主题文档时原位重写，不新建平行版本或拆分子文档。

## 事实优先级

材料不一致时，以当前系统真实行为为准：

1. 当前可运行代码与属性、协议定义；
2. 已验证测试和运行证据；
3. 最新 review 结论；
4. 实现方案与澄清文档；
5. 原始需求和早期讨论。

方案与代码不一致时，记录实际实现。历史原因只有在它仍约束未来修改时才保留。

不确定的信息不得写成权威结论。若它影响当前正确使用，只写明确的现状边界，例如“跨区场景不支持”，不要写成待办。

## 应该记录什么

### 1. 职责与边界

用少量文字说明：

- 模块解决什么问题；
- 权威实体或组件是谁；
- 主要消费者是谁；
- 复用了什么既有机制；
- 明确不改变或不负责什么。

不重写完整需求，不描述本次开发过程。

### 2. 核心规则

只记录决定外部行为或约束未来修改的规则，例如：

- 某资格何时成立、何时失效；
- 多个入口必须共享哪一个公共判定；
- 状态变化后需要实时重算还是读取缓存；
- 哪些看似相近的关系或接口不能合并；
- 哪些顺序、幂等、唯一性或失败语义必须保持。

先写系统结论，再用一句话说明原因或影响。除非调用顺序本身就是契约，否则不要展开逐函数调用链。

### 3. 数据与持久化

对关键属性和状态说明：

- 权威所有者；
- 是否持久化；
- 是否存在其他实体或客户端镜像；
- 镜像由谁、在什么时机同步；
- 哪些结果只在运行时派生，不应重复持久化。

只记录影响一致性和恢复行为的数据，不展开完整 Schema 或字段清单。

### 4. 关键协作契约

记录跨模块、跨实体或跨端的稳定合同：

- 属性同步方向和生命周期语义；
- RPC 或事件的发送时机、方向和业务含义；
- 公共判定或唯一事实来源；
- 配置控制什么，以及由哪个稳定入口消费。

代码名和路径只作为定位锚点。只列唯一事实来源和主要入口，不做完整文件目录。

### 5. 修改约束

只保留少量、不写就容易产生隐蔽错误的不变量。普通实现细节、通用编码规范和可从局部代码直接看出的内容不写。

同一系统事实只描述一次；若职责、规则、数据与协作内容属于同一个问题，应放在相邻位置，不为了分类完整而拆散或另建文档。

## 禁止写入

默认删除：

- 配表当前值、表格行号、资源数值、时长、耐久和概率等可调参数；
- TODO、待办、延期项、未完成项和后续优化建议；
- 临时 bug、修复过程、排查日志、测试记录和客户端崩溃修复步骤；
- 完整文件清单、逐函数说明、逐分支伪代码和长调用链；
- “本次新增或修改了什么代码”的实现汇报；
- 扩展清单、未来功能设计和任务拆分；
- 占位资源、短期兼容方案和已关闭问题；
- 可从类型、命名和局部实现直接推断的内容；
- 与主文档内容重复的架构、接口、数据或维护子文档。

数字标识仅在它属于跨系统协议、存档或兼容契约时保留；普通枚举值和配置值不写。

未解决问题应留在代码 TODO、issue 或 review 文档中，不进入长期权威文档。已经存在但必须让使用者知道的限制，改写成当前支持边界。

## 工作流程

### 1. 确定模块边界

明确文档对应的业务模块、权威所有者、主要消费者和既有机制边界。边界不清时先从数据所有权和外部行为反推，不按文件夹机械划分模块。

同时查找已有同主题文档；若存在，选择唯一权威文档原位更新，不新建替代品。

### 2. 从代码重建事实

检查入口、状态变化、属性定义、持久化、镜像同步、RPC、事件、配置消费和失败语义。过程文档用于解释原因和发现遗漏，不能替代代码调查。

### 3. 提炼稳定契约

把候选内容归类为职责、规则、数据、协作和修改约束。每条内容都要通过：

1. 半年后它仍大概率成立吗？
2. 不记录它，维护者是否容易破坏系统语义？
3. 它是否描述了代码之外仍需要明确的契约？

未通过则删除，或改放代码注释、测试、TODO、issue 和 review 文档。

### 4. 过滤临时与重复信息

主动移除配置快照、任务状态、实现证据链、修复记录和普通代码细节。不要因为调研时花了很多精力，就把所有发现都写进文档。

若其他文档与本权威文档重复，应合并必要的稳定契约并删除或废弃重复文档，而不是维持多个真相来源。

### 5. 原位重写

已有文档存在重复、过时或粒度过细内容时，直接删除和重写对应章节。不要在末尾继续堆叠“补充说明”“扩展清单”“延期项”，也不要创建新版文件。

### 6. 最终压缩

- 相同结论只出现一次；
- 同一问题的相关信息尽量相邻；
- 能用一段说明的，不拆成完整流程；
- 没有实质内容的章节直接删除；
- 删除任意一段后若不影响理解或安全修改，就应删除。

## 默认文档结构

```markdown
# <功能或模块名>

> 最后核对：<commit / 日期>
> 权威入口：`path/to/authority`

## 职责与边界

## 核心规则

## 数据与持久化

## 关键协作

## 修改约束
```

章节不是必须全部出现。简单模块可以很短，不为结构完整而填充；若同一问题横跨多个分类，优先保证相邻可读性，而不是机械服从标题。

## 写作标准

- 以业务语义和系统契约为主，代码名只用于定位；
- 属性说明所有者、同步方向、持久化与否，不复制完整 Schema；
- RPC 说明发送时机、调用方向和语义，不复制实现；
- 配置只说明控制内容和消费方，不记录当前取值；
- 同一规则被多个入口使用时，强调共享判定和一致性要求；
- 对客户端只记录服务端提供的数据合同，不深入客户端表现实现；
- 使用确定陈述描述当前事实，不混入计划、建议和任务状态；
- 同一模块不创建第二份说明文档。

## 完成前检查

确认文档能清楚回答：

- 模块的职责和边界是什么？
- 哪个实体或组件是唯一事实来源？
- 核心规则是什么？
- 数据由谁持有，哪些持久化，哪些镜像或运行时计算？
- 主要协作入口和消费者有哪些？
- 修改时最容易破坏什么不变量？

同时确认：

- 没有可调配表值和普通数字快照；
- 没有 TODO、待办、延期项或未来扩展清单；
- 没有实现过程、修复步骤和排查记录；
- 没有完整文件目录或重复调用链；
- 没有与本文件竞争权威性的平行文档；
- 每个现状结论都能在代码、属性定义或测试中找到依据；
- 文档已经压缩到继续删除会损害理解或修改安全的程度。

## 完成条件

- 项目内存在唯一、可发现的模块权威文档；
- 文档以当前实现为准，并注明最后核对版本；
- 职责、规则、数据权威、持久化、同步和关键协作清楚；
- 不包含配置快照、任务状态、实现复盘或易过期细节；
- 阅读者无需先通读完整代码，也能判断应从哪里读、哪些语义不能破坏。
