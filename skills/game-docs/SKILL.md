# 持久化游戏功能实现文档

## 目标

把需求与实现过程中的稳定结论转为项目内长期文档，让后续维护者快速知道“从哪里读代码、哪些边界不能破坏、哪里容易踩坑”。

**核心原则：文档是代码的导航和风险提示，不是代码的复制品。**

## 输入与默认产物

读取：

- `01-原始需求.md` 至 `07-交叉评审.md` 中实际存在的文档；
- 当前代码、配置、测试、迁移和运维入口；
- 项目既有文档结构、命名和索引约定；
- 当前提交或可确认的版本标识。

优先遵循项目已有文档目录。没有约定时默认写入：

```text
docs/features/<feature>.md
```

使用 [功能实现文档模板](references/功能实现文档模板.md)。已有同主题文档时原位更新，不新建 `v2`、`final` 等平行版本。

## 事实优先级

当材料不一致时：

1. 当前可运行代码与配置；
2. 已验证测试、迁移和运行证据；
3. 最新 review 结论；
4. 实现方案与澄清文档；
5. 原始需求和早期讨论。

方案描述与代码不一致时，记录实际实现，并只在“设计背景/差异”中保留仍有维护价值的原因。不要把过期计划写成现状。

## 应该记录什么

### 1. 功能定位与范围

用少量文字说明：

- 功能解决什么问题；
- 核心参与者和边界；
- 明确不负责什么；
- 与哪些系统存在关键连接。

不重写完整需求文档。

### 2. 实现框架

记录稳定结构：

- 模块/进程责任和数据所有权；
- 主要入口、核心编排和关键出口；
- 持久化实体、状态模型和生命周期；
- 配置来源、加载位置和跨端契约；
- 关键扩展点和替换边界。

用代码路径引导阅读。路径应指向稳定入口或目录，不依赖精确行号。

### 3. 关键不变量与决策理由

只记录后续修改容易破坏、但仅看局部代码不容易理解的内容，例如：

- 资产或次数为何必须在某处结算；
- 为什么由某模块拥有状态；
- 幂等键、唯一性或状态转换的约束；
- 为什么不能复用某个看似相近的接口；
- 兼容、迁移、灰度和回滚的关键限制。

重点记录“为什么”，而不是逐函数说明“怎么写”。

### 4. 坑点和失败处理

记录真实风险：

- 已发生或 review 发现的高价值坑点；
- 乱序、重试、重复请求和部分失败的处理原则；
- 配置误配、旧数据或混部时的表现；
- 线上排查入口、日志、指标和恢复手段。

不要把所有可能错误写成泛化清单。

### 5. 验证与代码导航

列出：

- 最关键的测试入口和 smoke test；
- 本地启动、导表或最小验证命令；
- 调试时首先查看的日志、指标和代码路径；
- 最后核对的提交或日期。

文档应促使读者打开相关代码，而不是让人绕过代码。

## 不应该记录什么

- 每个类、函数、字段和调用步骤；
- 可从类型和命名直接看出的内容；
- 当前配置的全部数值和表格副本；
- 短期 TODO、开发过程流水账和已关闭问题；
- 精确行号、易变私有函数和大段代码粘贴；
- 未经代码验证的方案设想；
- 为“文档完整”而重复 `01` 至 `07` 的全部内容。

## 工作流程

### 1. 找到项目文档约定

先检查已有 feature、architecture、system 或 module 文档。复用其目录、标题和索引方式。只有没有约定时才使用默认路径。

### 2. 从代码重建稳定心智模型

从入口、数据所有者、状态变化、配置消费和失败路径反向理解实际框架。过程文档用于解释原因和发现遗漏，不替代代码调查。

### 3. 筛选长期价值

每条候选内容都要通过三个问题：

1. 半年后它仍大概率成立吗？
2. 不记录它，维护者是否容易做出错误修改？
3. 它是否能引导读者找到正确代码或验证入口？

未通过则删除或改为代码注释/测试，不放入长期文档。

### 4. 写短而可导航的文档

推荐结构不超过实际需要。简单功能可以很短；复杂功能也应优先使用架构图、表格、短段落和代码路径。

文档顶部记录“最后核对提交/日期”。这不是保证永远最新，而是让读者判断可信度。

### 5. 更新而不是堆叠

已有文档时：

- 删除已失效结构；
- 更新代码入口和不变量；
- 保留仍能解释当前设计的历史理由；
- 将已经修复且不再有教育价值的坑点移除；
- 按项目约定更新索引。

没有代码访问或无法确认当前实现时，不宣称文档已更新，只输出待核对项。

### 6. 自检

完成前检查：

- 文档中的每个“现状”能在代码或测试中找到依据；
- 没有把计划、延期项或旧方案写成已实现；
- 核心不变量和危险坑点足够醒目；
- 代码路径能把读者带到正确入口；
- 删除一半细节后是否仍能达到目的；若能，继续压缩。

## 完成条件

- 项目内存在唯一、可发现的功能实现文档；
- 文档以当前代码为准，注明核对版本；
- 实现框架、关键不变量、集成点和坑点清楚；
- 没有大量易过期的逐函数或逐字段细节；
- 阅读者能据此快速定位需要阅读和验证的代码。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把所有过程文档拼接成长期文档 | 只提炼稳定框架、关键决策和坑点 |
| 用文档替代代码阅读 | 给出入口和心智模型，引导阅读代码 |
| 记录精确行号和私有函数 | 指向稳定目录、模块、公共类型或入口 |
| 方案与代码冲突时沿用方案 | 以当前代码和验证证据为准 |
| 害怕过期而不写任何文档 | 写稳定内容并注明最后核对版本 |
| 文档越写越长从不删除 | 更新时主动删除失效和低价值细节 |
