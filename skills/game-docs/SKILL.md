# 游戏模块权威文档

## 目标

从当前已实现代码中提炼一份简洁、稳定、可长期信任的模块文档，使维护者能够快速回答：

- 模块负责什么，不负责什么；
- 核心业务规则和唯一事实来源在哪里；
- 数据由谁持有，哪些持久化，哪些只是镜像或运行时派生；
- 模块通过哪些属性、RPC、事件或公共判定与其他实体协作；
- 修改时有哪些不可破坏的系统约束。

**核心原则：分析可以深入，落盘只保留长期稳定的系统契约。**

**单文档硬限制：同一功能或模块只能存在一份权威实现文档。** 不得另建架构摘要、数据说明、接口手册、实现复盘、维护清单、FAQ、`v2` 或 `final` 平行版本。已有内容必须原位重写；代码注释、测试、协议定义和配置源属于事实来源，不算旁支权威文档。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。写入必须调用本 skill 自带的 `scripts/document_record.py append`；该脚本使用 UTF-8（无 BOM）字节单次追加，并在追加前静默校验已有文件仍是 UTF-8 JSONL。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过；找不到脚本、现有文件编码异常或追加失败时，必须明确告知用户并停止记录写入。记录至少包含时间、skill、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

文档描述当前生效的系统事实，不是代码导读、实现复盘、评审报告、排查记录或任务清单。

## 输入与默认产物

读取：

- `01-原始需求.md` 至 `07-交叉评审.md` 中实际存在且仍有解释价值的结论；
- 当前代码、属性定义、RPC、持久化、配置消费点和测试；
- 项目既有文档结构、命名和索引约定；
- 当前提交或可确认的版本标识。

优先遵循项目已有文档目录。没有约定时默认写入：

```text
docs/features/<feature>.md
```

使用 [功能实现文档模板](references/功能实现文档模板.md)。已有同主题文档时原位重写，不新建平行版本或拆分子文档。

## 事实优先级

材料不一致时，以当前系统真实行为为准：

1. 当前可运行代码与属性、协议定义；
2. 已验证测试和运行证据；
3. 最新 review 结论；
4. 实现方案与澄清文档；
5. 原始需求和早期讨论。

方案与代码不一致时，本阶段权威文档记录实际实现，并在同一轮完成更新、明确告知用户路径。若该不一致同时说明 `01` 至 `07` 的过程文档已经过时，不得顺手改写；必须主动列明受影响文档和拟修改内容，获得用户确认后再更新。

历史原因只有在它仍约束未来修改时才保留。

不确定的信息不得写成权威结论。若它影响当前正确使用，只写明确的现状边界，例如“跨区场景不支持”，不要写成待办。

## 应该记录什么

### 1. 职责与边界

用少量文字说明：

- 模块解决什么问题；
- 权威实体或组件是谁；
- 主要消费者是谁；
- 复用了什么既有机制；
- 明确不改变或不负责什么。

不重写完整需求，不描述本次开发过程。

### 2. 核心规则

只记录决定外部行为或约束未来修改的规则，例如：

- 某资格何时成立、何时失效；
- 多个入口必须共享哪一个公共判定；
- 状态变化后需要实时重算还是读取缓存；
- 哪些看似相近的关系或接口不能合并；
- 哪些顺序、幂等、唯一性或失败语义必须保持。

先写系统结论，再用一句话说明原因或影响。除非调用顺序本身就是契约，否则不要展开逐函数调用链。

### 3. 数据与持久化

对关键属性和状态说明：

- 权威所有者；
- 是否持久化；
- 是否存在其他实体或客户端镜像；
- 镜像由谁、在什么时机同步；
- 哪些结果只在运行时派生，不应重复持久化。

只记录影响一致性和恢复行为的数据，不展开完整 Schema 或字段清单。

### 4. 关键协作契约

记录跨模块、跨实体或跨端的稳定合同：

- 属性同步方向和生命周期语义；
- RPC 或事件的发送时机、方向和业务含义；
- 公共判定或唯一事实来源；
- 配置控制什么，以及由哪个稳定入口消费。

代码名和路径只作为定位锚点。只列唯一事实来源和主要入口，不做完整文件目录。

### 5. 修改约束

只保留少量、不写就容易产生隐蔽错误的不变量。普通实现细节、通用编码规范和可从局部代码直接看出的内容不写。

同一系统事实只描述一次；若职责、规则、数据与协作内容属于同一个问题，应放在相邻位置，不为了分类完整而拆散或另建文档。

任何一项稳定契约形成、变化或被证伪后，必须立即原位更新权威文档并告知用户，不等待整份文档核对结束。

## 禁止写入

默认删除：

- 配表当前值、表格行号、资源数值、时长、耐久和概率等可调参数；
- TODO、待办、延期项、未完成项和后续优化建议；
- 临时 bug、修复过程、排查日志、测试记录和客户端崩溃修复步骤；
- 完整文件清单、逐函数说明、逐分支伪代码和长调用链；
- “本次新增或修改了什么代码”的实现汇报；
- 扩展清单、未来功能设计和任务拆分；
- 占位资源、短期兼容方案和已关闭问题；
- 可从类型、命名和局部实现直接推断的内容；
- 与主文档内容重复的架构、接口、数据或维护子文档。

数字标识仅在它属于跨系统协议、存档或兼容契约时保留；普通枚举值和配置值不写。

未解决问题应留在代码 TODO、issue 或 review 文档中，不进入长期权威文档。已经存在但必须让使用者知道的限制，改写成当前支持边界。

## 工作流程

### 1. 确定模块边界

明确文档对应的业务模块、权威所有者、主要消费者和既有机制边界。边界不清时先从数据所有权和外部行为反推，不按文件夹机械划分模块。

同时查找已有同主题文档；若存在，选择唯一权威文档原位更新，不新建替代品。边界确认或变化后，立即更新该文档并告知用户。

### 2. 从代码重建事实

检查入口、状态变化、属性定义、持久化、镜像同步、RPC、事件、配置消费和失败语义。过程文档用于解释原因和发现遗漏，不能替代代码调查。

每获得一项足以改变权威文档的可靠事实，立即原位更新并告知用户，不把发现积攒到最后统一写入。

### 3. 提炼稳定契约

把候选内容归类为职责、规则、数据、协作和修改约束。每条内容都要通过：

1. 半年后它仍大概率成立吗？
2. 不记录它，维护者是否容易破坏系统语义？
3. 它是否描述了代码之外仍需要明确的契约？

未通过则删除，或改放代码注释、测试、TODO、issue 和 review 文档。通过的契约应立即写入权威文档并告知用户。

### 4. 过滤临时与重复信息

主动移除配置快照、任务状态、实现证据链、修复记录和普通代码细节。不要因为调研时花了很多精力，就把所有发现都写进文档。

若其他长期实现文档与本权威文档重复，应合并必要的稳定契约并删除或废弃重复文档；涉及删除或改写此前阶段的过程文档时，必须先说明具体文档和拟修改内容，获得用户确认后再操作。

### 5. 原位重写

已有文档存在重复、过时或粒度过细内容时，直接删除和重写对应章节。不要在末尾继续堆叠“补充说明”“扩展清单”“延期项”，也不要创建新版文件。

每次重写完成后立即告知用户已更新的具体路径。若重写依据证明 `01` 至 `07` 需要同步修订，先完成当前权威文档更新，再主动列明上游修改建议并等待确认。

### 6. 最终压缩

- 相同结论只出现一次；
- 同一问题的相关信息尽量相邻；
- 能用一段说明的，不拆成完整流程；
- 没有实质内容的章节直接删除；
- 删除任意一段后若不影响理解或安全修改，就应删除。

最终压缩引起内容变化时，也必须立即写入并告知用户，不能只在回复里描述修改建议。

## 默认文档结构

```markdown
# <功能或模块名>

> 最后核对：<commit / 日期>
> 权威入口：`path/to/authority`

## 职责与边界

## 核心规则

## 数据与持久化

## 关键协作

## 修改约束
```

章节不是必须全部出现。简单模块可以很短，不为结构完整而填充；若同一问题横跨多个分类，优先保证相邻可读性，而不是机械服从标题。

## 写作标准

- 以业务语义和系统契约为主，代码名只用于定位；
- 属性说明所有者、同步方向、持久化与否，不复制完整 Schema；
- RPC 说明发送时机、调用方向和语义，不复制实现；
- 配置只说明控制内容和消费方，不记录当前取值；
- 同一规则被多个入口使用时，强调共享判定和一致性要求；
- 对客户端只记录服务端提供的数据合同，不深入客户端表现实现；
- 使用确定陈述描述当前事实，不混入计划、建议和任务状态；
- 同一模块不创建第二份说明文档；
- 每次内容更新后明确告知用户已更新的文件路径。

## 完成前检查

确认文档能清楚回答：

- 模块的职责和边界是什么？
- 哪个实体或组件是唯一事实来源？
- 核心规则是什么？
- 数据由谁持有，哪些持久化，哪些镜像或运行时计算？
- 主要协作入口和消费者有哪些？
- 修改时最容易破坏什么不变量？

同时确认：

- 没有可调配表值和普通数字快照；
- 没有 TODO、待办、延期项或未来扩展清单；
- 没有实现过程、修复步骤和排查记录；
- 没有完整文件目录或重复调用链；
- 没有与本文件竞争权威性的平行文档；
- 每个现状结论都能在代码、属性定义或测试中找到依据；
- 没有未经用户确认而被改写的 `01` 至 `07` 上游文档；
- 文档已经压缩到继续删除会损害理解或修改安全的程度。

## 完成条件

- 项目内存在唯一、可发现的模块权威文档；
- 文档以当前实现为准，并注明最后核对版本；
- 职责、规则、数据权威、持久化、同步和关键协作清楚；
- 不包含配置快照、任务状态、实现复盘或易过期细节；
- 无尚待用户确认修订的上游文档阻塞；
- 阅读者无需先通读完整代码，也能判断应从哪里读、哪些语义不能破坏。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 调查完成后才一次性重写文档 | 可靠事实一旦改变当前内容，就在同一轮立即更新并告知用户 |
| 发现过程文档过时后直接改写 | 先列明受影响文档和拟修改内容，获得用户确认后再更新 |
| 只在聊天中给出新的权威结论 | 必须写回唯一权威文档，并明确告知路径 |
| 为修订结果创建 `v2` 或补充文档 | 原位重写唯一权威文档 |
