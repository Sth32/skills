# 游戏模块权威文档

## 目标

从当前已实现代码中提炼一份简洁、稳定、可长期信任的模块文档，使维护者能够快速回答模块职责、核心规则、数据权威与持久化、关键协作契约和不可破坏约束。

**核心原则：分析可以深入，落盘只保留长期稳定的系统契约。**

**单文档硬限制：同一功能或模块只能存在一份权威实现文档。** 不得另建架构摘要、数据说明、接口手册、实现复盘、维护清单、FAQ、`v2` 或 `final` 平行版本。已有内容必须原位重写；代码注释、测试、协议定义和配置源属于事实来源，不算旁支权威文档。

**分支汇合输入规则：过程工作流若存在 `00-工作流索引.md`，必须先用它定位全部实际工作单元，再读取唯一 `07-交叉评审.md` 与当前代码。`00` 只用于找到分支材料，不得把工作单元 ID、DAG、阶段状态、任务进度或过程拓扑写入长期权威文档。若索引显示仍有未汇合叶工作单元，或 `07` 尚未达到可交付终态，应停止正常文档收敛并回到 `game-review`；不得在长期文档阶段替代 review 汇合。**

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**阶段切换门禁硬限制：阶段文档顶部“状态”是阶段状态的唯一权威来源，聊天中的“完成”“可以进入下一阶段”不构成阶段完成。结束本阶段时，必须先满足本阶段完成/收敛条件，再在同一轮把顶部状态写为本阶段模板定义的可移交终态，同步最后更新时间、未解决计数、当前步骤等受影响元信息，并重新读取文档确认终态已经落盘；在这些动作完成前，不得宣称本阶段完成、移交或下一阶段可以开始。开始或恢复一个按工作流顺序进入的下游阶段时，在创建或修改本阶段文档、配置或代码之前，必须读取本 skill 要求的上游阶段文档顶部状态；任一实际前置上游不是其正常可移交终态时，必须明确指出具体文件与当前状态并停止正常推进，返回对应上游闭环，不得用聊天记录、记忆或推断覆盖文档状态，也不得静默替上游补成已完成。若本 skill 明确允许独立、提前或并行执行，只检查它声明的实际前置；用户在看到状态警告后明确要求带未闭环上游并行推进时，只能进行不依赖未决上游结论的安全工作，并在当前阶段文档显式记录上游阻塞/例外，不得把这种例外描述成正常阶段切换。**

本阶段的实际前置是已完成的整体 `game-review`：未分支时读取单线 `01`–`07`；已分支时读取 `00`、所有仍有解释价值的分支材料与唯一 `07`。不要求长期文档复刻分支结构。

**文档变更记录硬限制：每次创建、修改、删除或重命名本阶段文档后，必须在目标文档所在目录的 `record.jsonl` 追加一条 JSON 记录；`record.jsonl` 是审计元数据，不属于阶段过程文档，记录文件自身的追加不触发再次记录。新记录使用 schema v3，并区分“实际使用 skill”和“未使用 skill”：只要当前 Agent 实际加载/执行了本 skill（即使用户没有显式写出 skill 名称），就必须调用本 skill 自带的 `scripts/document_record.py append --skill <当前skill>`，写入 `skill_usage=used`，`skill_version` 由写入器从当前 `SKILL.md` 的 `metadata.version` 自动读取，禁止 Agent 手填、猜测或沿用历史值；若一次变更实际没有使用任何 skill，才可使用 `--no-skill`，写入 `skill_usage=not_used`、`skill=null`、`skill_version=null`，不得挑选一个“最接近”的 skill 冒充来源。用户是否显式声明 skill 不是归因依据，实际是否加载/执行才是。写入器 append 前只校验已有文件仍可逐行解析为 UTF-8 JSON object；历史行的 schema 字段缺失或语义错误（例如旧 schema v2 缺少 `skill_version`）必须由 `check` 报告，但不得阻塞后续独立追加，也不得静默修改旧行；只有非 UTF-8、非法 JSON、非 object 等存储层损坏才拒绝 append。历史 schema v1 或非法 v2 无版本记录在查询和统计时统一视为 `skill_version=unknown`；no-skill v3 视为 `skill=none`、`skill_version=not_applicable`，不得回填猜测版本。禁止使用 `>`、`>>`、`echo`、PowerShell `Add-Content`/`Set-Content`/`Out-File` 或通用文本写入 API 直接修改 `record.jsonl`，脚本失败时也不得降级绕过。记录至少包含时间、skill usage、skill/版本归因、运行环境、模型、思考等级、动作、文档路径、触发原因、问题与根因、修改摘要、验证结果、结果状态和预防建议；无法获知的模型、思考等级或运行环境写 `unknown`，不得猜测。评估滚动更新的 skill 时必须只使用 `skill_usage=used` 且按 `skill_version` 过滤或分组，不能把 no-skill、版本未知或多个版本直接混为同一版本效果。禁止写入完整提示词、文档正文、用户敏感信息或思维过程。需要评审记录时，只能按条件查询或读取最近有限条目，不得把全文注入上下文。**

文档描述当前生效的系统事实，不是代码导读、实现复盘、评审报告、分支拓扑、排查记录或任务清单。

## 输入与默认产物

读取：

- 当前代码、属性定义、RPC、持久化、配置消费点和测试；
- 唯一 `07-交叉评审.md` 及其最终结论；
- 若存在 `00-工作流索引.md`，用它定位所有与最终实现有关的 `Uxx` 文档和共享上游；
- 若未分支，读取 `01-原始需求.md` 至 `06-完整实现方案.md` 中实际仍有解释价值的结论；
- 项目既有文档结构、命名和索引约定；
- 当前提交或可确认版本标识。

分支模式下，不机械拼接所有 Uxx 文档正文。优先级仍是当前代码与已验证证据；过程文档只用于解释为什么某个稳定契约存在、帮助发现遗漏或冲突。

优先遵循项目已有文档目录。没有约定时默认写入：

```text
docs/features/<feature>.md
```

使用 [功能实现文档模板](references/功能实现文档模板.md)。已有同主题文档时原位重写，不新建平行版本或拆分子文档。

## 事实优先级

材料不一致时，以当前系统真实行为为准：

1. 当前可运行代码与属性、协议定义；
2. 已验证测试和运行证据；
3. 唯一 `07` 的最新 review 结论；
4. 分支/共享实现方案与澄清文档；
5. 唯一 `01` 和早期讨论。

方案与代码不一致时，本阶段权威文档记录实际实现并立即更新。若该不一致说明某个 `Uxx` 或共享过程文档已经过时，不得顺手改写；必须明确指出具体文档和拟修改内容，获得用户确认后再更新。

历史原因只有在仍约束未来修改时才保留。不确定信息不得写成权威结论。

## 应该记录什么

### 1. 职责与边界

用少量文字说明模块解决什么、权威所有者是谁、主要消费者是谁、复用什么既有机制、不负责什么。不重写完整需求，不描述工作单元如何拆分。

### 2. 核心规则

只记录决定外部行为或约束未来修改的规则，例如资格成立/失效、共享公共判定、状态重算、不能混淆的关系、顺序/幂等/唯一性/失败语义。先写系统结论，再说明原因或影响。

### 3. 数据与持久化

对关键属性和状态说明权威所有者、是否持久化、镜像与同步、运行时派生。即使这些事实原先来自多个 Uxx，长期文档也按系统语义合并，不按 Uxx 分章。

### 4. 关键协作契约

记录跨模块/实体/端的稳定合同：属性同步方向和生命周期、RPC/事件时机与语义、公共判定/唯一事实来源、配置控制内容和稳定消费入口。

### 5. 修改约束

只保留少量不写就容易产生隐蔽错误的不变量。普通实现细节、通用规范、分支状态、DAG 和 task progress 不写。

同一系统事实只描述一次；如果多个工作单元最终实现同一个系统契约，应在长期文档合并为一个结论，而不是保留 Uxx 视角。

## 禁止写入

默认删除：

- `U01/U02` 等工作单元 ID、`00` DAG、阶段状态与任务进度；
- 配表当前值、行号、资源数值、时长、耐久和概率等可调参数；
- TODO、待办、延期项和后续优化建议；
- 临时 bug、修复过程、排查日志、测试记录；
- 完整文件清单、逐函数说明、长调用链；
- “本次新增/修改了什么代码”的实现汇报；
- 分支拆分理由、并行/串行执行历史、review 流水；
- 可从类型、命名和局部实现直接推断的内容；
- 与主文档竞争权威性的平行文档。

数字标识仅在属于跨系统协议、存档或兼容契约时保留。

## 工作流程

### 1. 验证 review 已汇合

先查找 `00-工作流索引.md`：

- 不存在：确认单线 `07-交叉评审.md` 已达到可交付终态；
- 存在：确认其 Review 汇合指向唯一 `07-交叉评审.md`，所有当前叶工作单元已经进入该 review 基线，且 `07` 已达到可交付终态。

不满足时停止正常长期文档生成，明确指出应回到 `game-review` 的原因；不得自行把未完成分支“总结成已完成”。

### 2. 确定模块边界

从当前代码的数据所有权和外部行为反推模块边界，查找已有同主题长期文档并选择唯一权威文件。边界确认或变化后立即更新并告知用户。

### 3. 从代码重建事实

检查入口、状态变化、属性定义、持久化、镜像同步、RPC、事件、配置消费和失败语义。若存在多个 Uxx，只把它们当定位线索，不能把“分支文档都写了什么”当系统事实本身。

每获得足以改变权威文档的可靠事实立即原位更新。

### 4. 提炼稳定契约

候选内容需通过：半年后仍大概率成立；不记录会增加破坏语义风险；它描述代码之外仍需要明确的契约。未通过则删除或留在代码/测试/issue/review。

### 5. 过滤临时、分支与重复信息

主动移除配置快照、任务状态、实现证据链、修复记录、普通代码细节以及 `00/Uxx` 拓扑。多个 Uxx 最终形成的同一契约只保留一处系统级表述。

若其他长期文档与本权威文档重复，应合并必要稳定契约并删除或废弃重复文档；涉及过程文档时先说明拟修改内容并获得用户确认。

### 6. 原位重写与最终压缩

已有文档重复、过时或粒度过细时直接删除和重写对应章节。相同结论只出现一次；同一问题相关信息尽量相邻；没有实质内容章节直接删除。每次内容变化后立即告知路径。

## 默认文档结构

```markdown
# <功能或模块名>

> 最后核对：<commit / 日期>
> 权威入口：`path/to/authority`

## 职责与边界
## 核心规则
## 数据与持久化
## 关键协作
## 修改约束
```

章节不是必须全部出现。简单模块可以很短；不因为前期有多个工作单元就按工作单元分章。

## 完成前检查

确认文档能回答模块职责、唯一事实来源、核心规则、数据持久化/镜像、主要协作入口、关键不变量；并确认：

- 没有配置快照、TODO、实现过程、分支拓扑或任务状态；
- 没有完整文件目录或重复调用链；
- 没有与本文件竞争权威性的平行文档；
- 每个现状结论都能在代码、属性定义或测试中找到依据；
- `07` 已完成整体汇合，未绕过尚未闭环的 Uxx；
- 没有未经用户确认而被改写的过程文档；
- 文档已经压缩到继续删除会损害理解或修改安全的程度。

## 完成条件

- 项目内存在唯一、可发现的模块权威文档；
- 文档以当前实现为准，并注明最后核对版本；
- 职责、规则、数据权威、持久化、同步和关键协作清楚；
- 不包含 `00/Uxx` 流程拓扑、配置快照、任务状态、实现复盘或易过期细节；
- 已确认全部分支在唯一 `07` 汇合并达到可交付终态；
- 无尚待用户确认修订的上游文档阻塞。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把 U01/U02 作为长期文档章节 | 按最终系统职责与契约合并，而不是保留开发拓扑 |
| 分支尚未汇合就开始写长期权威文档 | 返回 game-review，先完成唯一 07 |
| 调查完成后才一次性重写文档 | 可靠事实改变当前内容时同轮更新 |
| 发现过程文档过时后直接改写 | 先列明具体文档与拟修改内容，获得确认后更新 |
| 为修订结果创建 v2/补充文档 | 原位重写唯一权威文档 |
