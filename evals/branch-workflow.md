# 分支工作流行为评估

用于回归 `01` 后可分支、`07` 前强制汇合的工作流协议。所有场景都要求过程文档仍位于同一个 `docs/requirements/<feature>/` 目录，不允许为工作单元增加子目录。

## 场景 1：简单需求不制造分支成本

给定一个范围紧凑、无需独立推进的功能，依次执行 `game-spec` 到 `game-implement`。

期望：

- 只有 `01-原始需求.md`、`02-需求挖掘.md`……`06-完整实现方案.md` 等原文件名；
- 不创建 `00-工作流索引.md`；
- 不创建 `U01` 只是为了形式统一。

失败：无实际分支却强制创建索引、工作单元或平行文档。

## 场景 2：在中间阶段拆成并行工作单元

`01`、`02` 已完成；进入 `03` 后发现“战斗”和“奖励”可以独立澄清、独立阻塞并由不同 session 推进，用户接受拆分。

期望：

- 首次拆分时创建 `00-工作流索引.md`；
- 分配稳定 ID，例如 `U01=战斗`、`U02=奖励`；
- 生成 `03-U01-战斗-程序实现澄清.md` 与 `03-U02-奖励-程序实现澄清.md`；
- 原有共享 `03` 若已写入共同内容，只保留共同基线并标记 `已拆分`，不把相同内容复制到两个子文档；
- 所有文件仍位于同一目录。

失败：创建 `U01/`、`U02/` 子目录；使用 `A1/A2.1` 等把拓扑编码进 ID；复制共享事实到每个分支。

## 场景 3：兄弟分支不互相阻塞

索引中 `U01` 与 `U02` 都只依赖共同 `ROOT`，`U01` 已进入 `05`，`U02` 仍在 `04`。

期望：

- `U01` 可以继续自己的 `05` 或后续阶段；
- Agent 只检查 `U01` 的实际依赖，不因为 `U02` 尚未完成而停止；
- 不宣称整个需求已经可以进入 `07`。

失败：仍按全局单阶段模型要求所有分支同步推进，或某一分支完成后提前开始完整 review。

## 场景 4：串行与多前驱依赖由 DAG 表达

索引中 `U03` 依赖 `U01,U02`。

期望：

- `U03` 等待两个前驱的必要终态；
- 依赖写在 `00`，不通过重命名成 `U01.1`、`after-U02` 等方式表达；
- 调整依赖时不重命名既有工作单元文件。

## 场景 5：实现 Step 不冒充工作单元

同一 `U01` 的完整实现需要三次人工 review，但三步共享同一状态模型，后一步只能在前一步稳定后继续，不能独立交付。

期望：

- 继续维护一份 `06-U01-<主题>-完整实现方案.md`；
- 使用文档内部 Step 1/2/3；
- 不因为“分三步”就创建 `U02/U03`。

失败：把实现步骤机械转换成工作流分支。

## 场景 6：客户端对接跟随工作单元

`U01` 与 `U02` 都产生不同的客户端合同。

期望：

- 使用 `U01-<主题>-客户端对接文档.md`、`U02-<主题>-客户端对接文档.md`；
- 不让两个分支争用同一个 `<主题>-客户端对接文档.md`；
- 若存在拆分前的共享对接文档，分支文档只记录各自新增/变化合同并引用共享基线，不复制整份合同。

## 场景 7：07 前必须全部汇合

`U01` 的 `06` 已完成，`U02` 的 `06` 仍为实现中。

期望：

- `game-review` 读取 `00` 后拒绝开始 `07`；
- 明确指出 `U02` 及其当前文档是阻塞；
- 不创建 `07-U01-*`，也不先 review 已完成分支来替代完整 review。

当所有叶工作单元均达到 pre-review 可移交终态后：

- 更新索引的 Review 汇合指针；
- 只创建一份 `07-交叉评审.md`；
- review 范围覆盖共享基线与全部工作单元，发现可标记所属 `Uxx`。

## 场景 8：review 中发现需要新增分支

完整 review 已开始，发现某个根因需要新增一个独立工作单元才能修复。

期望：

- 不在 `07` 内创建分支文档；
- 将 `07` 保持为阻塞/不通过，暂停 review；
- 回到合适的 `02`–`06` 阶段更新 `00` 并创建新工作单元；
- 新工作单元闭环后重新汇合到原 `07-交叉评审.md`。

失败：创建 `07-U03-交叉评审.md` 或第二份 review 报告。

## 场景 9：长期文档读取已汇合的分支工作流

存在 `00-工作流索引.md` 和已通过的 `07-交叉评审.md`，实现由多个工作单元完成。

期望：

- `game-docs` 用 `00` 定位所有相关分支材料，并以当前代码和 `07` 为主要事实来源；
- `00` 只用于定位，不把工作单元拓扑、任务状态或过程信息写入长期模块文档；
- 最终仍只有一份长期权威文档。
