# 结构性变更影响传播回归场景

## 目标

验证所有阶段 skill 在范围、状态、合同、数据权威、工作单元依赖或配置真源变化时，不只修改局部段落，而是完成受影响事实的传播扫描。

## 场景 1：范围变化后顶部元信息仍是旧值

用户确认当前工作单元从“军团 + 小队”缩小为“仅军团”。Agent 修改了正文规则，但文档顶部范围、需求矩阵和下一动作仍写“小队”。

期望：

- 当前阶段不能宣布已更新完成；
- 同一轮检查顶部元信息、正文规则/矩阵、验证结论、阻塞和下一动作；
- 删除或改写所有被新范围覆盖的当前事实；
- record 使用一个逻辑变更记录，而不是每个段落一条。

## 场景 2：03 合同变化影响 05/06/客户端文档

程序确认：原本被当成客户端可见的 View 实际只是内部 Host 路由。

已有：

- `03` 写旧合同；
- `05` 依赖旧 View 建框架；
- `06` 按旧 View 实现；
- 客户端对接文档声称客户端可直接读取该 View。

期望：

- 03 更新后立即执行影响扫描；
- 明确定位 05/06/客户端合同旧引用；
- skill 允许直接更新的下游内容立即同步；
- 若需要回改更早阶段，遵守上游确认规则，不静默修改；
- 未传播完成前不得描述为闭环。

## 场景 3：配置真源改变

用户确认某字段不再来自 Excel，而改为服务端运行时常量。

期望：

- 当前阶段更新配置真源；
- 搜索实际依赖该字段来源的 04/05/06、导表说明和验证结论；
- 不保留“需重导 Excel”与“运行时常量”两个互斥当前状态；
- 阶段完成前只保留唯一有效事实。

## 场景 4：工作单元依赖改变

`U02` 原来依赖 `U01` 的共享数据，后来改成独立权威源。

期望：

- 更新 `00-工作流索引.md` 中依赖；
- 检查 U02 当前阶段文档中对 U01 的旧前置引用；
- 检查 downstream review/handoff 范围是否因此变化；
- 不因兄弟单元旧状态继续错误阻塞 U02。

## 场景 5：只修局部、self-check 后才发现旧引用

Agent 修改了正文一处合同，准备继续编码；self-check 才发现另一章节还保留旧合同。

期望：

- 该失误应形成 `candidate` 或 `actionable` feedback；
- 推荐 pattern：`stage_doc_partial_sync` 或 `contract_propagation_gap`；
- 若同类问题已跨需求出现，应优先归因到 `skill`/`agent_execution`，不是默认 `project_context`。

## 判定失败

以下任一行为失败：

- 结构性变化只改用户指出的那一段；
- 不扫描当前文档顶部状态、矩阵和验证结论；
- 不检查已存在且实际依赖该事实的下游阶段/客户端合同；
- 需要用户确认的上游变化被静默改写；
- 传播未完成却宣布阶段已闭环；
- 同一次传播修正产生多条内容重复的 record。
