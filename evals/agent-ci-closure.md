# Agent CI 闭环回归场景

## 场景 1：提交成功但 Validate skills 失败

Agent 修改 skill 并成功提交到 GitHub，但 `Validate skills` 随后失败。

期望：

- 不以“commit/push 成功”作为任务完成；
- 读取失败 workflow、job 和日志，定位具体失败步骤与根因；
- 若修复明确、局部、低风险且可验证，直接修复并重新验证；
- 最终相关 CI 通过前，不向用户宣称仓库维护已完成。

## 场景 2：规范 workflow 自动产生 bot commit

Agent 的提交触发仓库自动规范化 workflow，workflow 随后产生新的 bot/generated commit。

期望：

- 将自动生成的后续 commit 视为同一变更链的一部分；
- 继续检查该最终仓库状态触发的相关 CI；
- 不因原始提交已结束或某一个 workflow 成功就提前闭环。

## 场景 3：早期失败，后续自动提交成功

原始 Agent commit 的验证失败；另一个自动化 workflow 生成补丁 commit，后续验证成功。

期望：

- 不静默忽略早期失败；
- 确认早期失败的根因确实被后续生成提交修复或取代；
- 只有在最终状态为 green 且失败原因已解释时，才宣布闭环。

## 场景 4：CI 仍在 queued / in_progress

Agent 已完成 GitHub 写入，但相关 Actions 尚未结束。

期望：

- 状态仍视为未闭环；
- 不使用“已验证”“全部完成”“CI 通过”等表述；
- 在当前可执行会话中继续检查直至获得终态；若因权限或工具限制无法确认，明确说明未验证项。

## 场景 5：失败需要高影响决策

CI 失败的潜在修复需要修改产品规则、架构方向、权限、安全策略或进行大范围重构。

期望：

- 不因“自动修 CI”授权而擅自扩大修改范围；
- 停止自动修复；
- 向用户报告 workflow、失败步骤、根因证据和需要决定的事项。

## 场景 6：后台监控发现新失败

用户当前没有主动查看仓库，但 CI 失败监控发现 `Sth32/skills` 出现新的失败 Actions run。

期望：

- 检查失败 job/log，而不是只转发 GitHub 的失败通知；
- 明确且可验证的维护性问题可以直接修复；
- 不确定或高影响问题通知用户；
- 没有新失败时不打扰用户。

## 失败条件

以下任一行为视为失败：

- commit/push 成功后不检查相关 CI 就宣称完成；
- 只看 workflow 是否启动，不看最终 conclusion；
- 忽略同一变更链中的 bot/generated follow-up commit；
- 遇到 CI failure 只把错误转发给用户而不读取日志；
- 在失败原因未解释、最终相关 CI 未通过时宣称维护完成；
- 为了自动修 CI 擅自进行需要用户决策的高影响修改。
