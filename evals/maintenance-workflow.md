# 轻量维护工作流 Evals

这些场景用于验证轻量维护 skill 是否真正绕开不必要的正式流程，同时在越过边界时能正确升级。

## 1. 开发期普通 Bug：不要假设线上数据

**用户**：某个新玩法还在开发，进入地图时偶发空引用，帮我修一下。

**期望**：

- 使用 `game-bugfix`；
- 从代码和日志定位触发条件与根因；
- 不主动展开线上存量数据迁移、灰度、在线玩家兼容；
- 不创建 `01–07` 文档；
- 修复后验证原路径和直接回归面。

**失败行为**：因为“以后可能上线”设计数据库迁移、兼容脚本和灰度方案。

## 2. 环境未由用户确认且会改变方案：只问一次

**用户**：这个字段类型需要改一下，把旧逻辑一起修掉。

**上下文**：如果已经上线并存在历史数据，直接改类型会需要额外兼容；用户没有说明当前是否按线上处理。

**期望**：

- 可以先调查字段定义、调用链和普通实现事实；
- 不从部署脚本、生产配置、版本号、schema 历史、运维目录等迹象自行判断“已经上线”；
- 若线上与开发期方案不同，直接询问用户“这次需要按已经上线、有存量数据的环境处理吗？”；
- 用户回答“还没上线，开发服可以清库”后，不继续线上迁移方向分析。

**失败行为**：Agent 根据仓库中存在生产配置或部署脚本自行进入 `game-hotfix`。

## 3. 小需求沿现有机制扩展

**用户**：已有领取奖励接口再加一个明确的资格判定，规则已经给定。

**期望**：

- 使用 `game-small-change`；
- 查找既有资格判定和奖励入口并复用；
- 不创建正式需求/技术澄清阶段；
- 只验证新增分支和直接旧行为。

## 4. 表面小需求实际改变公共合同

**用户**：给这个返回值顺便加一个新的客户端字段，含义还没最终定。

**期望**：

- 识别客户端合同和产品语义尚未确定；
- 不强行在 `game-small-change` 中猜字段含义；
- 升级到 `game-discovery` / `game-tech-clarify` 的最早必要节点。

## 5. 纯重构保持行为等价

**用户**：把三个重复的状态判断抽到公共函数，行为不要变。

**期望**：

- 使用 `game-refactor`；
- 先确认现有行为和调用方；
- 修改后验证关键输入、输出和副作用一致；
- 不把发现的旁路 bug 顺手混进重构。

## 6. 重构过程中发现真实行为必须改变

**场景**：抽公共函数时发现三个调用点其实有两个不同产品语义，无法在不改变行为的情况下统一。

**期望**：

- 停止称为纯 refactor；
- 说明差异和影响；
- 根据目标切换 `game-bugfix`、`game-small-change` 或正式流程。

## 7. 轻量 Review 不扩大成全系统审计

**用户**：Review 这个修复登录超时的小 diff。

**期望**：

- 使用 `game-light-review`；
- 固定 diff 和实际调用链；
- 检查超时、状态终态、旧异步回包等真实风险；
- 不机械审计无关配置、战斗、持久化系统；
- 默认只在对话输出 findings。

## 8. 用户明确确认线上事故后进入 Hotfix

**用户**：这是线上问题，部分玩家重复领取奖励，正在持续发生。

**期望**：

- 使用 `game-hotfix`；
- 将在线状态、已污染数据、资产重复、版本兼容、止损、回滚/补偿和观测作为相关风险点；
- 先复用项目实际已有机制，不假设一定存在灰度平台、配置开关、自动回滚或事故系统；
- 线上结果无法取得真实证据时保持未确认，不用 CI 或本地测试替代。

## 9. 开发期紧急 Bug 不是 Hotfix

**用户**：这个 bug 很急，今天必须修，但项目还没上线，开发库随时可以清。

**期望**：

- 使用 `game-bugfix` 而不是 `game-hotfix`；
- 不因为“急”引入生产数据与灰度约束。

## 10. 维护文档按需

**用户**：修这个 bug，不用写文档。

**期望**：不创建维护文档或 `01–07` 文件。

**用户后续**：这个问题今天修不完，写一份记录让我明天换 session 继续。

**期望**：使用 skill 自带维护记录模板，只记录当前事实、修改/验证、风险和接力点，不套正式阶段状态结构。

## 11. 项目具备生产能力不等于当前已上线

**场景**：仓库中存在 production 配置、部署脚本、灰度代码和数据库迁移工具；用户只说“修一下这个 bug”，没有说明当前版本是否上线。

**期望**：

- 不因为这些仓库证据自动进入 `game-hotfix`；
- 如果生产状态不会改变本次局部修复，不必追问，按普通维护完成；
- 如果是否有线上存量数据会实质改变方案，只向用户询问一次；
- 是否按生产环境处理的最终判断只来自用户确认。

## 12. Hotfix 不绑定项目实现

**用户**：这是线上 bug，帮我处理；项目没有灰度平台，也没有统一 Hotfix 系统。

**期望**：

- 仍可使用 `game-hotfix`；
- skill 只提醒检查与当前问题相关的在线状态、数据、兼容、恢复和观测风险；
- 不要求为了完成 Hotfix 先建设灰度、开关、回滚平台或事故系统；
- 发布与处置方式遵循项目现有能力和用户指令。
