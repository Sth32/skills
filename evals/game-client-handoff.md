# game-client-handoff 0.1.0 行为测试

## 场景 1：实体属性存在全量、增量和销毁同步

输入：

- Server 新增一个建筑实体；
- 登录和进入视野时发送全量属性；
- `buildStatus`、`processTimeout` 变化时增量同步；
- 建筑销毁时发送实体移除；
- 属性权威在 Building Actor，但由 WorldView 组件同步给客户端。

期望行为：

- 分别写明权威者和同步组件；
- 记录实体唯一标识、字段类型、状态枚举和时间单位；
- 说明首次同步、增量触发、销毁移除和重连恢复；
- 客户端可据此创建、更新和移除表现；
- 不展开客户端实体管理器或 UI 实现。

失败信号：

- 只抄字段列表；
- 把 WorldView 写成数据权威；
- 没有说明实体何时移除；
- 提供大量客户端伪代码。

## 场景 2：RPC 受理与最终结果分离

输入：

- 客户端发送 `ReqBuild`；
- 同步回包只表示请求已受理；
- 实际建造结果通过 `BuildResult` 推送；
- 请求包含 `requestId`、位置和建筑类型；
- 失败可能在同步回包或异步结果中出现。

期望行为：

- 写明客户端发送 RPC 的时机；
- 列出参数类型、含义和限制；
- 明确同步回包不是最终成功；
- 说明 `requestId` 如何关联异步结果；
- 区分两处错误语义。

失败信号：

- 把“已受理”写成“建造成功”；
- 只列 RPC 名称和参数；
- 忽略异步推送或 requestId。

## 场景 3：服务端数据不足以支撑表现

输入：

- 客户端需要显示倒计时和进度；
- Server 只同步当前状态，没有开始时间、结束时间或进度值；
- 现有文档建议客户端按固定 60 秒本地推算。

期望行为：

- 判断当前合同不足；
- 在“服务端缺口”中记录缺少时间基准；
- 说明其对重连、延迟和配置变化的影响；
- 建议由 Server 增加权威时间戳或进度数据；
- 不把本地固定推算写成既定方案。

失败信号：

- 默许客户端硬编码 60 秒；
- 编造 Server 已存在的字段；
- 深入设计客户端计时器实现。

## 场景 4：只需生成合同，不设计客户端架构

输入：

- Server 已提供实体属性、两个 RPC 和一个推送；
- 用户要求给客户端一份对接文档；
- 没有要求设计 UI 或客户端代码。

期望行为：

- 文档集中于属性、生命周期、RPC、推送和数据充分性；
- 只描述客户端理论上能够完成的表现；
- 不设计页面层级、MVC、状态仓库、缓存或资源加载框架；
- 文档控制在 50–120 个非空行附近。

失败信号：

- 输出客户端技术方案；
- 重复完整需求背景和服务端调用栈；
- 对每个内部字段和方法事无巨细展开。

## 场景 5：可见范围随阵营关系变化

输入：

- 同盟成员可见完整设施属性；
- 友盟仅可见位置和建成状态；
- 断交后实体不销毁，但友盟客户端应失去可见性；
- Server 通过视图重算发送属性清除或实体移除。

期望行为：

- 写明不同接收范围及字段差异；
- 说明断交触发的清除/移除行为；
- 区分实体仍存在与客户端不再可见；
- 说明重连时按当前关系重新全量同步。

失败信号：

- 只写“属性会同步”；
- 没有说明可见性降低后的客户端数据处理；
- 要求客户端自行查询同盟关系并猜测是否隐藏。
