# game-implement 行为测试

## 场景：骨架可运行但存在 TODO、旧数据与重复请求风险

输入：

- `05` 已确认；
- 主流程接线完成；
- 奖励补偿、旧数据默认值、幂等和回滚尚未完成。

期望行为：

- 先核对框架与实际代码；
- 建立需求完成矩阵并产出剩余实现方案；
- 用户确认后按行为闭环实现；
- 处理 TODO、占位返回、失败补偿、旧数据和重复请求；
- 添加并运行对应测试；
- 若发现状态所有权错误，回到框架方案修订，而不是继续打补丁。

失败信号：

- 把所有 TODO 视为低优先级留下；
- 只完成成功主流程；
- 无测试证据就宣称完整；
- 重新设计核心框架但不更新 `05`。

## 场景：实现范围过大，不适合一次人工 review

输入：

- `05` 已确认且骨架可运行；
- 剩余实现同时包含战斗资格与次数扣除、奖励结算与幂等、跨进程同步、旧数据兼容与回滚；
- 各部分存在明确依赖，但可以形成多个独立验证的行为闭环。

期望行为：

- 不因“技术上可以一次写完”就直接连续实现全部内容；
- 先从人工 review 负担和依赖关系判断是否需要分步；
- Agent 主动给出 2–5 个纵向闭环的建议拆法，并说明拆分依据；
- 询问用户采用还是调整建议拆法，而不是直接把“怎么拆”丢给用户；
- 用户接受分步后，将实现模式、步骤表、当前步骤和 review 门禁写入唯一的 `06-完整实现方案.md`；
- 一次只完成当前步骤，验证并更新 `06` 后停在 review 边界；
- 未得到当前步骤确认前，不进入下一步骤；
- 不为每个步骤额外创建实现文档。

失败信号：

- 大范围需求仍一次性给出全部实现并要求用户最后统一 review；
- 仅按文件、模块层或开发工种切步骤；
- 当前步骤完成后自动开始下一步；
- 每一步新建独立计划、验证或交接文档。

## 场景：用户隔较长时间后在新 session 继续第二步

输入：

- 分步模式共有 3 步；
- 第 1 步已实现、验证并经用户确认；
- 上一个 session 已结束；
- 新 session 只能读取仓库中的 `01` 至 `06`、实际代码、diff 和测试结果，不能依赖旧聊天。

期望行为：

- `06` 中已经包含实现模式、步骤总览、第 1 步完成证据、当前步骤状态、实际代码基线、关键代码入口、未决问题、下一动作和进入第 2 步的条件；
- 新 session 先读取 `06` 的当前接力点，再核对实际代码/diff；
- 若文档与代码一致，从已确认的第 2 步继续；
- 若文档与代码不一致，以实际代码事实为依据立即修正 `06` 并告知用户，再决定继续实现还是重新 review；
- `06` 不复制 `01` 至 `05` 的全文，只保留继续实现所需的引用、差异与当前状态。

失败信号：

- 需要用户重新解释上一 session 做了什么才能继续；
- 仅写“第 1 步已完成”，但没有代码入口、验证或下一动作；
- 假设旧聊天仍可访问并据此继续编码；
- 为跨 session 交接额外创建 handoff 文档。
