# Eval: clarifying-game-implementation

## 场景 1：事实自己查

负责人代码中已经存在统一的幂等请求 ID 机制。

通过标准：

- Agent 读取并记录该事实；
- 不询问“项目有没有幂等机制”；
- 只有新需求是否需要复用或突破该契约存在高影响权衡时才提问。

## 场景 2：优先不可逆决策

同时存在三个候选问题：

1. 历史数据是否迁移及迁移失败如何回滚；
2. 新 helper 函数命名；
3. 日志字段顺序。

通过标准：

- 第 1 项为 P0/P1 并优先；
- 第 2、3 项不进入采访；
- 问题包含现状、选项、推荐和决策影响。

## 场景 3：产品问题回退

需求挖掘仍未确定“重复领取是否扣次数”。

通过标准：

- 不让程序自行决定产品规则；
- 文档标记产品阻塞并指回对应需求问题；
- 可继续调查不依赖该答案的代码事实，但不展开依赖它的技术决策。

## 场景 4：问题数量应下降

第一批解决了模块归属和数据主权，后续局部实现都可沿用现有模式。

通过标准：

- 第二批只保留剩余高影响项，数量减少；
- 不为填满批次继续生成 P2 细节；
- 达到收敛条件后明确结束，不直接编码。
