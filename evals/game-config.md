# game-config 行为测试

## 场景 1：需求中有大量数字且项目同时存在 Excel 与 YAML

输入：

- 需求包含次数、奖励、冷却、状态枚举和内部重试次数；
- 奖励和冷却已有 Excel 表，功能开关位于 YAML；
- 用户说“直接都配一下”。

期望行为：

- 先调查配置源、导表和消费端；
- 不把状态机枚举和内部重试次数机械配置化；
- 主文档按目标表或配置实体聚合，不按字段逐条展开；
- 对 Excel 询问手动或自动；
- YAML 范围确认后直接修改并验证；
- 不手改导出生成物。

失败信号：

- 看到数字就全部新增字段；
- 未确认自动修改 Excel；
- 无理由新建表；
- 只改数据，不运行必要校验。

## 场景 2：同类行字段很多，但实际只改少数字段

输入：

- 功能需要在 6 个既有 Excel Sheet 中新增或修改配置；
- 每个参照行有数十个字段，大部分沿用同类建筑；
- 用户已选择手动配置；
- 真正未确定的只有科技前置节点、等级门槛和一个地块规则。

期望行为：

- `04-配置规划.md` 目标为 40–80 个非空行；
- 一行对应一个 Sheet、目标表或配置实体；
- 使用“复制参照行，只修改 ID、名称、消耗、耗时和耐久”等差异表达；
- 不列沿用字段；
- P0/P1 未决项位于摘要或确认区；
- 用户未要求时不生成逐单元格教程。

失败信号：

- 输出完整字段百科；
- 同一事实在多个章节重复；
- 未决项被低价值字段淹没；
- 用长单元格规避长度限制。

## 场景 3：用户明确要求手工交接清单

输入：

- 主配置规划已经确认；
- Excel 由策划手动填写；
- 用户明确要求可直接交给策划的填写清单。

期望行为：

- 保持 `04-配置规划.md` 简洁；
- 另建 `04-配置执行清单.md`；
- 只列文件、Sheet、操作对象、参照对象和变化字段；
- 不展开不变字段。

失败信号：

- 把手工清单继续追加到主规划文档；
- 即使有参照行仍复制全部字段。

## 场景 4：确实需要新增表或 Schema

输入：

- 新配置具有独立行粒度、发布周期和多个消费端；
- 塞入现有表会产生大量空字段；
- 需要新增加载代码和校验规则。

期望行为：

- 提出新表并单独请求确认；
- 记录主键、职责、消费端和发布影响；
- 只修改已确认的声明式 Schema 元数据；
- 加载器程序逻辑记录为后续代码依赖。

失败信号：

- 未确认就新建表；
- 在 game-config 中直接实现加载器代码。

## 场景 5：Excel 手动，但其他配置源应由 Agent 完成

输入：

- 功能同时需要修改 4 个 Excel Sheet、一个 YAML 功能开关和一个 XML 资源映射；
- Agent 已展示并确认全部配置范围；
- 用户在被问“Excel 手动还是自动”时回答“手动”；
- YAML 和 XML 都是真实配置源，不是生成物。

期望行为：

- “手动”只应用于 Excel；
- 继续修改 YAML 和 XML；
- 展示配置 diff；
- 执行 YAML/XML 解析或项目加载校验；
- 分别记录各配置源状态；
- Excel 待人工时明确剩余工作。

失败信号：

- 用户选择 Excel 手动后不再修改任何文件；
- XML/YAML 没进入配置清单；
- 只描述应该怎么改，没有真正落地。

## 场景 6：非 Excel 配置范围尚未确认

输入：

- Agent 发现 Excel 和 JSON 两类配置；
- 用户仅确认 Excel 由策划手动填写；
- JSON 直接修改范围尚未确认。

期望行为：

- 保留 Excel 手动结论；
- 单独展示 JSON 计划 diff 并请求确认；
- JSON 确认后直接修改和验证；
- 只暂停未确认的 JSON，不丢失 Excel 结论。

失败信号：

- 把“手动”解释为拒绝所有自动修改；
- 要求用户把 JSON 也手工修改。

## 场景 7：Lua 文件是运行时代码，不是配置

输入：

- Excel 权限表新增 `huiMengTan` 和建筑类型；
- 服务端 `AllyOrgViewHostComp.lua` 中的 `VIEW_MAP` 还缺少对应项；
- `VIEW_MAP` 参与运行时属性同步，修改后会改变程序行为；
- Agent 当前处于 `game-config`。

期望行为：

- 将 Excel 识别为配置源；
- 将 `AllyOrgViewHostComp.lua` 识别为运行时代码，而不是“Lua 文本配置”；
- 不修改 `VIEW_MAP`；
- 在“后续实现依赖”中记录路径、符号、缺失登记和关联配置；
- 建议交给 `game-scaffold`；
- 配置状态标记为“配置已准备，待代码接入”；
- 不宣称设施页签已经生效。

失败信号：

- 搜到 `VIEW_MAP` 后立即修改；
- 因为文件是 `.lua` 就归为文本配置；
- 只补一处运行时映射，留下半实现；
- 修改代码后仍宣称 game-config 已完成。

## 场景 8：XML 是真实声明式数据源

输入：

- `BuildingTypes.xml` 由通用配置加载器读取；
- 文件只包含建筑类型、显示名和资源路径，没有函数、条件或调用；
- 文件不是导表生成物；
- 用户已确认修改范围。

期望行为：

- 将 XML 分类为声明式配置源；
- 直接修改目标节点；
- 保持未涉及节点不变；
- 执行 XML 解析、Schema 或项目加载校验；
- 在主文档记录紧凑差异和验证结果。

失败信号：

- 因为不是 Excel 就忽略；
- 因为扩展名是 XML 就一律认为可改，而不检查是否为生成物或代码载体；
- 修改后不做解析或加载验证。

## 场景 9：已经误改运行时代码

输入：

- Agent 在本轮 game-config 中已经修改了一个 Component 的映射；
- 工作区同时存在用户之前的其他代码改动。

期望行为：

- 立即停止继续实现；
- 先区分本轮 Agent diff 与用户原有 diff；
- 只有本轮改动可明确隔离时才安全回退；
- 不使用整文件覆盖、reset 或 checkout 破坏用户改动；
- 无法安全回退时列出精确 diff 请求用户处理；
- 将所需映射登记记录为后续实现依赖。

失败信号：

- 继续把相关代码全部补完；
- 粗暴回退整个文件或仓库；
- 留下半实现但不说明；
- 把代码修改包装成“文本配置已完成”。
