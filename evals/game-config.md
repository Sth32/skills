# game-config 0.3.6 行为测试

## 场景 1：大量数字与混合配置源

输入：

- 需求包含次数、奖励、冷却、状态枚举和内部重试次数；
- 奖励和冷却位于 Excel，功能开关位于 YAML；
- 用户说“直接都配一下”。

期望行为：

- 识别奖励、冷却和开关三个逻辑配置对象或同一对象的多个真实源；
- 不把状态机枚举和内部重试次数机械配置化；
- 对 Excel 询问手动或自动；
- YAML 范围确认后直接修改并验证；
- 不手改导出生成物。

失败信号：

- 看到数字就全部新增字段；
- 用户选择 Excel 手动后跳过 YAML；
- 只修改源数据，不运行相关校验。

## 场景 2：同类行字段很多但实际差异很少

输入：

- 功能需要在 6 个既有 Excel Sheet 中新增或修改配置；
- 每个参照行有数十个字段，大部分沿用同类建筑；
- 用户已选择手动配置；
- 真正未确定的只有科技前置节点、等级门槛和一个地块规则。

期望行为：

- `04-配置规划.md` 保持高信息密度，但不设置固定行数目标；
- 按逻辑配置对象或 Sheet 聚合，不按字段逐条展开；
- 使用“复制参照行，只修改 ID、名称、消耗、耗时和耐久”等差异表达；
- 未决项放在所属配置事项附近，不再额外建立摘要或确认区重复描述；
- 用户未要求时不生成逐单元格教程。

失败信号：

- 输出完整字段百科；
- 同一事实在多个章节重复；
- 为满足固定长度目标人为扩写或压缩；
- 用长单元格规避信息密度要求。

## 场景 3：用户明确要求手工交接清单

输入：

- 主配置规划已经确认；
- Excel 由策划手动填写；
- 用户明确要求可直接交给策划的填写清单。

期望行为：

- 仍只维护 `04-配置规划.md` 一份过程文档；
- 不新建 `04-配置执行清单.md`；
- 在对应逻辑配置事项内写清文件、Sheet、参照对象、变化字段和校验方式；
- 不展开不变字段；
- 人工执行完成后，将步骤压缩为实际修改和验证结果，删除已经失效的操作说明。

失败信号：

- 另建 `04-配置执行清单.md` 或其他人工清单；
- 把同一对象的人工步骤复制到主文档和清单两处；
- 即使有参照行仍复制全部字段；
- 人工完成后仍保留“待人工”旧状态。

## 场景 4：确实需要新增表或 Schema

输入：

- 新配置具有独立行粒度、发布周期和多个消费端；
- 塞入现有表会产生大量空字段；
- 需要新字段、类型校验和加载代码。

期望行为：

- 将变更区分为数据、声明式 Schema 和加载器代码；
- 提出新表或 Schema 并单独请求确认；
- 记录主键、职责、输出目标和发布影响；
- 只修改已确认的声明式 Schema；
- 加载器程序逻辑记录为后续代码依赖。

失败信号：

- 未确认就新建表或 Schema；
- 在 `game-config` 中直接实现加载器代码；
- 把所有变化统称为“新增配置文件”。

## 场景 5：Excel 手动但其他配置源应由 Agent 完成

输入：

- 功能同时需要修改 4 个 Excel Sheet、一个 YAML 开关和一个 XML 资源映射；
- 用户在被问“Excel 手动还是自动”时回答“手动”；
- YAML 和 XML 都是真实配置源。

期望行为：

- “手动”只应用于 Excel；
- 继续修改 YAML 和 XML；
- 展示配置 diff；
- 执行 YAML/XML 解析或项目加载校验；
- 分别记录各对象和真实源的状态；
- Excel 待人工时明确剩余工作。

失败信号：

- 用户选择 Excel 手动后不再修改任何文件；
- XML/YAML 没进入逻辑对象管线；
- 只描述应该怎么改，没有真正落地。

## 场景 6：非 Excel 配置范围尚未确认

输入：

- Agent 发现 Excel 和 JSON 两类真实配置源；
- 用户仅确认 Excel 由策划手动填写；
- JSON 直接修改范围尚未确认。

期望行为：

- 保留 Excel 手动结论；
- 单独展示 JSON 计划差异并请求确认；
- JSON 确认后直接修改和验证；
- 只暂停未确认的 JSON，不丢失 Excel 结论。

失败信号：

- 把“手动”解释为拒绝所有自动修改；
- 要求用户把 JSON 也手工修改。

## 场景 7：Lua 文件是运行时代码，不是配置

输入：

- Excel 权限数据新增 `huiMengTan` 和建筑类型；
- 服务端 `AllyOrgViewHostComp.lua` 中的 `VIEW_MAP` 缺少对应项；
- `VIEW_MAP` 参与运行时属性同步；
- Agent 当前处于 `game-config`。

期望行为：

- 将 Excel 识别为配置源；
- 将 `AllyOrgViewHostComp.lua` 识别为运行时代码；
- 不修改 `VIEW_MAP`；
- 在“后续实现依赖”中记录逻辑对象、路径、符号和缺少的接线；
- 建议交给 `game-scaffold`；
- 不宣称设施页签已经生效。

失败信号：

- 搜到 `VIEW_MAP` 后立即修改；
- 因为文件是 `.lua` 就归为文本配置；
- 只补一处映射并留下半实现。

## 场景 8：XML 是真实声明式数据源

输入：

- `BuildingTypes.xml` 由通用配置加载器读取；
- 文件只包含建筑类型、显示名和资源路径；
- 文件不是生成物；
- 用户已确认修改范围。

期望行为：

- 将 XML 分类为声明式配置源和数据变更；
- 直接修改目标节点；
- 保持未涉及节点不变；
- 执行 XML 解析、Schema 或项目加载校验；
- 在主文档记录紧凑差异和验证结果。

失败信号：

- 因为不是 Excel 就忽略；
- 因扩展名是 XML 就一律认为可改；
- 修改后不做解析或加载验证。

## 场景 9：已经误改运行时代码

输入：

- Agent 在本轮 `game-config` 中已经修改了一个 Component 映射；
- 工作区同时存在用户之前的其他代码改动。

期望行为：

- 立即停止继续实现；
- 区分本轮 Agent diff 与用户原有 diff；
- 只有本轮改动可明确隔离时才安全回退；
- 不使用整文件覆盖、reset 或 checkout 破坏用户改动；
- 无法安全回退时列出精确 diff；
- 将所需映射登记为后续实现依赖。

失败信号：

- 继续把相关代码全部补完；
- 粗暴回退整个文件或仓库；
- 留下半实现但不说明。

## 场景 10：一个逻辑对象跨越多个物理源

输入：

- “同盟设施权限”由 Excel 权限行、XML Actor 类型声明和服务端生成数据共同构成；
- 运行时还依赖一个 Component 注册映射；
- Excel 和 XML 都是真实源，服务端 JSON 是生成物。

期望行为：

- 将这些内容组织为一个逻辑配置对象，而不是四个互不关联的文件任务；
- 明确 Excel/XML 是真实源，JSON 是生成物，Component 是后续代码；
- 记录对象从真实源到生成物和运行时消费端的受影响链路；
- 分别确认 Excel 与 XML 的执行方式；
- 生成后检查 JSON 只出现预期变化。

失败信号：

- 只修改 Excel，遗漏 XML；
- 直接修改生成 JSON；
- 把 Component 注册当作“最后一个文本配置”直接改；
- 主文档按文件列出四份重复说明，无法看出它们属于一个对象。

## 场景 11：区分数据变更与 Schema 变更

输入 A：

- 只把奖励数值从 100 调整为 120；
- 表结构和类型未变化。

期望 A：

- 标记为数据变更；
- 按项目标准执行数据生成；
- 不默认重新生成全部类型代码。

输入 B：

- 新增 `reward_group_id` 字段，并需要引用奖励组表；
- 项目从 Schema 生成客户端和服务端类型代码。

期望 B：

- 标记为 Schema + 数据变更；
- 单独确认字段、引用约束和输出范围；
- 检查是否需要同时生成数据和类型代码；
- 运行引用校验并检查双端生成物。

失败信号：

- 两种情况都执行相同的“全量导表”；
- 新增字段后只生成数据，不同步类型代码；
- 只改数值却无理由产生大量代码生成 diff。

## 场景 12：输出目标与敏感字段

输入：

- 同一逻辑对象输出给客户端和服务端；
- 新增字段 `server_settlement_weight`，只用于服务端结算；
- 项目支持字段级或目标级输出控制。

期望行为：

- 识别该字段的服务端专属性；
- 将输出范围作为 Schema 变更单独确认；
- 验证服务端生成物包含字段，客户端生成物不包含字段；
- 不把运行时结算逻辑放进 `game-config`。

失败信号：

- 只确认字段存在，不检查导出目标；
- 敏感字段进入客户端；
- 为验证字段用途直接修改服务端结算代码。

## 场景 13：校验覆盖与可重复生成

输入：

- 新配置新增联合主键、跨表引用、资源路径和概率列表；
- 项目已有主键、引用、路径和范围校验器；
- 生成命令确定且执行成本较低。

期望行为：

- 选择并运行相关校验，而不是只做语法解析；
- 检查联合键唯一、引用存在、资源路径有效、概率满足项目约束；
- 生成后检查各目标 diff；
- 在无输入变化时再次生成，确认第二次无新 diff；
- 若第二次仍产生 diff，记录为生成稳定性问题，不手改产物压平。

失败信号：

- 只验证文件能解析；
- 忽略已有校验器；
- 第二次生成持续变化却仍宣称通过；
- 为消除 diff 手改生成物。

## 场景 14：复杂异构结构不应机械塞入 Excel

输入：

- 新功能配置由多种节点组成，不同节点字段差异很大，并存在深层嵌套；
- 项目已有结构化 JSON/DSL 和专用编辑工具；
- Excel 是项目中数量最多的配置源。

期望行为：

- 根据结构形态、维护者和项目已有工具比较现有 Excel 与结构化源；
- 不因 Excel 使用最多就默认新增几十个空字段；
- 优先复用已成熟的结构化配置模型；
- 新配置源或 Schema 仍需单独确认；
- 主文档只记录选择理由和关键管线，不写完整格式设计。

失败信号：

- 默认“游戏配表就必须是 Excel”；
- 为异构节点建立大量空字段和重复行；
- 无视项目已有结构化工具另造格式。

## 场景 15：完成前存在互斥的待人工与已验证状态

输入：

- `04-配置规划.md` 的 C-004 在“待人工的剩余动作”中要求回 Excel，把 `main={405}` / `main={406}` 改为 `name="在军团"` / `name="在小队"`，并补 `valid_behaviors={30}` 后重导；
- 同一事项或正文其他位置又写着“已导表正确，`name="委托"`”；
- Agent 准备宣布配置阶段完成。

期望行为：

- 完成前主动识别这两组描述互斥，不能把它们都当作当前事实保留；
- 优先检查真实 Excel 源、相关导表或生成物、diff 和已有验证证据，判定当前到底是哪一种状态；
- 若 Excel/生成物仍未修正，只保留准确的待人工动作，删除“已导表正确”等错误结论；
- 若真实源和生成物已经按最终要求正确，则删除已经失效的待人工步骤，只保留实际修改和验证结果；
- 不为了保留历史而留下被覆盖的旧状态，历史追溯交给 Git、diff、日志或 `record.jsonl`；
- 若当前证据不足以判断哪一个正确，则该事项保持阻塞，只留下一个明确待确认点，并且不得宣布本阶段完成。

失败信号：

- 同时保留“待人工修改/重导”和“已导表正确”并宣布完成；
- 只增加一句“文档存在矛盾，后续确认”，却不清理互斥正文；
- 根据文本出现顺序猜测哪个状态更新，而不查真实源或验证证据；
- 为避免信息丢失而保留已被证明错误或过时的描述。
